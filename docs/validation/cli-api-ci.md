# 7.12 — CLI, API, and CI

This document specifies the official CLI, Application API, and Continuous Integration (CI) interfaces for the CMM OS Validation Infrastructure (Phase 7.12).

---

## 1. Architecture & Shared Flow

The validation infrastructure uses a single, unified pipeline engine for all interfaces:

```
+-------------------+      +---------------------+      +---------------------+
|   CLI (argparse)  |      |   Python App API    |      |  GitHub Actions CI  |
+---------+---------+      +----------+----------+      +----------+----------+
          |                           |                            |
          +-------------------+-------+----------------------------+
                              |
                              v
                +---------------------------+
                | ValidationAppService      |
                +-------------+-------------+
                              |
                              v
                +---------------------------+
                |     ValidationPipeline    |
                +-------------+-------------+
                              |
            +-----------------+-----------------+
            |                                   |
            v                                   v
+-----------------------+           +-----------------------+
|  Observability & Repo |           |  Commit Gate Service  |
| (.cmm/validation/)    |           |  (Evaluation only)    |
+-----------------------+           +-----------------------+
```

Key Architectural Principles:
1. **Single Engine**: CLI, Python API, and CI all invoke `ValidationApplicationService`, which delegates to `ValidationPipeline`.
2. **Deterministic Output**: Standard output contains human-readable text or pure JSON based on `--output`.
3. **Immutability & Safety**: No unauthorized Git modifications, pushes, or shell commands are performed.

## 2. Validation Exit Codes

`ValidationExitCode` (`cmm.validation.ValidationExitCode` / `cmm.validation.interfaces.ValidationExitCode`) defines stable integer exit codes:

| Code | Name | Description |
|------|------|-------------|
| `0` | `SUCCESS` | All validation steps passed and gate allowed. |
| `1` | `VALIDATION_FAILED` | Validation failed or commit gate rejected. |
| `2` | `INVALID_USAGE` | Invalid command usage or CLI arguments. |
| `3` | `NOT_FOUND` | Requested validation ID or artifact not found. |
| `4` | `CONFIGURATION_ERROR` | Unknown policy, step, or invalid configuration. |
| `5` | `INTERNAL_ERROR` | Internal system or persistence failure. |
| `6` | `CANCELLED` | Execution was cancelled cooperatively. |
| `7` | `TIMEOUT` | Execution timed out. |

## 3. CLI Commands

Base command: `cmm validation`

### 3.1 `cmm validation run`

Executes the validation pipeline with specified policies, steps, or files.

Options:
- `--policy <name>`: Select policy (`ci`, `small_change`, `structural_change`, `full`, etc.).
- `--step <step-name>`: Select specific step(s) to run (repeatable).
- `--files <path...>`: Validate specific files relative to project root.
- `--git-changes`: Automatically select files modified in Git status / diff.
- `--actor <actor>`: Record actor metadata (person or bot).
- `--output human|json`: Output format (default: `human`).
- `--verbose`: Include detailed step diagnostic outputs.
- `--quiet`: Suppress non-essential summaries.
- `--no-persist`: Skip persisting record to `.cmm/validation/`.

Examples:
```bash
cmm validation run
cmm validation run --policy small_change
cmm validation run --step lint --step syntax
cmm validation run --files cmm/cli.py --output json
```

### 3.2 `cmm validation inspect <validation-id>`

Inspects a previously stored validation execution record.

```bash
cmm validation inspect val-1700000000000 --output json
```

### 3.3 `cmm validation artifacts <validation-id>`

Lists or retrieves artifacts generated by a validation run.

Options:
- `--artifact <artifact-id>`: Retrieve specific artifact payload.

```bash
cmm validation artifacts val-1700000000000
cmm validation artifacts val-1700000000000 --artifact mypy_report --output json
```

### 3.4 `cmm validation gate <validation-id>`

Evaluates Commit Gate rules for a stored validation execution.

```bash
cmm validation gate val-1700000000000 --output json
```

## 4. Output Formats & JSON Schema

### Top-Level JSON Structure
When `--output json` is requested, `sys.stdout` outputs exclusively valid JSON:

Success response:
```json
{
  "schema_version": 1,
  "command": "validation.run",
  "success": true,
  "exit_code": 0,
  "validation_id": "val-1721860000000",
  "result": { ... },
  "error": null
}
```

Error response:
```json
{
  "schema_version": 1,
  "command": "validation.inspect",
  "success": false,
  "exit_code": 3,
  "validation_id": null,
  "result": null,
  "error": {
    "code": "validation_not_found",
    "message": "Validation execution record 'val-invalid' not found.",
    "details": { "validation_id": "val-invalid" }
  }
}
```

## 5. Application API

Python entry point: `cmm.validation.ValidationApplicationService`

### Public Service Interface

```python
from cmm.validation import (
    ValidationApplicationService,
    StartValidationRequest,
    ValidationHistoryQuery,
)

service = ValidationApplicationService(project_root="/path/to/project")

# Start validation
result = service.start_validation(
    StartValidationRequest(
        policy_name="small_change",
        use_git_changes=True,
        actor="developer",
    )
)

# Inspect record
record = service.get_result(result.validation_id)

# Evaluate Commit Gate
gate = service.evaluate_gate(result.validation_id)

# Cooperative cancellation
service.cancel_validation(result.validation_id)
```

### Cancellation Semantics & Boundaries

Cancellation is cooperative:
- When `cancel_validation(id)` is called, the registered `CancellationToken` is marked as cancelled.
- The pipeline checks `cancel.is_cancelled()` between step executions.
- Currently executing subprocesses finish cleanly before pipeline halts remaining steps.
- Remaining steps are recorded as status `cancelled`.

## 6. CI Integration

CI is configured via `.github/workflows/continuous-validation.yml`:

- **Triggers**: Pull Requests and Pushes to `main` or `feature/phase-7-continuous-validation`.
- **Policy**: `ci` policy (`formatter_check`, `lint`, `syntax`, `ast`, `custom_checks`).
- **Command**:
  ```bash
  python -m cmm validation run --policy ci --git-changes --output json > validation-report.json
  ```
- **Artifacts**: Uploads `validation-report.json` and `.cmm/validation/` storage with `if: always()`.

---

## 7. Security & Safeguards

1. **Path Traversal Guard**: All file paths are validated against `project_root`. Escaping paths (e.g. `../../etc/passwd`) raise `ValidationInvalidRequestError`.
2. **Step Injection Guard**: Step names are validated against registered steps. Freeform shell injection is impossible.
3. **Secret Sanitization**: All outputs, logs, and artifacts are filtered by `sanitize_validation_data`.
4. **Git Safety**: No commits, pushes, rebases, merges, or deployments are executed by default.

---

## 8. Agent Guide & Troubleshooting

- **Testing CLI locally**:
  ```bash
  python -m cmm validation run --policy ci --output json
  ```
- **Handling non-existent IDs**: `cmm validation inspect invalid-id` returns exit code `3` (`NOT_FOUND`).
- **Idempotency**: Requests with identical `request_id` parameters return cached results.
