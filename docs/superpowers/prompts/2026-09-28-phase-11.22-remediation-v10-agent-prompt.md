## 4. MAJOR-V10-001 — Embedded Windows drive-root bypass

### 4.1 Exact independently reproduced defect

The independent V10 audit proved that these values are accepted as public-safe and persisted:

```text
provider/C:/Windows/System32/config/SAM
cmm/C:/Windows/System32/config/SAM
provider//C:/Windows/System32/config/SAM
provider/./C:/Windows/System32/config/SAM
```

For the canonical example:

```text
provider/C:/Windows/System32/config/SAM
```

the current system was shown to produce:

```text
is_private_filesystem_reference(...) = False
validate_platform_identifier(...) = ACCEPT
EventSystem publish = ACCEPT
repository count 0 -> 1
persisted=True
```

The exact bypass was reproduced through all **13 shared identifier-bearing channels**:

1. payload request ID;
2. payload workflow ID;
3. payload aggregate ID;
4. payload producer;
5. header producer;
6. header aggregate ID;
7. header correlation ID;
8. header source;
9. permissions;
10. metadata error type;
11. nested result reference;
12. structured reference sequence;
13. domain reference sequence.

It was independently persisted using both:

- official in-memory repository;
- official file-backed repository.

This is not a theoretical classifier gap. It is a real durable persistence defect.

### 4.2 Root cause

The current Windows drive-root classifier is structurally anchored only at the beginning of the whole value:

```python
re.compile(r"^[A-Za-z]:[\\/]")
```

The V9 `file:` fix correctly moved `file:` semantics to a valid path-segment boundary:

```python
re.compile(r"(?:^|/)file:", re.IGNORECASE)
```

but the raw drive-root case remains vulnerable behind allowlisted outer logical roots such as `provider/` and `cmm/`.

The current flow is effectively:

```text
provider/C:/Windows/...
        ↓
not traversal
not whole-value absolute
whole-value drive-root pattern misses
public root = provider
        ↓
accepted
        ↓
persisted
```

### 4.3 Required canonical fix

Stay inside the **existing canonical identifier/filesystem safety authority**.

Do not create a second path scanner or a new Windows-path subsystem.

The smallest acceptable solution should make a raw Windows drive-root token unsafe when it occurs at a valid path-segment boundary, not merely character zero.

The semantic rule must cover at least:

```text
C:/Windows/System32/config/SAM
provider/C:/Windows/System32/config/SAM
cmm/C:/Windows/System32/config/SAM
provider//C:/Windows/System32/config/SAM
provider/./C:/Windows/System32/config/SAM
```

and equivalent alphabetic drive letters/casing supported by the identifier grammar.

A structurally appropriate form may be analogous to:

```text
(?:^|/)[A-Za-z]:/
```

after the existing analysis-only lexical normalization, but do not blindly paste this suggestion without inspecting the canonical code path and tests.

If backslashes are already rejected by the outer identifier grammar, record that as a positive fail-closed fact rather than widening the grammar.

Do **not** solve the defect by adding:

- `SAM`;
- `SECURITY`;
- `Windows/System32`;
- `ProgramData`;
- any audited literal path;
- more location-specific denylist entries.

The fix must be structural.

### 4.4 Preserve positive controls

At minimum preserve existing safe behavior for:

```text
provider/model
cmm/orchestration/step
workflow:123
domain:legal
https://example.com/model
provider/https://example.com/model
jdbc:postgresql://example.com/db
workflow:file:123
req:file:mod
```

Also preserve all V9 wrapped `file:` rejections.

Do not classify ordinary colon IDs as Windows drive roots unless the colon appears in actual drive-root syntax at a canonical segment boundary.

### 4.5 Analysis-only guarantee

The classifier must continue to:

- perform no filesystem I/O;
- perform no `Path.resolve()`;
- perform no host-dependent path resolution;
- not mutate accepted persisted identifiers;
- make safety decisions on analysis-only normalized forms.
