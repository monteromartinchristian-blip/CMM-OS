## 4. MAJOR-V11-001 — Windows drive-relative references

### 4.1 Exact independently reproduced defect

Windows distinguishes:

```text
C:/name     drive-root path
C:name      drive-relative path
```

The latter is still a Windows drive-qualified local filesystem reference.

The independent V11 audit verified standard-library Windows parsing semantics such as:

```text
ntpath.splitdrive("C:Windows") = ("C:", "Windows")
ntpath.splitdrive("C:id_rsa")  = ("C:", "id_rsa")
```

Fresh canonical reproductions accepted by the current authority include:

```text
C:Windows
C:id_rsa
C:.ssh
D:ProgramData
Z:tmp
```

In particular:

```text
is_private_filesystem_reference("C:id_rsa") = False
validate_platform_identifier("C:id_rsa") = ACCEPT
```

`id_rsa` is already a sensitive private-file marker in the existing canonical policy, so this is not merely an ambiguous identifier example.

`C:id_rsa` was independently accepted and persisted through all **13 shared identifier-bearing channels** using both:

- official in-memory repository;
- official file-backed repository.

Manual/prebuilt canonical `EventSystem.publish_event(...)` also accepted and persisted it.

### 4.2 Root cause

The current Windows drive-root rule correctly catches rooted drive paths:

```python
re.compile(r"(?:^|/)[A-Za-z]:[\\/]")
```

but it requires a separator after the drive colon.

Therefore:

```text
C:/Windows
```

is classified as filesystem syntax, while:

```text
C:Windows
```

is not.

The final path-shape branch also assumes that a value with no slash/backslash is not path-shaped. That assumption is invalid for Windows drive-relative syntax.

This is a structural Windows path-classification defect. It must not be fixed with literal filename additions.
