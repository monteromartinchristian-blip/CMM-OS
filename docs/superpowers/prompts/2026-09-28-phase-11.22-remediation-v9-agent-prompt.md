# 4. MAJOR-V9-001 — Wrapped non-authority `file:` URI bypass

## 4.1 Exact independent reproductions

The V9 audit independently demonstrated acceptance and persistence of wrapped local filesystem references such as:

```text
provider/file:C:/Windows/System32/config/SAM
cmm/file:C:/Windows/System32/config/SAM
provider/file:C:/Windows/System32/config/SECURITY
provider/file:/Windows/System32/config/SAM
provider/file:C:/ProgramData/Microsoft/Crypto/RSA/MachineKeys
```

At least:

```text
provider/file:C:/Windows/System32/config/SAM
```

was shown to:

- return non-private from the current filesystem classifier;
- pass the canonical identifier validator;
- pass canonical EventSystem publication;
- durably persist unchanged.

The bypass was reproduced across **13/13 shared identifier-bearing channels**:

1. payload request ID;
2. payload workflow ID;
3. payload aggregate ID;
4. payload producer;
5. header producer;
6. header aggregate ID;
7. header correlation ID;
8. header source;
9. permissions;
10. metadata error type;
11. nested result reference;
12. structured reference sequence;
13. domain reference sequence.

Manual canonical `publish_event(...)` also allowed it with both the official in-memory and file-backed repository paths.

## 4.2 Root issue

Current URI structural handling recognizes authority-bearing forms using `scheme://authority`.

The retained `file:` rejection still has a start-of-string blind spot for embedded **non-authority file URI syntax**, including:

```text
file:/...
file:C:/...
```

When wrapped under an allowed logical slash root such as `provider/` or `cmm/`, the outer public-root rule can incorrectly accept the value.

This is a structural classifier defect. Do **not** remediate it by adding reproduced Windows filenames or more sensitive-path literals to a denylist.

## 4.3 Required design behavior

Stay within the existing canonical identifier/filesystem safety authority.

Required invariant:

```text
WRAPPED_FILE_URI_REFERENCES_HAVE_THE_SAME_UNSAFE_CLASSIFICATION_AS_TOP_LEVEL_FILE_URI_REFERENCES
```

The implementation must detect unsafe local `file:` reference semantics even when:

- the `file:` token is not at character zero;
- `//` is absent;
- a valid logical wrapper precedes it;
- Windows drive syntax follows it;
- a slash-root allowlist would otherwise accept the wrapper.

At minimum reject:

```text
file:/etc/shadow
file:///etc/shadow
file:C:/Windows/System32/config/SAM
provider/file:/etc/shadow
provider/file:C:/Windows/System32/config/SAM
cmm/file:C:/Windows/System32/config/SAM
```

Also probe equivalent separators/case forms that are meaningful under the existing grammar, without inventing unsupported syntax.

The fix must:

- be analysis-only;
- use no filesystem I/O;
- use no host resolution;
- not mutate accepted persisted identifiers;
- reuse the existing identifier/path/URI safety authority;
- preserve ordinary colon IDs such as the actual supported `workflow:123` / `domain:legal` style identifiers;
- preserve supported credential-free network URI references;
- preserve supported logical slash forms such as actual `provider/model` and `cmm/...` references;
- not treat every colon-bearing logical ID as a URI;
- remain fail-closed for actual local filesystem semantics.
