# 7. MAJOR-V4-001 — `memoryview` binary bypass

## Audit finding

The binary rejection contains:

```python
isinstance(value, (bytes, bytearray, memoryview))
```

but the generic sequence predicate still treats `memoryview` as an ordinary sequence.

Therefore a value such as:

```python
memoryview(b"secret-binary")
```

is recursively converted into a list of integers and can enter canonical persisted content.

## Required RED tests

Reproduce rejection failure for:

```text
payload top-level memoryview
nested payload memoryview
metadata top-level memoryview
nested metadata memoryview
manual publish_event event containing memoryview
```

At minimum verify:

```text
publication fails before persistence
repository unchanged
subscriber not invoked
DLQ unchanged
binary bytes are not transformed into integer arrays
```

## Required implementation

Fix the **existing sequence/safety authority** so `memoryview` is classified as binary before generic sequence handling.

Do not add a second policy.

The invariant after remediation:

```text
bytes
bytearray
memoryview
```

must all fail closed in every persisted Phase 11.22 content channel.

# 9. MAJOR-V4-003 — unsafe exception type name entering DLQ

## Audit finding

Raw exception messages are already excluded.

However DLQ data currently derives:

```python
type(exc).__name__
```

without validating that class name as a safe bounded category.

Python allows dynamic exception classes such as:

```python
Evil = type(
    "api_key=abcdef1234567890",
    (Exception,),
    {},
)
```

The current DLQ can store that credential-bearing class name in:

```text
error_type
error
```

## Required RED tests

Subscriber raises dynamic exception whose class name contains:

```text
api_key=abcdef1234567890
```

Required before fix:

```text
dead letter created
secret appears in error_type/error
```

Also reproduce a private-marker class name such as:

```text
system_prompt=TOP SECRET
```

Control:

```text
RuntimeError
```

must remain meaningfully categorized.

## Required implementation

Create one bounded safe DLQ error-category derivation within the existing DLQ/event bus ownership.

Do not store:

- raw exception message;
- traceback;
- unsafe arbitrary class name.

A valid minimal rule:

```text
if exception class name is a narrow safe identifier
and passes existing credential/private scanning
→ store it

otherwise
→ neutral category such as "SubscriberDeliveryError" or "Exception"
```

Do not add another DLQ subsystem.

No unsafe original exception class name may appear anywhere in DLQ-facing fields.
