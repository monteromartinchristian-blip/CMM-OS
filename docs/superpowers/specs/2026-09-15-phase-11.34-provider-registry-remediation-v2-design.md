## 1. Purpose

Remediation V2 exists only to close the five majors reported by Independent Re-audit V2.

It must not redesign Phase 11.34 or reopen behavior already verified by V2.

The remediation is successful only if the exact five open findings are closed while preserving all established Provider Registry contracts, all prior phase invariants, Qwen separation, non-inference discovery, no-secret persistence, CMM Usage deferral, CMMChat deferral, and the historical audit trail.

## 4. Architectural decision A — manifest metadata must not outlive canonical provider identity

### 4.1 Authority model

`ProviderRegistry` remains the sole provider identity authority.

`ProviderManifestRegistry` remains only a metadata catalog bound to a specific canonical `ProviderRegistry`.

It may not expose manifest metadata for a provider that is no longer represented by the same canonical provider object with which the metadata was registered.

### 4.2 Binding model

Each registered manifest must be internally bound to the exact canonical `ProviderSpec` instance resolved at registration time.

Conceptually:

```text
provider_id
→ (bound ProviderSpec instance, ProviderManifest)
```

Lookup/list behavior must validate current canonical identity before returning metadata.

If:

```text
ProviderRegistry.get(provider_id) is bound_provider_spec
```

then the manifest remains valid.

If the canonical provider is missing, or if the same provider id was later re-registered as a different `ProviderSpec` object, the old manifest is stale and must not be returned as active metadata.

### 4.3 Purge semantics

Stale manifests should be removed lazily at lookup/list time or eagerly through the smallest implementation compatible with existing contracts.

No callback or synchronization bus from `ProviderRegistry` to manifest metadata is required.

Do not introduce bidirectional synchronization.

### 4.4 Re-registration safety

This exact adversary must hold:

```text
register provider A
register manifest M bound to A
remove provider A
re-register provider B with same id

M must not become valid again
```

Identity equality by `provider_id` alone is insufficient.

### 4.5 Capture coherence

`capture_provider_registry_state()` must refuse to serialize an incoherent graph.

Before building `ProviderRegistryState`, every manifest included in capture must correspond to the exact currently canonical provider identity.

If not, capture must raise a typed/focused error and produce no persisted state.

The system must never create a state that canonical restore cannot reconstruct.

## 5. Architectural decision B — one Provider Registry state coordinator

### 5.1 Motivation

Remediation V1 placed persistence/revision/audit logic directly inside onboarding.

That is insufficient because discovery and validation lifecycle mutations also need durable revisioned audit behavior.

Remediation V2 introduces one focused coordinator for Provider Registry state mutation/persistence.

Provisional name:

`ProviderRegistryStateCoordinator`

The implementation may choose a nearby name only to follow repository conventions.

### 5.2 Scope

The coordinator is Provider Registry-specific.

It is not:

- a general transaction manager;
- a general event bus;
- a Phase 11 persistence framework;
- a replacement registry;
- a routing engine.

### 5.3 Owned dependencies

The coordinator owns references to:

```text
ProviderRegistry
ProviderManifestRegistry
ModelCatalog
ProviderConnectionRegistry
ModelRouteCatalog
ProviderRegistryStateRepository
revision
audit_log
```

It does not own raw secrets.

### 5.4 Canonical persistence rule

All durable Provider Registry mutations that affect phase-owned state must use the same semantic sequence:

```text
canonical mutation
→ sanitized audit records
→ capture coherent aggregate
→ revision + 1
→ repository.save()
→ publish new in-memory revision/audit state
```

A persistence failure must not leave the coordinator believing the new revision committed.

### 5.5 Onboarding integration

`ProviderOnboardingService` must delegate persistence/revision/audit behavior to the coordinator.

The existing `_persist_after_acceptance()` logic must not remain as a parallel state-commit path.

Onboarding still owns:

- proposal creation;
- isolation preflight;
- credential preflight;
- credential creation;
- connection construction/registration;
- compensation of operation-owned side effects.

The coordinator owns only aggregate persistence/revision/audit commit.

### 5.6 Discovery integration

The existing pure administrative `discover_models()` function remains valid and must remain inference-free.

A coordinator operation must wrap it, conceptually:

```python
coordinator.discover_models(
    connection,
    manifest,
    client,
    seen_at=...,
)
```

The wrapper:

1. calls canonical `discover_models()`;
2. inspects `ModelDiscoveryResult`;
3. emits sanitized lifecycle audit records;
4. persists the resulting aggregate;
5. advances revision once per successful discovery mutation batch.

### 5.7 Route audit records

At minimum, use sanitized event types equivalent to:

```text
route.discovered
route.unavailable
route.restored
```

Each record must identify:

- revision;
- entity kind = route;
- route id;
- occurred_at;
- sanitized transition detail.

No provider response payload or secret material may enter audit detail.

### 5.8 Validation transition persistence

A real connection status transition must have one canonical operation.

Conceptually:

```python
coordinator.update_connection_status(
    connection_id,
    new_status,
    occurred_at=...,
)
```

It must:

- validate connection existence;
- no-op or reject when no state change occurs;
- replace/update the canonical connection through the existing registry's smallest compatible API;
- emit `provider.validation_changed`;
- persist the aggregate;
- advance revision once on success.

No second connection registry or validation engine is authorized.

### 5.9 Rollback semantics

The coordinator must not require a general transaction framework.

If a coordinated mutation fails at persistence:

- restore only the Provider Registry state changed by that coordinator call using the smallest safe snapshot/restore mechanism already available;
- preserve prior revision and audit log;
- propagate the original failure.

## 6. Architectural decision C — isolation is canonical provider policy

### 6.1 Problem

Isolation currently depends on observed external configuration:

```text
external_config_present
OR external_endpoint_override_present
```

This is insufficient for subscription bridges that are required to run under a CMM-owned profile even when only authentication evidence exists.

### 6.2 Manifest policy

Add an explicit immutable boolean policy to `ProviderManifest`:

```python
requires_isolation: bool = False
```

It is declarative metadata, not runtime state.

### 6.3 First-wave policy

The canonical first-wave manifests must set:

```text
codex         requires_isolation=True
claude-code   requires_isolation=True
antigravity   requires_isolation=True
```

Other providers retain `False` unless already required by their canonical design.

Do not infer this globally from `BillingClass.SUBSCRIPTION`.

Specifically:

- Qwen Token Plan remains a subscription surface;
- Qwen Token Plan must not automatically become a local profile-isolation provider merely because billing class is subscription.

### 6.4 Proposal derivation

`ProviderOnboardingService.propose()` must derive:

```text
requires_isolation =
    manifest.requires_isolation
    OR candidate.external_config_present
    OR candidate.external_endpoint_override_present
```

This preserves the existing external-risk rule while adding explicit canonical provider policy.

### 6.5 Auth-only adversary

For each of:

- Codex;
- Claude Code;
- Antigravity;

the following must hold:

```text
auth evidence present
config marker absent
validator passes

=> proposal.requires_isolation=True
=> CMM-owned isolation profile required
=> CONNECTED impossible without successful isolation
```

## 7. Architectural decision D — new-connection acceptance must not mutate unknown pre-existing side effects

### 7.1 Principle

Remediation V2 chooses **fail-before-mutation**, not secret/profile backup and restoration.

This preserves the secure secret-store boundary and avoids adding raw secret read APIs.

### 7.2 Credential ownership preflight

Before calling `CredentialStore.put()` for a new connection:

1. derive the exact credential ref using the canonical credential-ref helper;
2. call `CredentialStore.has(ref)`;
3. if it already exists while the new connection does not exist, reject acceptance with a focused ownership/conflict error;
4. do not overwrite;
5. do not delete.

`accept()` must never use `put()` as an implicit upsert for an unowned pre-existing credential.

Credential rotation/update remains a separate future operation and is out of scope.

### 7.3 Isolation target ownership preflight

Before profile creation for a new connection:

```text
target = profiles_root / provider_id
```

If that target already exists, reject before mutation.

Do not copy into, merge with, or overwrite an existing target during new-connection acceptance.

A future explicit "reuse/rotate profile" operation is out of scope.

### 7.4 Compensation stack

After preflight, every side effect created by the current operation is operation-owned.

Only those may be compensated.

The compensation stack may include:

- newly registered connection;
- newly created credential ref;
- newly created isolation target.

Pre-existing resources are never placed on the compensation stack.

### 7.5 Rollback failure

A rollback failure must not be silently treated as successful atomic compensation.

If cleanup of an operation-owned resource fails, the original failure must still be reported together with enough structured context to make the partial cleanup visible.

Do not log secret content.

### 9.1 Non-divergence after provider removal

Prove:

```text

manifest registered

old manifest does not revive
```

### 9.2 Route lifecycle audit persistence

Run three discovery passes:

1. route first discovered;
2. route disappears;
3. route reappears.

Require persisted audit history containing, in order:

```text
route.discovered
route.unavailable
route.restored
```

After process-equivalent restore, the same audit sequence must remain available.

### 9.3 Validation transition audit persistence

Start with a non-connected connection.

Change canonical status through the coordinator.

Require:

```text
provider.validation_changed
```

to be persisted with the new status and preserved after restart.

### 9.4 Auth-only subscription isolation

Using the real Codex/Claude/Antigravity detectors:

- write only authentication marker;
- write no config marker;
- detect candidate;
- propose;
- assert `requires_isolation=True`;
- accept with passing validator;
- assert `CONNECTED` only when CMM-owned isolation exists.

Also prove failed isolation never connects.

### 9.5 Pre-existing credential conflict

Pre-create the exact credential ref in the official in-memory credential store.

Attempt new connection acceptance.

Require:

```text
accept rejected before put/upsert
old credential preserved
connection absent
repository revision unchanged
```

Do not add a secret getter to production.

### 9.6 Pre-existing isolation target conflict

Pre-create target profile directory with representative content.

Attempt new connection acceptance.

Require:

```text
accept rejected before mutation
existing profile bytes unchanged
connection absent
repository revision unchanged
```

## 10. `DP-134` remains unchanged

Do not revise the frozen Design Point merely because Remediation V1 failed to implement all of it.

`DP-134` remains:

> **DP-134 — Canonical, Persistent and Fail-Closed Provider Registry:** CMM OS maintains exactly one authoritative provider identity inventory through the canonical `ProviderRegistry`, with `ModelCatalog`, accepted provider connections and provider-specific model routes referentially bound to that authority; Provider Registry state is locally persisted through one versioned, deterministic, no-secret repository boundary with atomic restore/save behavior and sanitized audit history; provider detection never grants connection authority; subscription providers requiring isolation cannot become connected without a validated CMM-owned isolation outcome; onboarding is atomic and failed operations cannot mutate pre-existing credentials, connection state or persisted revision; dynamic discovery remains administrative and performs no inference; Qwen Token Plan and Qwen Cloud PAYG remain distinct provider/account surfaces; no parallel provider inventory, persistence framework, isolation runtime, routing engine or usage catalog is introduced.

Remediation V2 exists to make the implementation satisfy this existing DP.
