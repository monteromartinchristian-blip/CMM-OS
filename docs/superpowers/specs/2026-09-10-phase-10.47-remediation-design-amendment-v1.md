# 4. MAJOR-01 remediation — Canonical declarative Domain Pack benchmark path

## 4.1 Problem

The audited implementation can preserve benchmarks through:

```text
Python DomainDefinition
    -> ParsedDomainPack.to_dict()
    -> ParsedDomainPack.from_dict()
```

but the official declarative path rejects the field itself:

```text
DomainManifest.from_declarative_dict(...)
    -> unknown field: benchmark_suites
```

That means built-in Python definitions can carry benchmarks while a real declarative/external Domain Pack document cannot.

This violates the Phase 10.47 requirement that benchmarks are portable **Domain Pack assets**.

---

## 4.2 Required architecture

The existing declarative Domain Pack path must be extended **minimally**.

The canonical flow after remediation must be:

```text
declarative Domain Pack mapping
    ↓
existing declarative Domain Pack parser
    ↓
strict benchmark_suites parsing
    ↓
canonical DomainBenchmarkSuite.from_dict(...)
    ↓
canonical DomainDefinition(
    ...,
    benchmark_suites=(...),
)
    ↓
existing pack validation
    ↓
existing loader / registry / rollback path
```

There must still be exactly one Domain Pack loader architecture.

---

## 4.3 Declarative field ownership

The declarative Domain Pack representation may recognize:

```text
benchmark_suites
```

as an optional top-level Domain definition asset field wherever the existing declarative parser currently recognizes definition-level fields.

The precise existing owner must be inspected before editing.

Expected owner is the current `DomainManifest.from_declarative_dict()` / declarative-known-field path identified by V1, but implementation must follow the actual repository code rather than create a parallel parser.

The field defaults to:

```python
()
```

when absent.

Backward compatibility is mandatory.

---

## 4.4 Parsing rule

Every declarative suite item must be parsed exclusively through:

```python
DomainBenchmarkSuite.from_dict(...)
```

or the exact canonical equivalent already introduced by 10.47.

Do not duplicate benchmark validation inside the declarative parser.

The declarative parser owns:

```text
field recognition
container-shape validation
handoff to canonical benchmark contract parsing
attachment to DomainDefinition
```

The benchmark contract owns:

```text
suite/case IDs
domain binding
cost validity
metadata validity
schema validity
duplicate case IDs
strict unknown benchmark fields
```

`DomainDefinition` remains responsible for definition-level suite-domain coherence and duplicate suite IDs.

---

## 4.5 Fail-closed behavior

The declarative path must reject:

```text
benchmark_suites with non-list/non-sequence declarative shape
non-mapping suite entries
unknown suite fields
unknown case fields
malformed suite IDs
malformed case IDs
suite/domain mismatch
case/domain mismatch
duplicate suite IDs
duplicate case IDs
invalid maximum_cost_eur
invalid metadata authority keys
invalid JSON schema values
```

Invalid benchmark content must **not** be silently dropped.

A pack containing invalid benchmark assets must remain invalid according to the existing loader/validation lifecycle.

---

## 4.6 Loader and rollback

The remediation must prove the behavior through the real loader path used by declarative packs.

No new:

```text
BenchmarkLoader
BenchmarkPackLoader
DomainBenchmarkLoader
BenchmarkRollbackManager
BenchmarkLifecycle
```

may be introduced.

The existing Domain loader/registration/rollback behavior must remain authoritative.

If the canonical loader already obtains a `ParsedDomainPack` from the declarative parser, no additional loader logic should be added beyond what is necessary to preserve the parsed `DomainDefinition`.

# 5. MAJOR-02 remediation — Separate schema validation from metadata authority validation

## 5.1 Problem

The audited implementation uses the same JSON-mapping validation helper for:

```text
required_schema
metadata
```

and applies reserved model/provider authority-key rejection recursively to both.

This creates two opposite defects:

```text
required_schema
    -> too restrictive

metadata
    -> still too permissive for obvious aliases
```

A valid output schema property such as:

```json
{
  "properties": {
    "provider": {"type": "string"}
  }
}
```

is rejected even though it may refer to a healthcare provider or ordinary domain output field.

Meanwhile metadata aliases such as:

```text
preferred_model
candidate_model
preferred_provider
candidate_provider
```

are accepted.

---

## 5.2 Required architecture: two distinct validation responsibilities

The remediation must split:

```text
generic JSON mapping validation / deep-freezing
```

from:

```text
benchmark metadata authority-key validation
```

Conceptually:

```python
def _freeze_json_mapping(
    value: Mapping[str, JsonValue],
    *,
    field_name: str,
) -> Mapping[str, JsonValue]:
    ...
```

performs only:

```text
mapping type validation
JSON-safe key/value validation
deep immutability
deterministic serialization compatibility
```

and:

```python
def _freeze_benchmark_metadata(
    value: Mapping[str, JsonValue],
    *,
    field_name: str,
) -> Mapping[str, JsonValue]:
    ...
```

performs:

```text
generic JSON mapping validation
+
reserved authority-key validation
```

Exact private helper names may follow existing code style, but the semantic separation is mandatory.

---

## 5.3 `required_schema` rule

`required_schema` is declarative output-schema data.

It must allow ordinary schema property names including:

```text
provider
model
models
provider_id
model_id
```

when those names occur **inside schema structure as fields being described**.

Examples that must be valid:

```json
{
  "type": "object",
  "properties": {
    "provider": {"type": "string"}
  }
}
```

and:

```json
{
  "type": "object",
  "properties": {
    "model": {"type": "string"}
  }
}
```

Phase 10.47 does not infer routing authority from schema property names.

The schema remains JSON-safe, deeply immutable and strictly serializable.

---

## 5.4 Metadata authority rule

Benchmark-owned metadata remains non-authoritative.

The authority-key prohibition applies to:

```text
DomainBenchmarkCase.metadata
DomainBenchmarkSuite.metadata
nested mapping keys inside those metadata mappings
```

It does **not** scan arbitrary prose values.

It does **not** scan `required_schema`.

---

## 5.5 Canonical metadata-key normalization

Before comparing metadata keys against the reserved authority set, normalize them deterministically.

Required semantic normalization:

```text
lowercase
camelCase -> snake_case
PascalCase -> snake_case
kebab-case -> snake_case
space-separated -> snake_case
collapse repeated underscores
strip leading/trailing underscores
```

Examples:

```text
preferredModel      -> preferred_model
PreferredModel      -> preferred_model
preferred-model     -> preferred_model
preferred model     -> preferred_model
PREFERRED_MODEL     -> preferred_model

candidateProvider   -> candidate_provider
candidate-provider  -> candidate_provider
```

No fuzzy natural-language classifier is needed.

Use deterministic string normalization only.

---

## 5.6 Reserved normalized metadata keys

At minimum reject these normalized keys:

```text
model
models
model_id
model_ids
model_family

candidate_model
candidate_models
preferred_model
preferred_models
prohibited_model
prohibited_models

provider
providers
provider_id
provider_ids

candidate_provider
candidate_providers
preferred_provider
preferred_providers
prohibited_provider
prohibited_providers

routing_weight
routing_weights
```

The implementation may retain additional already-reserved aliases if they are equally narrow and defensible.

Do not broaden the list to unrelated words merely because they contain `model` or `provider`.

For example, do not reject arbitrary keys such as:

```text
modeling_notes
provider_context_description
```

unless they are explicitly proven to carry model/provider selection authority.

---

## 5.7 Metadata value rule

Authority validation is based on metadata **keys**, not arbitrary values.

This must remain valid:

```python
metadata={
    "description": "This benchmark checks whether the response names a healthcare provider."
}
```

Likewise ordinary prose may mention:

```text
model
provider
routing
```

without being interpreted as authority.

# 6. MAJOR-03 remediation — Canonical Decimal serialization and digest identity

## 6.1 Problem

The audited implementation serializes:

```python
str(maximum_cost_eur)
```

directly.

Numerically equal `Decimal` values preserve different textual scales:

```text
Decimal("0.25")  -> "0.25"
Decimal("0.250") -> "0.250"
```

Thus:

```text
SEMANTIC_SUITE_EQUAL=True
EXPORT_EQUAL=False
DIGEST_EQUAL=False
```

This violates the explicit Phase 10.47 promise:

```text
same semantic suite -> same digest
```

---

## 6.2 Required canonical Decimal rule

`maximum_cost_eur` must serialize using a canonical decimal representation based on **numeric value**, never caller-provided textual scale.

No binary float conversion is permitted.

Recommended canonicalization:

```python
def _canonical_decimal_text(value: Decimal) -> str:
    if value == 0:
        return "0"

    normalized = value.normalize()
    text = format(normalized, "f")

    if "." in text:
        text = text.rstrip("0").rstrip(".")

    return text
```

The exact implementation may differ if the repository already has a proven canonical Decimal helper, but it must satisfy the behavioral invariants below.

Do not introduce a new generic decimal framework if an existing dependency-safe canonical helper already exists.

---

## 6.3 Canonicalization examples

All of the following must serialize identically within each equality group.

### Fractional equivalents

```text
Decimal("0.25")
Decimal("0.250")
Decimal("2.5E-1")
```

Canonical text:

```text
0.25
```

### Integer equivalents

```text
Decimal("1000")
Decimal("1E+3")
Decimal("1000.000")
```

Canonical text:

```text
1000
```

### Zero equivalents

```text
Decimal("0")
Decimal("0.0")
Decimal("-0")
Decimal("-0.000")
```

Canonical text:

```text
0
```

Distinct numeric values must remain distinct.

---

## 6.4 Round-trip rule

Serialization remains precision-safe:

```text
Decimal
    -> canonical decimal string
    -> Decimal
```

with no float conversion.

Required:

```python
Decimal(serialized_value) == original_value
```

for every valid cost.

The restored Decimal does not need to preserve the caller's original trailing-zero scale because benchmark semantic identity is numeric.

---

## 6.5 Export and digest rule

Because suite export/digest depend on `to_dict()`, canonical cost serialization must ensure:

```text
numerically equal benchmark costs
    -> identical to_dict
    -> identical export bytes
    -> identical SHA-256 content digest
```

Required independent-style probes after remediation:

```text
COST_025_EQ_0250=True
COST_025_EXPORT_EQUAL=True
COST_025_DIGEST_EQUAL=True

COST_1000_EQ_1E3=True
COST_1000_EXPORT_EQUAL=True
COST_1000_DIGEST_EQUAL=True

COST_ZERO_EQ_NEGATIVE_ZERO=True
COST_ZERO_EXPORT_EQUAL=True
COST_ZERO_DIGEST_EQUAL=True
```

And:

```text
DISTINCT_COST_EXPORT_DIFFERENT=True
DISTINCT_COST_DIGEST_DIFFERENT=True
```
