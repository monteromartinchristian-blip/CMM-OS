## 1. Purpose

This document amends the approved Phase 10.45 design exclusively for Audit V1 `MAJOR-03`:

> the Domain Selector cannot complete the roadmap-required `ADD_SUPPORTING` and `WITHDRAW_SUPPORTING` actions because no existing canonical seam accepts a membership delta command.

The amendment introduces **one** minimal canonical **Domain Selection Transition Coordinator** under Domain Intelligence. The coordinator is a command-authority coordinator, not a new source of state. It owns no store, resolver, composer, registry, session database, or permission engine. It performs canonical coordination only, reusing existing canonical services and the existing canonical optimistic session persistence boundary.

All other phases of the design (conversational view, Domain Center, Cross-Domain view, Review Center approvals, projection digest semantics, interface-neutral contracts, prohibition of interface-owned authority) are unchanged by this amendment except where the corrected `AT-DP-045` chain must additionally prove the coordinator path described here.

## 3. Audit V1 MAJOR-03 finding

Independent Audit V1 records, verbatim in substance:

- **Requirement violated:** the approved Phase 10.45 design and implementation plan require the Domain Selector to support interface-originated add-supporting and withdraw-supporting intents, with `ADD_SUPPORTING` validating eligibility and cross-domain permission and then delegating through canonical composition/session selection authority, and `WITHDRAW_SUPPORTING` delegating through existing canonical selection/session authority.
- **Current implementation:** for `ADD_SUPPORTING`, permission `DENY` is rejected and `APPROVAL_REQUIRED` becomes pending, but even canonical `ALLOW` is returned `accepted=False`, `status=UNAVAILABLE`, `reason_code=domain_selector_supporting_application_unavailable`. For `WITHDRAW_SUPPORTING`, the implementation always returns unavailable after validating membership.
- **Independent reproduction:** the dedicated tests codify the missing behavior with a case equivalent to "allowed permission still requires later platform", which conflicts with the approved plan.
- **Required remediation:** re-inspect the canonical resolution/composition/session seams and implement both actions through existing canonical authority only; never mutate `DomainResolutionResult`, `DomainComposition`, or `DomainSessionContext` directly; never create a new selector store, session store, composition engine, or policy engine; preserve permission intersection and fail closed; if no safe canonical authority exists, stop and escalate an architectural incompatibility requiring explicit design amendment instead of silently returning `UNAVAILABLE` on the successful path; update `AT-DP-045` to prove the amended behavior.

This amendment is that explicit design amendment. Repository inspection (below) proved the incompatibility and produced the safe canonical path documented in this file.

## 4. Architectural-block evidence

`docs/audits/phase-10.45-major-03-architectural-block-evidence.md` proves, with inspected code evidence, that no pre-amendment canonical seam accepts a membership delta command:

```text
- resolver derives supporting domains but accepts no membership delta command
- selection.py is pure
- composer is pure
- session resumer is lifecycle-reactive, not command-driven
- SharedSessionDomainAdapter is persistence only
- permission resolver returns decisions only
- WITHDRAW has no canonical command lever
```

The same inspection proved the enabling facts used by this amendment:

- the resolver is a deterministic pure function of a `DomainResolutionContext` plus a `DomainResolutionPolicy`;
- `DomainResolutionPolicy.required_domains` forces a domain into the resulting supporting set whenever the candidate is eligible (deterministic, per-transition input);
- `DomainResolutionPolicy.denied_domains` excludes a candidate from the resulting resolution (deterministic, per-transition input);
- a required domain that is rejected (disabled, unauthorized, policy-excluded) blocks resolution (`BLOCKED`/`INSUFFICIENT_INFORMATION`), which fails closed rather than silently succeeding;
- `build_domain_selection_transition(previous, current)` in `cmm/domains/selection.py` is a pure comparator of two canonical `DomainResolutionResult` objects and is the canonical transition record builder;
- `SharedSessionDomainAdapter.save_domain_session(context, expected_previous_revision=...)` in `cmm/domains/session_persistence.py` is the durable, authoritative session boundary and enforces strict revision+1 optimistic semantics;
- the canonical session resumer already demonstrates the full pattern this coordinator mirrors: fresh canonical resolution from registry/session state, canonical recomposition, and exactly one new immutable `DomainSessionContext` revision persisted only after pure authority computation succeeds.

## 5. Required amendment direction

Introduce one minimal canonical **Domain Selection Transition Coordinator** under Domain Intelligence, with contracts in `cmm/domains/selection_transition_contracts.py` and default implementation `DefaultDomainSelectionTransitionCoordinator` in `cmm/domains/selection_transition.py`.

The coordinator is dependency injected and coordinates, in order:

```text
validate current session/resolution/composition authority
validate target lifecycle/eligibility
validate cross-domain permission (ADD_SUPPORTING)
build request-scoped selection delta
canonical re-resolution
canonical recomposition
build DomainSelectionTransition
persist exactly one new DomainSessionContext revision
    through SharedSessionDomainAdapter.save_domain_session(...)
```

Interface-originated `ADD_SUPPORTING` and `WITHDRAW_SUPPORTING` intents delegate to this coordinator. `AUTO_RESOLVE` and `SELECT_PRIMARY` continue to use the existing canonical resolver authority unchanged. `EXPLAIN_SELECTION` is unchanged. `REQUEST_POLICY_CHANGE` remains `UNAVAILABLE`: repository inspection confirms no canonical policy write authority exists, which the approved plan permits.

## 6. Exact canonical seams reused

The coordinator consumes and composes only existing canonical seams:

```text
DomainRegistry / registry lifecycle          cmm/domains/registry.py
DefaultDomainResolver                        cmm/domains/resolver.py
DomainResolutionContext / DomainResolutionPolicy
                                             cmm/domains/resolution_contracts.py
DefaultDomainComposer                        cmm/domains/composer.py
DomainPermissionResolver                     cmm/domains/permission_resolver.py
DomainSessionContext                         cmm/domains/session_contracts.py
SharedSessionDomainAdapter                   cmm/domains/session_persistence.py
build_domain_selection_transition            cmm/domains/selection.py
DomainSelectionTransition                    cmm/domains/selection_contracts.py
DomainSessionTransition                      cmm/domains/session_contracts.py
DomainCompositionStatus                      cmm/domains/enums.py
```

Each is used for its canonical purpose only:

- the **registry** supplies the installed definitions and lifecycle status used to build the canonical resolution context and to recompose;
- the **resolver** performs the canonical re-resolution that produces the new membership;
- the **composer** performs the canonical recomposition (`DefaultDomainComposer.compose`) of the new resolution with the registry definitions;
- the **permission resolver** returns the typed cross-domain decision for the target on `ADD_SUPPORTING`;
- the **session context** is the immutable canonical state that is never mutated in place;
- the **session adapter** is the only persistence seam and enforces optimistic revision semantics;
- **`build_domain_selection_transition`** produces the canonical transition record comparing the canonical previous resolution (the one carried by the intent submission authority chain) with the canonical new resolution;
- **`DomainSessionTransition`** is appended to the session history exactly as the canonical session resumer appends transition records.

No seam is bypassed, wrapped into a parallel authority, or shadowed by a new store.

## 7. New coordinator responsibility

The coordinator's single responsibility is: **translate an interface-originated, permission-validated membership delta intent into exactly one canonical session revision through the canonical resolution, composition, transition, and session-persistence chain — or fail closed leaving every canonical object and store untouched.**

It is responsible for:

- binding validation: the supplied canonical `DomainSessionContext`, `DomainResolutionResult`, and `DomainComposition` must form one coherent authority chain (session ids, primary/supporting membership, composition id, last resolution id consistent with the resolution and composition supplied);
- target eligibility validation against the registry lifecycle (enabled, or allowed by canonical policy semantics; degraded handling per canonical policy; authorization fail-closed);
- membership preconditions (add target not already supporting and not primary; withdraw target currently supporting and not primary);
- cross-domain permission validation on add;
- building the request-scoped derived resolution policy without mutating the original;
- canonical re-resolution and recomposition;
- verifying the re-resolution outcome actually contains/excludes the delta and preserves the primary;
- building the canonical `DomainSelectionTransition`;
- persisting exactly one new immutable `DomainSessionContext` revision through the session adapter with the expected previous revision;
- returning a typed, immutable result that lets the Phase 10.45 selector project the interface intent outcome (accepted / blocked / pending / unavailable) without re-deriving authority.

## 8. Explicit non-responsibilities

The coordinator does **not**:

- own or create any store, repository, database, or cache;
- own or create any resolver, composer, registry, session system, or permission engine;
- mutate `DomainResolutionPolicy`, `DomainResolutionResult`, `DomainComposition`, `DomainSessionContext`, `DomainSelectionTransition`, or any registry record;
- disable or enable domains in the registry;
- patch the current session in place;
- persist anything before re-resolution and recomposition both succeed;
- retry, bypass, or soften optimistic revision conflicts;
- execute operations, workflows, or approval flows;
- project interface views or interpret interface intent kinds other than the membership delta commands;
- import or depend on Phase 10.45 interface integration modules (it is canonical Domain infrastructure below the interface layer).

## 9. Command data flow

```text
Interface intent (ADD_SUPPORTING | WITHDRAW_SUPPORTING)
    ↓
DefaultDomainInterfaceIntegrator (Phase 10.45 selector delegation)
    → builds typed DomainSelectionTransitionRequest
    ↓
DefaultDomainSelectionTransitionCoordinator
    1. bind: session ↔ resolution ↔ composition authority coherence check
    2. validate target lifecycle/eligibility/membership preconditions
    3. permission: ADD_SUPPORTING requires CrossDomainPermissionDecision.ALLOW
    4. derive request-scoped DomainResolutionPolicy (clone; never mutate)
       - ADD_SUPPORTING    → target added to required_domains
       - WITHDRAW_SUPPORTING → target added to denied_domains
    5. canonical re-resolution via DefaultDomainResolver
    6. verify: status RESOLVED; membership delta applied; primary preserved
    7. canonical recomposition via DefaultDomainComposer.compose
    8. verify: DomainCompositionStatus COMPOSED or PARTIAL
    9. build_domain_selection_transition(previous canonical resolution, new resolution)
    10. build exactly one new immutable DomainSessionContext revision
    11. SharedSessionDomainAdapter.save_domain_session(
            new_context, expected_previous_revision=current.revision)
    12. return typed DomainSelectionTransitionResult
    ↓
DefaultDomainInterfaceIntegrator projects DomainInterfaceIntentResult
```

The coordinator receives the canonical previous `DomainResolutionResult` and `DomainComposition` from the intent submission authority chain (`DefaultDomainAPI.submit_interface_intent` already receives them and validates type/identity). The phase 10.45 interface layer performs no transition algorithm; it submits the typed request and projects the typed result.

## 10. ADD_SUPPORTING semantics

Successful connected path (all conditions must hold):

```text
current canonical resolution/session/composition form one coherent authority chain
target is installed in the registry and active/eligible/authorized
target is not the current primary
target is not already a current supporting domain
CrossDomainPermissionDecision.ALLOW for the target
request-scoped derived policy requires the target as required supporting membership
canonical re-resolution remains RESOLVED
    and the new supporting set contains the target
    and the primary domain is unchanged
canonical recomposition is COMPOSED or PARTIAL
→ DomainSelectionTransition with supporting_changed=True
→ exactly one new persisted DomainSessionContext revision (revision + 1)
→ accepted=True
```

Fail-closed paths (no persistence, no registry mutation, no policy mutation):

```text
target already supporting
target is primary
target disabled (and canonical policy does not allow disabled)
target degraded when canonical policy forbids degraded
target unauthorized
permission DENY
permission APPROVAL_REQUIRED
re-resolution not RESOLVED (including required-domain conflicts)
recomposition BLOCKED/FAILED
new membership does not actually contain the target
primary would change
optimistic session revision conflict
authority-chain binding mismatch
```

The original `DomainResolutionPolicy` object is never mutated; the derived policy is used solely as resolution input for this transition.

## 11. WITHDRAW_SUPPORTING semantics

Successful connected path (all conditions must hold):

```text
current canonical resolution/session/composition form one coherent authority chain
target is currently a supporting domain of the session
target is not the current primary
request-scoped derived policy excludes the target as denied membership
canonical re-resolution remains RESOLVED
    and the new supporting set does not contain the target
    and the primary domain is unchanged
canonical recomposition is COMPOSED or PARTIAL
→ DomainSelectionTransition with supporting_changed=True
→ exactly one new persisted DomainSessionContext revision (revision + 1)
→ accepted=True
```

Fail-closed paths (no persistence, no registry mutation, no policy mutation):

```text
target not currently supporting
target is primary
withdrawal leaves no resolvable state (re-resolution not RESOLVED)
recomposition BLOCKED/FAILED
new membership still contains the target
primary would change
optimistic session revision conflict
authority-chain binding mismatch
```

Withdrawal is a retraction of existing membership: no registry disable, no global policy mutation, no direct session patch, and no new cross-domain permission grant is required for it.

## 12. Session revision semantics

A successful transition creates exactly one new immutable `DomainSessionContext` revision:

- `revision = current.revision + 1`;
- `updated_at =` coordinator clock (UTC);
- `primary_domain`, `supporting_domains`, `composition_id`, and `last_resolution_id` are the canonical values of the new resolution/composition;
- `domain_transitions` = current transitions + exactly one new `DomainSessionTransition` record describing the membership change and referencing the new resolution/composition;
- `domain_versions` are refreshed to the registry versions of the resulting primary/supporting domains (same coherence rule the canonical session resumer applies);
- all other canonical session fields (questions, approvals, conflicts, partial results, traces, resources, knowledge refs, next recommended step, metadata, session id) are preserved unchanged unless a field is composition-derived and must be refreshed to remain coherent with the new composition (same recomposition semantics the canonical session resumer applies when it persists a recomposed session).

Persistence uses the canonical optimistic contract:

```text
SharedSessionDomainAdapter.save_domain_session(
    new_context,
    expected_previous_revision=current.revision,
)
```

Exactly one revision is persisted per successful transition. No partial write occurs before re-resolution and recomposition both succeed.

## 13. Permission semantics

- `ADD_SUPPORTING` always requires a canonical cross-domain permission decision for the target: `ALLOW` proceeds; `DENY` is a blocked outcome; `APPROVAL_REQUIRED` is a pending outcome. Neither `DENY` nor `APPROVAL_REQUIRED` persists any session revision.
- `WITHDRAW_SUPPORTING` requires no cross-domain permission grant because it retracts membership the session already holds; the lifecycle and membership preconditions above still fail closed.
- Permission intersection with the current session's effective permissions is preserved because the derived policy is a clone of the canonical policy in force and the canonical resolver/composer re-apply the effective permission state during re-resolution and recomposition.
- The Phase 10.45 selector continues to map these typed outcomes to `DomainInterfaceIntentResult` statuses (`BLOCKED` for deny, `PENDING` for approval-required, `UNAVAILABLE` for unsupported commands) so interface semantics do not change shape.

## 14. Rollback/failure semantics

The transition is all-or-nothing:

- all pure authority computation (permission decision, re-resolution, recomposition, transition record construction) completes and is verified **before** any persistence call;
- any required condition that fails stops the flow at its step and returns a typed failure result;
- on failure nothing is persisted, nothing in the registry is mutated, the original policy is untouched, and the current session context (including its revision) is untouched;
- an optimistic revision conflict (the session advanced concurrently) is reported as a typed conflict result and is never retried or force-written;
- canonical errors propagate unchanged from the underlying seams.

## 15. Concurrency/revision expectations

- Sessions are immutable, revisioned canonical objects. Only the shared `SessionStore` through `SharedSessionDomainAdapter` may commit a revision, and it enforces strict revision+1 with `expected_previous_revision`.
- A concurrent transition that commits between the coordinator's binding check and its persistence call surfaces as an optimistic conflict from the adapter; the coordinator reports it and persists nothing.
- The coordinator therefore never needs (and never takes) a lock, lease, or side table; the canonical optimistic contract is the concurrency boundary.

## 16. No-parallel-infrastructure rule

The amended design forbids, and Phase 10.45 architecture tests enforce, the emergence of parallel infrastructure:

```text
SelectionTransitionStore        SelectionTransitionRepository
InterfaceSelectionStore         InterfaceSessionStore
InterfaceCompositionEngine      InterfaceResolver
InterfacePermissionEngine       InterfaceReviewStore
InterfaceMemoryStore            InterfaceRuntime
InterfaceOrchestrator
```

`selection_transition.py` does not own persistence; it may call the existing session adapter. The coordinator is canonical Domain infrastructure: `cmm/domains/selection_transition*.py` must not import interface integration modules. Dependency direction is:

```text
interface_integration
    ↓
selection_transition
    ↓
resolver/composer/permission/session canonical services
```

and never the reverse. Earlier canonical Phase 10 modules must not import Phase 10.45 interface modules.

## 17. New contracts

`cmm/domains/selection_transition_contracts.py` defines only the minimum canonical contracts required:

```text
DomainSelectionTransitionCommandKind      (ADD_SUPPORTING | WITHDRAW_SUPPORTING)
DomainSelectionTransitionRequest
DomainSelectionTransitionResult
DomainSelectionTransitionCoordinator      (protocol)
```

Existing `DomainSelectionTransition` is reused, not duplicated. Contracts are immutable, typed, and validated; no dictionaries serve as authority-bearing escape hatches; canonical authority payloads are not typed as `Any`/`object`.

`DefaultDomainAPI` is extended minimally only if the coordinator requires a public seam: exact typed forwarding, canonical errors propagated unchanged, no `**kwargs`, no untyped authority dictionaries, no second API facade. Public export tests are updated if new public contracts are intentionally exported.
