# 5. MAJOR-02 — residual model/provider authority aliases

## 5.1 Problem

The V1 remediation correctly separated:

```text
required_schema validation
```

from:

```text
benchmark metadata authority validation
```

and correctly normalized simple aliases such as:

```text
preferredModel
preferred-model
candidateProvider
routingWeight
```

However the current metadata rule still uses a finite exact denylist after normalization.

Fresh independent Re-audit V2 reproductions show these direct authority aliases remain accepted:

```text
preferred_model_id=ACCEPTED
candidate_model_id=ACCEPTED
prohibited_model_id=ACCEPTED

preferred_provider_id=ACCEPTED
candidate_provider_id=ACCEPTED
prohibited_provider_id=ACCEPTED

model_preference=ACCEPTED
provider_preference=ACCEPTED
routing_model=ACCEPTED
routing_provider=ACCEPTED
```

At minimum:

```text
preferred_model_id
candidate_model_id
preferred_provider_id
candidate_provider_id
```

are direct semantic equivalents of forbidden model/provider authority.

This violates the Phase 10.46/10.47 model-agnostic boundary.

---

## 5.2 Design rule

Metadata authority detection must remain:

```text
deterministic
key-based
non-fuzzy
narrow
auditable
```

Do not implement semantic NLP classification.

Do not scan arbitrary metadata values.

Do not scan `required_schema`.

Do not reject unrelated keys merely because they contain the substring `model` or `provider`.

---

## 5.3 Canonical key normalization

Retain deterministic normalization already introduced:

```text
camelCase -> snake_case
PascalCase -> snake_case
kebab-case -> snake_case
space-separated -> snake_case
uppercase -> lowercase
collapse repeated underscores
strip leading/trailing underscores
```

Examples:

```text
PreferredModelId       -> preferred_model_id
preferred-model-id     -> preferred_model_id
candidateProviderId    -> candidate_provider_id
routingProvider        -> routing_provider
```

---

## 5.4 Authority grammar

After normalization, reject keys matching the following narrow authority grammar.

### Explicit identifiers

```text
model
models
model_id
model_ids
provider
providers
provider_id
provider_ids
model_family
```

### Candidate/preference/prohibition authority

```text
(candidate|preferred|prohibited)_(model|provider)
(candidate|preferred|prohibited)_(model|provider)_(id|ids)
```

Examples rejected:

```text
candidate_model
candidate_model_id
candidate_model_ids
preferred_model
preferred_model_id
preferred_provider
preferred_provider_id
prohibited_model
prohibited_provider_id
```

### Reversed preference/candidate authority

Reject:

```text
(model|provider)_(candidate|candidates|preference|preferences|preferred|prohibited)
(model|provider)_(candidate|preferred|prohibited)_(id|ids)
```

Examples:

```text
model_preference
provider_preference
model_candidate
provider_candidates
```

### Routing authority

Reject:

```text
routing_(model|provider)
routing_(model|provider)_(id|ids)
routing_weight
routing_weights
```

Examples:

```text
routing_model
routing_provider
routing_model_id
routing_provider_ids
```

---

## 5.5 Negative controls

The rule must **not** reject unrelated descriptive metadata.

These must remain valid:

```text
modeling_notes
provider_context_description
model_output_description
provider_response_format
routing_explanation
```

provided they are not direct authority keys defined above.

Ordinary prose values mentioning models/providers remain valid.

Example:

```python
metadata={
    "description": "Explains which healthcare provider is mentioned and how the model output is structured."
}
```

must remain accepted.

---

## 5.6 Nested metadata

The authority grammar applies recursively to nested metadata mapping keys.

Reject:

```python
metadata={
    "evaluation": {
        "preferredModelId": "x"
    }
}
```

Accept unrelated nested descriptive keys.

---

## 5.7 Preferred implementation shape

Do not expand a giant hand-maintained flat denylist unnecessarily.

A small deterministic predicate is preferred.

Conceptually:

```python
def _is_reserved_authority_key(normalized_key: str) -> bool:
    if normalized_key in _EXPLICIT_RESERVED_KEYS:
        return True

    parts = normalized_key.split("_")

    # narrow deterministic grammar checks
    ...
```

or a compact compiled regex/table if clearer.

The exact private implementation may follow repository style.

The behavior above is authoritative.

# 6. MAJOR-03 — exact, context-independent Decimal canonicalization

## 6.1 Problem

The Remediation V1 helper uses:

```python
value.normalize()
```

before formatting.

`Decimal.normalize()` is context-sensitive.

It can round a valid `Decimal` according to the active Decimal precision.

Independent Re-audit V2 reproduced:

```text
ORIG=123456789012345678901234567890.123456789
SER=123456789012345678901234567900
ROUNDTRIP_EQUAL=False
```

and:

```text
PREC10_SER=123456789000000000000000000000
PREC50_SER=123456789012345678901234567890.123456789

CONTEXT_INDEPENDENT_EXPORT=False
CONTEXT_INDEPENDENT_DIGEST=False
```

This violates:

```text
precision-preserving
deterministic
reproducible
same semantic suite -> same digest
```

---

## 6.2 Canonical Decimal requirements

The canonical representation must be derived without context-sensitive arithmetic.

Required:

```text
no float conversion
no normalize() if it can use context
no quantize() dependent on ambient context
no arithmetic that can round
no precision loss
no process-global Decimal-context dependence
```

Canonicalization must operate directly on the exact stored Decimal representation, preferably through:

```python
Decimal.as_tuple()
```

or an equivalent context-independent method.

---

## 6.3 Required semantic properties

### Numeric equality canonicality

Equivalent values must serialize identically:

```text
0.25
0.250
2.5E-1
→ 0.25

1000
1E+3
1000.000
→ 1000

0
0.0
-0
-0.000
→ 0
```

### Precision preservation

For any valid finite non-negative Decimal `d`:

```python
Decimal(_canonical_decimal_text(d)) == d
```

must hold.

### Context independence

For the same suite and same `Decimal`:

```text
localcontext().prec = 10
localcontext().prec = 28
localcontext().prec = 50
```

must produce identical:

```text
to_dict()
export bytes
content digest
```

### Distinct-value separation

Different numeric costs must continue to produce different canonical values and digests.

---

## 6.4 Canonical fixed-point construction

If the Phase 10.47 contract retains fixed-point decimal strings, construct them exactly from:

```python
sign, digits, exponent = value.as_tuple()
```

without context arithmetic.

Conceptually:

```text
digits = exact coefficient digits
exponent = exact base-10 exponent

strip insignificant trailing coefficient zeros only when this preserves numeric value
place decimal point deterministically from exponent
remove insignificant fractional trailing zeros
canonicalize all numeric zero values to "0"
never emit exponent notation if fixed-point remains the chosen serialization contract
```

The implementation must handle positive exponent values exactly.

Example:

```text
Decimal("1E+30")
```

must serialize to the exact fixed-point integer representation without rounding.

---

## 6.5 Reasonable resource guard

`maximum_cost_eur` is already validated as finite/non-negative.

Do not introduce arbitrary precision truncation.

If extremely large exponents could create unreasonable output strings, do not silently round or switch semantics.

Any resource-bound policy would be a new public contract and is outside this remediation unless the existing Phase 10.47 contract already defines one.

Therefore Remediation V2 should preserve exact semantics.

---
