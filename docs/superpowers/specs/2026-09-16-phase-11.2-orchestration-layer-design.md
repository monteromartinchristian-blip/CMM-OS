## 1. Purpose

Phase 11.2 introduces the first global request-coordination layer of CMM OS.

Its job is to decide:

```text
which canonical components participate
+
in what order
+
under which already-authoritative permissions and policies
```

It is not a new cognitive engine, planner, domain engine, agent runtime, workflow
engine, validation system, memory system, provider router, API backend or event
bus.

The Orchestration Layer is the control plane that coordinates those existing
owners.

The governing principle is:

```text
orchestrate existing authority
≠
rebuild existing authority
```

## 3. Resolution of the roadmap ambiguity

The detailed Phase 11 architecture defines:

```text
11.2 — Orchestration Layer
11.3 — Application Backend
```

The detailed 11.2 section makes orchestration responsible for:

- intent resolution;
- context resolution;
- domain routing;
- execution-path / agent routing;
- orchestration policy;
- decision recording;
- multichannel coordination.

The detailed 11.3 section separately owns:

- API resources;
- endpoints;
- application services;
- command/query application surfaces;
- idempotency;
- streaming;
- pagination;
- concurrency;
- OpenAPI;
- API versioning.

A later condensed Version Plan uses the label `11.2 — Orchestration Backend`
and mentions API/application services. That condensed wording is treated as a
summary drift, not as authority to duplicate the explicit 11.3 boundary.

This spec freezes the repository implementation boundary as:

```text
11.2 = Orchestration Layer
11.3 = Application Backend
```

Therefore Phase 11.2 must not implement HTTP/API/application-backend behavior.

## 7. New public boundary contracts

Phase 11.2 introduces the following new public orchestration values because no
canonical global request-orchestration equivalents exist.

### 7.1 `OrchestrationRequest`

An immutable, serializable request to the global Orchestration Layer.

Conceptual shape:

```python
OrchestrationRequest(
    request_id="request-123",
    user_id="user-123",
    session_id="session-456",
    bot_id=None,
    channel=OrchestrationChannel.CONVERSATION,
    input={...},
    context={...},
    requested_capabilities=("knowledge.read",),
    intent_hint=None,
)
```

Required properties:

- stable non-empty `request_id`;
- stable non-empty `user_id`;
- optional `session_id`;
- optional opaque `bot_id`;
- explicit `channel`;
- JSON-safe immutable `input`;
- JSON-safe immutable caller-provided `context`;
- immutable requested capability IDs;
- optional explicit `intent_hint`.

`bot_id` is an opaque reference only.

Phase 11.2 does not implement Bot identity, Bot repositories or Bot runtime
authority.

### 7.2 `OrchestrationResult`

An immutable, serializable result of request coordination.

It describes the orchestration decision, not hidden model reasoning.

Conceptual shape:

```python
OrchestrationResult(
    request_id="request-123",
    status=OrchestrationStatus.ROUTED,
    intent=IntentKind.QUESTION,
    primary_domain="domain:health",
    supporting_domains=(),
    profile_id="HealthProfile",
    route=ExecutionRoute.DIRECT_RESPONSE,
    agent_id=None,
    workflow_id=None,
    approval_refs=(),
    decision_id="decision-123",
    trace_refs=(...),
    error=None,
)
```

The result may carry identifiers/references produced by canonical owners.

It must not copy arbitrary canonical internal state.

### 7.3 No raw chain-of-thought field

The roadmap's conceptual `reasoning_trace={...}` field must not be implemented
as hidden model reasoning or chain-of-thought.

Phase 11.2 exposes only safe trace references and categorical decision facts:

```text
trace_refs
reason_codes
decision_id
domain selection refs
approval refs
workflow refs
agent refs
```

No hidden reasoning, prompts, credentials, provider payloads or sensitive source
content may be placed in `OrchestrationResult`.

### 7.4 No direct memory mutation field

The roadmap's conceptual `memory_updates=[...]` does not authorize Phase 11.2
to write memory.

The result may reference an already-produced canonical proposal or update record,
but Phase 11.2 never becomes a Memory owner.

## 9. Intent Resolver

### 9.1 Ownership

Phase 11.2 introduces one global request `IntentResolver`.

It does not replace:

- Domain resolution;
- Agent resolution;
- operation parsing;
- provider/model routing;
- specialized domain intent contracts.

### 9.2 Deterministic baseline

The initial resolver must be deterministic and fail closed.

It may use:

- explicit `intent_hint`;
- structured request fields;
- explicit target references;
- explicit command/goal/workflow/update/approval/cancellation shapes;
- safe caller-provided categorical metadata.

It must not silently make an external model call.

It must not depend on Phase 11.35 Model Gateway.

### 9.3 Ambiguity

When request evidence is insufficient to distinguish intent safely:

```text
IntentKind.UNKNOWN
→ OrchestrationStatus.NEEDS_CLARIFICATION
```

The resolver must not guess a side-effecting intent.

### 9.4 Initial classification precedence

The default deterministic resolver should prioritize the most explicit
side-effect/control signals first:

```text
approval response
cancellation
continuation
configuration change
information update
workflow request
goal
command
explicit question/reflection
unknown
```

Exact shape detection will be frozen in the implementation plan after tests
inspect existing request conventions.

### 9.5 `cmm_agent.router.IntentRouter`

The historical `cmm_agent.router.IntentRouter` is not the canonical owner of
Phase 11.2 intent classification.

Its current narrow `route(goal: str) -> str` surface does not express the
required ten-intent contract.

It must not be deleted or silently repurposed.

If compatibility requires it later, it may be wrapped by an adapter.

## 10. Context Resolver

### 10.1 Purpose

`ContextResolver` determines which authorized context references are relevant
to the current request.

It does not own any context source.

### 10.2 Existing owners to reuse

Where available, it must reuse or adapt:

- `cmm.runtime.sessions.SessionStore`;
- shared session state;
- Domain Session resumption infrastructure;
- Goal repositories;
- workflow repositories/registries;
- canonical memory readers;
- canonical knowledge readers;
- canonical event/read surfaces;
- preferences/configuration readers when those later become canonical.

No new Session Store, Goal Store, Workflow Store, Memory Store or Knowledge
Store may be created.

### 10.3 Read-only adapter rule

When an existing repository has no exact orchestration-facing read protocol, a
thin read-only adapter may be introduced.

Such an adapter:

- contains no source-of-truth state;
- does not cache authoritative data;
- performs no ranking beyond its source's documented semantics;
- does not persist;
- does not mutate canonical state.

### 10.4 No context-source registry

Phase 11.2 must not create a generic Context Registry or Loader Registry.

Context collaborators are constructor-injected explicitly.

### 10.5 Two-stage context resolution

Because domain-specific context may only be safe after domain selection, the
resolver supports two conceptual stages:

```text
base context
    ↓
domain selection
    ↓
authorized domain context projection
```

The public implementation may expose this as two methods or one method with an
optional resolved-domain argument, but the safety ordering must remain explicit.

### 10.6 Base context

Base context may include safe references from:

- current shared session;
- caller-provided request context;
- active goals;
- open workflows;
- prior orchestration decisions;
- safe recent event references.

### 10.7 Domain context

Domain context must reuse existing Domain Intelligence permission/projection
semantics.

Supporting domains may only receive the minimum authorized projection.

A supporting domain must never widen permissions.

### 10.8 Missing context

Missing required context is not fabricated.

The resolver reports missing references/gaps so the Orchestrator can choose:

```text
NEEDS_CLARIFICATION
or
HUMAN_ESCALATION
```

## 11. Session semantics

The canonical session authority remains:

```text
cmm.runtime.sessions.SessionStore
```

and existing Domain Session infrastructure.

Phase 11.2 may:

- load a supplied `session_id`;
- recognize missing/unknown sessions;
- use existing session state as context;
- record orchestration references into an authorized existing session seam only
  when that seam already exists and the operation is explicitly injected.

Phase 11.2 does not introduce:

- a new session repository;
- database migrations;
- API session creation;
- a conversation database.

Creation of product-facing sessions is primarily a Phase 11.3 Application
Backend responsibility.

## 12. Domain Router

### 12.1 Purpose

`DomainRouter` is an orchestration facade over canonical Domain Intelligence.

It does not implement domain scoring.

### 12.2 Canonical authority

Primary domain and supporting domain selection remain owned by:

```text
cmm.domains.resolver.DomainResolver
cmm.domains.resolver.DefaultDomainResolver
```

The Orchestration Layer must call that authority.

### 12.3 Additional canonical Domain collaborators

Where needed, the router may coordinate existing:

- `DomainProfileResolver`;
- `DomainProfileRegistry`;
- `DomainPermissionResolver`;
- permission gates;
- `DomainComposer`;
- `DefaultCrossDomainEngine`;
- Domain trace contracts;
- Domain cognitive integration;
- Domain session resumer;
- Domain planner/workflow integration.

It may not duplicate their algorithms.

### 12.4 `DomainRouteDecision`

The orchestration-facing domain result should contain references only:

```text
resolution status
primary domain ID
supporting domain IDs
profile ID/reference
permission decision references
handoff requirements
allowed resource references
domain trace references
reason codes
```

### 12.5 Domain ambiguity

When the canonical resolver returns ambiguity or insufficient evidence, the
Orchestrator must not invent a domain.

The result becomes:

```text
NEEDS_CLARIFICATION
```

unless existing policy requires a stronger denial/escalation.

### 12.6 Cross-domain invariants

The router must preserve all inherited Domain Intelligence invariants:

- one explicit primary domain;
- zero or more explicit supporting domains;
- restrictive permission intersection;
- source-domain authority;
- provenance;
- epistemic kind;
- temporal validity;
- uncertainty;
- sensitivity;
- no supporting-domain permission widening;
- no supporting-domain epistemic promotion.

## 13. Agent Router

### 13.1 Purpose

The roadmap name `AgentRouter` is retained, but its Phase 11.2 responsibility is
broader than choosing an agent ID.

It chooses the execution path:

```text
DIRECT_RESPONSE
OPERATION
WORKFLOW
AUTONOMOUS_AGENT
HUMAN_ESCALATION
```

### 13.2 Agent selection authority

When the route is `AUTONOMOUS_AGENT`, actual agent compatibility/selection
remains owned by:

```text
AgentRegistryService
AgentResolver
```

Phase 11.2 must not create another Agent Registry or agent scoring algorithm.

### 13.3 Initial deterministic route mapping

The baseline route selection must be explicit and testable.

A safe initial matrix is:

```text
QUESTION               → DIRECT_RESPONSE
REFLECTION             → DIRECT_RESPONSE
COMMAND                → OPERATION
WORKFLOW_REQUEST       → WORKFLOW
GOAL                    → AUTONOMOUS_AGENT
INFORMATION_UPDATE     → OPERATION
APPROVAL_RESPONSE      → existing approval/continuation path
CONTINUATION           → existing workflow/runtime continuation path
CANCELLATION           → existing cancellation path
CONFIGURATION_CHANGE   → OPERATION or HUMAN_ESCALATION according to policy
UNKNOWN                → NONE
```

Policy and canonical permission evidence may narrow/escalate the route.

They may not silently upgrade a low-authority route into a more autonomous one.

### 13.4 No direct execution runtime

`AgentRouter` returns a route decision.

It is not:

- a workflow engine;
- operation executor;
- Agent Runtime loop;
- planner;
- model router.

## 14. Orchestration Policy

### 14.1 Purpose

`OrchestrationPolicy` evaluates whether the proposed route may proceed.

It is not a new global authorization system.

### 14.2 Inputs

The policy may consider:

- channel;
- user/reference identity;
- selected domain;
- sensitivity;
- existing canonical permission decisions;
- approval requirements;
- autonomy level;
- cost/budget evidence;
- risk;
- action type;
- session state.

### 14.3 Most-restrictive rule

The Phase 11.2 policy may only preserve or narrow authority.

Invariant:

```text
canonical DENY
cannot become
orchestration ALLOW
```

Likewise:

```text
canonical REQUIRE_APPROVAL
cannot become
silent ALLOW
```

### 14.4 Precedence

Default precedence:

```text
canonical deny / invalid authority
    ↓
DENY

required missing critical information
    ↓
ESCALATE or clarification

approval required
    ↓
REQUIRE_APPROVAL

route exceeds autonomy / channel / risk constraint
    ↓
ESCALATE or DENY

otherwise
    ↓
ALLOW_ROUTE
```

### 14.5 No generic policy engine

Phase 11.2 must not introduce a new broad policy language or policy repository.

The initial implementation is a small deterministic coordinator over existing
canonical evidence plus immutable orchestration configuration.

Persistent user policy management belongs to later platform/configuration work.

### 15.1 Requirement

The roadmap requires every operational orchestration decision to be recordable.

Phase 11.2 therefore introduces:

```text

```

as a narrow repository protocol specifically for orchestration decision records.

### 15.2 Official in-memory implementation

Phase 11.2 may provide:

```text

```

for:

- tests;
- local composition;
- connected acceptance.

### 15.3 Durable database implementation deferred

File/SQLite/relational durability is not part of 11.2.

Phase 11.15 owns broad storage/persistence infrastructure.

### 15.4 `OrchestrationDecisionRecord`

A decision record contains safe structured facts only:

```text
decision_id
request_id
session_id
channel
intent
primary_domain
supporting_domains
execution_route
policy_disposition
selected_agent_id
workflow_id
approval refs
reason codes
trace refs
occurred_at
```

It must not persist:

- raw request text by default;
- secrets;
- credentials;
- prompts;
- chain-of-thought;
- provider payloads;
- copied sensitive domain content.

## 17. Orchestrator

### 17.1 Single global coordinator

Phase 11.2 introduces one global `Orchestrator`.

There must not be multiple competing global request orchestrators.

Specialized existing subsystem orchestrators keep their local authority.

### 17.2 Constructor injection

The Orchestrator receives explicit collaborators.

At minimum:

```text
IntentResolver
ContextResolver
DomainRouter
AgentRouter
OrchestrationPolicy
OrchestrationDecisionRepository
OrchestrationEventSink
```

Optional canonical service collaborators may be injected when a route requires
a safe reference/resolution.

The Orchestrator must not reach into a global service locator during normal
request processing.

### 17.3 Core pipeline

The canonical Phase 11.2 pipeline is:

```text
1. validate OrchestrationRequest
2. emit request-received event
3. resolve intent
4. stop for clarification if intent is unknown
5. resolve base context
6. resolve canonical domain selection
7. stop for clarification if domain resolution is ambiguous
8. resolve authorized domain context/profile references
9. derive proposed execution route
10. evaluate orchestration policy over canonical evidence
11. stop on deny / approval / escalation
12. resolve canonical agent only if autonomous route requires one
13. create safe OrchestrationDecisionRecord
14. persist decision record
15. emit terminal routing event
16. return OrchestrationResult
```

### 17.4 No hidden execution

Phase 11.2 does not silently execute an operation merely because it selected
`ExecutionRoute.OPERATION`.

Likewise it does not silently start a workflow or Agent Runtime run.

The result is a stable handoff decision for canonical downstream execution.

This boundary makes 11.3 and later vertical integration explicit and testable.

### 17.5 Direct-response route

`DIRECT_RESPONSE` means the request does not require operation/workflow/agent
execution.

It does not authorize Phase 11.2 to introduce a new model call.

A later application/cognitive response service may consume the routed result.

## 19. Contract immutability and serialization

All new public Phase 11.2 value objects must be:

- frozen/immutable;
- JSON-serializable through explicit `to_dict()` / `serialize()` surfaces;
- deterministic;
- validated at construction;
- defensive against caller mutation;
- explicit about enum parsing/coercion.

Opaque arbitrary runtime objects must never appear in public orchestration
contracts.

## 20. Input and context safety

### 20.1 JSON-safe values

`OrchestrationRequest.input` and caller context must be structurally JSON-safe.

No live client/service object may be embedded.

### 20.2 Sensitive input

The Orchestration Layer may coordinate sensitive input, but it must not copy it
unnecessarily into:

- decision records;
- events;
- errors;
- traces;
- inspection snapshots.

### 20.3 Minimum projection

Only the minimum context required for the selected route may be forwarded.

This design does not create a new privacy engine; it consumes existing privacy
and permission decisions.

## 24. Existing subsystem ownership map

## 25. Policy invariants inherited from Domain Intelligence

The Orchestrator must preserve:

```text
most restrictive wins
```

for permissions and sensitivity.

A supporting domain may not:

- widen permissions;
- lower sensitivity;
- override a primary domain's authoritative claim;
- convert hypothesis/inference into confirmed fact;
- obtain more context than the active purpose authorizes.

These are not new Phase 11.2 rules.

They are inherited constraints that Phase 11.2 must not bypass.

---

## 26. Approval invariants

Phase 11.2 may detect that approval is required.

It may return:

```text

```

and approval references.

It must not:

- auto-approve;
- invent approval state;
- treat `approval_required` as authorization;
- bypass canonical approval services.

---

## 27. Autonomy invariants

Autonomy is progressive and explicit.

The Orchestration Layer must not convert:

```text
direct response
```

into:

```text
autonomous agent
```

without explicit route rules and policy compatibility.

Canonical Agent Runtime autonomy, budget and permission systems remain
authoritative once an autonomous route is selected.

## 28. Cost and budget evidence

Phase 11.2 may consume existing cost/budget evidence.

It does not own:

- model pricing;
- provider limits;
- token ledgers;
- action budgets;
- routing policy.

If required budget evidence is absent for a route that needs it, the Orchestrator
must fail closed or escalate according to policy.

## 29. Decision ordering and side effects

Phase 11.2 should remain side-effect-light.

Before the final decision:

```text
no operation execution
no workflow execution
no agent run
no memory mutation
no knowledge mutation
no provider call
```

The unavoidable Phase 11.2 side effects are limited to:

```text
decision record persistence
safe event emission
```

and only after the request has been validated sufficiently.

---

## 30. Failure ordering

The Orchestrator must stop at the earliest decisive failure.

Representative order:

```text
malformed request
→ fail

unknown intent
→ clarification

invalid/missing required session reference
→ clarification/fail according to request

domain ambiguity
→ clarification

permission deny
→ blocked

approval required
→ routed-to-approval state

unsupported execution route
→ escalation/fail

autonomous route without compatible agent
→ escalation/fail

decision repository failure
→ fail closed
```

No downstream side effect may occur after a terminal deny/failure.

## 31. Idempotency boundary

Full backend idempotency belongs to 11.3.

Phase 11.2 nevertheless requires stable `request_id` and `decision_id` references
so later idempotency can be implemented without contract migration.

The in-memory decision repository must reject or deterministically return a
previous decision when the same unique decision identity is reused according to
the implementation plan.

It must not silently create contradictory duplicate decisions.

---

## 32. Observability boundary

Phase 11.2 records safe orchestration decisions and emits safe lifecycle events.

Full distributed tracing, metrics infrastructure, dashboards and alerting are
later Phase 11 work.

The Orchestration Layer should propagate existing:

```text

session_id
trace refs
domain refs
agent refs
workflow refs
approval refs
```

rather than inventing a second observability system.

## 46. Design Point `DP-102`

### 46.1 Name


## 79. Final design summary

Phase 11.2 adds one missing architectural capability:

```text
global canonical request coordination
```

It does so through:

```text
OrchestrationRequest
→ deterministic IntentResolver
→ authorized ContextResolver
→ CanonicalDomainRouter
→ CanonicalAgentRouter / execution-route selection
→ restrictive OrchestrationPolicy
→ safe decision record + event
→ OrchestrationResult
```

while every specialized authority remains where it already belongs.

The intended architecture is therefore:

```text
one director
many existing specialists
zero duplicated owners
```
