## 1. Purpose

Phase 10.49 defines how Domain Intelligence specializes the canonical Phase 8
`KnowledgePackage` without creating a second knowledge representation, a second
package builder, or any Domain-owned knowledge runtime.

The phase introduces a declarative, immutable, versioned, serializable
Domain-owned schema/policy that constrains and validates the canonical
`cmm.cognitive.knowledge_packages.KnowledgePackage`.

The central architectural rule is:

```text
Domain Knowledge Package specialization
        ↓
declarative restrictions over
        ↓
canonical Phase 8 KnowledgePackage
```

Not:

```text
Domain-specific KnowledgePackage class
Domain-specific KnowledgePackage builder
Domain-specific KnowledgePackage store
Domain-specific KnowledgePackage runtime
```

The Cognitive Layer remains the sole semantic owner of knowledge representation
and package construction. Domain Intelligence contributes specialization only.

## 3. Design Point

### DP-049 — Declarative Domain Specialization of the Canonical Phase 8 KnowledgePackage

A Domain Pack may declare an immutable, typed, versioned and serializable
`DomainKnowledgePackageSchema` that constrains the canonical Phase 8
`KnowledgePackage`.

The schema:

- belongs to the Domain Pack;
- identifies exactly one Domain;
- targets the canonical Phase 8 `KnowledgePackage`;
- describes structural and policy constraints;
- does not store knowledge;
- does not retrieve knowledge;
- does not construct an alternative package;
- does not execute models, providers, tools or opaque validators;
- does not grant privacy, permission or execution authority;
- may only narrow or validate canonical semantics;
- composes across Domains deterministically and fail-closed.

The package that reaches callers remains:

```python
cmm.cognitive.knowledge_packages.KnowledgePackage
```

No Domain-specific subtype becomes a parallel knowledge truth.

- permissions represented by canonical Cognitive contracts;
- package construction;
- knowledge validation already owned by Phase 8;
- Knowledge Store / Knowledge Graph semantics.

Phase 10.49 must not duplicate these concepts.

### 4.2 Domain Intelligence owns

Phase 10.49 owns only:

- the Domain-level declaration of Knowledge Package specialization;
- structural restrictions applicable to a Domain;
- Domain-specific required/optional/prohibited logical sections;
- Domain-specific field policies expressed against canonical package fields;
- minimum sensitivity constraints;
- opaque validator references;
- deterministic multi-domain schema composition;
- validation that a canonical `KnowledgePackage` conforms to the effective
  Domain schema;
- first-party schema catalogs for currently implemented Domain Packs.

## 5. Canonical contract

Phase 10.49 introduces one primary contract:

```text
DomainKnowledgePackageSchema
```

It must be:

- immutable;
- typed;
- versioned;
- deterministic;
- JSON-safe;
- serializable through canonical `to_dict()` / `from_dict()` semantics;
- fail-closed on malformed serialized input;
- Domain-owned;
- provider-independent;
- runtime-independent.

### 5.1 Required fields

The contract must represent at minimum:

```text
id
domain_id
version
base_schema
required_sections
optional_sections
prohibited_sections
field_policies
minimum_sensitivity
validator_refs
metadata
```

The exact Python types belong to implementation planning, but the semantic
contract is fixed by this specification.

### 5.2 `base_schema`

`base_schema` identifies the canonical package family.

For Phase 10.49 the only valid semantic target is:

```text
KnowledgePackage
```

The implementation must not allow Domain Packs to select or invent an
alternative package model.

A future migration may version this target explicitly, but Phase 10.49 must not
create multiple competing base package types.

### 5.3 Section sets

The schema distinguishes:

- `required_sections`;
- `optional_sections`;
- `prohibited_sections`.

These are logical specialization requirements over the canonical package
content. They are not permission grants and do not create a second presentation
system.

Invariants:

```text
required ∩ prohibited = ∅
optional ∩ prohibited = ∅
required identifiers are unique
optional identifiers are unique
prohibited identifiers are unique
```

Whether `required ∩ optional` is normalized or rejected must be fixed in the
implementation plan and tested deterministically; the preferred behavior is
fail-closed rejection because duplicate classification is ambiguous.

### 5.4 Field policies

`field_policies` define declarative restrictions over canonical
`KnowledgePackage` fields or canonical semantic attributes.

They must not introduce a second value store.

A field policy may constrain such matters as:

- field presence;
- minimum evidence requirements;
- admissible epistemic kinds;
- temporal requirements;
- contradiction visibility;
- uncertainty preservation;
- provenance requirements;
- missing-information requirements;
- resource/reference requirements.

The exact policy vocabulary must remain finite, typed and validated. Arbitrary
executable Python callbacks are prohibited.

### 5.5 Minimum sensitivity

The roadmap's conceptual example uses `privacy_policy="SENSITIVE"`. That
wording must not be implemented as a new Domain privacy-policy enum because the
repository already separates sensitivity, privacy metadata, permissions and
processing policy.

Phase 10.49 therefore uses a semantic sensitivity floor:

```text
minimum_sensitivity
```

or an equivalent canonically named field using the existing Cognitive
sensitivity contract.

The effective result may remain equally or more restrictive, never less
restrictive.

Phase 10.50 owns Domain Privacy Defaults and must remain the phase responsible
for processing-policy defaults and their full composition.

### 5.6 Validator references

`validator_refs` are opaque identifiers only.

They may declare that an authoritative validator is required, but Phase 10.49
does not:

- resolve validator implementations;
- execute validators;
- create a validator registry;
- select providers or models;
- interpret arbitrary code embedded in a Domain Pack.

Unknown or malformed required references fail closed at the appropriate
validation boundary.

### 5.7 Metadata

Metadata is descriptive and auditable only.

Metadata must never:

- grant authority;
- bypass privacy;
- bypass permission checks;
- change package ownership;
- execute code;
- override canonical Cognitive semantics.

## 6. DomainDefinition integration

`DomainDefinition` gains one additive optional field:

```text
knowledge_package_schema
```

with a backward-compatible empty/default state.

The expected semantic shape is:

```text
DomainKnowledgePackageSchema | None
```

Requirements:

1. Existing serialized Domain Packs that omit the field must continue to load.
2. `DomainDefinition.to_dict()` and `from_dict()` must preserve the schema.
3. `ParsedDomainPack` round-trip must preserve the schema.
4. `DomainPack` round-trip must preserve the schema.
5. The declarative loader path must preserve and validate the schema.
6. The schema's `domain_id` must match the owning `DomainDefinition.id`.
7. Duplicate or malformed declarations fail closed.
8. The field must coexist with:
   - `model_policy`;
   - `benchmark_suites`;
   - `quality_metrics`;
   - all earlier DomainDefinition fields.

No second Domain Pack parser is allowed.

## 7. Canonical KnowledgePackage semantics

The schema must reuse canonical Phase 8 representations rather than copying
their data into Domain-owned parallel fields.

### 7.1 Objective

Package objective remains represented by the canonical Phase 8 request/package
semantics.

Phase 10.49 may require or constrain objective information but must not create
a Domain-owned objective truth.

### 7.2 Provenance

Use canonical:

- `Evidence`;
- `ResourceProvenance`;
- `KnowledgePackage.provenance`;
- existing trace/reference semantics where applicable.

No Domain provenance store or provenance graph may be introduced.

### 7.3 Epistemic type

Use canonical Cognitive epistemic representation, including the existing
knowledge-item kind/classification.

A Domain schema may restrict admissible kinds but may not redefine their
meaning.

### 7.4 Temporal validity

Use canonical temporal contracts such as `TemporalScope` and existing resource
temporal semantics.

A Domain schema may require freshness or temporal evidence but may not create a
parallel temporal engine.

### 7.5 Contradictions

Use canonical Phase 8 contradiction representation.

Phase 10.49 validates preservation/visibility requirements only. It must not
resolve truth independently from Phase 8 or Phase 10.32.

### 7.6 Uncertainty

Use canonical confidence, unknowns, remaining uncertainty and related Cognitive
semantics.

A Domain schema may require uncertainty to remain explicit. It must never turn
uncertainty into certainty.

### 7.7 Missing information

Use the canonical package/request representation for unresolved or missing
information.

A Domain schema may require certain gaps to remain represented or may require
question escalation through already-existing systems. It must not add a
parallel question engine.

### 7.8 Privacy

Use existing `PrivacyMetadata`, sensitivity and privacy integration.

Phase 10.49 may define a minimum sensitivity constraint only.

It must not implement Phase 10.50 Domain Privacy Defaults.

### 7.9 Permissions

Use canonical resource/package permission semantics and already-existing Domain
permission infrastructure.

A schema must never grant authority. If permission information conflicts, the
effective result is most restrictive or fails closed according to the canonical
owner.

### 7.10 Profile

Domain profile identity/configuration remains owned by existing Domain Profile
contracts.

A Knowledge Package schema may reference relevant profile requirements but
must not embed a second profile model.

### 7.11 Resources

Use canonical Cognitive `Resource` and existing Domain resource authority.

No resource registry or resource store is introduced by this phase.

### 7.12 Version

Versioning must preserve:

- Domain Knowledge Package schema version;
- canonical package schema version;
- canonical resource/knowledge versions where present.

Phase 10.49 must not collapse these distinct version authorities.

## 8. Schema validation

Phase 10.49 introduces pure validation of an already-produced canonical
`KnowledgePackage` against a `DomainKnowledgePackageSchema`.

The validator must be:

- deterministic;
- side-effect free;
- fail-closed;
- independent of model/provider;
- independent of runtime execution;
- independent of persistence.

Validation may check:

- exact base schema compatibility;
- required logical sections;
- prohibited logical sections;
- field policy satisfaction;
- minimum sensitivity;
- provenance requirements;
- temporal requirements;
- uncertainty preservation;
- contradiction preservation;
- required validator references being structurally present when applicable.

Validation must not mutate the package.

Validation output should be immutable and auditable if a structured result is
needed. The implementation plan must prefer reuse of an existing validation
result contract where semantically adequate rather than creating a redundant
result hierarchy.

## 9. Multi-domain composition

When several Domains participate, their Knowledge Package schemas combine
monotonically.

The effective schema must never be broader or less restrictive than any
participating schema.

### 9.1 Set composition

Default composition semantics:

```text
required_sections   = union(all required)
prohibited_sections = union(all prohibited)
optional_sections   = deterministic union(all optional)
```

After composition:

```text
required ∩ prohibited != ∅
    => fail closed
```

Likewise, an optional section prohibited by another participating Domain cannot
remain effectively optional.

### 9.2 Field-policy composition

Compatible restrictions compose most-restrictively.

Incompatible restrictions fail closed.

The implementation must not select a winner based on:

- ordering;
- primary-domain status;
- confidence score;
- arbitrary lexical priority;
- provider/model behavior.

If a canonical owner already defines a stricter composition rule for a
particular semantic field, that canonical rule wins.

### 9.3 Sensitivity composition

The effective minimum sensitivity is the most restrictive floor required by
participating schemas, interpreted through the canonical sensitivity ordering.

A Domain schema cannot lower sensitivity required by another Domain, a
resource, the user, the session or any higher authority.

### 9.4 Validator references

Required opaque validator references compose additively and deterministically.

No execution occurs in this phase.

## 12. Backward compatibility

The Phase 10.49 extension must preserve existing Domain Pack compatibility.

Required behavior:

```text
old DomainDefinition payload without knowledge_package_schema
    => valid
    => knowledge_package_schema is absent/None/default
```

Existing first-party and external packs must not be forced to declare a schema
unless the design explicitly marks one mandatory for a specific built-in pack.

No schema migration may alter historical Phase 10.46, 10.47 or 10.48 payload
semantics.

## 13. External Domain Packs

External Domain Packs may declare a `DomainKnowledgePackageSchema` through the
same public declarative contract.

They do not receive new authority by doing so.

External schemas remain subject to:

- Domain Pack trust policy;
- canonical permissions;
- privacy restrictions;
- validation;
- Domain SDK validation;
- existing installation/activation boundaries.

A malicious or malformed schema cannot:

- redefine `KnowledgePackage`;
- embed executable code;
- grant remote processing;
- grant cross-domain access;
- relax a canonical permission;
- relax canonical privacy;
- install validators;
- mutate Cognitive stores.

## 14. Error handling

Malformed or incoherent declarations fail closed.

At minimum, the implementation must reject:

- unknown serialized fields where strict contracts require rejection;
- missing required contract fields;
- invalid IDs;
- invalid versions;
- invalid `base_schema`;
- `domain_id` mismatch;
- duplicate section identifiers;
- required/prohibited conflicts;
- optional/prohibited conflicts;
- malformed field policies;
- unknown policy kinds;
- invalid sensitivity values;
- malformed validator references;
- invalid metadata shape;
- incompatible multi-domain policies.

Errors must integrate with the existing Domain error hierarchy where adequate.

No broad `Exception` swallowing is permitted.

## 15. Security and authority invariants

Phase 10.49 preserves all previously closed security boundaries.

A schema is configuration, not authority.

It cannot:

- grant execution;
- grant tool access;
- grant provider access;
- grant network access;
- grant file access;
- grant Domain activation;
- grant resource access;
- grant cross-domain transfer;
- grant approval;
- lower privacy;
- lower sensitivity;
- bypass validation;
- bypass trust;
- mutate stores.

The strongest applicable canonical restriction remains authoritative.

## 19. Public API expectations

The canonical Domain public API may expose the new immutable schema contract if
that matches existing public-export conventions.

The phase must not add a public API that constructs an alternative package.

A consumer should conceptually be able to:

1. inspect a Domain's declared Knowledge Package schema;
2. round-trip it through canonical Domain Pack serialization;
3. compose several schemas through a pure deterministic helper;
4. validate an already-produced canonical `KnowledgePackage`.

Any public helper must remain side-effect free.

### E — Domain validation

Validate the produced package through the Phase 10.49 schema and prove a valid
package passes.

### F — Fail-closed structural violation

Remove or violate a required Domain constraint and prove validation rejects the
same canonical package shape without mutation or fallback broadening.

### G — Multi-domain composition

Compose at least two real implemented first-party Domain schemas and prove
deterministic most-restrictive effective policy.

### H — Conflict rejection

Create an irreconcilable required/prohibited or field-policy conflict and prove
fail-closed behavior independent of Domain ordering.

### I — Authority boundary

Prove a schema cannot grant permissions, lower privacy/sensitivity, execute a
validator, select a provider/model, or mutate Cognitive storage.

Prove the path uses the existing Phase 8 `KnowledgePackageBuilder` and
`KnowledgePackage`, with zero production Domain package builder/registry/store/
runtime/engine.

implementations where persistence seams are needed.

## 26. Commit and audit discipline

The implementation process must preserve the project workflow:

```text
SPEC COMMIT
→ PLAN COMMIT
→ IMPLEMENTATION PROMPT
→ TDD IMPLEMENTATION
→ TESTS/GATES
→ DOCUMENTATION
→ IMPLEMENTATION COMMIT(S)
→ CLEAN WORKTREE
→ EXACT-HEAD git archive TAR.GZ
→ INDEPENDENT CHATGPT AUDIT
→ REMEDIATION IF REQUIRED
→ FINAL PASS
→ SEPARATE DOCS-ONLY CLOSURE COMMIT
```

No `push` or `merge` is authorized by this specification.

No `git stash`, `stash pop/apply/drop`, `git reset`, `git clean`, or
`git worktree` operation is authorized.

The quarantine stash must remain preserved.

Audit bundles must be produced from the exact committed HEAD, preferably with
`git archive`, and accompanied by SHA-256 and audited HEAD.

## 28. Final design decision

Phase 10.49 is not a new knowledge subsystem.

canonical Phase 8 `KnowledgePackage`.

```text
Domain Pack
  └── DomainDefinition
        └── DomainKnowledgePackageSchema

        canonical KnowledgePackageBuilder
```

with:
