## 1. Purpose

Phase 10.38 establishes one narrow security boundary for Domain Intelligence:

> A Domain Pack must never obtain authority, permissions, activation rights, sensitive access, memory-write capability, external-operation capability, or cross-domain capability merely because it was discovered, loaded, marked trusted, or contains instructions requesting those powers.

The phase is intentionally small.

It does **not** attempt to harden all of CMM OS, redesign the global security architecture, or pre-implement the broader platform-security work scheduled for Phase 11.

The repository inspection showed that the major security primitives already exist:

- canonical Domain manifest validation;
- immutable/read-once manifest handling;
- checksum validation;
- canonical Domain validation pipeline;
- `domain.security`;
- secret scanning;
- forbidden-command scanning;
- unauthorized-import scanning;
- prompt-injection heuristics;
- file/resource scan limits;
- dependency validation;
- atomic Domain loading;
- loader rollback;
- canonical Domain permission resolution;
- restrictive permission composition;
- canonical approval requirements;
- mandatory permission gate;
- cross-domain permission controls;
- Agent Runtime security contracts and services;
- existing trace/reference security boundaries.

Phase 10.38 therefore closes the missing **Domain Pack trust/authority boundary** by composing this infrastructure rather than duplicating it.

## 2. Architectural principle

The defining invariant is:

```text
DISCOVERY != TRUST
TRUST != AUTHORITY
LOAD != ENABLE
INSTALL != AUTHORIZATION
PROMPT != POLICY
CONTENT != AUTHORITY
PERSISTED STATE != CURRENT AUTHORIZATION
```

A Domain Pack may contribute declarative specialization.

It may not become a new security principal capable of expanding CMM OS authority.

Trust may only **restrict** or **require additional review**.

Trust must never grant permissions that are absent from the canonical permission system.

The phase therefore uses this model:

```text
Domain Source / Candidate
        ↓
Canonical Discovery
        ↓
Canonical Validation
        ↓
Domain Trust Policy
        ↓
Canonical Loader / Registry
        ↓
Explicit Enablement
        ↓
Canonical Permission / Approval Gate
        ↓
Canonical Operation / Workflow execution
```

No new runtime, engine, registry, loader, store, event bus, authorization system, or security subsystem is introduced.

## 3. Repository inspection findings that constrain the design

The implementation must preserve the following inspected repository facts.

### 3.1 Manifest and integrity

`DomainManifestReader` already reads the manifest once and ensures the same bytes are used for checksum and parsing.

The loader recomputes SHA-256 from those bytes and rejects checksum mismatch.

Therefore Phase 10.38 MUST NOT create another integrity reader or checksum pipeline.

### 3.2 Loader

`DeclarativeDomainLoader` is the canonical loader.

It already provides:

- fail-closed handling for untrusted candidates by default;
- explicit `allow_untrusted=True` override;
- atomic load/unload/reload behavior;
- registry snapshot/restore rollback;
- explicit rollback-failure errors;
- loaded-state tracking without automatic enablement.

`allow_untrusted=True` means only:

```text
explicit permission to load/register an untrusted candidate
```

It MUST continue to mean **neither activation nor execution authority**.

Phase 10.38 MUST NOT create another loader.

### 3.3 Domain validation

`PipelineDomainValidator` already includes the canonical `domain.security` step and a shared bounded scan session.

Existing security validation already covers:

- secrets;
- forbidden commands;
- unauthorized imports;
- selected prompt-injection patterns;
- binary/encoding/file-size safety;
- file-count limits;
- total-size limits;
- depth limits.

Phase 10.38 MUST extend or reuse these checks only where a specific trust-boundary gap is proven.

It MUST NOT create a parallel Domain security scanner.

### 3.4 Permissions and approvals

The repository already owns:

- `DomainPermissionResolver`;
- restrictive permission intersection;
- `DomainPermissionGate`;
- operation/workflow permission adapters;
- canonical approval requirements;
- cross-domain controls;
- operation allow/deny constraints.

Phase 10.38 MUST NOT invent a Domain-specific permission engine.

Trust policy is an **additional ceiling**, never an alternative permission source.

### 3.5 Domain API

Phase 10.36 established:

```text
install_domain(candidate) -> canonical loader
enable_domain(...) -> canonical registry enable
execute_operation(...) -> canonical operation orchestrator
start_workflow(...) -> canonical workflow infrastructure
```

and the permanent invariants:

```text
INSTALL != ENABLE
INSTALL != AUTHORIZATION
```

Phase 10.38 must preserve the existing API model.

No second API or lifecycle facade is required.

## 4. Approved scope

Phase 10.38 implements only the following missing capability.

### 4.1 Explicit Domain trust levels

Introduce the canonical enum:

```text
DomainTrustLevel
```

with exactly:

```text
trusted
verified
internal
community
untrusted
blocked
```

These values describe **trust posture**, not permission grants.

They do not imply an ordering that grants progressively broader authority unless an explicit policy rule says so.

### 4.2 Domain trust policy

Introduce one immutable typed contract:

```text
DomainTrustPolicy
```

The minimum required semantic surface is:

```text
domain_id
trust_level
authorized_source_ids
allow_code_execution
allow_external_access
allow_memory_write
allow_sensitive_resources
allow_destructive_operations
require_manual_enable
require_signature
metadata
```

The implementation may use the repository's normal immutable/JSON-safe contract conventions.

No mutable trust store is required.

No trust registry is required.

No persistence layer is required.

The policy is supplied by the caller/configuration boundary that already owns runtime wiring.

### 4.3 Trust decision

A pure deterministic evaluation must answer whether the current candidate/domain satisfies its trust policy.

The implementation may introduce a small immutable decision/result contract if this is required to preserve structured evidence and testing.

The decision must be derived from canonical inputs such as:

- `DomainCandidate`;
- candidate source identity;
- candidate/source trust declaration;
- manifest signature presence;
- validation result;
- explicit manual-enable evidence where applicable;
- `DomainTrustPolicy`.

The evaluator:

- MUST NOT execute code;
- MUST NOT access the network;
- MUST NOT persist state;
- MUST NOT mutate the registry;
- MUST NOT issue permissions;
- MUST NOT issue approvals.

### 4.4 Authorized sources

The trust policy must support explicit authorized source IDs.

For a policy that declares an authorized-source list:

```text
candidate.source_id ∉ authorized_source_ids
    → fail closed
```

A source being marked `trusted=True` during discovery is evidence only.

It is not sufficient to bypass an explicit policy source restriction.

### 4.5 External and low-trust default ceiling

For:

```text
community
untrusted
blocked
```

the safe default posture must not silently allow:

```text
code execution
external access
memory writes
sensitive resources
destructive operations
automatic enablement
```

`blocked` is always rejected for activation/use.

`untrusted` is fail-closed for activation unless an explicit policy allows the specific boundary and all canonical permission/approval requirements still pass.

`community` requires explicit review/manual enablement by default.

The exact trust level does not grant an operation.

The canonical permission gate remains authoritative after the trust boundary is satisfied.

### 4.6 Manual enablement

Where:

```text
require_manual_enable=True
```

a Domain must not become enabled solely because it was discovered, validated, loaded or registered.

The repository already separates load from enable.

Phase 10.38 must preserve that separation and add only the minimum trust-policy enforcement required before activation.

No new approval service is created.

If existing canonical approval infrastructure can represent the required high-risk review without architectural distortion, it may be reused.

Otherwise the trust decision may require an explicit caller-supplied manual-enable fact for Phase 10.38.

### 4.7 Optional signatures

The manifest already contains an optional `signature` field.

Phase 10.38 defines only this semantic rule:

```text
require_signature=True AND manifest.signature absent
    → fail closed
```

A present signature is **not** treated as cryptographically verified unless an existing canonical verifier proves it.

Phase 10.38 does not introduce:

- PKI;
- certificate authorities;
- key management;
- signing key rotation;
- package-signature infrastructure;
- remote trust authorities.

Cryptographic verification belongs to a future security/supply-chain phase unless a canonical verifier already exists.

### 4.8 Prompt/content authority boundary

Existing prompt-injection scanning remains the canonical static Domain Pack scanner.

Phase 10.38 additionally establishes the normative invariant:

```text
Domain Pack prompts/resources/configuration = DATA / CONFIGURATION
Domain Pack prompts/resources/configuration != SECURITY POLICY
```

Pack content must not be interpreted as authority to:

- disable global rules;
- change permissions;
- request or expose secrets;
- redefine contracts;
- bypass canonical validators;
- bypass permission/approval gates;
- write memory directly;
- authorize cross-domain transfers;
- grant external access.

The implementation should enforce this through existing validation and execution boundaries.

It must not build an LLM-based prompt-injection detector or a second prompt firewall.

### 4.9 Permission ceiling

Trust evaluation is a ceiling.

Conceptually:

```text
effective_authority
=
canonical_permission_authority
∩ trust_policy_ceiling
∩ current approval evidence
```

A trust policy can remove authority.

It cannot add authority.

Examples:

```text
policy.allow_external_access=False
    → external capability remains denied

policy.allow_memory_write=False
    → memory-write capability remains denied

policy.allow_sensitive_resources=False
    → sensitive-resource access remains denied

policy.allow_destructive_operations=False
    → destructive operations remain denied
```

Any implementation must reuse the canonical permission vocabulary/contracts where possible rather than create duplicate capability names.

### 4.10 Existing limits remain authoritative

Phase 10.38 reuses existing limits for Domain Pack validation and runtime execution.

The phase does not create a resource scheduler.

Existing canonical controls remain responsible for:

- file count;
- file size;
- total scan bytes;
- scan depth;
- operation/workflow constraints;
- cross-domain limits;
- runtime budgets/timeouts where already owned by Agent Runtime or workflow/operation infrastructure.

A missing limit may be added only when a RED test proves a concrete gap inside the DP-038 boundary.

## 7. Data flow

### 7.1 Discovery

```text
DomainSource
    ↓
FileSystemDomainDiscovery
    ↓
DomainCandidate
```

Discovery provides provenance and a `trusted` source signal.

It does not grant runtime authority.

### 7.2 Validation

```text
DomainCandidate / pack path
    ↓
PipelineDomainValidator
    ↓
manifest/contracts/permissions/dependencies/compatibility/security/fragmentation/tests
    ↓
DomainValidationResult
```

A blocking validation result prevents progression.

Trust evaluation cannot override validation failure.

### 7.3 Trust evaluation

```text
candidate
+ manifest facts
+ validation result
+ DomainTrustPolicy
+ explicit manual-enable fact where required
    ↓
pure trust evaluation
    ↓
structured allow / deny / review-required evidence
```

The decision must be fail-closed on missing required evidence.

### 7.4 Load

Canonical load remains:

```text
DeclarativeDomainLoader.load(...)
```

It remains transactional and does not enable.

`allow_untrusted=True` may still permit an explicitly requested load for inspection/registration.

It must not imply activation or operation authority.

### 7.5 Enable

Before a low-trust/external Domain is enabled, the trust boundary must be satisfied.

No automatic enablement is introduced.

### 7.6 Runtime execution

After enablement:

```text
request
    ↓
canonical Domain permission resolution
    ↓
trust-policy ceiling / existing security binding
    ↓
canonical approval handling
    ↓
canonical permission gate
    ↓
operation/workflow execution
```

No operation or workflow is dispatched directly from the trust evaluator.

## 8. Error and fail-closed semantics

Phase 10.38 must use structured, deterministic failure.

At minimum the design must distinguish reasons equivalent to:

```text
trust.blocked
trust.source_not_authorized
trust.validation_failed
trust.signature_required
trust.manual_enable_required
trust.code_execution_denied
trust.external_access_denied
trust.memory_write_denied
trust.sensitive_resource_denied
trust.destructive_operation_denied
```

Exact error/result class names are implementation details for the plan.

Requirements:

- no secret material in exceptions;
- no raw prompt/user content in authority evidence;
- no traceback-derived sensitive payloads;
- deterministic reason codes;
- no implicit fallback from deny to allow;
- no trust escalation from missing metadata;
- no treating unknown trust levels as trusted.

Unknown/missing required trust evidence fails closed.

## 9. Public API and compatibility

Phase 10.38 should avoid expanding the public Domain API unless a RED integration test proves that the trust boundary cannot be enforced through canonical collaborators.

The preferred implementation is to enforce policy in canonical lifecycle/security collaborators injected into the API rather than add convenience methods.

Existing behavior must remain compatible where it is not an authority violation.

In particular:

```text
loader.load(untrusted_candidate)
    → rejected by default

loader.load(untrusted_candidate, allow_untrusted=True)
    → may load/register
    → MUST NOT imply enablement
    → MUST NOT imply authorization
```

The current Domain Event catalog must not be expanded merely for Phase 10.38.

Phase 10.37 observability remains read-only.

No new security event type is required for acceptance unless repository reality proves an existing canonical event contract must be reused.

## 10. DP-038 — Domain Pack Authority Boundary

### Design Point

**DP-038 — Domain Pack Authority Boundary**

> Domain Pack provenance, trust labels, installation state, manifest content and prompt content never grant implicit runtime authority. A Domain may act only within the intersection of its explicit trust ceiling and the existing canonical permission/approval boundaries.

DP-038 is satisfied only if the implementation proves:

1. discovery does not authorize;
2. source `trusted=True` does not create permission grants;
3. load does not authorize;
4. `allow_untrusted=True` does not authorize;
5. blocked/unauthorized-source policies fail closed;
6. manual enablement requirements cannot be bypassed by load/registration;
7. optional signature policy fails closed only when signature is required and absent;
8. trust restrictions cannot be widened by Domain Pack content;
9. prompt/configuration content cannot replace system security policy;
10. canonical permission/approval gates remain authoritative;
11. denied memory/external/sensitive/destructive capabilities remain denied;
12. failure does not leave partial activation or mutated authorization state.

## 11. AT-DP-038 — connected acceptance

The acceptance test must use real canonical components or official in-memory implementations.

Mocks alone are insufficient.

### Required acceptance scenario

Build a temporary declarative external Domain Pack using the existing Domain test fixtures/SDK-compatible pack structure.

Use real canonical components for:

```text
discovery
manifest reading
validation
loader
registry
permission registry/resolver
permission gate
operation registry/orchestrator where needed
approval service official in-memory implementation where needed
```

The acceptance must prove both a safe path and rejected paths.

### 11.1 Safe path

A policy-compliant pack:

1. is discovered;
2. passes canonical validation;
3. satisfies the configured source/trust policy;
4. is loaded through `DeclarativeDomainLoader`;
5. remains disabled until explicitly enabled;
6. after enablement, can execute only an operation already allowed by canonical permission policy.

### 11.2 Rejected source

A candidate from a source outside `authorized_source_ids`:

```text
→ trust decision DENY
→ not enabled
→ no execution
→ no authorization mutation
```

### 11.3 Blocked Domain

A `blocked` policy:

```text
→ cannot be enabled/used
```

even if:

```text
candidate.trusted=True
validation passes
checksum passes
```

### 11.4 Untrusted load is not authority

Load an untrusted candidate using the canonical explicit:

```text
allow_untrusted=True
```

Then prove:

```text
loaded/registered == true
enabled == false until explicit boundary passes
operation authority == absent
```

### 11.5 Prompt/configuration cannot escalate

Include pack content that attempts to instruct CMM OS to:

```text
ignore policy
grant a permission
reveal a secret
write memory directly
```

Prove either:

- canonical validation blocks it when the current scanner classifies it as blocking; or
- where content is only warning/non-blocking, the runtime trust/permission boundary still refuses to treat the text as authority.

The acceptance must not depend on a model interpreting natural language.

### 11.6 Permission ceiling

Configure the pack with a trust policy denying at least one privileged capability.

Prove the Domain cannot obtain that capability even when the Domain's own declarative content requests it.

Use the canonical permission vocabulary and gate.

### 11.7 Atomicity

For each rejected activation/use path, assert relevant canonical state before and after.

At minimum verify that no rejected trust decision creates partial enabled/authorized state.

Loader rollback behavior itself should be regression-tested rather than reimplemented.

## 17. Alternatives considered and rejected

### Alternative A — Full Domain Security subsystem

Create a new `DomainSecurityEngine`, trust registry, security store, scanner, runtime and audit pipeline.

**Rejected.**

It duplicates Phase 7, Phase 9, Phase 10.15 and the existing Domain validation/permission infrastructure, increases attack surface, and pre-implements Phase 11 work.

### Alternative B — Harden every security item listed in the roadmap now

Implement cryptographic signing, secrets management, OS isolation, network restrictions, SBOM, vulnerability scanning, broad runtime quotas and platform authentication.

**Rejected.**

This is materially larger than the actual missing Domain Intelligence boundary and belongs to later platform-security phases.

### Alternative C — Minimal trust/authority boundary over canonical infrastructure

Introduce only the missing trust contract/evaluation and connect it to the existing validation, loader, activation and permission boundaries.

**Selected.**

This closes the architectural gap with the smallest new surface and keeps existing owners authoritative.

## 19. Success criterion

Phase 10.38 succeeds when CMM OS can truthfully state:

> An external or unreliable Domain Pack may be discovered, inspected, validated and — when explicitly requested — loaded without that act granting it authority. Activation and runtime capabilities remain constrained by an explicit Domain trust policy and the existing canonical permission/approval system, and Domain Pack content cannot redefine those controls.

That is the complete Phase 10.38 boundary.

Broader system hardening remains outside this phase.
