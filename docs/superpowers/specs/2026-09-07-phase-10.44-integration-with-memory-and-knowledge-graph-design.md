## 1. Purpose

Phase 10.44 integrates Domain Intelligence with the canonical shared memory and knowledge infrastructure so specialization can operate across domains without creating knowledge silos.

The phase must allow one canonical piece of knowledge to participate in multiple domains, preserve provenance and temporality, expose only authorized cross-domain projections, relate knowledge to goals/events/decisions/constraints/resources/workflows/results/contradictions/dependencies, and support cross-cutting timelines and impact analysis without duplicating knowledge or inventing causal truth.

This is an **integration phase**, not a new memory subsystem and not a new Knowledge Graph implementation.

The architectural rule is:

> Domain Intelligence may select, specialize, project, qualify, relate, and propose against canonical knowledge. It must not become the owner of a second knowledge truth.

## 3. Canonical roadmap requirement

The detailed Domain Intelligence roadmap assigns Phase 10.44 the objective:

> Allow specialization without creating knowledge silos.

The shared Knowledge Graph should be able to relate:

- entities applicable to several domains;
- goals;
- events;
- decisions;
- constraints;
- resources;
- workflows;
- results;
- contradictions;

The system should:

- reuse entities;
- retain applicable domains;
- control access;
- avoid sensitive inferences;
- build cross-cutting timelines;

The system should not:

- automatically expose all information to all domains;
- transfer sensitive resources without permission;
- duplicate entities;
- convert correlation into causality;

## 5. Architectural decision

### 5.1 Selected approach

Phase 10.44 SHALL implement a **thin Domain-owned Memory/Knowledge integration layer** over existing canonical Cognitive Layer and Agent Runtime contracts.

The integration layer may:

- compose authorized reference-only knowledge projections for a resolved Domain composition;
- preserve and expose canonical identity references across applicable domains;
- traverse canonical relations that are visible under current authority;
- project timeline entries from canonical temporally-scoped knowledge;
- surface canonical contradictions and dependency/impact paths by reference;
- produce reference-only relation/update proposal bindings to existing proposal contracts;
- fail closed when authorization, evidence, temporal ordering, identity coherence, or relation semantics are insufficient.

It may not own the underlying truth or persistence.

### 5.2 Rejected approaches

The following approaches are explicitly rejected:

1. **Extending Phase 10.18 into a second cognitive subsystem.**
   `memory_view.py`, `memory_contracts.py`, and `memory_validation.py` remain the Phase 10.18 reference-only memory-view boundary. They may receive only narrowly justified compatible extensions.

2. **Creating a Domain Knowledge Graph.**
   No `DomainKnowledgeGraph`, `DomainGraphStore`, `DomainGraphRepository`, `DomainGraphRegistry`, `DomainGraphResolver`, or equivalent may be introduced.

3. **Using `cmm.memory.KnowledgeGraph` as the personal Domain Intelligence graph.**
   The repository inspection shows `cmm.memory.KnowledgeGraph` and `TechnicalMemory` are technical/project memory infrastructure. Phase 10.44 must not silently reinterpret that subsystem as the Phase 8 Cognitive Layer's canonical personal/general knowledge model.

4. **Creating per-domain persistent memory.**
   No domain-owned persistent copies, caches acting as truth, or domain-specific entity tables are permitted.

## 7. Phase 10.18 contracts are mandatory inputs

Phase 10.44 SHALL build on Phase 10.18 rather than bypass it.

The following Phase 10.18 invariants remain mandatory:

1. **One shared memory.**
   Domain memory is a view over canonical knowledge, not an independent store.

2. **Reference-only Domain views.**
   `DomainMemoryView` and `DomainMemoryReference` contain references and policy metadata, not copied knowledge payloads.

3. **Reference-only proposal bindings.**
   Domain execution binds to canonical Phase 8/9 proposals by ID.

4. **Capability separation.**
   `READ != PROPOSE != APPROVE != APPLY != INVALIDATE != DELETE`.

5. **Canonical identity uniqueness.**
   One `canonical_id` maps to one canonical reference identity. One canonical object may be applicable to several domains through `applicable_domains`.

6. **Temporal reference-only semantics.**
   Domain code mirrors/uses canonical temporal truth; it does not own a temporal engine.

7. **History preservation.**
   Supersession, invalidation, unresolved conflict, and unknown ordering remain explicit.

8. **Strict privacy boundary.**
   Forbidden sensitive content must not leak into Domain metadata or diagnostics.

9. **Pure deterministic resolution/validation.**
   Domain memory selection and validation do not perform hidden store queries or mutations.

Phase 10.44 MAY consume additional canonical context beyond a `DomainMemoryView` only when that context is supplied through explicit read-only ports/contracts and remains governed by the same authority snapshot.

## 9. Phase 9 proposal flow is the write boundary

Phase 10.44 does not directly mutate canonical knowledge.

Any proposed change arising from Domain specialization — including a newly suggested relation — MUST flow through existing canonical proposal mechanisms such as:

- `MemoryUpdateProposal`;
- `AgentKnowledgeUpdateProposal`;
- existing knowledge update candidates/relations;
- canonical approval/decision/repository/execution mechanisms.

The integration layer may return proposal IDs and proposal-binding references. It must never treat proposal creation as proposal approval or persistence.

A proposed relation is not established knowledge.

## 10. Proposed public integration surface

Exact naming may be refined during implementation only if existing repository conventions prove a better name, but the semantic boundary is fixed.

The preferred new modules are:

```text
cmm/domains/memory_knowledge_integration_contracts.py
cmm/domains/memory_knowledge_integration.py
```

The preferred service identity is:

```text
DefaultDomainMemoryKnowledgeIntegrator
```

No separate package is required unless implementation inspection proves the module would become materially incoherent.

### 10.1 Protocol

A small `@runtime_checkable` protocol MAY be introduced, for example:

```text
DomainMemoryKnowledgeIntegrator
```

It should define read-only projection and proposal-preparation behavior, not persistence or autonomous execution.

### 10.2 Request contract

A request SHOULD bind the projection to an already-resolved authoritative context and should include only identifiers/snapshots required to prove authority and integrity, such as:

- request ID;
- primary domain;
- supporting domains;
- Phase 10.18 memory view ID + full digest;
- current Domain composition/resolution reference;
- permission decision references / immutable permission snapshots;
- optional trace/session/run references;
- temporal reference;
- requested projection capabilities;
- candidate canonical relation/entity/reference inventory supplied by the canonical host/adapter.

It MUST NOT carry raw sensitive resource payloads merely for convenience.

### 10.3 Result contract

The result SHOULD be immutable, deterministic, JSON-safe, and content-bound.

It may expose reference-only structures such as:

- selected canonical knowledge references;
- shared canonical entity/reference identities;
- applicable domain IDs;
- canonical relation references;
- contradiction references;
- dependency/impact paths;
- timeline entries as canonical-reference + temporal metadata;
- relation/update proposal IDs;
- permission/approval/validation/trace references;
- explicit exclusions and fail-closed diagnostics.

It MUST NOT embed a copied knowledge graph.

## 11. Canonical identity reuse

### 11.1 One identity, several domains

If two or more domains refer to the same underlying canonical object, Phase 10.44 MUST expose the same canonical identity with multiple applicability labels rather than create separate Domain copies.

Example:

```text
canonical_id = knowledge:study-capacity:current
applicable_domains = {health, university, oppositions, life_plan}
```

This does not mean every domain can see the object. Applicability and access are separate concepts.

### 11.2 Applicability is not authority

`applicable_domains` is descriptive routing metadata. It does not authorize:

- reading the item;
- transferring it to another domain;
- persisting it;
- proposing changes;
- exposing sensitive provenance;
- executing an operation.

All positive authority remains with canonical permission/approval owners.

### 11.3 Duplicate rejection

If candidate inventories present multiple reference identities for the same canonical identity in a way that violates Phase 10.18 uniqueness, the integration MUST fail closed or exclude the incoherent candidates according to the canonical 10.18 validator semantics.

It MUST NOT silently pick one duplicate.

---

## 12. Cross-domain visibility and sensitive information

### 12.1 Default rule

Cross-domain relevance does not imply cross-domain disclosure.

A Health item may be relevant to University, Oppositions, Sport, or Life Plan while its sensitive source details remain inaccessible.

### 12.2 Purpose-minimized projection

Where canonical policy allows a downstream domain to know only a minimized consequence, Phase 10.44 should expose the authorized canonical reference/result level, not the sensitive underlying resource.

Example:

```text
Health source knowledge: restricted
Authorized cross-domain consequence: "temporary study-capacity constraint"
University receives: authorized canonical consequence reference
University does not receive: medication name, diagnosis, clinical record, private note
```

Any such consequence must itself be backed by canonical evidence/knowledge semantics; Phase 10.44 may not invent a sanitized fact solely to bypass access controls.

### 12.3 Fail-closed behavior

If the system cannot establish that a cross-domain projection is authorized under the current authority snapshot, it must not expose the reference.

Missing authority is not equivalent to allow.

## 13. Relation semantics

### 13.1 Existing relations

Phase 10.44 may traverse and project canonical relations whose source, target, semantics, evidence, temporality, and current visibility satisfy existing canonical contracts and current Domain permissions.

### 13.2 Relation proposals

When Domain reasoning identifies a potentially useful relation not yet represented canonically, Phase 10.44 may prepare/reference a proposal through existing update machinery.

The proposal MUST preserve:

- source canonical identity;
- target canonical identity;
- relation kind supported by the canonical relation vocabulary;
- provenance/evidence references;
- temporal qualification;
- epistemic status/confidence where the canonical contracts support it;
- originating domain/run/trace references;
- required permissions/approvals.

If the canonical relation contract cannot represent the proposed semantic faithfully, Phase 10.44 must fail closed or leave the relationship as an unresolved hypothesis/reference. It must not create a parallel relation model.

## 14. Correlation, association, impact, and causality

The roadmap explicitly prohibits converting correlation into causality.

Phase 10.44 SHALL enforce the following semantic hierarchy:

```text
temporal co-occurrence != association established by evidence
association != correlation
correlation != causal relation
possible impact != established impact
transitive path != proof of transitive causality
relation proposal != persisted relation
persisted relation != universal truth outside its evidence/temporal scope
```

### 14.1 `affects` paths

The roadmap example:

```text
Medication
  ↓ affects
Symptom
  ↓ affects
Study Capacity
  ↓ affects
Opposition Goal
  ↓ part_of
Life Plan
```

is a graph/traversal example, not permission to synthesize causal claims.

An `affects` edge may be used only when the canonical knowledge relation semantics and evidence justify that relation at the represented epistemic level.

A path containing `affects` edges may demonstrate an **impact path** but must not automatically produce a new direct causal edge between the first and last nodes.

### 14.2 Inference-sensitive domains

Health, Mental Health, Relationships, Concerns, Parenthood, Neurodivergence, and similarly sensitive domains require particular care. A cross-domain projection must not promote:

- screening to diagnosis;
- self-report to confirmed fact;
- interpretation to observation;
- hypothesis to established cause;
- temporal coincidence to medical/psychological causation.

Existing Domain Pack epistemic rules remain authoritative.

## 15. Cross-cutting timelines

### 15.1 No second temporal engine

Phase 10.44 SHALL NOT implement a new timeline/temporal reasoning engine.

Cross-cutting timelines are read-only projections over canonical temporal metadata.

### 15.2 Timeline representation

A timeline entry should contain only what is necessary to identify and order an authorized canonical object, such as:

- canonical reference ID;
- kind;
- applicable domain references;
- `observed_at`;
- `valid_from`;
- `valid_to`;
- `expires_at`;
- `last_verified_at`;
- invalidation reference/status;
- supersession reference;
- ordering state;
- contradiction reference when applicable.

### 15.3 Incompatible periods

Objects from incompatible periods MUST NOT be merged into a synthetic current state.

Examples:

- an expired medication state cannot be used as current medication truth;
- a previous university semester cannot silently satisfy a current study-plan constraint;
- an old relationship state cannot be presented as current merely because it remains in history;
- a superseded Life Plan decision cannot be treated as the active decision.

### 15.4 Unknown ordering

If canonical temporal metadata cannot establish order, Phase 10.44 must preserve the unknown ordering state.

It must not infer chronology from input order, identifier order, retrieval rank, or convenience.

## 16. Contradictions

### 16.1 Canonical contradiction owner

Phase 10.44 MUST reuse Phase 8 contradiction detection/truth contracts and Phase 10.32 Domain conflict policy where applicable.

It may not introduce a `DomainContradictionEngine` or independently decide cognitive truth.

### 16.2 Projection

A cross-domain projection may expose:

- contradiction IDs;
- involved canonical references;
- current contradiction status;
- resolution references where they already exist;
- whether the contradiction blocks a requested projection/action under canonical policy.

### 16.3 Temporal succession is not contradiction

A newer version replacing an older valid state is not automatically a contradiction.

Phase 10.44 must continue the Phase 10.18 invariant distinguishing temporal succession from unresolved contradiction.

---

## 17. Dependency and impact paths

### 17.1 Purpose

Phase 10.44 should make it possible to identify how authorized canonical knowledge can affect goals, plans, workflows, constraints, or decisions across domains.

Examples include:

- a canonical health constraint affecting a sport workflow;
- an academic deadline affecting an opposition study goal;
- a financial constraint affecting a parenthood scenario;
- a project dependency affecting a Life Plan milestone.

### 17.2 Read-only path semantics

An impact/dependency path is a projection of canonical relations/references.

The path result MUST state or preserve the relation identity for each hop. It must not flatten a multi-hop path into a stronger direct relation.

### 17.3 Blocking versus advisory

Whether a dependency path blocks execution remains owned by the relevant canonical planning/workflow/rule/permission system.

Phase 10.44 may surface the path; it does not become another planner or policy engine.

## 25. Determinism and content binding

New Phase 10.44 immutable contracts SHOULD follow the deterministic/content-bound conventions established by Phase 10.18 and later Domain phases.

Where IDs/digests are introduced:

- serialization must be canonical;
- digests must cover all authority-relevant and semantic fields;
- changing supporting domains, temporal reference, permission snapshot, selected references, relation/path references, or proposal references must change the content digest where those fields affect semantics;
- unknown fields and ambiguous legacy aliases should fail closed;
- diagnostics must remain non-sensitive.

A stale or mismatched `DomainMemoryView` digest MUST be rejected rather than silently rebound to current content.

## 26. Error handling

The thin integration layer MAY define a small Domain-owned error family only for failures it genuinely owns, for example:

- integration request malformed;
- view/reference digest mismatch;
- canonical identity mismatch;
- unsupported projection kind;
- unauthorized cross-domain reference;
- ambiguous temporal ordering where strict ordering is required;
- relation semantics not representable canonically;
- proposal binding mismatch.

It MUST preserve canonical exceptions from underlying owners where appropriate and must not translate them into broader authority.

Error messages must be sanitized and must not echo sensitive rejected metadata or payloads.

## 27. Side effects and purity

Read-only projection must be side-effect free.

Calling the 10.44 projection/integration service must not by itself:

- persist knowledge;
- mutate a Knowledge Store;
- alter a canonical relation;
- resolve a contradiction;
- approve a proposal;
- apply a proposal;
- enable a Domain;
- change Domain permissions;
- execute a workflow;
- run an operation;
- update a session revision;
- emit an external effect.

Proposal preparation may create a canonical proposal object only through the existing explicit proposal lifecycle and only when the caller has the necessary propose authority. Proposal creation is still not persistence of truth.

## 30. Security and privacy invariants

Phase 10.44 MUST preserve at least the following security guarantees:

1. No sensitive resource is transferred merely because two domains are related.
2. `applicable_domains` never grants access.
3. Supporting-domain resolution never grants memory-write authority.
4. Missing permission fails closed.
5. `ABSTAIN`/unknown policy outcomes are never upgraded to allow.
6. Trust boundaries from 10.38 remain ceilings.
7. Read authority does not imply proposal authority.
8. Proposal authority does not imply approval/apply authority.
9. A downstream domain sees only authorized references/metadata.
10. Error/diagnostic surfaces do not echo sensitive payloads.
11. Trace/result serialization remains reference-first.
12. No chain-of-thought/private prompt/model-provider payload is added to memory/graph projections.

---

## 31. Temporality invariants

1. Temporal truth comes from canonical Phase 8 contracts.
2. Current-state queries must exclude expired/invalidated/superseded objects according to canonical policy.
3. Historical queries may retain them as history without promoting them to current state.
4. Unknown temporal order remains unknown.
5. Temporal succession is not contradiction by default.
6. Incompatible periods are never merged into one synthetic state.
7. Impact paths must preserve the temporal validity of every hop where temporality is relevant.
8. A relation proposal must not imply a timeless relation when evidence is time-bounded.

---

## 32. Epistemic invariants

1. Facts remain facts; hypotheses remain hypotheses.
2. User reports remain user reports unless canonical evidence upgrades them.
3. Domain inference does not silently become persisted truth.
4. Correlation does not become causation.
5. Contradictions remain explicit until canonical resolution.
6. Confidence/provenance/uncertainty are preserved when represented by canonical contracts.
7. A relation path does not strengthen the epistemic status of its individual edges.
8. Missing evidence is not treated as negative evidence unless an existing canonical rule says so.

## 51. Final architecture statement

Phase 10.44 makes Domain Intelligence **knowledge-connected without becoming knowledge-owning**.

After this phase, a canonical fact/entity/event/goal/decision/constraint may legitimately matter to several domains while remaining one canonical object with one provenance/temporal history. Each domain receives only the references and consequences it is authorized to see. Cross-domain timelines, contradictions, dependencies, and impact paths are projections of canonical truth, not new truth stores. New relations remain proposals until the existing knowledge-update lifecycle authorizes and applies them.

The invariant to preserve is:

```text
ONE CANONICAL KNOWLEDGE TRUTH
+ MANY DOMAIN-SPECIALIZED AUTHORIZED VIEWS
+ REFERENCE-ONLY CROSS-DOMAIN PROJECTIONS
+ CANONICAL PROPOSAL/APPROVAL/WRITE FLOW
= SPECIALIZATION WITHOUT KNOWLEDGE SILOS
```

And explicitly:

```text
NO DOMAIN KNOWLEDGE GRAPH
NO DOMAIN KNOWLEDGE STORE
NO DOMAIN PERSISTENT MEMORY
NO DOMAIN TEMPORAL ENGINE
NO DOMAIN CONTRADICTION ENGINE
NO CAUSALITY FROM CORRELATION
NO SENSITIVE TRANSFER WITHOUT AUTHORITY
NO DIRECT DOMAIN WRITE
```
