## 1. Purpose

Phase 10.47 establishes the canonical **declarative benchmark asset layer** for Domain Intelligence.

A Domain Pack must be able to ship representative, versioned, reproducible and exportable benchmark cases describing what a model or future evaluation framework would need to demonstrate for that domain.

Phase 10.47 does **not** execute models.

Phase 10.47 does **not** rank models.

Phase 10.47 does **not** define domain-specific quality weights, score thresholds, aggregate scores or blocking quality metrics.

Phase 10.47 does **not** implement the Phase 11 Model Evaluation Framework.

Its output is a stable set of **portable benchmark assets** that later canonical infrastructure can consume.

The durable separation is:

```text
Phase 10.47
    defines benchmark assets
        ↓
Phase 10.48
    defines domain quality metrics
        ↓
Phase 11.36
    executes models, evaluates outputs, compares versions,
    ranks candidates and feeds historical evidence to routing
```

## 3. Superseded conceptual roadmap fields

The older conceptual Phase 10.47 roadmap sketch included fields such as:

```python
candidate_models=[]
quality_criteria=[]
evaluation_policy={}
privacy_policy={}
default_budget={}
```

This design refines that sketch to comply with the already-audited architecture of Phase 10.46 and the future boundaries of 10.48 and Phase 11.

### 3.1 `candidate_models` is removed

A Domain Benchmark Case must not name candidate models or providers.

The following fields or equivalents are prohibited from canonical Domain benchmark assets:

```text
candidate_models
preferred_models
prohibited_models
model_id
model_ids
model_family
candidate_providers
preferred_providers
prohibited_providers
provider_id
provider_ids
routing_weight
```

Rationale:

Phase 10.46 established that Domain Packs must remain stable while providers, model catalogs, subscriptions and routing strategies change.

Benchmark evidence may later influence AUTO routing, but a Domain Pack must not become the owner of the model candidate set.

Candidate models belong to the future **evaluation run request**, not the benchmark asset.

### 3.2 `quality_criteria` becomes unweighted `evaluation_criteria`

Phase 10.47 may describe semantic criteria that an evaluator should inspect.

It may not assign:

```text
weight
minimum_score
blocking
aggregate_score
metric confidence
ranking contribution
```

Those are Phase 10.48 Domain Quality Metrics responsibilities.

The canonical Phase 10.47 field is therefore:

```python
evaluation_criteria: tuple[str, ...]
```

It is descriptive and unweighted.

### 3.3 Suite-owned evaluation/budget/privacy engines are removed

A benchmark suite does not own an evaluation policy engine, a budget engine or a privacy engine.

Case-level declarations may carry:

```text
maximum_cost_eur
sensitivity
privacy_requirement
evaluator_ids
human_review_required
```

These values are **requirements/evidence declarations only**.

They never grant authority, execute a policy, reserve budget, authorize egress or choose a provider.

## 4. Design Point

## DP-047 — Portable, Model-Agnostic Domain Benchmark Suites

> A Domain Pack may declare immutable, typed, versioned, reproducible and exportable benchmark suites composed of representative domain cases. Cases describe inputs by safe references, expected evidence, required constraints, prohibited behavior, output format/schema, sensitivity, minimum privacy requirements, maximum benchmark cost, automatic-evaluator references and human-review requirements without selecting concrete models/providers or defining domain quality weights. Benchmark assets are provider-independent and consumable by the future canonical Model Evaluation Framework. Phase 10.47 does not execute models, rank models, own model/provider registries, or implement Phase 10.48 quality metrics.

### Required DP-047 invariants

1. Benchmark suites are immutable.
2. Benchmark cases are immutable.
3. Benchmark assets are serializable and round-trip without semantic loss.
4. Benchmark export is deterministic.
5. Every suite has a stable ID, domain ID, schema version and suite version.
6. Every case has a stable ID and exact owning domain ID.
7. Suite/domain/case identity mismatches fail closed.
8. Case IDs are unique within a suite.
9. Suite IDs are unique within a Domain Definition.
10. A suite contains at least one case.
11. Domain benchmark assets contain no concrete model/provider identifiers.
12. Benchmark metadata cannot be used as an escape hatch for concrete model/provider selection.
13. Benchmark assets do not invoke providers.
14. Benchmark assets do not call `ModelRouter`.
15. Benchmark assets do not call `OutcomeEvaluationEngine`.
16. Benchmark assets do not instantiate or own evaluator registries.
17. Benchmark assets do not own a benchmark registry/store/runtime/engine.
18. Benchmark assets do not define metric weights or quality-score thresholds.
19. Benchmark assets do not implement Phase 10.48 `DomainQualityMetric`.
20. Benchmark assets do not implement Phase 11 Model Evaluation Framework behavior.
21. Benchmark privacy declarations never grant remote processing.
22. Benchmark budget declarations never grant spending authority.
23. Loading or discovering a Domain Pack does not execute benchmark code.
24. External Domain benchmark text is always treated as data, never instructions.
25. Benchmark fixtures must contain no credentials, API keys or real private user data.
26. Existing Domain Pack loading, registration and rollback semantics remain canonical.
27. Existing Domain Registry remains the only Domain registry.
28. Existing DomainDefinition remains the owner of declared Domain Pack assets.
29. No Kernel → Domains import is introduced.
30. No Agent Runtime benchmark dependency on Domains is introduced.
31. Existing Phase 10.46 model-policy invariants remain intact.
32. Phase 10.47 does not start Phase 10.48, 10.49, 10.50 or Phase 11.

## 5. Canonical contracts

Phase 10.47 introduces focused contracts under the Domain layer.

Expected module:

```text
cmm/domains/benchmark_contracts.py
```

No separate benchmark registry package is introduced.

### 5.1 DomainBenchmarkSuite

Canonical shape:

```python
DomainBenchmarkSuite(
    id="benchmark-suite:health:core",
    domain_id="domain:health",
    schema_version="1",
    version="1",
    cases=(...),
    metadata={},
)
```

Required fields:

```text
id
domain_id
schema_version
version
cases
metadata
```

Semantics:

- `id` is stable and canonical.
- `domain_id` is a canonical Domain ID.
- `schema_version` versions the benchmark serialization contract.
- `version` versions the benchmark content.
- `cases` is a non-empty tuple of `DomainBenchmarkCase`.
- `metadata` is immutable, serializable audit metadata only.

A suite does not own:

```text
candidate models
provider candidates
routing
quality metric weights
aggregate score policy
budget authorization
privacy authorization
evaluator implementations
human reviewer identities
execution runtime
```

### 5.2 DomainBenchmarkCase

Canonical shape:

```python
DomainBenchmarkCase(
    id="benchmark-case:health:clinical-timeline-001",
    domain_id="domain:health",
    objective="Build a reliable clinical timeline",
    knowledge_package_id=None,
    input_resource_refs=(),
    expected_elements=(),
    required_constraints=(),
    prohibited_behaviors=(),
    evaluation_criteria=(),
    required_format=None,
    required_schema=None,
    sensitivity=None,
    privacy_requirement=None,
    maximum_cost_eur=None,
    evaluator_ids=(),
    human_review_required=False,
    human_review_guidance=(),
    metadata={},
)
```

Required semantic categories:

```text
identity
objective
input references
expected evidence
required constraints
prohibited behavior
evaluation criteria
format/schema expectations
sensitivity
privacy requirement
maximum execution cost
automatic evaluator references
human-review requirement/guidance
audit metadata
```

## 6. Benchmark identity

Benchmark identifiers must be deterministic and domain-bound.

Canonical forms:

```text
benchmark-suite:<domain-slug>:<suite-slug>
benchmark-case:<domain-slug>:<case-slug>
```

Examples:

```text
benchmark-suite:health:core
benchmark-case:health:clinical-timeline-001

benchmark-suite:project:core
benchmark-case:project:architecture-consistency-001
```

The embedded domain slug must agree with `domain_id`.

For example:

```text
id=benchmark-case:health:clinical-timeline-001
domain_id=domain:project
```

must fail closed.

The implementation should reuse existing dependency-neutral Domain ID validation where possible.

It must not create a second Domain identifier model.

## 7. Case inputs

Phase 10.47 does not define a new knowledge store or benchmark fixture store.

Case inputs are declared through:

```python
input_resource_refs: tuple[str, ...]
```

and, when relevant:

```python
knowledge_package_id: str | None
```

These are references only.

A benchmark case does not embed or persist live user knowledge.

First-party benchmark fixtures must be:

```text
synthetic
sanitized
static
non-secret
non-user-specific
safe to export
```

If a future benchmark requires a portable fixture bundle, Phase 11 may define the execution/export envelope around these references.

Phase 10.47 does not create that bundle runtime.

## 8. Expected elements and constraints

`expected_elements` describes information or behavior expected in a satisfactory output.

Example:

```python
expected_elements=(
    "chronology is explicit",
    "symptoms are separated from confirmed facts",
    "missing information is identified",
)
```

`required_constraints` describes rules that must hold.

Example:

```python
required_constraints=(
    "preserve source uncertainty",
    "do not infer treatment chronology not present in evidence",
)
```

`prohibited_behaviors` describes unacceptable behaviors.

Example:

```python
prohibited_behaviors=(
    "invent diagnosis",
    "attribute unsupported intent",
    "silently discard contradictory evidence",
)
```

These are benchmark semantics.

They are not weighted metrics.

---

## 9. Evaluation criteria

`evaluation_criteria` contains unweighted semantic evaluation dimensions.

Examples:

```text
factual fidelity
temporal correctness
ambiguity preservation
missing-information detection
architectural consistency
tool-call appropriateness
```

Phase 10.47 does not calculate a score for these criteria.

Phase 10.48 may later define typed `DomainQualityMetric` contracts such as:

```text
weight
minimum_score
blocking
evaluator version
aggregate score contribution
```

No Phase 10.47 contract may contain those fields.

---

## 10. Automatic evaluator references

A case may declare:

```python
evaluator_ids=("evaluator:required-elements",)
```

These IDs are opaque references.

Phase 10.47 validates only that they are:

```text
non-empty
deterministic
unique
serializable
```

Phase 10.47 does not:

- resolve evaluator IDs;
- dynamically import evaluator code;
- register evaluator implementations;
- execute evaluators;
- infer a callable from an arbitrary string;
- create a Domain evaluator registry.

The future Model Evaluation Framework owns evaluator resolution/execution.

Existing Agent Runtime `OutcomeEvaluationEngine` remains untouched.

---

## 11. Human evaluation

A benchmark case may declare:

```python
human_review_required=True
human_review_guidance=(
    "Check whether uncertainty is preserved",
    "Check whether tone remains proportionate",
)
```

Phase 10.47 records only the requirement and guidance.

It does not:

```text
create review tasks
assign reviewers
store review decisions
calculate reviewer consensus
resolve disagreement
```

Those belong to the future execution/evaluation layer.

---

## 12. Required format and schema

A case may constrain output through:

```python
required_format: str | None
required_schema: Mapping[str, JsonValue] | None
```

Examples:

```text
required_format="json"
required_format="markdown"
required_format="structured"
```

`required_schema` must be JSON-compatible, deeply immutable and deterministically serializable.

A benchmark case may describe an expected schema.

It does not perform runtime response validation.

Existing canonical validation remains authoritative.

---

## 13. Sensitivity and privacy

A case may declare:

```python
sensitivity: str | None
privacy_requirement: str | None
```

These are benchmark requirements, not grants.

The following invariant is mandatory:

```text
benchmark privacy requirement
    can restrict a future run
    but can never authorize a future run
```

A future Model Evaluation Framework must combine benchmark requirements with:

```text
global privacy
user privacy
session privacy
Domain privacy
resource privacy
provider policy
egress permissions
```

using canonical privacy infrastructure.

Phase 10.47 does not implement Phase 10.50 Domain Privacy Policies.

A value such as:

```text
SENSITIVE
```

must never imply:

```text
remote processing allowed
provider allowed
cache allowed
export allowed
cross-domain transfer allowed
```

## 14. Cost declarations

A case may declare:

```python
maximum_cost_eur: Decimal | None
```

Rules:

- `None` means the benchmark asset defines no additional maximum.
- a value must be finite and non-negative;
- bool values are invalid;
- serialization is deterministic and precision-preserving.

This field is a maximum requirement only.

It does not:

```text
reserve budget
approve spending
select a cheaper model
override user/session budget
authorize premium use
```

Existing economic/budget infrastructure remains authoritative.

---

## 15. Metadata

Benchmark metadata must be:

```text
Mapping
JSON-safe
deeply immutable
deterministically serializable
```

Metadata is not an authority channel.

To prevent Phase 10.46 circumvention, benchmark validation must reject reserved model/provider-selection metadata keys at any benchmark-owned metadata surface.

At minimum reserve semantic keys equivalent to:

```text
model
model_id
models
candidate_models
preferred_models
prohibited_models
provider
provider_id
providers
candidate_providers
preferred_providers
prohibited_providers
routing_weight
routing_weights
```

The implementation may centralize this list in the benchmark contract module.

The rule applies to Domain Benchmark Suite and Domain Benchmark Case metadata.

## 16. Immutability

`DomainBenchmarkSuite` and `DomainBenchmarkCase` must follow the existing immutable Domain contract style:

```text
frozen
slotted
tuple-based collections
deep-frozen metadata/schema mappings
strict type validation
unknown-field rejection on deserialization
```

No mutable list/dict supplied by a caller may remain live inside the object.

Round-tripped contracts must compare equal.

---

## 17. Serialization

Every benchmark contract must support the repository's established style:

```python
to_dict()
from_dict(...)
```

Requirements:

- deterministic field names;
- strict required fields;
- strict unknown-field rejection;
- JSON-safe representation;
- exact round-trip;
- no code execution during parsing.

`maximum_cost_eur`, when present, must use an existing precision-safe project convention.

If no common helper exists, serialize it as a canonical decimal string.

---

## 18. Deterministic export

A suite must support deterministic export.

The preferred design is a small pure helper in the benchmark contract module or a tightly scoped sibling module:

```python
export_domain_benchmark_suite(
    suite: DomainBenchmarkSuite,
) -> bytes

import_domain_benchmark_suite(
    payload: bytes,
) -> DomainBenchmarkSuite
```

The export format is canonical JSON:

```text
UTF-8
sorted keys
stable separators
no incidental whitespace dependency
no local filesystem paths
no generated timestamps
no random IDs
```

A fresh export of the same suite must produce identical bytes.

Import(export(suite)) must equal `suite`.

No benchmark export store or repository is introduced.

---

## 19. Content digest

A benchmark suite must expose deterministic content identity.

Preferred contract:

```python
suite.content_digest
```

or an equivalent pure helper.

Digest:

```text
SHA-256
```

over the canonical serialized suite content, excluding the digest itself if materialized.

Required:

```text
same semantic suite -> same digest
changed case content -> changed digest
export/import -> same digest
```

The digest does not replace the explicit suite version.

Version and digest have separate meanings:

```text
version = declared semantic release
digest  = exact content identity
```

## 20. DomainDefinition integration

Benchmark suites are Domain Pack assets.

The canonical integration is an optional collection on `DomainDefinition`.

Expected shape:

```python
DomainDefinition(
    ...,
    model_policy=...,
    benchmark_suites=(...),
)
```

Preferred field:

```python
benchmark_suites: tuple[DomainBenchmarkSuite, ...] = ()
```

The field must be appended in a backward-compatible way following the pattern established by Phase 10.46's optional `model_policy`.

Existing DomainDefinition constructors that do not declare benchmark suites must continue to work unchanged.

`to_dict()` / `from_dict()` must preserve benchmark suites.

No separate `DomainBenchmarkRegistry` is introduced.

---

## 21. Domain Pack integration

`ParsedDomainPack` and `DomainPack` already own canonical pack definition/manifest coherence.

Phase 10.47 extends only the existing pack parsing/coherence path as required to preserve `DomainDefinition.benchmark_suites`.

Required pack coherence checks:

1. every suite `domain_id` equals `DomainDefinition.id`;
2. every case `domain_id` equals its suite `domain_id`;
3. suite IDs are unique within the definition;
4. case IDs are unique within each suite;
5. benchmark payloads are valid before the pack becomes usable;
6. invalid benchmark assets cause pack validation/loading to fail closed;
7. pack load rollback remains the existing canonical rollback path.

Do not create a benchmark-specific loader.

Do not create a benchmark-specific lifecycle.

Do not create a benchmark-specific rollback mechanism.

## 22. Domain Registry integration

The existing `DomainRegistry` remains the canonical registry.

A registered `DomainDefinition` naturally carries its benchmark suites.

Consumers may retrieve:

```text
DomainRegistry -> DomainDefinition -> benchmark_suites
```

No secondary index or registry is required in Phase 10.47.

If later performance needs require indexing, that is a future evidence-backed change.

YAGNI applies here.

## 28. Security requirements

Benchmark assets are declarative data.

They must not:

- contain credentials;
- contain API keys;
- contain provider tokens;
- contain real user private data;
- execute code during import;
- execute code during Domain discovery;
- resolve arbitrary callables from strings;
- import arbitrary modules named by a pack;
- contain dynamic Python expressions;
- weaken Domain trust rules;
- bypass pack validation;
- bypass current privacy/permission infrastructure.

External pack benchmark assets remain subject to existing Domain Pack trust, validation and fragmentation protections.

Benchmark evaluator IDs are identifiers only.

They are never dynamic import paths in Phase 10.47.

---

## 29. Privacy and fixture safety

No first-party benchmark case may copy actual private user material.

Synthetic fixtures may simulate:

```text
clinical history
relationship ambiguity
academic constraints
project code scenarios
personal planning
```

but must be fabricated specifically for testing.

Sensitive semantics may be represented.

Sensitive real content may not.

This rule applies to:

```text
case metadata
suite metadata
input resource fixtures
human-review guidance
expected elements
prohibited behaviors
```

## 35. No benchmark registry

The following is not needed:

```python
class DomainBenchmarkRegistry:
    ...
```

Benchmark suites belong to Domain Definitions.

The existing Domain Registry already owns Domain Definitions.

A parallel benchmark registry would fragment source of truth.

Therefore:

```text
DOMAIN_BENCHMARK_REGISTRY=PROHIBITED
```

for Phase 10.47.

## 36. Validation

Benchmark validation occurs in two layers.

### Contract validation

Each benchmark object validates itself:

```text
types
required fields
IDs
non-empty values
collection uniqueness
domain ownership
cost validity
metadata safety
schema JSON-compatibility
model/provider-field prohibition
```

### Domain Pack coherence validation

Existing pack validation additionally checks:

```text
suite domain == definition domain
case domain == suite domain
suite IDs unique in definition
invalid suite blocks pack usability
```

No new validation engine is introduced.

## 37. Fail-closed behavior

Invalid benchmark assets fail closed.

Examples that must be rejected:

```text
empty suite cases
duplicate case IDs
duplicate suite IDs
malformed benchmark IDs
suite/case domain mismatch
invalid Domain ID
negative maximum cost
NaN/infinite maximum cost
non-bool human_review_required
mutable/non-serializable metadata
non-JSON required schema
model/provider selection fields hidden in metadata
dynamic evaluator import path semantics
unknown serialized fields
```

An invalid benchmark suite must not be silently dropped while the rest of a pack loads.

The pack must remain invalid according to existing canonical loading/rollback semantics.

## 38. Determinism

The same source benchmark definition must produce identical:


## 39. Versioning rules

Every suite has:

```text
schema_version
version
content_digest
```

Semantics:

- `schema_version` changes when the serialization contract changes.
- `version` changes when the benchmark suite author makes a semantic benchmark release.
- `content_digest` identifies exact serialized content.

Changing a case's expected elements, prohibited behaviors, constraints or fixture references changes the digest.

Phase 10.47 does not implement a benchmark migration engine.

Existing Domain Pack versioning remains the package-level authority.

## 55. Design rationale

The chosen architecture intentionally treats benchmarks as **data assets**, not an execution subsystem.

This creates a clean ownership model:

```text
Domain Pack owns:
    what representative domain cases exist
    what must be present
    what must not happen
    what constraints matter
    what evaluation dimensions are relevant
    what privacy/cost limits the case declares
    what automatic/human evaluation is required

Domain Pack does not own:
    which model is tested
    which provider is tested
    how the model is invoked
    how evaluators run
    how metrics are weighted
    how scores aggregate
    how rankings are produced
    how routing decisions are made
```

This matches the existing CMM OS principle that Domain Intelligence specializes semantics without cloning shared runtime infrastructure.

---

## 56. Design conclusion

Phase 10.47 establishes a durable benchmark boundary:

> **Domains define representative evidence cases. Phase 10.48 defines how domain quality is measured. Phase 11 executes and compares models.**

The Domain Pack becomes capable of carrying benchmark evidence without becoming a benchmark runtime.

The result is:

```text
portable
provider-independent
model-agnostic
versioned
reproducible
exportable
auditable
privacy-aware
budget-aware
future-evaluation-compatible
```

while preserving:

```text
one Domain Registry
one Agent Runtime
one routing system
one validation architecture
one source of model/provider authority
```

This design is the authoritative Phase 10.47 architecture unless a later independently reviewed amendment explicitly changes it.
