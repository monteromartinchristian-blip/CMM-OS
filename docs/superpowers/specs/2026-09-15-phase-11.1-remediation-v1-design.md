## 1. Purpose

This remediation fixes only the three MAJOR findings from Independent Audit V1.

It does not redesign Phase 11.1, reopen Phase 11.34, implement Phase 11.2, or introduce new platform subsystems.

The remediation must preserve the already-correct architectural properties of the Phase 11.1 implementation while strengthening three fail-closed guarantees:

1. canonical bindings must validate the runtime object that claims canonical authority;
2. public service descriptor metadata must be secret-free and recursively immutable;
3. invalid `ServiceMode` values must be rejected before any container can become `READY`.

---

## 2. Audit findings in scope

### MAJOR-01 — Canonical runtime boundary not enforced

Audit V1 independently demonstrated that:

```python
provider_registry_binding(object())
```

could produce a binding that reached:

```text
ContainerState.READY
```

while claiming:

```text
service_id = provider.registry
authority  = provider-registry
```

The platform therefore validated the descriptor identity more strongly than the implementation object behind it.

### MAJOR-02 — Descriptor metadata secret and mutability gap

Audit V1 independently demonstrated that `ServiceDescriptor.metadata` accepted values such as:

```python
{
    "token": "sk-secret",
    "nested": {
        "password": "p",
    },
}
```

and that nested mutable data remained mutable even though the outer mapping was wrapped by `MappingProxyType`.

### MAJOR-03 — Invalid service mode can reach READY

Audit V1 independently demonstrated that:

```python
ServiceDescriptor(..., mode="bogus")
```

could reach `ContainerState.READY`, while later snapshot serialization failed because `"bogus"` was not a valid `ServiceMode`.

## 4. Design decision for MAJOR-01

### 4.1 Principle

A canonical service binding must validate both:

```text
canonical descriptor identity
+
compatible runtime implementation boundary
```

A service must not become authoritative merely because its metadata claims a canonical service ID.

### 4.2 Runtime boundary strategy

Use the strongest boundary already available in the repository.

Preferred order:

1. existing canonical runtime-checkable protocol;
2. existing canonical abstract/base interface;
3. existing canonical concrete class when replacement is not intended;
4. a minimal Phase 11.1 adapter protocol only when legitimate alternate implementations must remain replaceable and no existing compatible boundary exists.

Do not use `Any` as the effective runtime boundary for a canonical authority.

Do not create wrapper implementations solely to satisfy type validation.

### 4.3 Canonical binding behavior

Canonical binding builders must continue to accept already-created subsystem instances.

They must not instantiate canonical subsystems.

For example:

```python
provider_registry_binding(existing_provider_registry)
```

remains valid.

But:

```python
provider_registry_binding(object())
```

must fail deterministically before registration/readiness.

### 4.4 Binding contract

Each canonical binding must carry an enforceable `runtime_contract` whenever runtime identity can be checked safely.

Representative target shape:

```python
ServiceBinding(
    descriptor=...,
    implementation=provider_registry,
    runtime_contract=ProviderRegistry,
)
```

If an existing runtime-checkable protocol is more appropriate than the concrete class, use that protocol instead.

### 4.5 Replacement compatibility

Runtime enforcement must not destroy the legitimate replacement/test-adapter feature.

Where a service is intended to support alternate implementations:

- define or reuse an explicit protocol/interface;
- both production and test adapters must satisfy it;
- replacement must still pass contract metadata compatibility;
- replacement remains prohibited after freeze/readiness.

Do not solve MAJOR-01 by disabling replacement support.

### 4.6 Canonical services covered

The remediation must inspect and enforce the boundary for at least the canonical service bindings introduced by Phase 11.1:

- `provider.registry`;
- `domain.registry`;
- `validation.application`;
- `cognitive.service`;
- `agent.runtime.integration`;
- `workflow.registry`;
- `execution.registry`.

Where a current repository implementation cannot be safely checked with `isinstance`, the implementation must document the exact reason and use an explicit compatible protocol instead of leaving the binding effectively unchecked.

## 5. Design decision for MAJOR-02

### 5.1 Principle

`ServiceDescriptor.metadata` may remain, but only as small descriptive metadata.

It must not become a storage surface for:

- secrets;
- credentials;
- provider payloads;
- prompts;
- hidden reasoning;
- mutable runtime objects;
- domain-sensitive content;
- live service state.

### 5.2 Allowed value grammar

Metadata values must be recursively limited to immutable descriptive values.

Allowed scalar values:

```text
None
bool
int
float
str
```

Allowed composite values:

```text
tuple[allowed_value, ...]
mapping[str, allowed_value]
```

Mappings must be normalized to an immutable representation.

Mutable input may be accepted only if it is copied and recursively frozen during construction.

Arbitrary object instances are rejected.

### 5.3 Secret-shaped keys

Keys must fail closed when their normalized name represents secret-bearing content.

At minimum reject exact or segmented forms containing:

```text
secret
secrets
credential
credentials
password
passwd
token
api_key
apikey
access_key
private_key
auth
authorization
cookie
session_key
prompt
reasoning
provider_payload
payload
```

The implementation should use a deterministic key-normalization rule and a fixed denylist.

It must not perform heuristic content scanning or build a generic DLP subsystem.

### 5.4 Secret-shaped nested content

The same key rule applies recursively to nested mappings.

For example:

```python
metadata={
    "display": {
        "token": "...",
    },
}
```

must be rejected.

### 5.5 Values

Metadata validation must reject arbitrary opaque objects even if the key itself is harmless.

Example:

```python
metadata={"client": SomeLiveClient()}
```

must be rejected.

The remediation does not need to inspect arbitrary string contents for entropy or secret patterns. The boundary is structural and key-based, not heuristic.

### 5.6 Recursive immutability

After construction:

- no nested mapping can be modified;
- no nested sequence can be modified;
- mutating the original input object must not alter the descriptor;
- the descriptor remains stable and deterministic.

A suitable representation may use:

- `MappingProxyType` recursively;
- immutable tuples;
- another simple immutable mapping representation already used in the repository.

Do not add a new generic immutable collection framework.

### 5.7 Inspection behavior

The existing safe inspection allowlist remains unchanged.

`ServiceDescriptor.metadata` must still not be automatically serialized into public inspection snapshots.

Fixing descriptor safety must not widen inspection output.

## 6. Design decision for MAJOR-03

### 6.1 Principle

A `READY` container must imply that every public composition value needed for inspection is valid and serializable.

Malformed enum-like values must fail at the earliest public contract boundary.

### 6.2 `ServiceDescriptor.mode`

`ServiceDescriptor.mode` must require a real `ServiceMode`.

Inputs such as:

```python
mode="bogus"
```

must be rejected during descriptor construction.

Do not silently coerce arbitrary strings.

If repository serialization/deserialization later needs string parsing, that belongs in an explicit parser/adapter boundary, not in the core dataclass constructor.

### 6.3 `ServiceInspection.mode`

`ServiceInspection` must defensively validate its mode as well.

This protects the public snapshot boundary against malformed values introduced by future callers or manual construction.

### 6.4 READY invariant

For every successfully built container:

```python
container.state is ContainerState.READY
```

must imply:

```python
container.snapshot().to_dict()
```

succeeds deterministically.

This must become an explicit regression/acceptance assertion.

## 10. Required RED tests

### 10.1 MAJOR-01

At minimum:

```python
with pytest.raises(...):
    provider_registry_binding(object())
```

Equivalent rejection tests must exist for every canonical builder with a safely enforceable runtime boundary.

Also prove:

```python
binding.implementation is canonical_instance
```

for valid canonical objects.

Where test adapters are supported by protocol:

```python
compatible_adapter -> accepted before readiness
unrelated_object   -> rejected
```

### 10.2 MAJOR-02

At minimum:

```python
with pytest.raises(...):
    ServiceDescriptor(
        ...,
        metadata={"token": "secret"},
    )
```

Nested key:

```python
with pytest.raises(...):
    ServiceDescriptor(
        ...,
        metadata={"nested": {"password": "secret"}},
    )
```

Opaque object:

```python
with pytest.raises(...):
    ServiceDescriptor(
        ...,
        metadata={"client": object()},
    )
```

Recursive immutability:

```python
source = {"nested": {"label": "before"}}
descriptor = ServiceDescriptor(..., metadata=source)

source["nested"]["label"] = "after"

assert descriptor metadata still contains "before"
```

Attempts to mutate nested descriptor metadata must fail.

### 10.3 MAJOR-03

At minimum:

```python
with pytest.raises(...):
    ServiceDescriptor(
        ...,
        mode="bogus",
    )
```

and:

```python
with pytest.raises(...):
    ServiceInspection(
        ...,
        mode="bogus",
    )
```

READY invariant:

```python
container = ApplicationContainer.build(...)
assert container.state is ContainerState.READY
container.snapshot().to_dict()  # must not raise
```

## 19. Stop conditions

Stop remediation and report rather than widening scope if:

- a canonical service cannot be given any safe runtime boundary without changing its upstream architecture;
- fixing metadata requires a secrets subsystem;
- fixing `ServiceMode` requires a breaking contract migration outside `cmm.platform`;
- Phase 11.34 production semantics would need modification;
- Phase 11.2 orchestration would need implementation;
- an inherited closed phase must be reopened;
- an unrelated global regression appears that cannot be attributed to the remediation;
- repository safety would require stash/reset/clean/worktree/push/merge.
