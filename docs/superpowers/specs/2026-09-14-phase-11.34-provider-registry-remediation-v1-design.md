## 1. Purpose

Remediation V1 closes the findings from the first independent audit of Phase 11.34 without widening the phase beyond Provider Registry responsibilities.

The remediation must make Provider Registry a single-authority, locally persistent, versioned and auditable provider/model/route inventory with fail-closed subscription isolation and atomic onboarding, while preserving the already-closed canonical LLM contracts used by earlier phases.

This remediation does **not** implement the whole of future Phase 11 persistence, Model Gateway, Routing Policy Engine, CMM Usage integration, or CMMChat integration.

## 2. Audit findings in scope

The historical V1 audit is authoritative for remediation scope:

- `MAJOR-01` — provider identity fragmented across `ProviderRegistry` and `ProviderManifestRegistry`;
- `MAJOR-02` — durable, versioned, auditable local-first Provider Registry persistence is absent;
- `MAJOR-03` — Claude and Antigravity isolation can fail open into `CONNECTED`;
- `MAJOR-04` — failed duplicate onboarding can overwrite an existing credential;
- `MAJOR-05` — mandatory Design Point / connected Acceptance Test and lifecycle status are absent;
- `MINOR-01` — snapshot immutability test is Python-version-sensitive.

No unrelated refactor is authorized.

## 3. Canonical infrastructure discovered by inspection

### 3.1 Provider/model authority already exists

The existing canonical LLM path is:

- `kernel/llm/provider_registry.py` — `ProviderRegistry` / `ProviderSpec`;
- `kernel/llm/model_catalog.py` — `ModelCatalog`, explicitly constructed with `ProviderRegistry`;
- `kernel/llm/model_router.py` — `ModelRouter`, explicitly consumes `ProviderRegistry` + `ModelCatalog`;
- `kernel/llm/provider_factory.py` — consumes `ProviderRegistry`;
- `kernel/llm/model_selection.py` — consumes `ProviderRegistry`;
- Phase 10.46 acceptance uses the same `ProviderRegistry` / `ModelCatalog` contracts.

These contracts remain canonical and must not be replaced.

### 3.2 Additional Phase 11.34 entities have distinct legitimate ownership

The following concepts are not provider-identity registries and may remain as distinct focused components:

- `ProviderConnectionRegistry` — accepted provider accounts/connections;
- `ModelRouteCatalog` — provider-specific model routes and route lifecycle;
- `ProviderManifest` — declarative provider onboarding/configuration metadata;
- `ProviderCandidate` — detected-but-not-authorized evidence;
- credential-store implementations;
- provider discovery and onboarding services.

They must remain subordinate to the canonical provider identity owned by `ProviderRegistry`.

### 3.3 Persistence and transaction patterns already exist elsewhere

Inspection found established patterns that may be reused as design references:

- repository/store protocols with official in-memory implementations;
- local file-backed stores;
- SQLite-backed stores;
- schema/version checks;
- transaction context managers;
- snapshot/restore rollback;
- atomic file replacement patterns;
- explicit repository error taxonomies.

Remediation V1 may introduce a Provider Registry-specific persistence adapter because provider state is a distinct domain, but it must follow existing repository patterns and must not introduce a general-purpose parallel storage framework.

## 4. Architectural decision A — one authoritative provider identity

### 4.1 `ProviderRegistry` remains the sole provider identity authority

`ProviderRegistry` is the only authoritative in-memory inventory of provider identity.

A provider is considered registered only if its canonical `ProviderSpec` exists in `ProviderRegistry`.

All production services that need to decide whether a provider exists must resolve through this authority.

### 4.2 `ProviderManifestRegistry` must cease to be an independent authority

`ProviderManifestRegistry` must not remain a second provider-ID catalog capable of diverging from `ProviderRegistry`.

Allowed remediation shapes are limited to:

1. eliminate the production registry and retain `ProviderManifest` only as an immutable declarative value object; or
2. retain a manifest lookup helper whose authoritative keys are derived from / validated against the canonical `ProviderRegistry` and which cannot independently create provider identity.

The implementation plan must choose the smallest compatible shape after inspecting public compatibility requirements.

It is expressly forbidden to solve MAJOR-01 with bidirectional synchronization between two authoritative registries.

### 4.3 First-wave provider registration

First-wave manifests remain declarative definitions, not provider authority.

The canonical bootstrap flow must be conceptually:

```text
first-wave declarative manifest
        ↓ validate
canonical ProviderSpec
        ↓
ProviderRegistry
        ↓
Provider-specific onboarding/discovery metadata may be associated by provider_id
```

A first-wave provider must never exist only in a manifest registry while being absent from `ProviderRegistry`.

### 4.4 Referential integrity

Components that hold provider-related state must validate provider ownership:

- a `ProviderConnection` must reference a provider present in `ProviderRegistry`;
- a provider-owned `ModelSpec` remains subject to existing `ModelCatalog` provider validation;
- a `ModelRoute` must resolve through a registered connection/provider path;
- restore from persistence must fail closed on orphaned provider, connection, model or route references.

## 5. Architectural decision B — local-first persisted Provider Registry state

### 5.1 Persistence boundary

Introduce one focused Provider Registry persistence contract, provisionally named:

`ProviderRegistryStateRepository`

The implementation name may vary only if an existing canonical naming convention requires it. The concept is fixed: one persistence adapter for the Phase 11.34 aggregate, not another provider registry.

It must have:

- an official in-memory implementation for tests and ephemeral use;
- a local persistent implementation;
- deterministic serialization;
- strict schema validation;
- explicit schema version;
- explicit state revision;
- atomic save semantics;
- deterministic load/round-trip semantics;
- corruption/incompatibility errors that fail closed.

### 5.2 Persisted aggregate

The persisted Provider Registry state must cover, at minimum:

- canonical providers / provider definitions required to rebuild `ProviderRegistry`;
- canonical model catalog entries required by the Phase 11.34 inventory;
- accepted `ProviderConnection` records;
- credential references only;
- `ModelRoute` records;
- route capability states and confidence;
- route availability;
- `first_seen_at` / `last_seen_at`;
- connection validation state;
- isolation-profile reference where applicable;
- schema version;
- monotonically meaningful state revision;
- sanitized audit/history metadata sufficient to explain state transitions.

### 5.3 Never persist secrets

The repository must never persist:

- raw API keys;
- OAuth tokens;
- refresh tokens;
- session cookies;
- passwords;
- raw credential payloads;
- credential-store command output containing secret material.

Only opaque `credential_ref` values may cross the persistence boundary.

### 5.4 Local persistent implementation

The first durable implementation should be the smallest repository-native local implementation compatible with existing patterns.

A deterministic JSON file with atomic replace is preferred unless inspection during planning identifies an already-canonical generic repository abstraction that can be reused without semantic coupling.

Do **not** reuse Cognitive, Domain, Memory or Agent Runtime stores as the owner of provider state merely because they already persist data.

SQLite is not required for Remediation V1 unless the implementation plan demonstrates that it reduces complexity while reusing an existing generic persistence seam.

### 5.5 Load order and reconstruction

Restore must reconstruct the aggregate in dependency order:

1. parse and validate envelope/schema/revision;
2. rebuild canonical `ProviderRegistry`;
3. rebuild `ModelCatalog` against that exact registry;
4. rebuild accepted connections with referential validation;
5. rebuild model routes and capabilities against canonical providers/connections/models;
6. restore sanitized audit metadata;
7. reject the entire load on structural or referential corruption.

Partial silent restore is forbidden.

### 5.6 Versioning and auditability

The persisted envelope must have at least:

- `schema_version`;
- `revision`;
- deterministic serialization;
- timestamp or equivalent audit metadata where already part of canonical events;
- transition/audit records sufficient to identify accepted connection, validation and route lifecycle changes without exposing secrets.

Schema migrations beyond the initial supported schema are out of scope. Unsupported versions must fail closed with a typed compatibility error.

## 6. Architectural decision C — provider-aware fail-closed isolation

### 6.1 Normalize detector evidence at the boundary

Current provider detectors use provider-specific metadata keys such as:

- `codex_home`;
- `claude_home`;
- `antigravity_home`.

Onboarding must not contain provider-specific ad-hoc extraction branches for only one provider.

Candidate/proposal evidence must expose a normalized isolation-source concept, e.g. `source_home`, while preserving enough origin metadata to audit which provider/detector supplied it.

The exact field name may follow existing contract naming, but there must be one normalized onboarding input.

### 6.2 Isolation prerequisite

For any provider/manifest with `requires_isolation=True`:

```text
isolation missing
OR isolation creation failed
OR isolation validation failed
=> connection MUST NOT become CONNECTED
```

A successful credential check or provider validator must never override a failed isolation prerequisite.

### 6.3 Subscription providers

Connected acceptance must exercise the real official in-memory or filesystem-safe components for:

- ChatGPT Plus via Codex;
- Claude Pro via Claude Code;
- Google AI Pro via Antigravity.

The user's ordinary external profile/home must not be mutated.

### 6.4 `SubscriptionProfileManager`

The existing `SubscriptionProfileManager` or its canonical successor must evolve to understand provider-aware isolation.

A second isolation manager/runtime is forbidden.

## 7. Architectural decision D — atomic onboarding

### 7.1 New connection acceptance is not credential rotation

Creating a new connection and rotating/updating credentials for an existing connection are distinct operations.

`accept()` for a new connection must not behave as an implicit upsert.

If `connection_id` already exists, the operation must fail before mutating credential state.

### 7.2 Required acceptance ordering

The logical sequence for a new connection is:

```text
1. normalize + validate proposal
2. preflight provider existence
3. preflight connection identity uniqueness
4. preflight all side-effect-free constraints
5. prepare/validate required isolation
6. write new credential
7. register canonical connection
8. persist aggregate
9. emit sanitized success/audit state
```

If the implementation requires a different order for technical reasons, it must preserve the same observable atomicity.

### 7.3 Compensation

Any side effect created during this operation must be compensatable if a later step fails.

At minimum:

- a newly written credential must be deleted/restored if connection registration or persistence fails;
- a newly created isolation profile owned solely by the failed operation must be removed or rolled back if safe;
- pre-existing credentials/profiles must never be deleted by rollback;
- the persistent aggregate must not advance revision on failed acceptance.

Use existing snapshot/rollback/transaction patterns where appropriate. Do not create a general transaction engine.

### 7.4 Duplicate-accept invariant

The Audit V1 reproduction becomes a mandatory regression:

```text
existing connection deepseek:main
existing secret = secret-one

attempt duplicate accept with secret-two
=> duplicate error
=> connection count unchanged
=> stored connection unchanged
=> credential remains secret-one
=> persisted revision/state unchanged
```

## 8. MINOR-01 — Python-version-independent immutability proof

The production frozen snapshot contracts are retained.

The failing test must be corrected so each snapshot is tested by assigning to a field that actually exists on that snapshot type.

The test must not depend on the exception behavior for assignment to a nonexistent slotted attribute.

At minimum verify:

- `ProviderConnectionSnapshot` real field mutation fails;
- `ModelRouteSnapshot` real field mutation fails;
- `ProviderInventorySnapshot` real field mutation fails.

The remediation must preserve the declared supported Python policy. Narrowing `requires-python` is not an authorized workaround.

## 9. Design Point `DP-134`

`DP-134` is the canonical design point for Phase 11.34 Provider Registry.

### 9.1 DP-134 statement

> **DP-134 — Canonical, Persistent and Fail-Closed Provider Registry:** CMM OS maintains exactly one authoritative provider identity inventory through the canonical `ProviderRegistry`, with `ModelCatalog`, accepted provider connections and provider-specific model routes referentially bound to that authority; Provider Registry state is locally persisted through one versioned, deterministic, no-secret repository boundary with atomic restore/save behavior and sanitized audit history; provider detection never grants connection authority; subscription providers requiring isolation cannot become connected without a validated CMM-owned isolation outcome; onboarding is atomic and failed operations cannot mutate pre-existing credentials, connection state or persisted revision; dynamic discovery remains administrative and performs no inference; Qwen Token Plan and Qwen Cloud PAYG remain distinct provider/account surfaces; no parallel provider inventory, persistence framework, isolation runtime, routing engine or usage catalog is introduced.

`DP-134` must be recorded in the appropriate Phase 11 requirements/reference matrix without colliding with historical Design Points.

## 10. Connected Acceptance `AT-DP-134`

Create one connected acceptance file:

`tests/llm/test_provider_registry_dp134_acceptance.py`

The acceptance must use real canonical components or their official in-memory implementations. Isolated mocks are insufficient.

### 10.1 Scenario A — single provider authority

- bootstrap first-wave provider definitions;
- assert provider identities exist in canonical `ProviderRegistry`;
- prove no independently divergent production manifest registry can create provider identity;
- verify `ModelCatalog` uses that same `ProviderRegistry`.

### 10.2 Scenario B — Qwen route/account separation

- Qwen Token Plan and Qwen Cloud PAYG remain distinct provider/account surfaces;
- same canonical model may have multiple provider-specific routes;
- provider model IDs remain provider-specific;
- route selection inventory does not collapse billing/provider identity.

### 10.3 Scenario C — detect is not connect

- detect an approved provider candidate;
- prove candidate existence does not create a registered connection;
- explicit acceptance is required.

### 10.4 Scenario D — Codex isolation

- provider requires isolation;
- normalized source-home evidence is accepted;
- CMM-owned isolation profile is produced;
- only then may validation reach `CONNECTED`.

### 10.5 Scenario E — Claude isolation

Same invariants as Scenario D using Claude-specific detector evidence.

### 10.6 Scenario F — Antigravity isolation

Same invariants as Scenario D using Antigravity-specific detector evidence.

### 10.7 Scenario G — fail-closed isolation adversaries

For each required-isolation provider:

- missing source evidence;
- isolation creation failure;
- invalid isolation result;

must never yield `CONNECTED`.

### 10.8 Scenario H — atomic duplicate acceptance

Reproduce MAJOR-04:

- pre-existing connection and credential;
- duplicate `accept()` with a different secret;
- operation fails;
- original secret, connection and persisted revision remain unchanged.

### 10.9 Scenario I — durable no-secret round trip

Using the official local persistent repository:

- save canonical aggregate;
- create fresh process-equivalent component instances;
- reload;
- canonical providers/models/connections/routes/capabilities/timestamps/validation state match;
- route historical availability is preserved;
- persisted bytes contain credential refs but none of the test secrets.

### 10.10 Scenario J — corruption/version fail closed

- unsupported schema version rejects;
- malformed payload rejects;
- orphan connection rejects;
- orphan route rejects;
- partial canonical state is not exposed after failed load.

### 10.11 Scenario K — discovery without inference

- execute administrative model discovery through the canonical path;
- update route inventory;
- prove no chat/generation/inference entry point is invoked.

### 10.12 Scenario L — capability filtering

- provider-specific route capability state is retained;
- required capabilities filter deterministically;
- unknown/unsupported capability cannot falsely satisfy the requirement.

### 10.13 Scenario M — immutable safe projections

- inventory snapshots contain no secret material;
- snapshot objects remain frozen using real-field mutation checks;
- credential refs/profile paths/endpoints/raw external metadata remain excluded where the approved public projection contract excludes them.

## 13. Security invariants

Mandatory:

1. raw secrets never enter provider manifests;
2. raw secrets never enter provider candidates;
3. raw secrets never enter persistence;
4. raw secrets never enter logs/events/inventory snapshots;
5. Keychain operations keep secrets out of argv;
6. external provider profiles are evidence, not authority;
7. contaminated external base URLs do not silently become canonical endpoints;
8. required isolation is fail closed;
9. failed onboarding produces no unauthorized side effects;
10. persisted credential refs cannot embed plaintext secret markers.

## 20. Design invariants summary

Remediation V1 is successful only if all of the following are simultaneously true:

- exactly one authoritative provider identity inventory exists;
- existing canonical `ProviderRegistry` remains that authority;
- no synchronization-based dual-authority workaround exists;
- provider state survives restart through one local-first versioned repository boundary;
- persistence contains no raw secrets;
- connections/routes are referentially bound to canonical providers;
- Codex/Claude/Antigravity required isolation is fail closed;
- failed onboarding cannot mutate pre-existing credentials or persistent state;
- detection remains non-authoritative;
- discovery remains non-inference;
- Qwen Token Plan and PAYG remain distinct;
- `DP-134` exists;
- `AT-DP-134` is connected and executable;
- Phase 10.46 and inherited LLM contracts remain green;
- CMM Usage and CMMChat remain deferred;
- Phase 11.34 remains pending independent verification until Re-audit V2 PASS.
