## 1. Purpose

Phase 10.43 integrates Domain Intelligence with the canonical Phase 7 Continuous Validation system.

The phase exists to make validation obligations explicit, policy-bound, auditable, and fail-closed across:

1. Domain Pack installation;
2. Domain Pack update/reload;
3. Domain operations;
4. Domain workflows;
5. cross-domain execution;
6. Project Domain code changes;
7. specialized Domain results.

The phase MUST NOT create a second validation architecture.

The shared architectural rule remains:

```text
Same Kernel
Same Cognitive Layer
Same Knowledge Model
Same Agent Runtime
Same Planner
Same Workflow System
Same Operation Contracts
Same Validation System
Same Memory
    +
Domain specialization
```

The Phase 7 Validation System remains the semantic owner of validation execution, policies, step execution, findings, result status, observability, history, and commit gating.

Domain Intelligence may declare, select, constrain, and bind validation requirements, but it may not replace those owners.

## 4. Design Point

### DP-043 — Canonical Domain Validation Integration

`DP-043` is defined as follows:

> Domain Intelligence expresses specialized validation policies and validation obligations, while all authoritative validation execution remains owned by the canonical Phase 7 Validation System and, for agentic runtime execution, the existing Phase 9 validation bridge. Domain Pack installation/update, Domain operations, Domain workflows, cross-domain execution, specialized results, and Project Domain code changes fail closed when mandatory validation is missing, unknown, malformed, unavailable, or unsuccessful. No parallel validation pipeline, registry, executor, policy engine, store, history, commit gate, runtime, or validation truth source is introduced.

For closure:

```text
DP-043=VERIFIED_EXISTING
```

means the implementation proves this architecture in the repository rather than merely documenting it.

## 5. Primary architectural invariant

There is one validation truth source.

```text
Domain declaration / Domain policy
        ↓
thin Domain integration
        ↓
Phase 7 ValidationPolicy / ValidationContext / ValidationStep
        ↓
Phase 7 ValidationRegistry
        ↓
Phase 7 ValidationExecutor
        ↓
Phase 7 ValidationPipeline
        ↓
Phase 7 ValidationResult
        ↓
existing Phase 9 runtime decision mapping where agentic execution is involved
```

Domain Intelligence MUST NOT decide that validation "passed" independently from the canonical `ValidationResult`.

The following are explicitly false:

```text
validation node exists == validation passed
validation_policy_id exists == validation passed
validator registered == validation passed
Domain Pack parsed == Domain Pack valid
Domain Pack loaded == Domain Pack enabled
operation completed == operation validated
workflow completed == workflow validated
no finding == PASS unless the canonical result says so
warning == error
missing evidence == success
```

## 7. Policy architecture

The six roadmap policy families MUST be implemented as Domain-owned bindings or builders that resolve to canonical Phase 7 `ValidationPolicy` behavior.

They MUST NOT subclass or replace `ValidationPipeline`.

They MUST NOT create a second policy registry.

They MUST NOT persist independent validation policy state.

The public names are normative:

```text
DomainPackInstallationPolicy
DomainPackUpdatePolicy
DomainOperationPolicy
DomainWorkflowPolicy
CrossDomainExecutionPolicy
ProjectDomainChangePolicy
```

The exact Python representation may be factories, immutable bindings, or predefined `ValidationPolicy` values, but the implementation MUST preserve these public conceptual identities.

### 7.1 DomainPackInstallationPolicy

Purpose:

- validate a Domain Pack before registration/activation;
- require all blocking structural, security, compatibility, permission, dependency, fragmentation, and pack-quality checks;
- prohibit install/activation when mandatory validation is missing or unsuccessful.

Minimum required Domain checks:

```text
domain.manifest
domain.contracts
domain.permissions
domain.dependencies
domain.compatibility
domain.security
domain.fragmentation
domain.tests
```

Additional checks introduced by 10.43, if not already semantically covered by those canonical validators, MUST be registered through the same Phase 7 registry/pipeline.

Installation policy is fail-closed.

A result in any of these canonical states MUST NOT authorize installation:

```text
FAILED
ERROR
TIMED_OUT
CANCELLED
unknown/malformed
```

Warnings MAY be allowed only where the underlying Phase 7 policy and existing Domain installation gate explicitly permit them.

### 7.2 DomainPackUpdatePolicy

Purpose:

- revalidate a new version or reload candidate before it can replace the current effective Domain state;
- preserve the prior working Domain when update validation fails;
- validate version/compatibility/dependencies/contracts/security/permissions/fragmentation/tests;
- validate migration declarations when present;
- never execute migrations merely because they validate.

Required invariant:

```text
failed update validation
!=
partial replacement of active domain
```

The current version remains authoritative until the update passes its required gates and the existing atomic loader commits the replacement.

### 7.3 DomainOperationPolicy

Purpose:

- bind Domain operation validation declarations to the canonical runtime validation path;
- support pre-execution and post-execution validation as required;
- validate specialized operation results where a result contract exists;
- prohibit silent omission of `validation_policy_id`.

For operation execution:

```text
DomainOperationDefinition
    ↓
validation_policy_id
    ↓
Phase 10.42 planning projection
    ↓
Agent Runtime validation requirement/node
    ↓
AgentValidationAdapter
    ↓
Phase 7 validation
    ↓
canonical validation result
```

If an operation mandates validation and no capable adapter/policy/step can be resolved, execution MUST fail closed.

Operation validation cannot grant permission, approval, trust, availability, autonomy, or rollback authority.

### 7.4 DomainWorkflowPolicy

Purpose:

- bind workflow-level validation obligations into the canonical workflow plan/runtime;
- preserve validation obligations across required subworkflow dependency closure;
- prohibit a supporting or nested workflow from removing validation required by another workflow;
- validate final structured workflow output when required.

A workflow may add validation obligations.

A workflow may not remove a mandatory global, Domain, operation, dependency, or Project Domain validation obligation.

### 7.5 CrossDomainExecutionPolicy

Purpose:

- compose validation requirements across all effective participating domains;
- preserve the most restrictive effective requirement set;
- fail closed on incompatible or unresolved required policy IDs;
- prevent a lower-risk supporting domain from weakening a higher-risk primary/supporting domain requirement.

Composition rule:

```text
effective validation obligations
=
mandatory global obligations
∪ primary-domain obligations
∪ all eligible supporting-domain obligations
∪ operation obligations
∪ workflow obligations
∪ dependency obligations
∪ Project Domain code-change obligations when applicable
```

No caller-supplied metadata may remove members from this effective set.

If two policies conflict and no canonical Phase 7 resolution exists, execution MUST block rather than choose the weaker policy.

### 7.6 ProjectDomainChangePolicy

Purpose:

- guarantee that any Project Domain code change is validated through Phase 7 before acceptance;
- reuse Phase 7 change-impact, syntax/AST, lint/format, affected tests, static/security analysis, full-suite escalation, and commit-gate capabilities as appropriate;
- preserve rollback/recovery ownership in existing execution/runtime layers.

Project Domain operations that can mutate code or project files MUST be covered, including the canonical `project.modify_code` path and any equivalent mutating operation resolved through the Project Domain.

The policy must be selected by semantic operation capability/risk, not by trusting free-form caller metadata.

The following must not be possible:

```text
project code mutation
→ successful execution
→ accepted outcome
without canonical validation evidence
```

`project.run_validation` is an explicit validation operation; it does not make validation optional for `project.modify_code`.

`project.prepare_commit` MUST remain downstream of canonical validation and the existing Phase 7 commit gate.

## 8. Domain validation step coverage model

Phase 10.43 MUST preserve the existing eight Domain validation steps.

The roadmap's broader vocabulary MUST map to concrete canonical checks rather than forcing artificial one-to-one step proliferation.

### 8.1 Required mapping

| Roadmap validation concept | Canonical Phase 10 / Phase 7 coverage |
|---|---|
| manifest | `domain.manifest` |
| schema | `domain.manifest` and existing manifest/schema contracts |
| contracts | `domain.contracts` |
| dependencies | `domain.dependencies` |
| compatibility | `domain.compatibility` |
| security | `domain.security` |
| permissions | `domain.permissions` |
| fragmentation | `domain.fragmentation` |
| rules | `domain.contracts` unless a distinct runtime rule validator is demonstrably required |
| operations | `domain.contracts` plus runtime `DomainOperationPolicy` |
| workflows | `domain.contracts` plus runtime `DomainWorkflowPolicy` |
| results | runtime result validation added by 10.43 |
| serialization | contract/result round-trip validation |
| migrations | declaration-only validation where migrations are present |
| tests | `domain.tests` |
| documentation | explicit pack documentation validation if not already covered |

### 8.2 New step rule

A new Domain validation step MAY be added only when all of the following are true:

1. the roadmap requirement is not already guaranteed by an existing canonical step;
2. the new step has a distinct semantic failure mode;
3. it runs through `ValidationRegistry` + `ValidationPipeline`;
4. it emits canonical `ValidationFinding` / `ValidationStepResult`;
5. it does not introduce another executor or result model;
6. its necessity is proven by a RED test first.

Expected legitimate additions may include:

```text
domain.results
domain.documentation
domain.migrations
```

but implementation MUST first prove the existing validators do not already cover the exact required invariant.

No duplicate alias step may be introduced merely to mirror wording in the roadmap.

## 9. Specialized result validation

Phase 10.43 owns validation of specialized Domain results before they are accepted as validated outcomes.

Result validation is NOT a second epistemic reasoning layer.

It verifies structural and declared output invariants such as:

- expected result type;
- required fields;
- JSON-safe serialization;
- deterministic round-trip where the contract supports it;
- domain identity coherence;
- operation/workflow identity coherence;
- status/result consistency;
- approval references not silently removed;
- validation references preserved;
- no impossible success state after validation failure;
- no malformed confidence/status values where the existing contract constrains them;
- privacy/reference-only invariants where an existing contract requires them.

Result validation MUST NOT:

- rewrite factual content;
- raise epistemic confidence;
- resolve contradictions;
- infer missing facts;
- produce a new reasoning result;
- replace Domain Presentation validation;
- replace Phase 8 cognitive validation.

When a canonical Domain-specific result validator already exists, 10.43 MUST call or bind it rather than reimplement it.

## 14. Cross-domain validation

Cross-domain execution introduces no second cross-domain validator engine.

The integration layer computes the effective required validation IDs from already-resolved Domain participation and canonical capability declarations.

Input authority MUST come from:

- `DomainResolutionResult`;
- `DomainComposition`;
- canonical Domain registries;
- canonical operation/workflow definitions;
- Phase 10.42 planning capability view;
- permission/approval authority;
- explicit configured validation policy catalog.

It MUST NOT derive validation authority from:

- free-form user text;
- prompt instructions;
- arbitrary metadata;
- model output;
- claimed validator names;
- supporting-domain presence alone.

The composition must be deterministic.

Equivalent inputs MUST produce equivalent ordered validation obligation sets.

## 15. Project Domain code-change boundary

The Project Domain is special because Phase 10.43 contains an explicit roadmap requirement tying code mutation to Phase 7.

A Project Domain change MUST pass through existing project-development execution and Phase 7 validation capabilities.

At minimum, the design must support policy escalation according to actual impact:

### Low/small code change

Potentially:

- format/lint;
- syntax/AST;
- affected tests;
- change impact.

### Structural or public-contract change

Potentially:

- all above;
- static analysis;
- API/contract validators;
- broader relevant tests;
- security checks.

### Broad/high-impact change

Potentially:

- full relevant subsystem tests;
- full suite when required by canonical policy;
- security/static analysis;
- project-specific validators;
- commit gate for commit authorization.

These are Phase 7 responsibilities.

Phase 10.43 only guarantees that the Project Domain cannot bypass them.

## 16. Installation/update publication blocking rule

The roadmap states that a Domain Pack cannot be installed, updated, or published with a blocking finding.

For 10.43:

- installation and update blocking are in scope;
- publication tooling itself is not expanded unless an existing publication path already exists and only requires the same canonical gate binding;
- no new package publishing service is created.

Any existing publish command/service that already consumes Domain validation MUST inherit the stricter canonical result semantics.

---

## 17. Documentation validation

Domain documentation validation is a quality gate, not a prose-quality model evaluator.

If a dedicated `domain.documentation` validator is required, its bounded responsibility is structural:

- required `README.md` presence where the pack contract requires it;
- referenced documentation paths exist;
- no manifest declaration points to missing docs;
- required public examples/usage references exist when declared;
- no invalid path escape;
- no need to assess prose style or semantic completeness using an LLM.

Documentation validation MUST be deterministic and local.

---

## 18. Migration declaration validation

Phase 10.43 does not build a migration engine.

If Domain Pack migrations are declared, validation may check:

- declaration shape;
- referenced migration path exists;
- version transition metadata is coherent;
- duplicate migration IDs are rejected;
- forbidden path escape is rejected;
- unsupported executable behavior is rejected by existing security rules.

It MUST NOT:

- execute a migration;
- mutate persistent schemas;
- introduce Phase 11 migration infrastructure;
- infer safe reversibility where no canonical migration contract exists.

---

## 19. Validation result references and traceability

Domain Trace remains reference-only.

Phase 10.43 may add or preserve references to canonical validation result IDs, but MUST NOT copy:

- complete ValidationResult payloads into DomainTrace;
- raw validator output;
- secret-shaped values;
- private user content;
- chain of thought;
- provider payloads.

Operation/workflow/session/outcome contracts should preserve canonical validation result IDs where their existing contracts already support them.

No second trace type is created.

## 20. Error semantics

The integration must fail closed for:

- unknown policy ID;
- unknown required validation ID;
- unavailable required validator;
- invalid policy configuration;
- malformed ValidationResult;
- validation pipeline exception;
- required validation timeout;
- required validation cancellation;
- result/validation identity mismatch;
- caller attempting to remove mandatory validation;
- Project Domain mutation with no applicable canonical validation path;
- cross-domain composition that cannot reconcile mandatory validation requirements.

Use existing exception families wherever ownership already exists.

A new Domain integration exception may be added only for errors genuinely owned by the thin Phase 10.43 binding layer.

Do not duplicate Phase 7 or Phase 9 error taxonomies.

---

## 21. Security invariants

Validation is a gate, not a source of authority.

A passing validation cannot:

- enable a Domain;
- authorize a Domain;
- elevate trust;
- grant a permission;
- approve an action;
- raise autonomy;
- enable external communication;
- allow sensitive memory write;
- bypass a Domain trust ceiling;
- bypass an existing approval;
- bypass a rollback requirement.

A Domain Pack cannot modify its validation policy at runtime to weaken host requirements.

Package content is data and configuration under host policy.

The host decides the effective validation requirements.

## 26. Test architecture

### 26.1 Policy unit tests

Prove:

- all six policy families exist;
- each resolves deterministically;
- required step IDs are canonical;
- unknown policy fails closed;
- serialization/immutability if new binding contracts exist;
- no policy weakens mandatory Domain validation.

### 26.2 Domain Pack validation tests

Prove:

- existing eight canonical Domain steps remain registered;
- installation policy uses the Phase 7 `ValidationPipeline`;
- blocking findings prevent install;
- validation error prevents install;
- timeout/cancelled required validation prevents install;
- update validation preserves prior working state on failure;
- documentation/migration/result additions use the canonical pipeline if added.

### 26.3 Operation integration tests

Prove:

- `validation_policy_id` becomes a real runtime obligation;
- missing `AgentValidationAdapter` blocks a validation-mandated operation;
- PRE validation can block execution;
- POST validation can reject/rollback/replan according to existing runtime semantics;
- validation result IDs are preserved;
- validation success does not grant permission or approval.

### 26.4 Workflow integration tests

Prove:

- workflow validation obligations generate canonical validation nodes;
- required subworkflow obligations are retained;
- optional ineligible branches do not invent obligations;
- mandatory nested validations cannot be silently omitted;
- result validation is connected where required.

### 26.5 Cross-domain tests

Prove:

- union/most-restrictive composition;
- supporting domains cannot weaken primary-domain requirements;
- caller metadata cannot remove requirements;
- unknown required policy blocks;
- deterministic ordering;
- no duplicate executions solely because the same validation ID is declared by several domains.

### 26.6 Project Domain tests

Prove:

- a code-changing Project operation cannot complete as accepted without Phase 7 validation;
- actual Phase 7 pipeline runs;
- failing affected test blocks acceptance;
- structural/public change escalates according to configured canonical policy;
- `project.prepare_commit` cannot bypass the Phase 7 commit gate;
- `project.run_validation` does not make validation optional for mutation.

### 26.7 Security/adversarial tests

Prove:

- Domain Pack cannot inject its own validation owner;
- prompt/config cannot mark validation as passed;
- fake validation result ID rejected;
- mismatched validation result rejected;
- validation cannot elevate trust;
- validation cannot grant permission;
- validation cannot activate a Domain;
- arbitrary metadata cannot downgrade Project validation;
- unknown validator ID fails closed;
- malicious documentation/migration paths cannot escape pack root.

### 26.8 Structural anti-fragmentation tests

Prove absence of new independent:

- pipeline;
- validation registry;
- executor;
- store/repository;
- history;
- event bus;
- commit gate;
- runtime.

## 35. Final architectural statement

Phase 10.43 is not "Domain Validation v2."

It is the point where Domain Intelligence becomes a first-class consumer of the validation system CMM OS already has.

The resulting architecture is:

```text
Domain Pack / Operation / Workflow / Cross-Domain / Project Change
                           ↓
                 Domain validation requirement
                           ↓
                 Phase 10.43 thin binding
                           ↓
              canonical Phase 7 Validation System
                           ↓
                 canonical ValidationResult
                           ↓
       Phase 9 runtime decision / existing Domain gate
                           ↓
         continue / block / retry / rollback / replan / escalate
```

One system validates.

Domains specialize what must be validated.

They do not create another validator runtime.
