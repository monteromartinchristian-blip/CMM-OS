## 4. MAJOR-02 — Fail-closed `notes` deserialization

### 4.1 Problem

At audited HEAD, `DomainQualityHumanReviewResult.from_dict()` pre-coerces serialized `notes`:

```python
notes=tuple(data.get("notes", ()) or ())
```

This allows malformed serialized shapes to bypass canonical container validation.

Observed V1 adversarial behavior:

```text
notes="abc"             -> accepted as ('a', 'b', 'c')
notes={"a":"x","b":"y"} -> accepted as ('a', 'b')
notes=123               -> raw TypeError
notes=True              -> raw TypeError
notes=b"abc"            -> DomainSerializationError
```

### 4.2 Required design

The deserializer must validate raw serialized input before semantic coercion.

The preferred minimal design is:

```text
raw notes from mapping
    ↓
canonical sequence validation
    ↓
tuple[str, ...]
    ↓
DomainQualityHumanReviewResult
```

Do not add another parser, validator registry, or serialization subsystem.

### 4.3 Valid serialized shape

Accepted:

```python
[]
["note"]
["note one", "note two"]
()
("note",)
```

subject to existing canonical string validation.

### 4.4 Invalid serialized shapes

Must fail with the canonical domain serialization error contract:

```text
str
bytes
bytearray
mapping
int
bool
float
None when explicitly incompatible with schema
nested sequence
non-string member
empty/invalid string member where canonical validator forbids it
```

No malformed input may:

- be silently coerced;
- be interpreted as mapping keys;
- leak raw `TypeError`;
- change semantic shape.

### 4.5 Error taxonomy

Malformed serialized payloads must surface as:

```text
DomainSerializationError
```

not raw Python container errors.

Constructor-side strictness must remain unchanged.

## 6. MINOR-02 — Decimal test/documentation correction

### 6.1 Ineffective non-unit-weight test

The existing test named approximately:

```text
test_assessment_weight_normalization_does_not_require_unit_sum
```

uses:

```text
0.5 + 0.5
```

which sums to exactly one.

Replace or strengthen it with a genuinely non-unit total, for example:

```text
0.1 + 0.2 = 0.3
```

or another deterministic set.

The test must prove:

- weights need not sum to one;
- normalized aggregate remains correct;
- ambient Decimal precision does not alter the result;
- no first-party catalog change is needed.

### 6.2 Non-terminating ratio documentation

Current reference wording incorrectly states that a non-terminating weighted ratio is effectively impossible with finite Decimals.

Correct semantics:

```text
finite Decimal inputs
    ↓
exact rational representation
    ↓
terminating decimal result -> exact Decimal reconstruction
non-terminating result     -> deterministic bounded rounding
                              independent of ambient decimal context
```

A ratio such as `2/3` is possible from finite Decimal operands.

The implementation arithmetic should remain unchanged unless a focused test proves a defect.
