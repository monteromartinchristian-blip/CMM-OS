# 1. Purpose

Remediation V2 exists for one reason only:

```text
MAJOR_V2_01=
CLIENT_BACKEND_EXACT_COMPOSITION_IDENTITY_IS_ENFORCED_ONLY_BY_THE_CONVENIENCE_BUILDER_AND_CAN_BE_BYPASSED_BY_A_HAND_BUILT_CANONICAL_SERVICE_BINDING
```

Independent Re-audit V2 verified that Remediation V1 correctly closed all other Audit V1 findings.

This design therefore does not reopen Phase 11.50 generally.

# 6. Root cause

Current Phase 11.1 registry semantics:

```python
isinstance(binding.implementation, binding.runtime_contract)
```

Current Remediation V1 builder semantics:

```python
type(service) is ClientBackend
```

Therefore:

```text
official builder
→ exact type enforced

hand-built ServiceBinding
→ registry falls back to isinstance
→ ClientBackendSubclass accepted
```

The exact-type invariant is therefore located in the wrong authority boundary.

---

# 7. Independently reproduced bypass

The failing shape is:

```python
class ClientBackendSubclass(ClientBackend):
    pass

official_binding = (
    build_client_backend_composition_module(service=exact_client_backend)
    .contribute(CompositionConfiguration())[0]
)

hand_built = ServiceBinding(
    descriptor=official_binding.descriptor,
    implementation=subclass_client_backend,
    runtime_contract=ClientBackend,
)

IntegrationServiceRegistry().register(hand_built)
```

Observed in Re-audit V2:

```text
CLIENT_BACKEND_SUBCLASS_HAND_BUILT_BINDING=ACCEPTED
```

This is the closure-blocking defect.

# 8. Architectural constraint

Phase 11.1 is already closed.

Its default runtime-contract rule must remain:

```text
INSTANCE_OF
```

for inherited services.

Remediation V2 must not globally replace:

```python
isinstance(...)
```

with:

```python
type(...) is ...
```

for all platform services.

That would silently redefine closed Phase 11.1 behavior and could invalidate adapters or inherited subtype-compatible contracts.

---

# 9. Chosen design

Add a reusable opt-in exact-runtime-type mechanism to the existing `ServiceBinding` / `IntegrationServiceRegistry` path.

The mechanism has two layers:

```text
1. explicit binding match mode
2. contract-level non-downgrade marker
```

The binding mode makes the intended rule visible and inspectable.

The contract-level marker prevents a hand-built binding from weakening an exact canonical contract back to ordinary `isinstance` semantics.

---

# 10. Runtime contract match enum

Add to:

```text
cmm/platform/contracts.py
```

a small immutable enum:

```python
class RuntimeContractMatch(str, Enum):
    INSTANCE_OF = "instance_of"
    EXACT_TYPE = "exact_type"
```

Semantics:

```text
INSTANCE_OF
→ existing Phase 11.1 behavior
→ isinstance(implementation, runtime_contract)

EXACT_TYPE
→ exact concrete identity
→ type(implementation) is runtime_contract
```

---

# 11. ServiceBinding extension

Extend canonical `ServiceBinding` with:

```python
runtime_contract_match: RuntimeContractMatch = RuntimeContractMatch.INSTANCE_OF
```

The default must preserve every inherited binding.

Existing code that constructs:

```python
ServiceBinding(..., runtime_contract=SomeType)
```

must continue to use `INSTANCE_OF` unless the binding or runtime contract explicitly opts into exact semantics.

---

# 12. Match-mode validation

`ServiceBinding` must reject malformed match values.

Required:

```text
runtime_contract_match must be RuntimeContractMatch
```

If:

```text
runtime_contract_match=EXACT_TYPE
```

then:

```text
runtime_contract must be a real type
```

because exact matching cannot be "not safely checkable".

Exact matching fails closed.

---

# 13. Exact-contract non-downgrade marker

A runtime contract may declare:

```python
__cmm_exact_runtime_contract__ = True
```

This marker is:

```text
private implementation metadata
not a public client API
not a service locator
not a registry
not a new authority
```

`IntegrationServiceRegistry` treats the marker as a minimum required semantic.

Therefore:

```text
contract marker exact + binding match INSTANCE_OF
→ effective match EXACT_TYPE

contract marker exact + binding match EXACT_TYPE
→ effective match EXACT_TYPE
```

A hand-built binding cannot downgrade an exact runtime contract merely by omitting the new field or setting it back to `INSTANCE_OF`.

---

# 14. Why the marker lives on the runtime contract

The Phase 11.1 registry must remain reusable and must not import:

```text
cmm.client_backend
```

A central hard-coded map such as:

```text
"client.backend" → ClientBackend
```

inside `cmm.platform` would invert the dependency direction and turn the platform registry into a growing catalogue of higher-layer service-specific rules.

That is forbidden.

The runtime contract already travels with every `ServiceBinding`.

The exactness marker therefore travels with the contract without adding a parallel policy registry.

---

# 15. ClientBackend opt-in

Add on the canonical class:

```python
class ClientBackend:
    __cmm_exact_runtime_contract__ = True
```

The marker must not require `cmm.client_backend.interface` to import `cmm.platform`.

This preserves layering.

---

# 16. Builder declaration

`build_client_backend_composition_module(...)` must additionally set:

```python
runtime_contract_match=RuntimeContractMatch.EXACT_TYPE
```

This is not the authoritative enforcement by itself.

It is the explicit canonical declaration.

The registry remains the enforcement boundary.

---

# 17. Authoritative effective match

`cmm/platform/service_registry.py` must compute one effective mode.

Conceptually:

```python
declared_match = binding.runtime_contract_match

if runtime_contract declares __cmm_exact_runtime_contract__ is True:
    effective_match = EXACT_TYPE
else:
    effective_match = declared_match
```

No caller may downgrade exact contract semantics.

---

# 18. INSTANCE_OF path

For ordinary inherited contracts:

```text
effective_match=INSTANCE_OF
```

retain current behavior:

```python
isinstance(binding.implementation, contract)
```

including current Phase 11.1 safely-uncheckable behavior.

Do not change inherited semantics.

---

# 19. EXACT_TYPE path

For:

```text
effective_match=EXACT_TYPE
```

the registry must require:

```python
type(binding.implementation) is contract
```

No subclass acceptance.

No adapter acceptance under that exact contract.

No duck typing.

No fallback to `isinstance`.

---

There must be one shared runtime-contract assertion path.

# 78. Final design decision

The defect is not solved by making the convenience builder stricter.

It is solved only when the existing canonical composition registry understands a reusable exact-runtime-contract semantic and `ClientBackend` opts into it in a way that cannot be downgraded by a hand-built binding.

That is the complete Remediation V2 scope.
