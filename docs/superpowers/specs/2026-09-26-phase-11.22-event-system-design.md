## 1. Purpose

Phase 11.22 turns the event capabilities already implemented across CMM OS into one coherent platform event system without creating a second event bus, a second event registry, a second event store, or a second execution authority.

The phase is an integration and hardening phase.

Its job is to make existing event-producing components able to hand off safe lifecycle facts to one canonical delivery path that provides:

- publishing;
- subscription;
- persistence;
- replay;
- deduplication;
- correlation;
- causation;
- deterministic local ordering;
- bounded delivery retries;
- dead-letter handling;
- event-system introspection suitable for Phase 11.23 Observability.

The event system is infrastructure for coordination and observation. It is not a new business runtime, workflow engine, state machine, command bus, task queue, audit log, or source of domain truth.

## 3. Architectural ruling

### 3.1 One transport authority

The existing Phase 9 `AgentRuntimeEventBus` remains the sole event transport authority.

Phase 11.22 may extend it additively where required by the platform capabilities, but must not create any sibling bus such as:

- `PlatformEventBus`;
- `GlobalEventBus`;
- `ApplicationEventBus`;
- `DomainEventBus`;
- `ObservabilityEventBus`;
- `PersistentEventBus`;
- `EventBroker`;
- any equivalent parallel publish/subscribe runtime.

### 3.2 One registry authority

`AgentRuntimeEventRegistry` remains the sole mutable event-type registry used by the canonical transport.

Phase 11.22 may define immutable platform event-name constants and an explicit translation table, but that catalog must not become another registry.

No second discovery, registration, alias or schema-resolution authority is permitted.

### 3.3 One event repository contract

`AgentRuntimeEventRepository` remains the canonical repository contract for transported events.

Phase 11.22 may add a durable implementation of that existing contract.

It must not create an unrelated `PlatformEventStore`, `EventLogRepository`, `EventPersistenceService`, or generic storage framework.

### 3.4 One replay authority

`AgentRuntimeEventReplayer` remains the canonical replay owner.

Phase 11.22 may extend that existing owner to support safe replay into the existing transport.

It must not create a second replay engine.

### 3.5 One dead-letter authority

The existing runtime-event dead-letter contracts and queue remain canonical.

Phase 11.22 may strengthen their integration with delivery retries and replay, but must not define a parallel DLQ subsystem.

## 4. Phase 11.22 platform integration surface

Phase 11.22 may introduce a thin platform composition facade named conceptually `EventSystem`.

Its purpose is composition only.

It may own references to the already-canonical:

- event factory/normalizer;
- event registry;
- event repository;
- event bus;
- event replayer;
- dead-letter queue.

It must not reimplement their algorithms.

A valid `EventSystem` facade may expose a deliberately small surface such as:

- `publish(...)`;
- `subscribe(...)`;
- `unsubscribe(...)`;
- `replay(...)`;
- `list_dead_letters(...)`;
- `replay_dead_letter(...)`;
- read-only statistics/health projection.

The exact public names may follow the repository's existing naming conventions, but the authority split above is frozen.

The facade must be transport-neutral and must not expose hidden implementation objects as an escape hatch.

## 5. Canonical platform event catalog

Phase 11.22 shall make the historical minimum Phase 11.22 event names valid platform event contracts:

- `session.created`;
- `message.received`;
- `intent.resolved`;
- `domain.selected`;
- `reasoning.completed`;
- `goal.created`;
- `goal.updated`;
- `workflow.started`;
- `workflow.paused`;
- `workflow.completed`;
- `workflow.failed`;
- `operation.executed`;
- `validation.completed`;
- `approval.requested`;
- `approval.resolved`;
- `knowledge.updated`;
- `memory.updated`;
- `backup.created`;
- `plugin.failed`;
- `security.alert`.

This list is a contract catalog, not permission to fabricate lifecycle facts.

### 5.1 Producer truth rule

An event may be emitted only when a real canonical owner supplies evidence for that lifecycle fact.

If the owning subsystem is not implemented or has no safe emission seam at Phase 11.22 time, the event name may be registered/reserved but must not be synthetically emitted.

In particular, Phase 11.22 must not create fake backup, plugin or security owners merely to make the catalog appear active.

### 5.2 Existing producer names

Existing closed phases may already use more specific names, including:

- `orchestration.request_received`;
- `orchestration.intent_resolved`;
- `orchestration.domain_resolved`;
- Agent Runtime `agent.*` events;
- Domain lifecycle event names;
- validation lifecycle event names.

Phase 11.22 must preserve those producer contracts.

Where a platform-level canonical name is required, an adapter may translate one already-authoritative source event into one platform event.

Translation is allowed only when:

1. the semantic mapping is explicit and one-way;
2. no authority is added;
3. no payload content is invented;
4. correlation/causation is preserved;
5. duplicate semantic delivery is controlled.

## 6. Event contract reuse

The platform transport event must reuse the existing `AgentRuntimeEvent` family rather than creating a semantic copy.

The implementation must first inspect the exact current header/payload shape before adding fields.

### 6.1 Required semantic facts

For platform use, the canonical transported event must be capable of representing:

- stable event ID;
- event type;
- schema version;
- occurrence time;
- emission time where already supported;
- safe producer identity;
- optional aggregate/reference identity;
- structured safe payload;
- correlation ID;
- causation ID;
- sensitivity;
- existing Agent Runtime references where applicable.

### 6.2 Additive-field rule

If the existing contract already has an equivalent field, it must be reused.

Only if inspection proves no equivalent exists may Phase 11.22 add backward-compatible optional fields to the existing canonical event header.

Permitted additive concepts are limited to platform-neutral facts genuinely required by the Phase 11.22 contract, such as:

- `producer`;
- `aggregate_id`.

No duplicate field with equivalent semantics may be added.

No existing required field may be removed, renamed or repurposed.

## 7. Safe payload policy

Platform events are lifecycle facts, not content mirrors.

An event payload must default to references and categorical facts.

Allowed examples:

- session/request/workflow/goal/operation/approval IDs;
- canonical status values;
- domain IDs;
- capability IDs;
- result references;
- error category/code;
- bounded counts;
- safe durations;
- safe version identifiers;
- boolean lifecycle facts.

The event path must reject or redact according to existing canonical policies:

- prompts;
- raw user text unless a pre-existing canonical event contract explicitly permits a safe projection;
- hidden reasoning;
- chain of thought;
- provider raw request/response payloads;
- credentials;
- authorization headers;
- tokens;
- cookies;
- secret values;
- arbitrary binary payloads;
- tracebacks;
- filesystem secrets/paths where not public-safe;
- opaque executable/runtime objects.

Phase 10.33 Domain Event privacy checks and Phase 11.2 orchestration event safety rules are inherited invariants, not optional examples.

## 8. Persistence design

### 8.1 Existing contract remains authoritative

Durable persistence must be implemented as an implementation of `AgentRuntimeEventRepository`.

The in-memory repository remains official for tests and ephemeral/local composition.

### 8.2 Durable local implementation

Phase 11.22 may add a file-backed append-only event repository inside the existing runtime-event repository module or package.

It must:

- use canonical event serialization/deserialization;
- persist one canonical event representation;
- preserve insertion order;
- reject duplicate event IDs unless the platform publication layer proves an identical already-persisted event and treats the attempt as an idempotent duplicate;
- fail closed on same-ID/different-content conflicts;
- fail closed on malformed or corrupted stored events;
- never silently skip corrupt records;
- create parent storage only in an explicitly configured CMM OS data location;
- use restrictive local file permissions where supported;
- flush durable writes before reporting persistence success;
- never use `pickle`, unsafe YAML, `eval`, `exec`, or arbitrary object deserialization.

A JSON/JSONL implementation is acceptable if it satisfies these invariants.

### 8.3 No generic database phase

Phase 11.22 must not implement:

- schema migration infrastructure;
- a general SQL abstraction;
- SQLite platform storage;
- a generic Unit of Work;
- a global repository registry.

Those belong to other platform phases.

## 9. Publication transaction semantics

The platform publication path shall be:

```text
Producer fact
→ safe adapter / canonical event factory
→ validate and normalize
→ deduplication check
→ durable repository append
→ canonical Event Bus delivery
→ subscriber result
→ bounded retry when eligible
→ dead-letter after retry exhaustion
```

### 9.1 Persist before delivery

A new event must be durably recorded before subscriber delivery is considered successful.

If persistence fails, delivery must not proceed.

If persistence succeeds but delivery partially fails, the event remains recorded and the failed delivery can be retried/replayed.

### 9.2 Deduplication

Deduplication is identity based and content bound.

For the same event ID:

- same canonical fingerprint/content → idempotent duplicate, no second persistence and no second normal publication;
- different canonical fingerprint/content → fail closed as an identity conflict.

The raw Phase 9 bus may preserve its existing duplicate-error behavior.

The higher Phase 11.22 publication facade may convert exact identical republish attempts into a no-op result, but must never hide a content conflict.

---

## 10. Ordering guarantees

Phase 11.22 guarantees only what a local-first single-process event system can prove.

Guaranteed:

- publication order inside one canonical process;
- FIFO delivery according to the existing bus contract;
- deterministic subscriber priority behavior;
- append order in the durable repository;
- chronological/deterministic replay order from stored evidence.

Not claimed:

- distributed total ordering;
- cross-device global ordering;
- exactly-once execution across distributed processes;
- transactional ordering with external remote systems.

Any later distributed transport must preserve these semantics or explicitly version a stronger contract.

---

## 11. Correlation and causation

Existing correlation and causation fields are canonical and must be preserved through every adapter.

Rules:

1. an adapter must carry an existing correlation ID unchanged;
2. an adapter must carry an existing causation ID unchanged;
3. it must not mint a new correlation root when a valid root already exists;
4. existing normalizer behavior may derive correlation from causation where the canonical contract already allows it;
5. replay must preserve the original event ID, correlation and causation;
6. dead-letter metadata must reference the original event, subscriber and attempt evidence without copying unsafe exception content.

This prepares Phase 11.23 distributed tracing without implementing tracing in 11.22.

---

## 12. Subscription semantics

The existing Event Bus subscription model remains canonical.

Phase 11.22 may add only backward-compatible subscription metadata required for replay safety or delivery policy.

### 12.1 Replay safety

Replaying historical events must not silently re-run operational side effects.

Therefore replay delivery must be opt-in.

A backward-compatible subscription flag such as `accept_replay=False` may be added if no equivalent exists.

Default:

`accept_replay = False`

Replay sends an event only to subscribers that explicitly opt in.

This makes replay suitable for:

- rebuilding projections;
- observability;
- audit/read models;
- safe cache reconstruction.

It prevents replay from automatically re-running:

- mutations;
- approvals;
- tool calls;
- provider calls;
- workflow operations;
- memory writes;
- external side effects.

---

## 13. Delivery retries

Phase 11.22 adds bounded subscriber-delivery retries to the existing transport path.

Requirements:

- retry count is finite;
- default compatibility behavior for legacy direct bus use must not unexpectedly multiply handler invocations;
- the canonical Phase 11.22 composed system explicitly configures its delivery policy;
- one subscriber failure must not prevent independent subscribers from receiving the event;
- retry attempts preserve event identity;
- no new event is created merely because delivery is retried;
- final failure creates one dead-letter record;
- exception values must not leak secrets, tracebacks or raw payloads into the DLQ.

Backoff orchestration, circuit breakers and broader failure policy belong primarily to Phase 11.24 and must not be overbuilt here.

---

## 14. Dead-letter semantics

A dead-letter record means:

> a canonical event was persisted but a specific subscriber delivery could not complete within the configured bounded delivery policy.

A dead-letter entry must preserve safe references to:

- event ID;
- event type;
- subscription/subscriber identity;
- final delivery status;
- attempt count;
- safe error category/type;
- timestamp.

It must not copy raw exception text when that text may contain sensitive data.

Dead-letter replay must:

1. resolve the original stored event;
2. preserve event identity;
3. target the intended subscriber or a safe replay-enabled path;
4. remove/resolve the dead-letter record only after successful replay;
5. leave the record intact on replay failure.

---

## 15. Replay semantics

Phase 11.22 must turn the existing replay owner into a real safe delivery-replay capability.

Replay supports filters already represented by the canonical replay request where possible, including:

- event type;
- correlation;
- bounded limits;
- time/identity filters if already supported.

Replay must:

- read from the canonical event repository;
- preserve original event identity and event facts;
- never persist a duplicate merely because an event is replayed;
- never mutate the original record;
- deliver only to replay-authorized subscribers;
- report replay counts deterministically;
- support dry-run without subscriber invocation;
- not bypass permissions or command authority.

Replay is replay of event notification evidence, not replay of business commands.

## 16. Platform adapters

### 16.1 Orchestration adapter

Phase 11.22 shall implement a production adapter satisfying the already-existing `OrchestrationEventSink`.

It must:

- accept only the closed Phase 11.2 lifecycle event set;
- preserve the Phase 11.2 safe-payload validation;
- map supported orchestration lifecycle facts into canonical platform event names where defined;
- preserve request correlation;
- publish through the one Phase 9 bus path;
- not call the Orchestrator back;
- not make routing decisions;
- not modify orchestration state.

The existing `RecordingOrchestrationEventSink` remains the official simple in-memory recorder for its existing tests/use cases.

It must not be deleted or redefined as the platform bus.

### 16.2 Kernel event adapter

A thin callable adapter may receive existing `kernel.events.Event` objects from producers such as Validation or Domain Intelligence.

It must:

- validate the source event;
- translate only explicitly mapped event names;
- preserve safe payload evidence;
- publish through the one canonical event path.

It is not a second Kernel event system.

### 16.3 Agent Runtime events

Existing Phase 9 runtime events already speak the canonical transport contract.

They should be connected directly where practical rather than translated through another semantic event layer.

### 16.4 Workflow events

Existing workflow event contracts remain workflow-owned.

Phase 11.22 may project workflow lifecycle facts into the platform transport through a thin adapter, but may not redefine workflow state or event truth.

## 23. Security invariants

The implementation must preserve:

1. events grant no authority;
2. event receipt grants no permission;
3. replay grants no permission;
4. a subscriber may mutate canonical state only through already-authorized commands/services;
5. hidden reasoning never enters platform events;
6. raw provider payloads never enter platform events;
7. secrets and credentials never enter event persistence or DLQ data;
8. event adapters are one-way;
9. event metadata cannot select a model/provider/domain/agent outside canonical authorities;
10. event types cannot be dynamically used as arbitrary import paths or callables;
11. unknown event types fail according to the canonical registry mode;
12. malformed persisted events fail closed;
13. same-ID/different-content events fail closed;
14. replay cannot invoke non-replay-authorized subscribers;
15. dead-letter replay cannot bypass normal subscriber identity/policy.

## 27. DP-122

`DP-122` is the following architectural design point:

> CMM OS has exactly one canonical in-process event transport authority, reusing and hardening the Phase 9 runtime event infrastructure for platform-wide safe lifecycle facts. New platform events are validated, content-bound and durably appended before normal delivery; identical retries are deduplicated, conflicting identities fail closed, local ordering is deterministic, subscriber failures are isolated and bounded by retry policy, exhausted deliveries enter the canonical dead-letter path, and stored events can be safely replayed only to replay-authorized subscribers while preserving event identity, correlation, causation, privacy and all pre-existing subsystem authorities.

## 35. Final architectural statement

Phase 11.22 is not “build an event bus”.

CMM OS already has one.

Phase 11.22 is:

> make the existing canonical event transport genuinely platform-usable, durable, replayable, deduplicated, failure-aware and safely integrated, while keeping every existing subsystem as the sole authority for the facts it emits.
