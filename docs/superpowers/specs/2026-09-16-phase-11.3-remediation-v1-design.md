# 6. MAJOR-01 — Root cause

The current idempotent command path is logically:

```text
fingerprint command
    ↓
repository.get(key)
    ↓
if no record:
    execute canonical command
    ↓
repository.put(record)
```

The individual repository calls are separate.

The repository is not itself thread-safe.

Therefore two simultaneous equivalent requests may both observe:

```text
repository.get(key) -> None
```

before either inserts the result.

Both can then enter the canonical owner.

The audit reproduced exactly this race against the real Orchestrator.

That violates the required property:

```text
same idempotency key + same semantic command
    -> one canonical execution
```

---

# 7. Remediation architecture for MAJOR-01

The canonical remediation is:

```text
ApplicationGateway
    owns one private in-process lock
    protecting the complete idempotent command critical section
```

Exact critical section:

```text
acquire private idempotency lock
    ↓
fingerprint command
    ↓
repository.get(key)
    ↓
if matching record exists:
    replay stored safe response
    ↓
if conflicting record exists:
    fail IDEMPOTENCY_CONFLICT
    ↓
otherwise:
    execute canonical command
    ↓
repository.put(record)
    ↓
return result
    ↓
release lock
```

The lock spans:

```text
get → canonical execution → put
```

not merely `get()` or `put()` independently.

---

# 8. Lock type

Use the Python standard library:

```python
threading.Lock
```

or:

```python
threading.RLock
```

Only one is needed.

Preferred:

```python
threading.Lock
```

because the idempotent dispatch path is not designed for recursive re-entry.

If implementation evidence proves recursive re-entry occurs, `RLock` may be used
instead, but that must be explained in the implementation handoff.

No third-party concurrency library is permitted.

---

# 9. Lock ownership

The lock belongs privately to:

```text
ApplicationGateway
```

Recommended internal field:

```python
self._idempotency_lock
```

It must not be exported.

It must not be registered in `ApplicationContainer`.

It must not become a service.

It must not become a public contract.

---

# 10. Why ApplicationGateway owns the lock

`ApplicationGateway` already owns application-boundary idempotency coordination.

The repository only stores completed idempotency records.

The gateway is the layer that knows the full transactional sequence:

```text
lookup
execute
record
replay/conflict
```

Therefore the smallest correct repair is to make that gateway sequence atomic.

This preserves the existing repository protocol and avoids creating a second
concurrency subsystem.

---

# 11. Deliberate v1 trade-off

One gateway-wide lock serializes all idempotent commands, including commands with
different idempotency keys.

This is accepted for Remediation V1.

Reason:

- correctness is mandatory;
- the backend is local-first;
- Phase 11.3 does not claim horizontally distributed idempotency;
- introducing per-key lock registries would create more state and lifecycle
  complexity;
- the current scope requires correctness, not maximum command parallelism.

A future performance phase may redesign the internal mechanism only if it
preserves the same public semantics and receives its own reviewed scope.

# 14. Equivalent concurrent command requirement

Two simultaneous commands with:

```text
same idempotency key
same operation
same actor
same session
same expected revision
same semantic payload
same metadata
different request_id
```

must result in:

```text
one canonical command execution
one canonical orchestration decision
one persisted idempotency record
two safe public results representing the same operation
```

The second caller may preserve its own `request_id` only if existing replay
semantics already define that behavior.

Do not change sequential replay semantics merely to satisfy the concurrent test.

---

# 15. Conflicting concurrent command requirement

Two simultaneous commands with:

```text
same idempotency key
different semantic fingerprint
```

must result in:

```text
at most one canonical command execution
one IDEMPOTENCY_CONFLICT
```

The conflicting request must not enter the canonical owner.

It must not create a second orchestration decision.

# 38. Minimal implementation

Preferred implementation shape:

```python
from threading import Lock

class ApplicationGateway:
    def __init__(...):
        ...
        self._idempotency_lock = Lock()

    def _dispatch_idempotent(...):
        with self._idempotency_lock:
            ...
```

The exact method name remains whatever the current gateway already uses.

Do not refactor unrelated dispatch code.

---

# 39. Lock coverage requirement

The lock must protect:

```text
fingerprint resolution
existing record check
conflict decision
canonical command execution
record persistence
```

It is acceptable to compute a pure fingerprint before acquiring the lock if the
fingerprint uses only immutable request data.

However the complete:

```text
get -> execute -> put
```

sequence must be under one lock.

---

# 40. Exception safety

Python context-manager locking must guarantee release if canonical execution
raises.

An exception must not permanently deadlock future requests.

Existing safe error conversion remains authoritative.

Add a regression if implementation structure makes this non-obvious.
