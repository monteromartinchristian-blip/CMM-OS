## 1. Purpose

Phase 11.5 establishes the canonical conversational boundary of CMM OS.

Its purpose is to make the already-integrated platform usable through persistent natural conversation without creating a second runtime, a second session system, a second orchestration path, a second Domain Intelligence layer, a second approval system, or a CMMChat-owned authority boundary.

Phase 11.5 is **not** the visual implementation of CMMChat. CMMChat is the first-party client of the contracts defined here. Alternative clients must be able to consume the same versioned conversational surface.

The phase shall turn the canonical stack already closed through Phase 11.4 into an interface-neutral conversational product boundary:

```text
Client / CMMChat / CLI / API
            ↓
Canonical Conversational Interface
            ↓
Phase 11.3 Application Backend / ApplicationGateway
            ↓
Phase 11.2 Orchestrator
            ↓
Canonical Domain Intelligence / Agent / Workflow / Approval authorities
            ↓
Canonical Session / Memory / Knowledge / Validation authorities
```

No client implementation becomes authoritative merely because it renders or initiates conversational interaction.

## 3. Canonical Requirement

### 3.1 `F11-019 — Canonical Conversational Interface`

CMM OS shall expose one canonical, version-aware, interface-neutral, fail-closed conversational boundary that:

1. provides persistent multi-turn natural interaction over canonical shared sessions;
2. uses the existing Phase 11.3 `ApplicationGateway` for application-facing message submission;
3. reaches the canonical Phase 11.2 `Orchestrator` rather than implementing alternate routing;
4. consumes existing authorized Domain Intelligence interface projections rather than reconstructing domain state;
5. preserves canonical session revision and optimistic-concurrency semantics;
6. supports safe public conversational messages and responses;
7. exposes requested versus effective conversational capabilities;
8. exposes authorized context, domain, source, question, workflow, action, approval, result, contradiction, warning, and memory-proposal references when available;
9. supports auditable editing and controlled regeneration without destructive transcript rewriting;
10. represents attachment/document references without creating a parallel file authority;
11. exposes streaming and cancellation truthfully according to canonical effective capability;
12. keeps normal conversation usable without Bot or Agent binding;
13. treats optional Bot identifiers as non-authoritative until the canonical Bot phase owns their semantics;
14. leaks no hidden reasoning, secrets, raw sensitive context, internal exceptions, credentials, or unauthorized references;
15. remains consumable by CMMChat and alternative clients through stable contracts;
16. introduces no parallel stores, engines, runtimes, registries, routers, planners, approval managers, permission engines, memory systems, knowledge systems, provider systems, or session systems.

## 4. Design Point

### 4.1 `DP-105 — Session-Backed Canonical Conversation Boundary`

The canonical conversational interface is a thin application-facing coordination and projection layer backed by the existing canonical shared-session authority.

A conversation does **not** introduce a second persistence identity or lifecycle in Phase 11.5.

For Phase 11.5:

```text
conversation continuity identity == canonical session identity
```

The `session_id` remains the authoritative identity used to:

- create or resume continuity;
- enforce optimistic concurrency;
- resolve authorized context;
- bind Domain Intelligence state;
- submit messages to the application backend;
- associate conversational history;
- bind edits and regenerations;
- bind questions, approvals, workflows, actions, and result references.

Phase 11.5 must not create a general-purpose `ConversationStore`, `ConversationRuntime`, `ConversationEngine`, or alternative session authority.

If conversational state must be persisted beyond the fields already present in the canonical session, it shall be stored through a **versioned, namespaced conversational extension of the canonical shared session**, using the existing session persistence/revision boundary.

## 5. Reused Canonical Authorities

Phase 11.5 is primarily an integration and projection phase.

The following existing owners must be reused.

### 5.1 Application boundary

Reuse:

- `cmm.application.ApplicationGateway`;
- `ApplicationRequest`;
- `ApplicationCommand`;
- `ApplicationResponse`;
- `ApplicationMessage`;
- `ApplicationSession`;
- `SessionApplicationService`;
- `RequestApplicationService`;
- existing application error contracts;
- existing idempotency and session-revision semantics.

Phase 11.5 must not bypass the `ApplicationGateway` for ordinary conversational message submission.

### 5.2 Orchestration

Reuse the canonical Phase 11.2 orchestration path:

- intent resolution;
- authorized context resolution;
- domain routing;
- agent routing;
- orchestration policy;
- approval evidence;
- decision persistence;
- orchestration events.

Phase 11.5 must not implement conversational intent routing independently.

### 5.3 Sessions

Reuse:

- `cmm.runtime.sessions.SessionStore`;
- `SharedSessionState`;
- `SharedSessionChange`;
- `InMemorySessionStore`;
- `FileSessionStore`;
- existing revision-conflict semantics.

No second transcript persistence authority may be introduced.

### 5.4 Domain Intelligence interface projection

Reuse the closed Phase 10.45 interface-neutral projection boundary, especially:

- `DefaultDomainInterfaceIntegrator`;
- `ConversationalDomainView`;
- presentation visibility;
- canonical question references;
- canonical approval references;
- source references;
- contradiction references;
- workflow references;
- result references;
- memory-proposal references;
- confidence and warning projection;
- selected primary/supporting domains.

Phase 11.5 may render or repackage authorized projections, but it may not derive hidden Domain state or re-resolve domain authority independently.

### 5.5 Approval, workflow, execution, memory and knowledge

These remain owned by their existing canonical subsystems.

The conversational interface may:

- display canonical references;
- collect user interaction;
- submit an application-level request through a canonical command surface;
- report an unavailable capability.

It may not create an alternate approval engine, workflow engine, execution engine, memory store, knowledge store, or permission engine.

## 6. Proposed Package Boundary

The implementation is expected to introduce a small `cmm.conversation` package.

The exact module split may be refined during the implementation plan, but responsibilities must remain narrow.

Expected structure:

```text
cmm/conversation/
├── __init__.py
├── contracts.py
├── errors.py
├── state.py
├── projection.py
├── capabilities.py
├── service.py
└── platform_module.py
```

Expected responsibilities:

| Module | Responsibility |
|---|---|
| `contracts.py` | Versioned, immutable, public-safe conversational contracts |
| `errors.py` | Safe conversational-boundary errors only |
| `state.py` | Namespaced session-backed conversational state and lineage helpers; no independent store |
| `projection.py` | Compose already-authorized public/application/domain projections into conversational views |
| `capabilities.py` | Requested/effective capability representation |
| `service.py` | Thin coordinator over ApplicationGateway/session/projection collaborators |
| `platform_module.py` | Phase 11.1 composition binding without new ownership |

A different file split is acceptable only if it preserves these authority boundaries.

## 7. Public Conversational Contracts

All new public contracts must be:

- versioned;
- immutable or treated as immutable values;
- deterministic to serialize;
- recursively public-safe;
- bounded in size;
- free of secret-bearing metadata;
- free of raw exceptions;
- free of hidden reasoning;
- transport-neutral.

### 7.1 `ConversationMessage`

Conceptual contract:

```python
ConversationMessage(
    id="message-123",
    session_id="session-456",
    bot_id=None,
    role="user",
    content=[...],
    created_at="...",
    references=[...],
    attachments=[...],
    lineage={...},
    metadata={...},
)
```

Minimum semantics:

- `id` is stable and non-empty;
- `session_id` binds the message to canonical session authority;
- `bot_id` is optional and non-authoritative in Phase 11.5;
- `role` is constrained to public conversation roles;
- `content` is public-safe and bounded;
- `references` are typed or namespaced canonical references;
- `attachments` contain references only, not an embedded parallel object-store model;
- `lineage` records edit/regeneration relationships;
- `metadata` must use strict safe-value and secret-rejection rules.

### 7.2 `AssistantResponse`

Conceptual contract:

```python
AssistantResponse(
    message={...},
    sources=[...],
    reasoning_summary={...},
    pending_questions=[...],
    proposed_actions=[...],
    approval_requests=[...],
    workflow_updates=[...],
    domain_state={...},
    capability_state=[...],
    memory_updates=[...],
    warnings=[...],
)
```

`reasoning_summary` is a public, structured explanation surface only.

It must never contain:

- model chain-of-thought;
- raw hidden reasoning traces;
- private scratchpad content;
- raw prompts;
- provider secrets;
- internal exception detail;
- unauthorized source content.

### 7.3 Reference-first rule

Where a canonical subsystem already owns an object, the conversational response shall prefer references/projections instead of redefining that object.

Examples:

- approval → approval reference/projection;
- workflow → workflow reference/projection;
- source → authorized source reference/projection;
- contradiction → canonical contradiction reference;
- memory update → proposal reference/projection;
- action → canonical operation/action reference where available.

## 8. Conversation State

### 8.1 No separate conversation authority

Phase 11.5 must not introduce a second persistence owner for the conversational transcript.

Conversational persistence must be implemented through the canonical shared session.

### 8.2 Namespaced session extension

If the existing session requires an extension, use a versioned namespace conceptually equivalent to:

```text
extensions["conversation.v1"]
```

The implementation plan shall verify the exact existing session extension contract before fixing the final serialization shape.

The conversational extension may contain only state necessary to support the Phase 11.5 interaction model, such as:

- public message records or references;
- message order;
- current active branch/head;
- lineage relationships;
- conversational mode;
- optional opaque Bot association;
- public client-safe metadata;
- capability-state snapshot when required for deterministic replay.

It must not become a dumping ground for canonical subsystem state.

### 8.3 Append-only and revision-aware

State changes must:

- preserve canonical session revision semantics;
- append an auditable session change;
- fail on stale expected revision;
- avoid silent overwrites;
- avoid mutation outside the session persistence boundary.

## 9. Continuous Conversation

The minimum multi-turn flow is:

```text
Client starts/resumes canonical session
↓
ConversationService receives user turn
↓
Validate session revision / conversational state
↓
Build canonical ApplicationCommand / ApplicationMessage
↓
ApplicationGateway
↓
RequestApplicationService
↓
Orchestrator
↓
Canonical Domain / Agent / Workflow / Approval routing
↓
Safe ApplicationResponse
↓
Authorized conversational/domain projections
↓
AssistantResponse
↓
Persist conversational extension through canonical SessionStore
↓
Return public-safe conversational result
```

A second turn must reuse the same canonical session and its updated revision.

No client-maintained hidden transcript is required for correctness.

## 10. Context and Transparency

When available and authorized, the conversational interface shall expose:

- canonical context references used;
- active primary domain;
- supporting domains;
- selected public profile reference if allowed;
- consulted source references;
- information gaps;
- pending questions;
- proposed actions;
- approval-required actions;
- workflow status/update references;
- contradictions and warnings;
- public confidence;
- memory update proposals;
- requested/effective capability state.

Visibility must never imply execution authority.

If canonical authority has hidden, denied, filtered, unavailable, stale, or withheld an item, Phase 11.5 must not recreate or infer it for display.

## 11. Message Editing

Message editing is non-destructive.

An edit shall not silently mutate or erase the original message.

The implementation must use lineage semantics conceptually equivalent to:

```text
new_message.supersedes_message_id = original_message.id
```

Requirements:

1. preserve original message;
2. create a new message identity;
3. preserve author/session binding;
4. record lineage;
5. enforce expected session revision;
6. re-run the canonical application/orchestration path for downstream consequences;
7. preserve an auditable active branch/head;
8. never rewrite historical approvals, workflows, or results as if they had not occurred.

The exact branch model shall remain deliberately minimal in Phase 11.5.

A full generalized conversation version-control subsystem is out of scope.

---

## 12. Controlled Regeneration

Regeneration creates a new assistant result.

It must not:

- reuse hidden chain-of-thought;
- clone provider-internal state;
- bypass the `ApplicationGateway`;
- bypass current permission or domain policy;
- overwrite the original response.

A regeneration shall:

1. identify the user turn / public state from which regeneration starts;
2. create a new request identity;
3. pass through the canonical application gateway and orchestrator;
4. evaluate current effective capabilities and policy;
5. produce a new public assistant response;
6. record lineage conceptually equivalent to:

```text
new_response.regenerates_message_id = prior_response.id
```

7. preserve the prior response for auditability.

---

## 13. Questions and Human Interaction

The interface must support dynamic questions by surfacing canonical pending question references when available.

Phase 11.5 may provide a public interaction command that submits the user's answer through the application boundary.

It must not introduce a new question engine.

A question can be:

- visible and answerable;
- already answered;
- stale;
- blocked;
- unavailable.

The conversational layer must preserve canonical state rather than fabricating completion.

---

## 14. Proposed Actions and Approvals

A proposed action displayed in conversation is **not authorization**.

The interface shall distinguish at minimum:

```text
proposed
approval_required
approved
rejected
blocked
unavailable
completed
failed
cancelled
```

Only existing canonical approval/permission/execution authority may change the real state.

If Phase 11.5 lacks an application command to submit a particular approval response, it must expose that capability as unavailable rather than implementing approval state itself.

---

## 15. Workflow Interaction

The conversational layer may expose:

- workflow reference;
- state;
- progress/status projection;
- questions;
- pending approvals;
- proposed next action;
- pause/resume/cancel availability.

It must not become workflow authority.

Pause, resume, cancellation, retry, or replan may be invoked only through canonical application commands that exist at implementation time.

Unavailable operations remain explicit and fail closed.

## 16. Requested vs Effective Capabilities

### 16.1 Requirement

Phase 11.5 shall distinguish what a caller requests from what CMM OS can actually provide.

Conceptual contract:

```python
ConversationCapabilityState(
    capability="streaming",
    requested=True,
    effective="response_event_stream",
    status="available",
    reason=None,
)
```

Possible status values should minimally represent:

- `available`;
- `degraded`;
- `approval_required`;
- `blocked`;
- `unavailable`.

### 16.2 No authority from declaration

A requested capability does not create execution authority.

A client cannot enable a capability by setting metadata or a request flag.

Effective capability must derive from composed canonical owners.

---

## 17. Streaming

Phase 11.3 already owns the public SSE transport boundary.

At the Phase 11.5 baseline, that transport delivers deterministic stream events for an already-computed application result; it is not provider-token live generation.

Phase 11.5 shall therefore preserve semantic truth.

Example:

```text
requested capability: streaming
effective capability: response_event_stream
```

Phase 11.5 must not introduce:

- a provider token-stream runtime;
- a second model invocation path;
- WebSocket inference ownership;
- a hidden active-generation registry.

If a future canonical owner supports live generation, the capability can evolve additively.

---

## 18. Cancellation

The application boundary already defines request cancellation, but at the current baseline the canonical application gateway reports cancellation as unavailable because no canonical cancellable-request runtime owns it.

Phase 11.5 must preserve that fact.

It must not create an `ActiveRequestRegistry`, cancellation engine, or task runtime merely to make cancellation appear functional.

The client-facing capability shall expose the current effective state.

Future canonical cancellation support may be consumed without changing the Phase 11.5 authority model.

---

## 19. Attachments and Documents

Phase 11.5 shall support message attachment references.

It may:

- accept authorized attachment/document references;
- associate references with a message;
- display them in conversational projections;
- forward authorized resource references through existing application/context seams when supported.

It shall not implement the later global file authority.

Specifically, Phase 11.5 does **not** own:

- conversation file workspaces;
- global artifact library;
- object storage;
- file version history;
- cross-device synchronization;
- import/export archive ownership;
- global file search.

Those responsibilities remain reserved for the later dedicated file/artifact phase, including Phase 11.57.

If upload/ingestion has no canonical owner at implementation time, `document_upload` must remain explicitly unavailable.

---

## 20. Bot Association

A conversation may contain an optional `bot_id`.

In Phase 11.5:

- normal conversation must work with `bot_id=None`;
- `bot_id` is an opaque association only;
- `bot_id` cannot grant tools;
- `bot_id` cannot grant permissions;
- `bot_id` cannot force Agent selection;
- `bot_id` cannot select providers;
- `bot_id` cannot authorize Computer Use;
- `bot_id` cannot change memory/privacy policy by itself.

Canonical Bot identity, configuration and runtime semantics remain outside Phase 11.5 and are reserved for the dedicated Bot phase.

---

## 21. Interaction Modes

Phase 11.5 shall support the roadmap interaction modes as interface metadata/projection where canonical backing exists:

- general conversation;
- domain conversation;
- session linked to a goal;
- session linked to a workflow;
- reflection session;
- review session;
- configuration session.

A mode is not a second runtime.

A mode may narrow presentation and request semantics but may not bypass canonical authority.

Unsupported modes shall fail closed or report unavailable.

---

## 22. Error Semantics

Conversation-facing errors must:

- use stable codes;
- contain public-safe messages;
- preserve correlation identifiers where allowed;
- never expose raw internal exception messages;
- never expose tracebacks;
- never expose filesystem paths;
- never expose secrets;
- never expose hidden prompts/reasoning.

Known application failures should be mapped rather than copied.

Unknown failures must become one safe internal-failure category.
