## 1. Purpose

Phase 11.21 establishes the single canonical model invocation boundary for CMM OS.

The Model Gateway shall provide provider-independent execution for local and remote language/model providers while preserving every existing authority boundary already closed in Phase 8, Phase 9, Phase 10 and Phase 11.1–11.5 / 11.34.

The gateway exists to connect already-canonical model metadata, provider identity, model requirements, privacy, application/orchestration contracts and provider adapters into one executable path.

It is **not** a second provider registry, model catalog, router, policy engine, validation system, agent runtime, tool runtime, file store, conversation runtime or application backend.

The immediate product purpose is to unblock CMMChat without requiring the remainder of Phase 11:

1. real explicit model selection;
2. real provider-independent reasoning-effort control;
3. real image input;
4. real PDF/document input;
5. capability-aware model presentation;
6. normalized structured output;
7. normalized tool calling;
8. provider token streaming;
9. model-call cancellation;
10. privacy-safe local/remote execution.

## 5. Canonical request contract

Phase 11.21 shall introduce one immutable, typed, versioned `ModelGatewayRequest` (name may be shortened to `ModelRequest` only if that does not collide with an existing canonical contract).

Conceptual shape:

```python
ModelGatewayRequest(
    request_id="model-request-123",
    model_id="model-123",
    provider_id=None,
    selection_mode=ModelSelectionMode.EXPLICIT,
    input_parts=(...),
    reasoning_effort=ReasoningEffort.DEFAULT,
    required_capabilities=(),
    tools=(),
    structured_output=None,
    stream=False,
    timeout_seconds=60.0,
    privacy=effective_privacy,
    metadata={},
)
```

The exact contract must preserve the following invariants.

### 5.1 Explicit model authority

When a caller supplies an explicit `model_id`:

- that model is authoritative;
- the gateway validates it through canonical model/provider metadata;
- an incompatible explicit model fails closed;
- the gateway MUST NOT silently substitute another model;
- the gateway MUST NOT silently alter requested reasoning effort;
- automatic fallback to a different model is prohibited unless the caller supplied an explicit authorized fallback sequence.

### 5.2 AUTO mode

`AUTO` may exist only as a thin reuse of the already-existing canonical model-requirement and basic model-selection path.

11.21 MUST NOT introduce:

- quality scoring policy;
- cost optimization policy;
- preference learning;
- adaptive provider ranking;
- benchmark-driven routing;
- user-specific routing heuristics.

Those belong to 11.35+.

## 6. Reasoning effort

### 6.1 Canonical enum

Reasoning effort must be a closed provider-independent type, not a free-form string.

Minimum canonical values:

```text
DEFAULT
NONE
LOW
MEDIUM
HIGH
EXTRA_HIGH
```

`DEFAULT` means “do not impose an explicit effort override”.

A provider adapter may translate these values to provider-native settings, but provider-native names must never leak into the public canonical contract.

### 6.2 Capability truth

Model capability metadata must state which reasoning-effort levels are actually supported.

If current Phase 11.34 metadata does not expose sufficient detail, 11.21 may add a **strictly additive, backwards-compatible metadata seam** to the existing model capability contract. It may not change Provider Registry ownership, persistence authority or existing semantics.

### 6.3 Fail-closed behavior

If the user explicitly requests an unsupported effort:

```text
UNSUPPORTED_REASONING_EFFORT
```

must be returned before external provider I/O.

The gateway must never silently map:

```text
HIGH → MEDIUM
EXTRA_HIGH → HIGH
NONE → DEFAULT
```

or any equivalent semantic downgrade/upgrade.

## 7. Multimodal input

### 7.1 Required input kinds

11.21 must support real provider-facing input parts for:

```text
TEXT
IMAGE
DOCUMENT
```

`DOCUMENT` includes at minimum:

```text
application/pdf
text/plain
text/markdown
```

Additional office formats may be supported only when an adapter can truthfully handle them.

Audio/video are not required by this subphase.

### 7.2 No fake multimodality

The following does **not** satisfy 11.21:

- storing only a filename;
- passing only attachment metadata;
- converting an image to the string `"[image]"`;
- converting a PDF to `"[document]"`;
- claiming support because CMMChat can visually display an attachment.

For IMAGE and DOCUMENT acceptance, the provider adapter must receive the actual authorized content bytes or an equivalent provider-native content object derived from those bytes.

### 7.3 File/storage boundary

The Model Gateway is not a file store and must not become one.

It MUST NOT:

- own upload persistence;
- enumerate user files;
- create a new artifact repository;
- read arbitrary filesystem paths supplied by a model;
- fetch arbitrary remote URLs.

The caller must provide already-authorized content or an injected authorized resolver.

Audit/event output must include safe metadata such as:

- media type;
- byte length;
- content digest where appropriate;

and must not log raw image/document bytes.

### 7.4 Native capability validation

A model that does not support image/document input must fail before provider I/O.

The gateway must not silently degrade a PDF to extracted text unless the caller explicitly requested a canonical preprocessing path owned elsewhere.

## 8. Tool calling

11.21 normalizes tool declarations and tool calls.

It does **not** execute tools.

Flow:

```text
canonical tool definition
        ↓
Model Gateway
        ↓
provider-native tool schema
        ↓
provider result
        ↓
canonical ModelToolCall
        ↓
Agent Runtime / canonical operation authority
```

A provider-generated tool call grants no execution authority.

Tool execution continues to require canonical:

- operation resolution;
- permission evaluation;
- approval;
- validation;
- execution policy.

## 9. Structured output

A request may declare a typed structured-output requirement and optional JSON schema.

The gateway owns:

- provider-native structured-output translation;
- normalization of the returned structured value;
- deterministic parse/contract errors.

The gateway does not become a second response-quality validator.

Semantic or domain validation remains owned by Phase 7 / existing domain validation.

## 10. Streaming

11.21 introduces the canonical provider-token streaming owner.

A normalized stream must use typed events such as:

```text
STARTED
CONTENT_DELTA
TOOL_CALL_DELTA
USAGE
COMPLETED
CANCELLED
ERROR
```

The exact names may vary in implementation, but the semantics must be frozen.

### 10.1 Hidden reasoning prohibition

No event may expose hidden chain-of-thought or provider-private reasoning traces.

Reasoning metadata may expose only safe information such as:

- requested effort;
- effective effort;
- whether reasoning capability was used;
- provider-reported non-sensitive usage counters where available.

### 10.2 Existing Phase 11.3/11.5 streaming

The existing application/conversation event-stream surface is not rewritten in 11.21.

11.21 creates the missing provider-token streaming owner. Projection into CMMChat-facing streaming is reserved for the later stable-client slice.

---

## 11. Cancellation

11.21 owns model-call cancellation mechanics.

Preferred contract:

- caller provides/receives a cancellable model-call handle or cancellation token;
- adapter implementations must cooperate with cancellation;
- after cancellation, no additional content/tool events may be emitted;
- cancellation must produce a deterministic terminal event/result;
- provider-specific cancellation must be normalized.

11.21 MUST NOT create a global workflow/request cancellation authority.

Application-level `/runs/.../cancel` or equivalent belongs to the later stable backend/client interface and canonical run/workflow owners.

---

## 12. Timeout, retry and fallback

### 12.1 Timeout

The gateway owns per-model-call timeout enforcement.

Timeout must:

- terminate or abandon the provider request safely;
- normalize the failure;
- never leave a call reported as running indefinitely.

### 12.2 Retry

Transport retry may occur only under an explicit bounded policy.

The gateway MUST reuse existing retry/recovery semantics where available and must not create an unbounded retry engine.

### 12.3 Failover

11.21 implements failover **mechanics**, not a new routing policy engine.

An authorized fallback sequence must be explicit or produced by the existing canonical fallback/selection authority.

Failover must preserve:

```text
privacy
permissions
required capabilities
reasoning effort
tool requirements
structured-output requirements
input modalities
context requirements
budget constraints already present
```

Fallback may never relax any of them.

This is intentionally narrower than Phase 11.35 Routing Policy Engine.

---

## 13. Privacy and local/remote enforcement

Immediately before any remote provider I/O, the gateway must evaluate effective canonical privacy.

Required invariant:

```text
LOCAL_ONLY + remote provider = DENY before external call
```

Approval cannot convert a canonical privacy denial into authorization.

`LOCAL_PREFERRED` and remote-allowed behavior must preserve the canonical privacy semantics already implemented by the Cognitive Layer and Domain privacy policies.

Provider availability never implies permission to transmit.

Secrets must never be inserted into:

- model content;
- normalized metadata;
- stream events;
- audit records;
- public errors.

Provider credentials continue to be resolved only through canonical provider connection/secret seams.

---

## 14. Provider adapters

11.21 introduces a narrow adapter protocol around existing provider implementations.

Conceptual operations:

```python
class ModelProviderAdapter(Protocol):
    def capabilities(...): ...
    def execute(...): ...
    def stream(...): ...
```

The adapter contract must be replaceable and testable.

Existing OpenAI-compatible, Ollama and other provider implementations must be wrapped/reused where possible rather than forked.

Provider-specific translation belongs only inside the adapter.

Core gateway code must not branch on arbitrary provider names.

Prohibited:

```python
if provider == "openai": ...
elif provider == "anthropic": ...
elif provider == "qwen": ...
```

inside the gateway core.

## 15. Capability discovery

The gateway must expose a read-only model capability projection derived from canonical Provider Registry / Model Catalog state.

This projection exists so future stable clients can ask:

```text
Which models are currently available?
Which accept images?
Which accept documents?
Which support tools?
Which support structured output?
Which reasoning-effort levels exist?
What context window is available?
Is the model local or remote?
Does it support provider token streaming?
```

No capability may be inferred from model name alone.

Unknown capability state must remain unknown/unavailable rather than guessed.

## 23. Design Point

### `DP-121` — Canonical Provider-Independent Model Gateway

CMM OS has exactly one canonical provider-independent model-call execution boundary that:

1. consumes the exact Phase 11.34 Provider Registry / canonical Model Catalog;
2. validates explicit model and capability requirements before provider I/O;
3. preserves explicit user model selection;
4. preserves explicit reasoning effort without silent substitution;
5. transports real image and document content;
6. normalizes tools and structured output without executing tools;
7. normalizes provider token streaming without exposing hidden reasoning;
8. supports bounded timeout/cancellation/failover mechanics;
9. enforces canonical privacy before remote egress;
10. returns normalized usage/cost/latency facts;
11. is composed through Phase 11.1;
12. creates no parallel registry, router-policy engine, validation engine, privacy engine, runtime or backend.

## 24. Connected acceptance

### `AT-DP-121`

The acceptance test must use canonical production components or official in-memory implementations. It must not prove the phase only through isolated mocks.

Minimum scenarios:

### A — canonical ownership

- construct the real Phase 11.34 `ProviderRegistry`;
- construct/use the real canonical `ModelCatalog`;
- bind them into the real Phase 11.1 composition path;
- construct exactly one Model Gateway;
- prove the gateway retains/reuses the exact canonical registry/catalog authority rather than copying or replacing it.

### B — explicit reasoning effort

- register an official in-memory provider/model that truthfully supports multiple effort levels;
- submit an explicit model with `HIGH`;
- prove the adapter receives the provider-native equivalent of `HIGH`;
- prove the normalized response records requested/effective effort;
- request an unsupported effort and prove failure occurs before adapter execution.

### C — real image input

- pass non-empty image bytes with a real image media type;
- prove the adapter receives the actual bytes/content digest;
- prove the response derives from the received image payload rather than attachment metadata alone.

### D — real PDF/document input

- pass a non-empty PDF fixture;
- prove the adapter receives the actual PDF bytes/content digest;
- prove document metadata alone is insufficient;
- prove a model without document capability fails before provider I/O.

### E — structured output

- request structured output with a schema;
- return provider-native structured data;
- prove canonical normalized structured output round-trips deterministically;
- malformed output fails with the canonical error.

### F — tool calling

- provide a canonical tool definition;
- provider returns one tool call;
- gateway normalizes the call;
- prove no tool operation was executed by the gateway.

### G — streaming

- official streaming adapter emits multiple provider-native chunks;
- gateway emits deterministic normalized stream events;
- no hidden reasoning content is exposed;
- terminal completion appears exactly once.

### H — cancellation

- cancel an active official in-memory streaming call;
- prove terminal `CANCELLED`;
- prove no later content events are emitted.

### I — privacy

- evaluate a real canonical `LOCAL_ONLY` privacy object against a remote adapter;
- prove the adapter call count remains zero;
- prove a compatible local adapter can execute;
- prove approval cannot widen the privacy denial.

### J — fallback safety

- first authorized adapter fails with a retry/fallback-eligible transport error;
- second explicitly-authorized candidate succeeds;
- prove capabilities, privacy and reasoning effort remain unchanged;
- an incompatible fallback must be rejected before its adapter executes.

### K — accounting

- normalize token, cached-token, latency and cost facts from an official adapter;
- prove absent provider metrics remain unknown rather than fabricated.
