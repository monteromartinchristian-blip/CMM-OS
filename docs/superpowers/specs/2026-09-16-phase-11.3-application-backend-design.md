# 1. Purpose

Phase 11.3 creates the first stable product-facing backend boundary of CMM OS.

The backend must expose CMM OS capabilities to interfaces, integrations and
future external clients without turning transport concerns into platform
architecture and without creating second owners for capabilities already owned
by Phase 11.1, Phase 11.2, Domain Intelligence, Agent Runtime, Validation,
Workflow, Execution, Sessions, Memory, Knowledge or Provider infrastructure.

The architectural shape is:

```text
CMMChat / future clients / integrations
                |
                v
        HTTP / OpenAPI adapter
                |
                v
        Application Backend Core
                |
                v
        ApplicationContainer
                |
                v
            Orchestrator
                |
                v
          canonical owners
```

The application core is transport-neutral.

HTTP is an adapter around the application core, never the owner of application
semantics.

The canonical backend boundary is deliberately narrower than the complete future
platform. It provides a stable public contract while capabilities that do not yet
have canonical owners remain explicitly unavailable rather than being silently
implemented here.

# 4. Normative requirement — F11-017

`F11-017 — Canonical Application Backend`

CMM OS shall expose stable application-facing capabilities through one
version-aware, transport-neutral, fail-closed application backend that:

1. composes through the canonical Phase 11.1 `ApplicationContainer`;
2. routes user-request processing through the canonical Phase 11.2
   `Orchestrator`;
3. exposes explicit public request, response and error contracts;
4. separates application commands from application queries;
5. prevents transport handlers from bypassing application services;
6. prevents application services from re-owning canonical domain, agent,
   workflow, execution, validation, session, memory, knowledge, provider or
   orchestration authorities;
7. maps internal failures to safe public errors;
8. supports explicit API versioning;
9. provides deterministic OpenAPI metadata for the HTTP adapter;
10. supports public streaming and cancellation contracts without creating a new
    event system or inference runtime;
11. supports repeatable command idempotency through a narrow backend-owned seam
    without introducing durable storage in Phase 11.3;
12. respects canonical session revision/concurrency semantics rather than
    inventing a global concurrency subsystem;
13. rejects unavailable or not-yet-owned capabilities explicitly;
14. exposes no secrets, raw internal exceptions, hidden reasoning or raw
    sensitive context;
15. remains local-first and independently testable without network access.

# 5. Design Point — DP-103

`DP-103 — Versioned, Fail-Closed Application Gateway`

`DP-103` is satisfied when one public application gateway can accept a
versioned application request and produce a versioned application response while:

- resolving only through explicit application services;
- reaching Phase 11.2 orchestration for central user-request processing;
- rejecting malformed or unsupported requests before internal execution;
- preserving canonical subsystem ownership;
- exposing deterministic public errors;
- enforcing command/query separation;
- enforcing safe idempotency semantics;
- preserving session revision/concurrency semantics;
- exposing public streaming/cancellation as bounded adapters;
- rejecting direct internal-owner access from transport;
- remaining independent from Model Gateway and Routing Policy Engine;
- remaining independent from real auth/RBAC;
- remaining independent from durable Phase 11.15 storage;
- remaining independent from Plugin System lifecycle;
- remaining independently testable in-process.

# 7. Architectural decision

The approved architecture is:

```text
Option A
transport-neutral application core
+
separate HTTP/OpenAPI adapter
```

Rejected alternatives:

## 7.1 Direct HTTP → Orchestrator / owners

Rejected.

Transport must not become the application architecture.

HTTP handlers must not directly resolve:

- domains;
- agents;
- providers;
- workflows;
- operations;
- sessions;
- memory;
- knowledge;
- validation;
- internal registries.

## 7.2 Application core only, no HTTP

Rejected for Phase 11.3.

The current canonical roadmap expects:

- public backend/API surface;
- versioning;
- OpenAPI;
- streaming;
- API-level concerns.

Therefore Phase 11.3 includes the first HTTP adapter.

```text
ApplicationCommand
ApplicationQuery
ApplicationResourceRef
```

- secret-free;

# 13. Contract versioning

Application contract version:

```text
v1
```

HTTP base path:

```text
/v1
```

Public contracts must not expose internal package paths as schema identity.

Contract evolution rules:

1. existing required fields cannot silently change semantics;
2. new optional fields may be additive;
3. incompatible contract changes require a new public API version;
4. internal owner changes do not require public version changes if the public
   contract remains compatible;
5. unknown enum values must fail safely or be represented through an explicit
   forward-compatible mechanism defined in implementation;
6. version mismatch must return an explicit public error.

---

# 14. Application request identity

Each public request must have a safe request identity.

Minimum fields:

```text
request_id
api_version
operation
session_id?
idempotency_key?
payload
metadata
```

Rules:

- `request_id` is caller-visible correlation identity;
- `session_id` references canonical session state where applicable;
- `idempotency_key` is accepted only for commands declared idempotent;
- `metadata` uses a constrained safe-value grammar;
- no secrets in metadata;
- no raw Python objects;
- no raw exception objects;
- no hidden reasoning;
- no unbounded arbitrary nested structures without validation.

Minimum response envelope:

```text
request_id
api_version

metadata
```

`status` must be a closed public enum.

The response must never expose:

- traceback;
- exception repr;
- arbitrary object repr;
- filesystem path;
- credential reference content beyond already-safe opaque identifiers;
- hidden reasoning;
- raw sensitive internal context;
- internal service locator state.

# 16. Public error model

Phase 11.3 must define one public application error model.

It may adapt from:

```text
cmm.platform.contracts.ErrorResult
```

but public errors must remain application-layer contracts.

Required error categories include at minimum:

```text
INVALID_REQUEST
UNSUPPORTED_VERSION
RESOURCE_NOT_FOUND
CONFLICT
CAPABILITY_UNAVAILABLE
IDEMPOTENCY_CONFLICT
CONCURRENCY_CONFLICT
CANCELLED
POLICY_DENIED
APPROVAL_REQUIRED
INTERNAL_FAILURE
```

Additional narrowly necessary codes may be added in the implementation plan.

Rules:

- errors are fail-closed;
- errors carry safe public messages;
- internal error details are not public;
- HTTP status mapping lives in `cmm/api`, not `cmm/application`;
- application status and HTTP status are not the same contract.

# 17. Command/query separation

Phase 11.3 must distinguish commands from queries.

Queries:

```text
read-only
no state mutation
no implicit persistence
no approval side effects
```

Commands:

```text
may request mutation
must delegate mutation to canonical owner
must obey policy/approval/permission boundaries
may require idempotency key
must expose explicit conflict/failure
```

The backend must never transform a query into an implicit write.

---

# 18. Canonical central request path

The central user-facing request path is:

```text
ApplicationMessage / application request
       |
       v
ApplicationRequestService
       |
       v
OrchestrationRequest
       |
       v
Orchestrator.orchestrate(...)
       |
       v
OrchestrationResult
       |
       v
ApplicationResponse
```

Phase 11.3 does not bypass Phase 11.2.

Phase 11.3 also does not reinterpret Domain or Agent selection.

It adapts public input into the canonical orchestration contract and adapts the
safe orchestration output into the public application response.

# 19. Important execution boundary

Phase 11.2 intentionally stops after route selection/handoff.

Phase 11.3 must preserve that boundary.

The first `/v1/sessions/{session_id}/messages` implementation may return an
application representation of the canonical `OrchestrationResult`.

Phase 11.3 does not create an unplanned downstream executor that runs:

```text
operation
workflow
agent
model
memory write
knowledge write
provider call
```

unless an already-existing canonical owner and an explicitly approved 11.3
application service contract require that call.

No full vertical execution engine is introduced merely to make the HTTP endpoint
look complete.

# 20. Session application service

Phase 11.3 should expose sessions as a public application concept while reusing
the canonical session owner.

Canonical storage remains:

```text
cmm.runtime.sessions.SessionStore
InMemorySessionStore
FileSessionStore
```

Phase 11.3 may introduce:

```text
ApplicationSessionService
```

It may:

- create a public session through canonical session semantics;
- read a public-safe session projection;
- carry revision/version identity;
- submit session-bound application messages;
- close or cancel only where canonical semantics exist.

It must not create:

```text
BackendSessionStore
APISessionStore
ConversationStore
SessionDatabase
```

# 21. Session concurrency

Phase 11.3 must reuse canonical optimistic session revision semantics.

A public command that mutates session state must be capable of carrying an
expected revision where required.

Conflict behavior:

```text
expected revision != canonical current revision
    => CONCURRENCY_CONFLICT
```

Phase 11.3 must not introduce a global:

```text
ConcurrencyManager
LockRegistry
GlobalSemaphore
TransactionEngine
```

Application-level locking may exist only as a narrow implementation detail when
strictly necessary and must not become a new authority.

---

# 22. Idempotency

Phase 11.3 introduces a narrow application-owned idempotency seam because
idempotency is part of a public command boundary.

Allowed:

```text
IdempotencyRepository (Protocol)
InMemoryIdempotencyRepository
IdempotencyRecord
```

Responsibilities:

- bind idempotency key to operation identity;
- bind idempotency key to a request fingerprint;
- replay the same safe application result for a repeated equivalent command;
- reject same key + materially different command;
- expose no hidden internal result data;
- be bounded by application scope.

Not allowed:

```text
IdempotencyDatabase
global persistence framework
distributed lock service
general transaction manager
```

Durable idempotency persistence is deferred to storage work.

---

# 23. Idempotency fingerprint

Idempotency fingerprint must derive from canonical public command semantics.

It must not include:

- object memory address;
- unstable serialization order;
- secret material;
- volatile timestamps unless they are semantically part of the command;
- internal implementation details.

It must include enough public command identity to detect same-key/different-command
collisions.

---

# 24. Streaming

Streaming belongs to Phase 11.3 as a public delivery contract, not as a new
inference engine.

Application-layer stream contract:

```text
ApplicationStreamEvent
```

Possible event kinds:

```text
STARTED
PROGRESS
DATA
COMPLETED
ERROR
CANCELLED
```

The exact set may be refined in the plan without creating a second Design Point.

Rules:

- events are public-safe projections;
- events contain no hidden reasoning;
- events contain no raw internal event payload;
- events have request/session correlation identity;
- final completion/error is explicit;
- order is deterministic within one application stream.

---

# 25. Streaming transport

HTTP streaming may use a single simple transport supported by the chosen HTTP
framework.

Preferred first transport:

```text
Server-Sent Events (SSE)
```

Rationale:

- one-way server-to-client delivery fits initial public response streaming;
- simpler than WebSockets;
- does not create a bidirectional protocol before needed;
- supports browser and native clients.

WebSockets are out of scope unless implementation evidence demonstrates SSE
cannot satisfy an approved requirement.

---

# 26. Cancellation

Cancellation must be explicit.

Public contract:

```text
ApplicationCancellationRequest
```

Transport may expose:

```text
POST /v1/requests/{request_id}/cancel
```

The application layer must delegate cancellation only to a canonical cancellable
operation/runtime if such a live operation exists.

If the target has no cancellable owner:

```text
CAPABILITY_UNAVAILABLE
```

or a safe no-longer-running response is returned.

Phase 11.3 must not create a new global cancellation runtime.

- secrets;
- credentials;
- raw provider auth material;

# 42. Approval semantics

It must not invent approval completion.

The backend may default to loopback-only in any optional runnable local server

```text

Scheduler
TaskBroker
```

Background execution belongs to later explicit platform work.

# 55. Async boundary

The HTTP adapter may be async because the framework is async.

The application core must not be forced into an async-only architecture unless
a canonical dependency requires it.

A thin sync/async adapter is acceptable.

Do not duplicate every service into sync and async variants.

---

# 56. Cancellation registry prohibition

Do not create a global `CancellationRegistry`.

If cancellation requires live request tracking, the application layer may own a
narrow request-lifecycle table scoped exclusively to active Phase 11.3 requests.

It must not become a persistent runtime owner.

Its semantics must be defined in the implementation plan before code.

# 57. Active request lifecycle

- cancellation handle/reference;

Forbidden contents:

- hidden reasoning;
- raw provider clients;
- raw domain context;
- full internal object graphs.

This seam is optional and must be introduced only if the implementation plan
shows it is mechanically required.

# 58. Application inspection

Phase 11.3 should provide deterministic safe inspection of its own services.

It may expose:

- API version;
- route/resource availability;
- service readiness;
- capability statuses.

Prefer adapting existing Phase 11.1 inspection output rather than creating a
second platform inspection framework.

No secrets in general application config.

No provider credentials.

No auth tokens.

# 60. Request size / bounded inputs

The backend must bound public input sizes.

The implementation plan must define at minimum:

- maximum metadata depth/size;
- maximum idempotency key length;
- maximum request ID length;
- maximum capability query breadth where applicable.

Oversized input fails before orchestration.

Public metadata must use a constrained value grammar similar in spirit to the
safe metadata work in Phase 11.1.

Allowed shape should be explicit.

No:

- arbitrary object;
- bytes unless intentionally encoded;
- secret-bearing credential structures;
- cycles;
- unbounded recursive depth.

# 62. Safe identifiers

Identifiers exposed publicly must be opaque or canonical public identifiers.

Do not expose filesystem paths or object IDs.

Examples:

```text

agent_id
domain_id
capability_id
```

Identifiers are not authorization tokens.

# 63. Public timestamps

If public timestamps are used:

- timezone must be explicit;
- serialization must be deterministic;
- monotonic sequencing must not rely solely on wall-clock equality;
- timestamps are descriptive, not authority.

---

# 64. Error provenance

Internal error provenance may be logged through an existing safe internal
mechanism if available.

Public error responses expose only:

```text
error_code
message
request_id
retryable?
details?  # only constrained safe values
```

No traceback or internal class repr.

---

# 65. Retry semantics

The application layer may declare whether a public error is retryable.

Retry policy itself is not a new engine.

No automatic hidden retries for state-changing commands unless an existing
canonical owner explicitly guarantees safe retry.

---

# 66. Idempotency + retry interaction

Repeated retries of an idempotent command with the same key and same canonical
fingerprint:

```text
return same application result
```

Same key + different fingerprint:

```text
IDEMPOTENCY_CONFLICT
```

A failed command must not be silently converted into success because a later
retry takes a different internal path.

---

# 67. Session + idempotency interaction

Idempotency key scope should include at least:

```text
operation
session_id where applicable
```

The implementation plan must freeze exact key scope.

A key used against a different session must not replay another session's result.

---

# 68. Session + concurrency interaction

If both an idempotency key and expected session revision are present:

1. idempotency identity is validated;
2. canonical previously completed equivalent result may be replayed;
3. otherwise the current session revision is checked before mutation.

The implementation plan must freeze exact ordering for correctness.

---

# 69. HTTP route ownership

HTTP route modules own only:

- path/method;
- transport DTO parsing;
- application service invocation;
- public response serialization;
- HTTP status/header mapping;
- SSE adaptation.

They do not own business decisions.

Preferred pattern:


or a small set of Phase 11.3 application services.

# 71. HTTP app factory

or equivalent.

The app factory receives a fully composed backend/application gateway.

It must not construct canonical Domain/Agent/Provider owners itself.

- default to local-only binding;
- not embed secrets;
- not own application semantics.

No daemon/service manager work belongs to 11.3.

# 152. Public architecture summary

The canonical Phase 11.3 design is:

```text
Client
  |
  v
cmm/api  (HTTP / OpenAPI / SSE)
  |
  v
cmm/application  (public application semantics)
  |
  +--> ApplicationContainer
  |
  +--> Session canonical boundary
  |
  v
cmm/orchestration  (central request decision path)
  |
  v
existing canonical owners
```

No lower layer depends upward on `cmm/application` or `cmm/api`.

No transport handler owns domain logic.

No application service owns provider/model routing.

No missing future subsystem is fabricated to make the API look complete.
