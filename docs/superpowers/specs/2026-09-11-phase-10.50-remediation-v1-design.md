# 4. MAJOR-01 — Strict nested `default_privacy` validation

## 4.1 Audited defect

`DomainPrivacyPolicy.from_dict(...)` currently validates unknown fields only at the outer `DomainPrivacyPolicy` level and then delegates:

```python
PrivacyMetadata.from_mapping(mapping["default_privacy"])
```

Canonical Phase 8 `PrivacyMetadata.from_mapping(...)` is intentionally tolerant of unknown fields and does not apply the Domain declarative credential-key filter to nested `metadata`.

Therefore a Domain Pack can currently provide a nested payload such as:

```python
{
    "policy": "remote_allowed",
    "allow_remote": True,
    "allow_cross_domain": True,
    "metadata": {
        "api_key": "secret-value",
    },
}
```

where:

- `allow_cross_domain` is silently ignored instead of rejected;
- `metadata.api_key` survives the canonical mapping path.

The direct constructor path also accepts:

```python
DomainPrivacyPolicy(
    ...,
    default_privacy=PrivacyMetadata(
        ...,
        metadata={"api_key": "..."},
    ),
)
```

because the Domain wrapper validates only its own `metadata`.

This violates the Phase 10.50 fail-closed declarative boundary.

---

## 4.2 Architectural decision for MAJOR-01

**Do not change global Phase 8 `PrivacyMetadata.from_mapping(...)`.**

Phase 8 remains authoritative and unchanged.

Instead, Phase 10.50 owns strictness at its **Domain declaration adapter boundary**.

`cmm/domains/privacy_policy_contracts.py` must add a private validation layer that understands the exact canonical serialized `PrivacyMetadata` field set and validates nested declarative data before delegating to Phase 8.

Conceptually:

```text
raw Domain Pack mapping
    ↓
DomainPrivacyPolicy nested strict validator
    ↓
canonical PrivacyMetadata.from_mapping(...)
```

For direct constructor use:

```text
canonical PrivacyMetadata instance
    ↓
DomainPrivacyPolicy validation of safe metadata boundary
    ↓
accepted or rejected
```

No duplicate privacy decision logic is introduced.

---

## 4.3 Exact nested field allowlist

The remediation implementation must derive and freeze the exact current canonical serialized field set from `PrivacyMetadata.to_dict()` / the actual current Phase 8 contract.

The Domain adapter must reject any unknown key before canonical deserialization.

The implementation plan must inspect the actual Phase 8 serializer first and then encode that exact set in the Domain adapter.

The validation is against **serialized contract fields**, not arbitrary Python attributes.

If the current canonical serialized fields are, for example:

```text
schema_version
policy
sensitivity
allowed_processing_locations
allowed_providers
prohibited_providers
allow_remote
allow_premium
allow_cache
allow_export
requires_redaction
requires_approval
inherited_from
permissions
permissions_denied
metadata
```

then those exact fields and only those fields are accepted.

The implementation must use the exact repository truth discovered at remediation time.

No field named:

```text
allow_cross_domain
cross_domain
provider_routing
model
api_key
token
credential
secret
```

may be accepted as an unknown extension.

Unknown nested fields fail closed.

---

## 4.4 Nested metadata secret rejection

The existing recursive sensitive-key predicate in `privacy_policy_contracts.py` must also apply to:

```python
default_privacy.metadata
```

This protection must exist for both:

1. declarative `from_dict()` / Domain Pack input;
2. direct construction using an already-instantiated canonical `PrivacyMetadata`.

The nested metadata remains allowed to contain ordinary JSON-safe non-sensitive metadata.

Examples that must be rejected recursively:

```text
api_key
apikey
access_key
secret
secret_key
password
token
auth_token
credentials
nested.credentials
list[*].token
```

Use the already-established Phase 10.50 sensitive-key vocabulary and recursion.

Do not create a second unrelated secret vocabulary.

---

## 4.5 Error semantics

Malformed nested declaration input must fail as the existing Phase 10.50 serialization/contract error family:

```text
DomainPrivacyPolicyContractError
DomainPrivacyPolicySerializationError
```

Use the existing `field` / `details` conventions.

Unknown nested privacy fields should identify:

```text
field=default_privacy
details={"unknown_fields": [...]}
```

or the closest existing compatible error shape.

Credential-like nested metadata must identify the nested privacy metadata boundary without exposing the credential value in the error.

Never include the secret value in an exception message/details.

# 5. MAJOR-02 — Canonically bound privacy-decision trace evidence

## 5.1 Audited defect

Phase 10.50 V1 added:

```python
DomainTraceReferenceKind.PRIVACY_DECISION
```

but tests manually created:

```python
DomainTraceReference(
    ref_id="privacy-decision:1",
    kind=DomainTraceReferenceKind.PRIVACY_DECISION,
    domain_id="domain:health",
)
```

or:

```python
ref_id=f"privacy-decision:{health_resource.id}"
```

without a production path that binds the reference to the actual result of:

```python
evaluate_privacy_operation(...)
```

The tests also proved that status/reason were not inline, but did not prove that those values were recoverable from safe authoritative evidence.

A free-form `ref_id` is not sufficient evidence.

---

## 5.2 Existing canonical trace seam

The audited repository already provides:

```text
cmm/domains/trace_contracts.py
    DomainTraceReferenceKind
    DomainTraceReference
    DomainResultTraceReference
    CrossDomainTraceReference
    DomainTraceReferenceInventory
    DomainTraceValidationCode

cmm/domains/trace_validation.py
    DefaultDomainTraceReferenceValidator
```

`DomainTraceReferenceInventory` is the existing external authoritative typed inventory used by the validator.

This is the correct extension point.

Do not create a new trace subsystem.

---

## 5.3 Architectural decision for MAJOR-02

Add one small immutable safe evidence contract to the existing trace contract layer:

```python
PrivacyDecisionTraceEvidence
```

The exact name may be adjusted only to match repository naming conventions, but the responsibility must remain exactly as defined here.

It represents a **safe audit projection** of one real canonical `PrivacyDecision`.

It is not:

- a second privacy decision;
- an authorization decision;
- a persistence store;
- a resolver;
- an evaluator;
- a copy of `PrivacyMetadata`;
- a raw operation context dump.

---

## 5.4 Safe evidence fields

The evidence contract may contain only:

```text
decision_id
domain_id
operation
allowed
status
reason_code
requires_redaction
requires_approval
excluded
```

where:

- `domain_id` is canonical `DomainId`;
- `operation` is canonical `PrivacyOperation`;
- `status` is canonical `PrivacyDecisionStatus`;
- `reason_code` is the canonical machine-safe reason code;
- booleans come directly from the canonical `PrivacyDecision`.

Do not include:

```text
PrivacyDecision.reasons
PrivacyDecision.metadata
PrivacyMetadata
PrivacyOperationContext.actor_id
PrivacyOperationContext.provider_id
prompt text
resource contents
source documents
user text
provider request/response payloads
chain of thought
secrets
credentials
tokens
```

The evidence is intentionally minimal.

---

## 5.5 Deterministic content-addressed decision identity

`decision_id` must be deterministic and content-addressed from the safe evidence fields other than `decision_id`.

Conceptually:

```python
payload = {
    "domain_id": str(domain_id),
    "operation": operation.value,
    "allowed": decision.allowed,
    "status": decision.status.value,
    "reason_code": decision.reason_code,
    "requires_redaction": decision.requires_redaction,
    "requires_approval": decision.requires_approval,
    "excluded": decision.excluded,
}

digest = sha256(canonical_json(payload))
decision_id = f"privacy-decision:{digest[:24]}"
```

Use the repository's existing canonical JSON / identifier helpers where available.

Requirements:

1. same safe evidence => same ID;
2. any safe audited decision-state change => different ID;
3. no raw sensitive input contributes to the serialized evidence payload;
4. no arbitrary caller-supplied free-form decision ID;
5. ID is canonical and deterministic.

---

## 5.6 Real production binding helper

Provide one small pure production helper that binds:

```text
domain_id
operation
PrivacyDecision
```

to:

```text
PrivacyDecisionTraceEvidence
DomainTraceReference(kind=PRIVACY_DECISION)
```

The helper may be a constructor/classmethod on the evidence contract or a tiny function in the existing trace contract layer.

Conceptually:

```python
evidence = PrivacyDecisionTraceEvidence.from_privacy_decision(
    domain_id=...,
    operation=...,
    decision=real_privacy_decision,
)

reference = evidence.to_reference()
```

The returned reference must be:

```python
DomainTraceReference(
    ref_id=evidence.decision_id,
    kind=DomainTraceReferenceKind.PRIVACY_DECISION,
    domain_id=evidence.domain_id,
)
```

No test may manually invent the ID for the connected acceptance path.

## 5.7 Authoritative inventory integration

Extend the existing:

```python
DomainTraceReferenceInventory
```

additively with:

```python
privacy_decisions: tuple[PrivacyDecisionTraceEvidence, ...] = ()
```

Requirements:

1. deterministic ordering;
2. strict serialization;
3. strict deserialization;
4. no duplicate `decision_id`;
5. each `privacy_decisions[*].decision_id` must correspond to exactly one inventory `DomainTraceReference` with:
   - same `ref_id`;
   - kind `PRIVACY_DECISION`;
   - same `domain_id`;
6. each inventory reference of kind `PRIVACY_DECISION` must have exactly one matching `privacy_decisions` evidence item;
7. orphan evidence fails closed;
8. unbound privacy reference fails closed;
9. mismatched domain fails closed;
10. wrong kind fails closed.

This turns the existing external inventory into the authoritative resolver of privacy-decision audit evidence.

No store is introduced.
