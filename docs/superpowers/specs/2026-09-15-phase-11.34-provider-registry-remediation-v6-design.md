## 1. Purpose

Remediation V6 exists only to close the single finding reported by Independent Re-audit V6:

```text
MAJOR-V6-01
```

The defect is confined to:

```text
ModelRouteCatalog.restore_all(...)
```

`restore_all()` currently conflates two semantically different operations:

```text
A. exact rollback of an already-established route binding
B. creation or rebinding of a route relation
```

The V5 architecture already established the correct authority rule for new route relations:

```text
new relation
→ connection must exist
→ connection must still be bound to the current ProviderSpec
→ current connection-registration marker must exist
```

That rule is already enforced by:

```text
ModelRouteCatalog.register(...)
ModelRouteCatalog.restore(...)
ModelRouteCatalog._current_connection_registration(...)
```

but `restore_all()` bypasses it.

The approved V6 design completes that route-authority boundary without changing persistence architecture, without creating another restore API, and without weakening rollback semantics.

## 3. Architectural classification

Remediation V6 is a findings-only architectural correction.

The code delta is expected to be small, but `restore_all()` is a canonical authority boundary because it decides whether a route relation:

```text
keeps an existing exact authority binding
```

or:

```text
creates/rebinds to current authority
```

That distinction must be explicit and deterministic.

## 4. Approved solution

For every incoming route:

```text
existing = current entry with same route_id, if any
```

Then:

```text
IF existing exists
AND existing.route.connection_id == incoming.connection_id:
    preserve existing.registration

ELSE:
    registration =
        _current_connection_registration(
            incoming.connection_id
        )
```

The input route is then stored with the selected registration.

This is the complete V6 authority rule.

## 5. Same relationship versus new relationship

The design distinguishes relationship identity using:

```text
route_id
connection_id
```

### 5.1 Same relationship

A route represents the same previously-established relation only when:

```text
existing.route.route_id == incoming.route_id
AND
existing.route.connection_id == incoming.connection_id
```

Because route ids are canonicalized inside `ModelRoute`, route-id lookup uses the existing normalized key behavior.

In this same-relationship case:

```text
existing.registration
```

must be preserved exactly.

Do not re-resolve the current connection registration.

Do not test whether the provider authority is currently valid.

Do not silently repair or rebind the route.

The purpose is rollback fidelity.

### 5.2 New relationship

A relation is new when:

```text
no existing route with the incoming route_id
```

This includes restoring a route into an empty catalog.

A new relationship must resolve through:

```python
_current_connection_registration(
    incoming.connection_id
)
```

Therefore it requires:

```text
connection exists
connection remains bound to current ProviderSpec
current connection-registration marker exists
```

### 5.3 Rebinding relationship

A relation is also new when:

```text
existing route_id matches
BUT
existing.route.connection_id != incoming.connection_id
```

This is not rollback.

It is a rebind.

The incoming connection must resolve through:

```python
_current_connection_registration(
    incoming.connection_id
)
```

If the incoming connection is current and authorized:

```text
rebind is accepted
binding becomes the current marker of the incoming connection
```

If the incoming connection is missing or stale:

```text
operation is rejected
```

## 6. Why connection-id equality does not weaken exact authority

The V4 architecture deliberately binds a route to an opaque in-memory connection-registration marker.

V6 does not replace that exact marker with connection-id equality.

The comparison:

```text
existing.route.connection_id == incoming.connection_id
```

is used only to classify the operation as:

```text
same historical relationship
```

versus:

```text
new/rebound relationship
```

If the same connection id has since been removed and re-registered under a new registration marker:

```text
same route id
same connection id
```

still means rollback of the same historical route relation.

Therefore:

```text
existing.registration
```

must remain preserved.

That is exactly what prevents rollback from silently rebinding a stale route to a same-id replacement connection.

## 9. Exact rollback required behavior

Given:

```text

  route_id=logical-route
  connection_id=x:main

```

```text

```

Then:

```text

```

```text

```

Rollback is restoring the exact historical relation, not authorizing a new one.

## 10. Atomicity

`restore_all()` must remain all-or-nothing.

The method must continue to:

```text
build a temporary entries mapping
validate the entire iterable
assign self._routes only after every entry succeeds
```

If any item fails because of:

```text
wrong type
naive timestamp
duplicate route id
unknown connection
stale provider-bound connection
invalid rebind
```

then:

```text
self._routes
```

must remain exactly unchanged.

No partial replacement is permitted.

## 31. Minimal implementation shape

The preferred implementation is conceptually:

```python
entries: dict[str, _RouteBinding] = {}

for route in routes:
    validate route type/timestamps
    reject duplicate route_id in incoming entries

    existing = self._routes.get(route.route_id)

    if (
        existing is not None
        and existing.route.connection_id == route.connection_id
    ):
        registration = existing.registration
    else:
        registration = self._current_connection_registration(
            route.connection_id
        )

    entries[route.route_id] = _RouteBinding(
        registration=registration,
        route=route,
    )

self._routes = entries
```

Exact formatting may follow repository style.

Do not call `_current_connection_registration()` before determining whether the entry is exact rollback, because exact rollback must remain possible under stale parent authority.

## 36. Same route/current connection rebind semantics

If:

```text
existing route id matches
incoming connection id differs
incoming connection is current
```

V6 chooses:

```text
accept coherent rebind
```

rather than unconditional rejection.

Reason:

- `restore_all()` remains a full-state replacement API;
- its public contract is broader than rollback;
- the route value explicitly declares the incoming connection;
- current authority can be resolved safely;
- rejecting every connection change would unnecessarily narrow existing behavior.

This is the canonical V6 decision.

## 38. Historical stale rollback semantics

