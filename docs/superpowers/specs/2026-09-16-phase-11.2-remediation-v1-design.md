## 1. Purpose

This remediation corrects exactly two independently reproduced architectural
defects in Phase 11.2:

```text
MAJOR_01=UNSAFE_ORCHESTRATION_ROLE_RUNTIME_CONTRACTS
MAJOR_02=CANONICAL_AGENT_AUTHORITY_NOT_ENFORCED
```

The remediation does not redesign Phase 11.2.

It does not add capabilities.

It tightens the existing orchestration boundary so that:

```text
a service can only occupy its intended orchestration role
+
canonical collaborators are actually canonical at runtime
```

The remediation principle is:

```text
make identity explicit
without creating new ownership infrastructure
```

## 2. Governing evidence

The remediation is based on the committed independent audit:

```text
docs/audits/phase-11.2-orchestration-layer-independent-audit-v1.md
```

The audit independently reproduced two failures.

### MAJOR-01

Two different runtime-checkable Protocol roles could satisfy each other because
both exposed a method named:

```text
route
```

Specifically:

```text
DomainRouter
AgentRouter
```

could be cross-wired.

The Phase 11.1 `ApplicationContainer` could reach:

```text
READY
```

with the wrong role implementation bound, and the failure appeared only on the
first real orchestration request.

### MAJOR-02

`CanonicalAgentRouter` accepted:

```text
registry_service: Any
```

and trusted any object exposing:

```text
resolve_agent(...)
```

A fake registry service could return:

```text
agent_id="forged.agent"
```

and the router would accept it as canonical agent selection.

The remediation must eliminate both behaviors.

## 5. Root cause — MAJOR-01

The problem is not the closed Phase 11.1 runtime contract system.

The problem is that Phase 11.2 supplied non-discriminating structural runtime
contracts to that system.

Current conceptual forms:

```python
@runtime_checkable
class DomainRouter(Protocol):
    def route(...): ...

@runtime_checkable
class AgentRouter(Protocol):
    def route(...): ...
```

At runtime, Protocol conformance checks member presence rather than full callable
signature compatibility.

Therefore:

```text
has route
```

is enough to satisfy both roles.

This means:

```text
role identity != method name presence
```

and the Phase 11.2 runtime boundary is unsafe.

---

## 6. Selected remediation for MAJOR-01

Rename the two role methods so the protocols become runtime-discriminating by
construction.

Required public protocol methods:

```python
class DomainRouter(Protocol):
    def route_domain(...): ...

class AgentRouter(Protocol):
    def route_agent(...): ...
```

Official implementations must expose:

```text
CanonicalDomainRouter.route_domain(...)
CanonicalAgentRouter.route_agent(...)
```

The Orchestrator must call those explicit role methods.

There must not remain a generic public:

```text
route(...)
```

compatibility method on these two official implementations.

Phase 11.2 is not closed, so preserving the unsafe ambiguous API would preserve
the defect.

---

## 7. Why role-method differentiation is preferred

Three approaches were evaluated.

### 7.1 Role markers

Example:

```text
__orchestration_role__ = "domain_router"
```

Rejected as primary design because the marker can be copied or lied about by an
unrelated implementation.

It adds metadata without making behavior itself discriminating.

### 7.2 Nominal inheritance hierarchy

Example:

```text
class DomainRouterBase(ABC)
class AgentRouterBase(ABC)
```

Rejected because it would unnecessarily force inheritance and reduce adapter
flexibility across the orchestration package.

### 7.3 Distinct role methods

Selected:

```text
route_domain
route_agent
```

because:

- runtime Protocol checking becomes meaningfully discriminating;
- the method names describe the role;
- adapters remain possible;
- no new registry/framework is required;
- Phase 11.1 `runtime_contract` enforcement becomes useful again;
- cross-role objects fail before `READY`.

## 10. Direct Orchestrator construction

Phase 11.2 must not rely exclusively on `platform_module.py` for role safety.

`Orchestrator.__init__()` must validate that injected collaborators satisfy the
intended runtime roles.

Required conceptual validation:

```text
intent_resolver        -> IntentResolver
context_resolver       -> ContextResolver
domain_router          -> DomainRouter
agent_router           -> AgentRouter
policy                 -> OrchestrationPolicy
decision_repository    -> OrchestrationDecisionRepository
event_sink             -> OrchestrationEventSink
```

A directly constructed Orchestrator with cross-wired roles must fail at
construction time.

This preserves correctness even outside `ApplicationContainer`.

## 11. Root cause — MAJOR-02

The current `CanonicalAgentRouter` constructor accepts an unrestricted
collaborator conceptually equivalent to:

```python
registry_service: Any | None
```

The router then trusts that object to implement:

```text
resolve_agent(...)
```

and treats its returned selection as canonical.

This makes canonical authority a naming convention rather than an enforced
runtime boundary.

---

## 12. Selected remediation for MAJOR-02

`CanonicalAgentRouter` must accept only the real canonical owner:

```text
cmm.agent_runtime.agent_registry_service.AgentRegistryService
```

or `None` where the route does not require agent selection.

The constructor must validate the collaborator immediately.

Required behavior:

```text
FakeRegistryService
→ TypeError before routing

real AgentRegistryService
→ accepted
```

The exact exception type may follow repository style, but failure must occur
before a fake authority can produce an agent selection.

## 14. Preserve legitimate adapters

This remediation distinguishes:

```text
role adapter
```

from:

```text
canonical authority owner
```

A role adapter may remain structural where the architecture deliberately allows
one.

But a component named `Canonical*Router` must not accept unrestricted
source-of-truth authority objects.

The selected rule is:

```text
outer orchestration role
→ may be Protocol-based if role identity is discriminating

inner canonical owner
→ must be a documented canonical concrete type or sanctioned canonical seam
```

## 16. CanonicalDomainRouter acceptance rule

The router must reject a fake authority for any collaborator that is supposed to
be canonical.

Examples:

```text
FakeDomainResolver
→ rejected if resolver is frozen as DefaultDomainResolver

FakeDomainRegistry
→ rejected if registry is frozen as DomainRegistry
```

Where Phase 10 explicitly defines a canonical adapter Protocol, a legitimate
implementation of that Protocol remains acceptable.

Every accepted seam must be documented.

## 17. Context session authority review

`DefaultContextResolver` must review its session-store seam.

The remediation must distinguish:

```text

```

```text

```

Acceptable authorities are the currently sanctioned canonical session-store
implementations, expected to include:

```text

```

or another current official implementation in the repository.

If `SessionStore` is itself a canonical runtime-checkable Protocol with a

Do not create a new Session Store interface.

## 18. ContextReferenceReader stays structural

`ContextReferenceReader` is intentionally not a source-of-truth authority.

It is a read-only orchestration adapter seam.

Therefore it may remain a structural Protocol if:

- it does not own state;
- it cannot mutate canonical sources;
- it returns safe references/projections;
- its role is discriminating;
- it cannot impersonate another orchestration role.

This is a deliberate exception and must be documented.

## 41. Final remediation design summary

Remediation V1 changes no architectural ownership.

It makes two existing promises enforceable:

```text
orchestration role identity
```

by replacing ambiguous:

```text
route
```

with explicit:

```text
route_domain
route_agent
```

and:

```text
canonical agent authority
```

by rejecting noncanonical registry services before routing.

The selected fix is intentionally narrow:

```text
explicit role methods
+
explicit canonical owner validation
+
permanent reproducer tests
+
no new infrastructure
```

That is sufficient to address both Audit V1 MAJOR findings without reopening
Phase 11.2 architecture.
