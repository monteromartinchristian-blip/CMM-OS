# 1. Purpose

Phase 10.40 integrates Domain Intelligence with the already-complete Phase 8 Cognitive Layer without duplicating cognitive ownership.

The phase exists to make Domain specialization affect cognitive execution through canonical Phase 8 contracts and services while preserving one shared:

- Knowledge Model;
- Knowledge Store;
- Knowledge Graph;
- reasoning infrastructure;
- contradiction model;
- temporal model;
- confidence model;
- information-gap model;
- question-generation authority;
- cognitive trace;
- session model;
- memory-update proposal model.

Domains contribute specialization inputs only.

They do not become independent cognitive runtimes.

---

# 2. Normative source requirement

The Phase 10 roadmap defines the Phase 10.40 objective as:

> Use all Phase 8 infrastructure without duplicating cognitive logic.

Domains contribute:

# 4. Architectural classification

Phase 10.40 is an architectural integration phase.

It connects two mature subsystems:

```text
Domain Intelligence
↕
Cognitive Layer
```

while preserving their existing authority boundaries.

The phase must therefore define:

- a canonical one-way integration contract;
- translation of resolved Domain artifacts into Phase 8 cognitive inputs;
- invocation ordering;
- ownership rules;
- result adaptation;
- trace/reference semantics;
- fail-closed behavior;
- explicit non-ownership rules.

It must not redesign Phase 8.

# 5. Design Point

## DP-040 — Canonical Domain-to-Cognitive Integration Boundary

> Domain Intelligence specializes the existing Phase 8 Cognitive Layer only through resolved domain resources, profiles, rules, priorities, permissions and presentation configuration. All knowledge, reasoning, information-gap, question, contradiction, temporality, confidence, cognitive trace, session and memory-update-proposal authority remains owned by the canonical Phase 8 infrastructure. Integration is one-way from `cmm.domains` into public `cmm.cognitive` contracts and services; `cmm.cognitive` must not depend on `cmm.domains`.

DP-040 is satisfied only if all of the following are true:

1. Domain resolution and composition happen before cognitive execution.
2. Domain profile/resource/rule specialization is translated into canonical Phase 8 inputs.
3. Cognitive reasoning is executed by existing Phase 8 owners.
4. Global rules remain global and are not overridden by Domain rules.
5. Domain rules augment specialization but do not create a second reasoning engine.
6. Information gaps are produced through canonical cognitive infrastructure.
7. Questions are produced through canonical cognitive infrastructure.
8. Contradiction handling remains canonical.
9. Temporality remains canonical.
10. Confidence remains canonical.
11. Cognitive trace ownership remains canonical.
12. Domain Trace references cognitive evidence; it does not become a second cognitive trace.
13. Session authority remains canonical and no parallel cognitive session is introduced.
14. Memory updates remain proposals under canonical ownership; Phase 10.40 does not directly persist cognitive memory.
15. No dependency from `cmm.cognitive` to `cmm.domains` is introduced.
16. No Agent Runtime dependency is required to use the Phase 10.40 boundary.
17. No parallel Cognitive Layer or cognitive owner is introduced.

# 7. Dependency direction

The integration direction is strictly:

```text
cmm.domains
    ↓
public cmm.cognitive contracts / services
```

Forbidden:

```text
cmm.cognitive
    ↓
cmm.domains
```

The Cognitive Layer must remain domain-agnostic.

Domain concepts must be adapted before crossing the boundary.

Phase 8 must not learn about:

- `DomainDefinition`;
- `DomainComposition`;
- `ResolvedDomainProfile`;
- `DomainResourceDefinition`;
- `DomainPermissionPolicy`;
- `DomainPresentationPolicy`;
- `DomainTrace`;
- Domain Pack manifests.

This preserves the shared cognitive substrate for non-Domain callers.

# 8. Recommended integration shape

Phase 10.40 should add a thin integration boundary under `cmm/domains`.

The likely architecture is:

```text
Domain resolution/composition artifacts
            ↓
Domain → Cognitive integration request
            ↓
thin Domain integration service/adapter
            ↓
canonical Phase 8 contracts/services
            ↓
canonical cognitive result/evidence
            ↓
Domain presentation + Domain trace references
```

The exact class/function names are implementation-plan decisions.

This spec intentionally does not mandate a new large subsystem name.

Any new production abstraction must be:

- small;
- stateless unless canonical state is injected;
- deterministic at the translation boundary;
- dependency-injected;
- testable with official in-memory Phase 8 implementations;
- incapable of becoming a second cognitive runtime.

---

# 9. Required input boundary

The Domain-to-Cognitive boundary may consume only already-resolved Domain artifacts.

It must not redo:

- domain discovery;
- domain resolution;
- domain composition;
- profile composition;
- resource registry ownership;
- permission resolution;
- session persistence.

A canonical integration request should be able to reference or contain the minimum necessary resolved artifacts, such as:

- selected/resolved Domain identity;
- `DomainComposition`;
- resolved effective Domain profile;
- resolved Domain resources;
- selected Domain reasoning rules;
- permission/approval outcome required for cognitive access;
- canonical session reference/context;
- correlation/trace identifiers;
- user/task/request payload as an existing canonical cognitive input shape or adapter input.

The implementation plan must minimize duplication in this request.

# 10. Domain profile adaptation

Domain profiles specialize cognition but do not replace cognitive policy.

The integration must translate relevant profile fields into canonical cognitive configuration.

Potential specialization inputs include existing Domain profile concepts such as:

- reasoning depth;
- risk tolerance;
- evidence expectations;
- temporal policy;
- uncertainty handling;
- sensitivity;
- presentation policy;
- priority/order metadata.

Rules:

1. Only fields with a canonical Phase 8 target may cross the boundary.
2. Unsupported Domain profile fields must remain Domain-side.
3. Domain profile values must not weaken mandatory global cognitive validation.
4. Domain profile adaptation must be explicit and testable.
5. No hidden free-form dictionary may silently redefine cognitive behavior.

---

# 11. Domain resource adaptation

Domain resources must be loaded through existing Domain resource resolution, then adapted to Phase 8 resource/knowledge inputs.

The adapter must preserve:

- resource identity;
- source/provenance;
- sensitivity;
- temporal policy;
- permissions;
- integrity/validation state;
- authoritative Domain where relevant;
- reference identity for tracing.

The adapter must not:

- persist directly into a Knowledge Store without canonical cognitive handling;
- discard provenance;
- convert uncertain/inferred content into facts;
- bypass Phase 8 privacy or validation;
- create a Domain-owned Knowledge Store.

---

# 12. Rule integration

Phase 10 already contains Domain reasoning-rule contracts based on Phase 8 reasoning-rule contracts.

Phase 10.40 must formalize execution ordering.

Required ordering:

```text
canonical global reasoning rules
→ selected Domain reasoning rules
→ canonical reasoning/result aggregation
```

Domain rules must not:

- replace the global reasoning registry;
- disable mandatory global rules;
- instantiate a separate reasoning engine;
- introduce incompatible result contracts;
- bypass contradiction, temporal, confidence or validation logic.

If existing Domain rule execution already uses `DefaultReasoningRuleEngine`, Phase 10.40 must reuse that path rather than wrap it in another engine.

---

# 13. Permissions

Domain specialization cannot grant cognitive authority.

Before a Domain-provided resource/rule/configuration is used, the canonical Domain permission/trust boundary must already permit that contribution.

Phase 10.40 may propagate or enforce permission outcomes, but must not create:

- a cognitive permission registry;
- an alternate Domain permission system;
- implicit authority based on Domain activation;
- trust inferred from Domain content.

Phase 10.38 invariants remain binding.

---

# 14. Information gaps and questions

Domains may supply specialized evidence or rules that influence what becomes a gap.

Domains must not own gap detection.

Required ownership:

```text
Domain specialization input
→ canonical Cognitive Layer reasoning
→ canonical gap detection
→ canonical question generation
```

Forbidden Domain-side owners include:

```text
DomainGapAnalyzer
DomainInformationGapEngine
DomainQuestionEngine
DomainInteractiveQuestionEngine
```

or equivalent parallel systems.

Domain presentation may control how a canonical question is shown, not whether a parallel question model exists.

---

# 15. Contradictions

Contradictions remain canonical Phase 8 knowledge/cognitive artifacts.

Domain rules may contribute:

- evidence;
- specialized interpretation;
- domain-specific constraints;
- rule findings.

They must not introduce an incompatible contradiction model.

Existing Domain conflict types remain Domain composition/selection/presentation conflicts and must not be silently treated as Phase 8 knowledge contradictions unless an explicit adapter exists.

---

# 16. Temporality

Temporal reasoning remains canonical.

Domain temporal policies may specialize:

- acceptable freshness;
- expected validity windows;
- domain-specific review expectations.

They must adapt into existing cognitive temporal semantics.

They must not create a second temporal truth model.

A Domain-specific rule may report a temporal finding, but canonical knowledge validity remains owned by Phase 8 contracts.

---

# 17. Confidence and uncertainty

Phase 8 `Confidence` and cognitive uncertainty semantics remain authoritative.

Domain-specific profiles/rules may:

- influence confidence inputs;
- request stricter thresholds;
- emit findings that affect confidence through canonical mechanisms.

They must not create an incompatible confidence scale or silently overwrite canonical confidence.

Presentation must preserve:

- confidence;
- uncertainty;
- warnings;
- contradictions;
- provenance;
- approval state where relevant.

---

# 18. Cognitive trace vs Domain Trace

These are different responsibilities.

## Cognitive trace

Owned by canonical cognitive infrastructure.

Represents structured cognitive evidence/reference data.

## Domain Trace

Owned by Domain Intelligence.

Represents:

- selected Domains;
- Domain contributions;
- Domain result references;
- cross-domain references;
- presentation/result linkage.

The Domain Trace must reference cognitive artifacts by stable typed references where available.

It must not:

- copy hidden chain-of-thought;
- duplicate full cognitive trace content;
- invent a parallel cognitive trace schema;
- become the canonical reasoning trace.

---

# 19. Sessions

Phase 10.40 must not create parallel cognitive sessions.

Existing Domain session contracts must remain an extension/view over the shared session infrastructure.

Any cognitive session/context required by Phase 8 must use the existing canonical session owner.

Required invariant:

```text
one shared session authority
+
Domain-specific session extension/reference data
```

Forbidden:

```text
DomainCognitiveSessionStore
DomainReasoningSessionRuntime
parallel cognitive session persistence
```

---

# 20. Memory update proposals

Phase 10.40 must not directly write cognitive memory as a side effect of reasoning.

If reasoning produces durable-memory candidates, they remain proposal/reference artifacts under existing canonical ownership.

Phase 10.40 may carry:

- proposal references;
- Domain provenance;
- Domain authority metadata;
- justification references.

It must not:

- persist a proposal as fact;
- bypass approval/permission;
- write directly to cognitive stores;
- create Domain-owned memory-update execution.

The Phase 9 `MemoryUpdateProposal` implementation remains outside Phase 10.40 ownership.

# 22. Relationship to Cross-Domain Engine

Existing cross-domain cognitive ports are evidence of prior integration patterns.

They must not become the general owner of Phase 10.40.

The Cross-Domain Engine remains responsible for cross-domain coordination.

Phase 10.40 establishes the general Domain Intelligence → Cognitive Layer boundary usable for:

- one resolved Domain;
- composed multi-Domain contexts;
- callers other than the Cross-Domain Engine.

No duplication of the Cross-Domain Engine is allowed.

# 23. Error and fail-closed model

Integration must fail closed when mandatory translation cannot be proven safe.

Examples:

- unresolved/blocked Domain composition;
- invalid resolved profile;
- rejected resource;
- permission denial;
- incompatible cognitive adapter input;
- missing mandatory provenance;
- invalid temporal metadata;
- invalid sensitivity metadata;
- invalid canonical rule contract;
- unsupported mandatory profile setting;
- broken cognitive result/reference integrity.

Failure must use existing exception/result conventions where practical.

Do not introduce an opaque catch-all error architecture.

No partial cognitive execution should occur after a mandatory precondition has failed.

---

# 24. Determinism

The integration boundary must be deterministic for equivalent:

- Domain resolution;
- Domain composition;
- resolved profile;
- resolved resources;
- selected rules;
- permissions;
- cognitive input;
- injected canonical services.

Ordering must be stable.

Any generated identifiers must use existing canonical deterministic/ID conventions where required.

# 40. Design decision summary

The approved Phase 10.40 architecture is:

```text
RESOLVE DOMAIN
→ COMPOSE DOMAIN
→ RESOLVE PROFILE / RESOURCES / RULES / PERMISSIONS
→ THIN DOMAIN→COGNITIVE ADAPTATION
→ EXISTING PHASE 8 COGNITIVE INFRASTRUCTURE
→ CANONICAL COGNITIVE RESULT / GAPS / QUESTIONS / CONFIDENCE / TEMPORALITY / CONTRADICTIONS
→ DOMAIN PRESENTATION
→ DOMAIN TRACE REFERENCES
```

Ownership stays:

```text
Domain specialization = Phase 10
Cognitive reasoning authority = Phase 8
Agent orchestration = Phase 9 / future Phase 10.41 integration
```

This is the central invariant of DP-040.
