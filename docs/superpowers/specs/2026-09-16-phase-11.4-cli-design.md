# 1. Purpose

Phase 11.4 turns the already-existing CMM OS command-line surfaces into one
stable operational interface for development, administration, automation and
advanced use.

This phase is **not** a greenfield CLI implementation.

The repository already contains:

```text
pyproject.toml
    [project.scripts]
    cmm = "cmm.cli:main"

cmm/cli.py
cmm/__main__.py
kernel/cli.py

cmm/validation/cli.py
cmm/domains/sdk/cli.py

cmm/agent_runtime/agent_runtime_cli.py
cmm/agent_runtime/agent_runtime_cli_app.py
cmm/agent_runtime/agent_runtime_cli_commands.py
cmm/agent_runtime/agent_runtime_cli_context.py
cmm/agent_runtime/agent_runtime_cli_errors.py
cmm/agent_runtime/agent_runtime_cli_formatters.py
cmm/agent_runtime/agent_runtime_cli_parsers.py
cmm/agent_runtime/agent_runtime_cli_result.py
```

Therefore Phase 11.4 is a consolidation and stabilization phase.

It must extend the existing canonical CLI rather than creating a second CLI
framework or a second command authority.

# 6. Functional identity

Requirement:

```text
F11-018 — Canonical Operational CLI
```

Definition:

> CMM OS shall expose one canonical, scriptable and human-usable command-line
> interface through the existing `cmm` console entrypoint and root `argparse`
> command tree. The CLI shall adapt to canonical application and subsystem
> contracts without becoming an execution, routing, storage, provider, domain,
> agent, workflow, validation, approval or configuration authority; shall
> preserve existing specialized CLI surfaces; shall reserve the roadmap's
> public namespace with explicit fail-closed unavailable capability behavior;
> and shall provide stable structured output and exit-code semantics suitable
> for automation and CI.

Design Point:

```text
DP-104 — Single-Front-Door Fail-Closed Operational CLI
```

Connected acceptance:

```text
AT-DP-104 — Canonical CLI Integration Acceptance
```

No other new Phase 11 requirement/DP/AT identifier is needed for 11.4.

# 7. Primary architectural decision

Phase 11.4 uses:

```text
ONE public CLI front door
        ↓
existing cmm console script
        ↓
cmm.cli:main
        ↓
existing cmm.__main__ argparse root
        ↓
thin CLI adapters
        ↓
canonical application/subsystem contracts
```

Not:

```text
new Typer app
new Click app
new second argparse root
new CommandRouter
new CommandRegistry
new command bus
new CLI service locator
new CLI runtime
```

---

# 8. Canonical public entrypoint

The existing package metadata remains authoritative:

```toml
[project.scripts]
cmm = "cmm.cli:main"
```

The public execution forms remain equivalent:

```text
cmm ...
python -m cmm ...
```

`cmm/cli.py` remains the console-script entrypoint.

`cmm/__main__.py` remains the root parser/dispatch surface.

Phase 11.4 must not create:

```text
cmm/cli/
```

because that would collide conceptually and structurally with:

```text
cmm/cli.py
```

fit.


CLI commands such as:


If a roadmap command has no canonical application/subsystem owner yet, it must
not be fabricated in the CLI.

# 17. Full namespace reservation decision

The user-approved Phase 11.4 rule is:

> Reserve the complete Phase 11.4 roadmap command namespace now, even when a
> backing capability is not yet implemented.

Therefore commands may exist before their backing authority exists.

Such commands must fail explicitly and safely.

They must never produce fake success.

---

# 18. Capability availability states

The CLI needs a presentation-level availability vocabulary.

Recommended values:

```text
AVAILABLE
UNAVAILABLE
DEFERRED
```

These values must not become a new platform capability registry.

They are CLI presentation results derived from existing canonical capability
evidence.

If Phase 11.3 `ApplicationCapability` already provides sufficient status
semantics, reuse it rather than defining a competing enum.

---

# 19. Unavailable capability behavior

A reserved command without a canonical owner must:

```text
parse successfully
identify the requested public capability
return a structured unavailable result
write no unauthorized side effects
use a stable non-zero exit code
emit no traceback by default
```

Example conceptual result:

```json
{
  "ok": false,
  "code": "CAPABILITY_UNAVAILABLE",
  "command": "backup.create",
  "message": "Backup is not available in this platform build."
}
```

The exact schema must be frozen in implementation planning.

---

# 20. No placeholder success

The following are forbidden:

```text
"not implemented yet" with exit 0
fake empty lists presented as operational success
creating temporary local stores just for CLI output
silently mapping unsupported commands to unrelated lower-level helpers
```

Unavailable means unavailable.

# 33. Status command

`cmm status` is a first-class Phase 11.4 command.

It should provide a safe operational summary based on canonical inspection and
application health/capability information.

It must not be a second health engine.

```text
platform state

```

Recommended structured output exposes the same semantics.

# 34. Doctor command

`cmm doctor` is a read-only diagnostic aggregator.

It is not an authority owner.

Doctor checks only evidence it can obtain from canonical owners.

Conceptual checks:

```text
configuration
database
storage
models
services
permissions
migrations
secrets
network
plugins
kernel state
```

Each check returns a stable diagnostic result.

---

# 35. Doctor status model

Recommended diagnostic states:

```text
PASS
WARN
FAIL
UNAVAILABLE
SKIPPED
```

The exact frozen enum/name may reuse existing validation/health concepts if
semantically compatible.

Doctor must distinguish:

```text
not configured
not implemented
unreachable
invalid
unsafe
healthy
```

instead of collapsing everything into success/failure.

---

# 36. Doctor side-effect rule

`cmm doctor` must be read-only by default.

It must not:

```text
repair configuration
migrate data
rotate credentials
install plugins
download models
mutate stores
restart services
change permissions
```

A future explicit repair command would require separate scope.

---

# 37. Doctor secrets rule

Doctor may verify the presence/shape/accessibility of secret configuration
without revealing secret values.

Forbidden output:

```text
API keys
tokens
passwords
secret-bearing environment dumps
raw credential-store payloads
```

---

# 38. Network diagnostics

Doctor may perform only bounded, explicitly scoped network checks supported by
canonical services.

Phase 11.4 must not make tests depend on live internet access.

Any network-facing check must be injectable/fakeable for tests.

# 39. Output architecture

Phase 11.4 introduces one shared CLI presentation seam.

It should normalize:

```text
human output
JSON output
YAML output
quiet mode
verbose mode
errors
exit codes
```

This is presentation infrastructure, not business authority.

---

# 40. Output modes

Canonical output selector:

```text
--output human
--output json
--output yaml
```

Default:

```text
human
```

If legacy command surfaces already use another output option shape, preserve
compatibility and converge only where safe.

---

# 41. JSON output

JSON mode must be:

```text
deterministic
machine-readable
UTF-8
single complete document unless streaming semantics explicitly require otherwise
no ANSI
no incidental logging on stdout
```

Errors in JSON mode must also be JSON.

---

# 42. YAML output

YAML mode must provide the same semantic fields as JSON.

Do not add a heavy YAML dependency unless repository evidence shows one already
exists or the implementation plan explicitly approves a minimal dependency.

Preferred options, in order:

1. reuse an existing YAML dependency if already canonical;
2. if absent, decide in implementation plan whether a small dependency is
   justified;
3. otherwise reserve `--output yaml` with explicit availability behavior until
   supported.

Do not hand-roll a general YAML serializer.

---

# 43. Human output

Human mode should be concise and readable.

It may use existing text formatting.

Phase 11.4 does not require a TUI framework.

Do not add:

```text
Textual
Rich
prompt_toolkit
```

solely for aesthetic output unless the plan proves a concrete requirement.

---

# 44. Quiet mode

Global:

```text
--quiet
```

Quiet means:

```text
suppress non-essential human commentary
preserve required command result
preserve errors
preserve exit status
```

For structured output modes, quiet must not remove required data fields.

---

# 45. Verbose mode

Global:

```text
--verbose
```

Verbose may expose:

```text
safe diagnostic detail
selected command path
safe capability status
timing metadata if already available
```

It must not expose:

```text
secrets
hidden reasoning
raw stack traces by default
sensitive internal context
live service objects
```

---

# 46. Stdout/stderr contract

Success payload/result:

```text
stdout
```

Diagnostics and errors:

```text
stderr
```

Structured success output must not be polluted by warnings/logging.

Structured error output should remain machine-readable when JSON/YAML mode is
selected.

---

# 47. Exit-code contract

Phase 11.4 must define stable exit codes.

Recommended conceptual categories:

```text
0   success
2   usage / parse error
3   invalid request / validation error
4   resource not found
5   capability unavailable / deferred
6   permission / approval denied
7   conflict / concurrency / idempotency conflict
8   dependency / service unhealthy
9   cancellation
10  internal failure
```

Exact numeric mapping must be frozen in the implementation plan and covered by
tests.

Do not reuse arbitrary HTTP status codes as process exit codes.

---

# 48. Application error mapping

Where the CLI calls `ApplicationGateway`, existing `ApplicationErrorCode`

Phase 11.4 maps those codes to:

```text

structured error envelope
```

It does not redefine application errors.

# 60. CLI channel semantics

Phase 11.2 already supports:

```text
OrchestrationChannel.CLI
```

If the Application Backend currently hardcodes the API channel for its HTTP
adapter path, Phase 11.4 must not bypass ApplicationGateway merely to set a CLI
channel.

The implementation plan must inspect whether ApplicationGateway has a
transport-neutral channel seam.

If a minimal application-level channel field is required, that is a controlled
Phase 11.3 compatibility extension and must preserve all DP-103 invariants.

No direct Orchestrator invocation is allowed merely to avoid that adaptation.

---

# 61. Application-boundary compatibility rule

If Phase 11.4 requires one minimal public application contract extension for
CLI context, the extension must:

```text
remain transport-neutral
remain versioned
not alter HTTP behavior
not expose new authority
keep AT-DP-103 green
```

Any such change must be explicit in the implementation plan and audited as an
inherited Phase 11.3 regression.

---

# 62. Cancellation

Roadmap expects cancellation.

Phase 11.3 currently exposes a public cancellation contract but may report it
unavailable.

Phase 11.4 must preserve that truth.

If cancellation capability is unavailable:

```text
CLI cancellation command/interaction fails explicitly
```

Do not create a background cancellation runtime in 11.4.

Interactive `Ctrl-C` should terminate the local CLI process cleanly without
claiming canonical remote/request cancellation succeeded.

---

# 63. Autocompletion

Roadmap expects autocompletion.

Phase 11.4 may satisfy this initially by exposing static completion metadata or
generating shell completion from the explicit parser tree.

It must not add a dynamic plugin discovery engine.

Supported shells should be scoped minimally.

The implementation plan must decide whether completion generation is feasible
without a new dependency.
