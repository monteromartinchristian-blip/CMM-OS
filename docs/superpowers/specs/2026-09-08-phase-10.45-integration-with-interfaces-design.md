## 1. Purpose

Phase 10.45 establishes the canonical integration boundary through which interfaces can consume Domain Intelligence state and submit interface-originated domain intents consistently.

The phase does **not** build a frontend. It does **not** implement CMMChat, SwiftUI, web views, navigation, rendering, streaming UI, styling, or a second application backend.

Its purpose is narrower and architectural:

> expose already-authoritative Domain Intelligence state through deterministic, immutable, permission-preserving, serializable interface projections, and provide a controlled command/intention seam for interface-originated domain-selection requests without creating new authority.

The boundary must be suitable for future use by:

- CMMChat;
- CLI surfaces;
- API surfaces;
- administrative tools;
- test harnesses;
- future platform interfaces.

Phase 11 may adapt this boundary to a concrete transport or UI, but Phase 10.45 itself remains independent of those concerns.

## 4. Design decision

Phase 10.45 will implement a **thin, stateless, interface-neutral integration layer inside `cmm.domains`**.

The layer will:

1. accept already-authoritative canonical Domain objects and references;
2. verify coherence between the supplied authority objects;
3. derive immutable interface-facing projections;
4. preserve canonical IDs and semantics instead of copying or reinterpreting upstream truth;
5. expose a small interface-intent seam for domain-selection actions;
6. delegate every authoritative change to existing canonical infrastructure;
7. fail closed when authority, identity, permission, visibility, status, or reference integrity cannot be proven.

It will not become:

- a UI framework;
- an application backend;
- an orchestrator;
- a presentation renderer;
- a session store;
- an approval engine;
- a permission engine;
- a workflow engine;
- a domain registry replacement;
- a metrics backend;
- an update service;
- a memory store;
- a knowledge store;
- a transport protocol;
- a websocket layer;
- an HTTP service.

## 5. Design Point

### `DP-045 — Canonical Domain Interface Integration`

**Requirement definition**

Domain Intelligence must expose one deterministic, permission-preserving, interface-neutral integration boundary through which conversational interfaces, domain selectors, domain-administration views, cross-domain views, and review surfaces can consume canonical Domain state and submit interface-originated domain-selection intents without duplicating resolution, composition, presentation, workflow, approval, permission, memory, knowledge, validation, observability, session, registry, loader, persistence, or execution authority.

Interface projections must:

- preserve canonical identities;
- preserve primary/supporting-domain authority;
- preserve provenance and source references;
- preserve epistemic semantics;
- preserve uncertainty;
- preserve contradictions;
- preserve confidence without strengthening it;
- preserve temporal validity;
- preserve approval requirements;
- preserve permission restrictions;
- preserve unavailable, disabled, degraded, partial, blocked, and pending states accurately;
- remain reference-oriented where upstream contracts are reference-oriented;
- reject incoherent or non-canonical authority fail-closed;
- never convert a proposal into an applied change;
- never convert pending approval into execution;
- never infer a new causal relation;
- never expose information that upstream policy did not authorize.

**Requirement source:** `SRC-R10:R10-C45`

The canonical requirements matrix currently ends at `DP-044`. During Phase 10.45 implementation documentation, the matrix must gain the `DP-045` row. Until independent audit PASS, that row must not claim closure or independent verification.

## 6. Architectural principle: interfaces consume authority; they do not create it

The core invariant is:

```text
Interface visibility != authority
Interface command != direct mutation
Interface projection != new source of truth
```

An interface may show authoritative state and may express a user intent.

It may not decide:

- which domain is actually authorized;
- whether a cross-domain transfer is permitted;
- whether an operation may execute;
- whether approval has been granted;
- whether a workflow is valid;
- whether memory may be persisted;
- whether knowledge is current;
- whether a contradiction is resolved;
- whether a domain is healthy;
- whether a domain update is safe;
- whether a sensitive resource may be disclosed.

Those decisions remain owned by existing canonical components.

## 7. Canonical infrastructure to reuse

Phase 10.45 must reuse the existing Domain Intelligence and shared-system contracts discovered in the repository.

At minimum, the implementation must integrate with the canonical equivalents of the following existing areas.

### 7.1 Domain resolution and composition

Reuse:

- `DomainResolutionContext`;
- `DomainResolutionResult`;
- canonical resolver implementation;
- `DomainComposition`;
- canonical composition engine;
- selection policies;
- conflict-resolution policies.

Phase 10.45 must not implement a second domain resolver or composition algorithm.

### 7.2 Domain registry and pack lifecycle

Reuse:

- Domain Registry;
- Domain Pack contracts;
- loader/discovery lifecycle;
- status/version/capability metadata;
- canonical health/degradation state.

Domain Center is a projection of this state, not a new registry.

### 7.3 Domain presentation

Reuse Phase 10.16 Domain Presentation.

Phase 10.16 remains responsible for reference-only presentation structure and visibility semantics after upstream resolution.

Phase 10.45 must not turn presentation contracts into a renderer or modify epistemic content.

The relation is:

```text
canonical result/state
        ↓
Domain Presentation authority
        ↓
Phase 10.45 interface projection
        ↓
future concrete renderer
```

### 7.4 Domain trace

Reuse Phase 10.17 Domain Trace.

The interface integration layer may surface trace references and attribution that are already authorized, but must not invent a second trace format or copy hidden/internal reasoning.

No private chain-of-thought is exposed by this phase.

### 7.5 Domain memory integration

Reuse Phase 10.18 domain memory view and proposal bindings.

Read, propose, approve, apply, invalidate, and delete remain separate capabilities.

Phase 10.45 may display memory-related references or proposal state only when authorized.

It must never interpret a proposal as persisted memory.

### 7.6 Domain API

Reuse the canonical `DefaultDomainAPI` facade and its established seams.

Any public Phase 10.45 integration point should extend the existing facade minimally rather than create a parallel `InterfaceAPI`, backend, controller tree, or transport layer.

### 7.7 Domain sessions

Reuse canonical Domain Session infrastructure.

The interface layer must not create an interface-owned session store.

If a selector request affects session-level domain preference/context, it must delegate through canonical session/selection mechanisms.

### 7.8 Domain operations and workflows

Reuse:

- canonical domain operation registry/contracts;
- shared Agent Runtime operation authority;
- canonical domain workflow registry/contracts;
- shared Workflow/Planner infrastructure;
- Phase 10.42 planner/workflow integration.

Interface projections may report current workflow/operation references and state.

Interface-originated requests may request an action, but Phase 10.45 must not execute operations or workflows directly.

### 7.9 Permissions and approvals

Reuse Phase 10.15 Domain Permissions and canonical Agent Runtime approval infrastructure.

The repository already contains approval contracts, repositories, and services. Phase 10.45 must not add:

- `InterfaceApprovalStore`;
- `DomainReviewStore`;
- a second approval queue;
- a new permission evaluator;
- a new autonomy policy.

Review Center is an aggregate **view** over canonical review-required references.

### 7.10 Validation

Reuse Phase 10.43 Domain Validation integration and the common Phase 7 validation infrastructure.

A Phase 10.45 projection may expose validation status/references where authorized, but cannot self-certify a domain pack, workflow, operation, or result.

### 7.11 Observability

Reuse canonical domain observability.

Metrics, errors, health, and degraded states shown in Domain Center must come from canonical observability/registry state.

Phase 10.45 must not implement a new telemetry store.

### 7.12 Memory and Knowledge Graph integration

Reuse Phase 10.44 `DefaultDomainMemoryKnowledgeIntegrator` and its projection contracts through the canonical Domain API seam.

Phase 10.45 must preserve:

- reference identity;
- resolved authority;
- temporal validity;
- provenance;
- relation kinds;
- contradictions;
- dependency paths;
- causal non-strengthening;
- proposal authority.

No Domain-owned knowledge graph, store, temporal engine, contradiction engine, or causal engine may be introduced.

## 9. Projection model

### 9.1 Root projection

A root projection should be content-bound to the exact canonical authority used to assemble it.

Conceptually:

```python
DomainInterfaceProjection(
    id="...",
    request_id="...",
    resolution_reference_id="...",
    composition_reference_id="...",
    session_reference_id=None,
    presentation_reference_id=None,
    conversational=...,
    selector=...,
    domain_center=...,
    cross_domain=...,
    review_center=...,
    generated_at="...",
    content_digest="...",
)
```

This is conceptual, not a mandatory exact schema.

The important invariants are:

- deterministic identity;
- deterministic ordering;
- exact resolution/composition binding;
- no hidden mutation;
- no invented authority;
- immutable output;
- JSON-safe serialization;
- stable canonical references.

If an upstream projection already provides a suitable digest/id binding, Phase 10.45 should reuse it rather than duplicate hashing logic unnecessarily.

## 10. Conversational Domain View

The conversational projection exists so any future conversational client can render Domain Intelligence context consistently.

It may expose, when authoritative and allowed:

- primary/active domain;
- supporting domains;
- workflow reference and state;
- pending question references;
- approval references;
- source/provenance references;
- confidence;
- contradiction references;
- result references;
- memory proposal references;
- relevant warnings;
- presentation sections/visibility directives already authorized upstream.

### 10.1 Prohibited behavior

The conversational projection must not:

- reveal all memory merely because it exists;
- reveal all supporting-domain data;
- downgrade sensitivity;
- hide contradictions required by presentation policy;
- strengthen confidence;
- convert hypotheses/inferences into facts;
- expose source content if only a source reference is authorized;
- claim a workflow completed if the canonical workflow is pending/failed/partial;
- claim memory was stored when only a proposal exists;
- render or generate final human prose as a new reasoning step.

Phase 11/CMMChat may render this projection visually.

## 11. Domain Selector

The Domain Selector is the only Phase 10.45 area that includes an interface-originated intent path rather than read-only projection alone.

Supported intent classes are limited to:

- request explicit primary-domain selection;
- request automatic resolution;
- request addition of a supporting domain;
- request withdrawal of a supporting domain;
- inspect/explain the canonical selection decision;
- request a domain-selection policy change through the existing policy authority.

### 11.1 No direct state mutation

The selector must not modify:

- `DomainResolutionResult`;
- `DomainComposition`;
- registry state;
- permission state;
- session state;
- policy state

by assignment or direct store access.

Instead:

```text
Interface intent
    ↓
validate intent contract
    ↓
delegate to existing canonical resolver / selection-policy / session authority
    ↓
receive canonical result
    ↓
return reference-bound intent result
```

### 11.2 Fail-closed rules

A selector intent must not:

- activate a disabled domain;
- upgrade a degraded/blocked domain to active;
- bypass a domain conflict;
- add a supporting domain without required permission;
- weaken the effective permission intersection;
- increase autonomy;
- treat denied cross-domain access as granted;
- bypass required clarification;
- silently replace the authoritative primary domain.

If the canonical authority rejects the request, Phase 10.45 returns the rejection state without reinterpretation.

## 12. Domain Center

Domain Center is a deterministic read projection over existing domain lifecycle and observability authority.

It may expose per-domain information such as:

- ID;
- display name where canonical;
- status;
- enabled/disabled state;
- version;
- kind;
- capabilities;
- permissions summary/references;
- registered operations;
- registered workflows;
- metrics references;
- errors/health findings;
- update availability only when supplied by an existing canonical source.

### 12.1 Update availability

Phase 10.45 must not introduce a domain update discovery engine merely to populate the roadmap field “available updates”.

If no current canonical component can authoritatively provide update availability, the projection must represent it as unavailable/unknown/not-supported rather than fabricate it.

Actual installation and update mechanics remain owned by the existing Domain Pack lifecycle and later platform integration.

## 13. Cross-Domain Interface View

The cross-domain view must project the already-resolved cross-domain state.

It may expose:

- primary domain;
- supporting domains;
- authorized transfer references;
- dependencies;
- conflicts;
- consolidated-result reference;
- partial/blocked status;
- cross-domain gaps where already canonical;
- relevant trace references.

### 13.1 Semantic preservation

The view must never:

- infer a dependency that upstream did not establish;
- convert correlation into causation;
- merge incompatible temporal periods;
- duplicate entities;
- disclose denied transfer content;
- suppress an unresolved conflict merely to present a cleaner view.

Relations and dependency kinds should use canonical enums/IDs from upstream systems.

---

## 14. Review Center View

Review Center is an aggregation surface, not a review authority.

It may expose references to canonical pending/review-required items in categories including:

- operation approval;
- multi-domain access;
- domain installation;
- domain upgrade;
- sensitive persistence;
- external action;
- unresolved conflict.

Each entry must preserve, where canonical:

- review/approval reference ID;
- category;
- current state;
- requested capability/action;
- originating domain;
- workflow/operation/session references;
- reason code/reference;
- reversibility metadata if canonical;
- expiry if canonical;
- policy/permission reference if canonical.

### 14.1 No second approval system

Review Center must not:

- create approvals itself;
- grant approvals itself;
- mutate approval repository records directly;
- duplicate approval payloads as a new truth;
- convert a permission request into approval;
- infer approval from user navigation or viewing.

Approval and rejection remain canonical Agent Runtime/domain permission actions.

## 15. Permission and visibility invariants

Every projection must follow the effective permission boundary established upstream.

The interface layer is not allowed to reason:

> “The user is viewing this screen, therefore the user may see everything relevant to it.”

Instead, every included reference must be justified by canonical visibility/permission state.

Required invariants:

1. denied resource → absent or explicitly denied reference, never disclosed content;
2. denied supporting domain → not presented as active/authorized;
3. sensitive cross-domain transfer → hidden unless authorized;
4. read permission → does not imply propose/apply;
5. propose permission → does not imply approve/apply;
6. approval pending → does not imply execution;
7. disabled domain → does not imply selectable;
8. degraded domain → degradation remains visible;
9. partial composition → never upgraded to complete;
10. unresolved contradiction → remains unresolved;
11. unknown update status → remains unknown;
12. unavailable operation → remains unavailable.

## 16. Canonical authority binding

Phase 10.45 must learn from Phase 10.44 audit history.

A projection cannot merely contain matching IDs assembled independently.

The integration boundary must verify exact coherence between relevant canonical objects.

At minimum, successful projection requires the equivalent of:

```text
request resolution reference
        ==
canonical resolution.id
        ==
canonical composition.resolution_id
```

and primary/supporting-domain membership/status must be coherent.

Where a session, presentation, memory view, workflow result, cross-domain result, or trace declares a binding to resolution/composition/session authority, Phase 10.45 must verify that binding before surfacing it as part of the same projection.

Duck-typed impostors or structurally similar but non-canonical contract objects must fail closed where existing phases use exact contract authority.

---

## 17. Determinism and serialization

All new public Phase 10.45 contracts must be:

- immutable;
- deterministic;
- canonical-order preserving;
- safe for repeated serialization;
- free from runtime-only object identity in serialized output;
- explicit about optional/unknown state;
- backward-compatible with existing contract conventions.

Equivalent inputs must produce equivalent projection content and stable ordering.

No sets or unordered registry iteration may leak into serialized output.

Mappings must be normalized according to existing repository conventions.

## 18. Side-effect boundary

Projection is pure.

Calling the projection path must produce **zero** mutation to:

- domain registry;
- loader state;
- sessions;
- workflows;
- operations;
- approval repository;
- permission policies;
- validation records;
- observability store;
- memory;
- knowledge store;
- cognitive store;
- trace stores.

The selector intent path is not pure, but any side effect must occur only through an already-authoritative canonical service.

Phase 10.45 itself owns no persistent state.

## 20. Security properties

Phase 10.45 must preserve the security boundary of previous phases.

Required behavior:

- fail closed on missing authority;
- fail closed on invalid status;
- fail closed on mismatched IDs;
- fail closed on missing permission;
- fail closed on dangling references when disclosure could be unsafe;
- do not echo unsafe payload values into error strings;
- do not expose hidden reasoning;
- do not expose secrets;
- do not expose unauthorized resource content;
- do not broaden cross-domain access;
- do not bypass approval;
- do not introduce arbitrary code execution;
- do not introduce direct external communication.

Interface intents are data, not policy.

- unavailable domain;
- incoherent composition;
- invalid/dangling reference;
- selector intent rejected;

## 23. `AT-DP-045` — connected acceptance

### 23.1 Purpose

`AT-DP-045` must prove that Phase 10.45 is a real integration boundary over canonical components rather than an isolated DTO/mock exercise.

### 23.2 Required connected path

The acceptance must connect, using canonical implementations or their official in-memory implementations:

```text
real Domain registry
    ↓
real resolver
    ↓
real DomainResolutionResult
    ↓
real composition
    ↓
canonical session/context where applicable
    ↓
canonical presentation
    ↓
canonical workflow/operation state
    ↓
canonical permission + approval state
    ↓
canonical observability state
    ↓
Phase 10.44 memory/knowledge projection
    ↓
DefaultDomainAPI
    ↓
Phase 10.45 interface integration
    ↓
five interface-facing views
```

The acceptance must not substitute mocked dictionaries for these contracts.

### 23.3 Required positive scenario

The connected scenario should include at least:

- one primary domain;
- at least one authorized supporting domain;
- a canonical resolved composition;
- visible source/provenance references;
- a confidence value;
- at least one contradiction or explicit empty contradiction set whose authority is proven;
- a workflow or operation reference;
- at least one approval/review item;
- a memory/knowledge projection or proposal reference;
- Domain Center state from the real registry/observability path;
- Cross-Domain View dependency/transfer state from canonical components;
- successful deterministic projection through `DefaultDomainAPI`.

### 23.4 Mandatory adversarial branches

`AT-DP-045` must exercise real rejection/preservation behavior for all of the following:

1. **Resolution authority mismatch**
   A projection assembled with mismatched resolution/composition identity must fail closed.

2. **Denied supporting-domain access**
   A supporting domain denied by canonical permission must not appear as authorized or transfer its protected content.

3. **Disabled/degraded domain**
   A disabled domain must not appear active/selectable. A degraded domain must not be silently upgraded.

4. **Selector privilege escalation**
   An interface request to add/select a domain cannot increase effective permissions or autonomy.

5. **Pending approval preservation**
   A pending operation approval must remain pending; the interface cannot convert it to executed/approved.

6. **Memory proposal preservation**
   A canonical memory/knowledge proposal displayed in the interface must remain a proposal and must not mutate stores.

7. **Contradiction preservation**
   A canonical unresolved contradiction cannot disappear or become resolved merely through presentation/interface projection.

8. **Confidence non-strengthening**
   Interface projection cannot increase upstream confidence.

9. **Temporal preservation**
   Superseded/invalidated/expired knowledge excluded by canonical upstream authority cannot re-enter through the interface.

10. **Causality non-strengthening**
    Correlation/dependency relations cannot be re-labelled as causation.

11. **Partial composition preservation**
    A canonical partial composition must remain partial.

12. **Unknown update availability**
    If there is no canonical update source, Domain Center must not claim an update is available.

### 23.5 Acceptance marker

Implementation may report:

```text
AT-DP-045=PASS
```

only when the connected acceptance itself passes.

Before independent audit, documentation must still state that Phase 10.45 is implemented and pending audit, not closed.

## 28. Commit discipline

The phase follows the project workflow.

Required sequence:

```text
INSPECTION
→ DEFINITION
→ SPEC COMMIT
→ PLAN COMMIT
→ AGENT IMPLEMENTATION PROMPT
→ TDD IMPLEMENTATION
→ TESTS / GATES
→ DOCUMENTATION
→ IMPLEMENTATION COMMIT(S)
→ CLEAN WORKTREE
→ EXACT-HEAD AUDIT BUNDLE
→ INDEPENDENT AUDIT
→ REMEDIATION IF REQUIRED
→ FINAL PASS
→ DOCS-ONLY CLOSURE COMMIT
```

Rules:

- no push unless explicitly requested;
- no merge unless explicitly requested;
- no rebase unless explicitly requested;
- no `git stash`;
- no `stash pop/apply/drop`;
- no `git reset`;
- no `git clean`;
- no `git worktree` without explicit authorization;
- preserve quarantine stash;
- do not modify historical audit artifacts silently;
- every commit must have clear scope;
- implementation being audited must be fully committed;
- worktree must be clean before bundle creation.

## 29. Audit bundle

After implementation and documentation are fully committed, the agent must create an exact-HEAD `.tar.gz` audit bundle, preferably via `git archive`.

The bundle must be generated from the exact committed HEAD, never from a potentially dirty worktree.

The implementation report must record:

```text
AUDITED_IMPLEMENTATION_HEAD=<full sha>
AUDIT_BUNDLE_SHA256=<sha256>
WORKTREE=CLEAN
QUARANTINE_STASH=PRESERVED
PUSH=NO
MERGE=NO
```

Independent audit will verify:

- archive integrity;
- exact HEAD;
- SHA-256;
- scope;
- architecture;
- spec compliance;
- plan compliance;
- public contracts;
- security;
- inherited invariants;
- `DP-045`;
- `AT-DP-045`;
- tests;
- documentation.

## 30. Closure criteria

Phase 10.45 may close only after independent audit reports at minimum:

```text
BLOCKERS=0
MAJORS=0
DP-045=VERIFIED_EXISTING
AT-DP-045=PASS
CLOSURE_ELIGIBLE=YES
```

Any blocker, major, or required minor enters the remediation cycle.

A remediation must:

- fix only audited findings;
- rerun required gates;
- create a new commit;
- create a new exact-HEAD audit bundle;
- compute a new SHA-256;
- preserve previous audit bundles/reports as historical evidence.

After final PASS, Phase 10.45 receives a separate docs-only closure commit.

No Phase 10.46 implementation begins before that closure commit is verified and the worktree is clean.

## 32. Success definition

Phase 10.45 succeeds when CMM OS has exactly one trustworthy, interface-neutral Domain Intelligence boundary that can answer:

- Which domain is authoritative?
- Which supporting domains are active and authorized?
- Why were they selected?
- What workflow/result/question/approval state is relevant?
- Which sources, confidence, contradictions, and memory proposals may be shown?
- What is the current Domain Center state?
- What cross-domain transfers/dependencies/conflicts may be shown?
- What requires human review?
- What happens when the user asks the interface to select, add, or withdraw a domain?

—and can answer all of those without creating a second source of truth or weakening any existing authority.

The resulting boundary must be sufficiently stable that Phase 11 can connect CMMChat and other clients without making them understand the internal topology of Domain Intelligence.
