## 1. Purpose

Remediation V4 exists only to close the four findings reported by Independent Re-audit V4:

- `MAJOR-V4-01` — capture can persist item-level provider/connection references that are no longer bound to the current canonical authority and can therefore produce either an unrestorable aggregate or a semantically stale same-id aggregate;
- `MAJOR-V4-02` — `ProviderOnboardingService.accept()` treats caller-supplied `ConnectionProposal` authority fields as trusted and can weaken canonical endpoint/isolation policy;
- `MAJOR-V4-03` — `ProviderRegistryStateCoordinator.discover_models()` accepts a caller-supplied same-id `ProviderManifest` that is not the active canonical manifest and can therefore inject foreign activation policy into canonical route state;
- `MINOR-V4-01` — an older discovery timestamp can regress `last_seen_at` and produce a newer revision with an older observation time.

No other behavior may be redesigned or reopened.

Remediation V4 must preserve every finding already independently verified as remediated, including:

- exact component-graph identity guards introduced in Remediation V3;
- durable `route.refreshed` persistence and rollback;
- same-timestamp true no-op behavior;
- auth-only isolation for Codex, Claude Code and Antigravity;
- ownership-safe onboarding for pre-existing credentials and isolation-profile targets;
- the Phase 11 requirements matrix and `F11-014`;
- the single Provider Registry state coordinator;
- durable validation transitions;
- Qwen Token Plan / Qwen Cloud PAYG separation;
- secret-boundary protections;
- administrative, non-inference discovery;
- CMM Usage deferral;
- CMMChat deferral;
- no Phase 11.35 implementation.

## 2. Authoritative Re-audit V4 evidence

### 2.1 `MAJOR-V4-01` — orphan capture

A single correctly wired runtime graph was constructed:

```text
ProviderRegistry:
  x

ModelCatalog:
  m -> provider x

ProviderConnectionRegistry:
  x:main -> provider x

ModelRouteCatalog:
  x:main:m -> connection x:main
```

Then only the canonical provider was removed:

```text
providers.remove("x")
```

The dependent catalogs retained their entries.

Read-only recovery reproduced:

```text
PROVIDERS_AFTER_REMOVE=[]
MODELS_AFTER_REMOVE=[('m', 'x')]
CONNECTIONS_AFTER_REMOVE=[('x:main', 'x')]
ROUTES_AFTER_REMOVE=[('x:main:m', 'x:main')]

ORPHAN_CAPTURE_ACCEPTED=True
CAPTURE_COUNTS=providers=0 manifests=0 models=1 connections=1 routes=1
ORPHAN_RESTORE_FAILS=True
ORPHAN_RESTORE_EXCEPTION=ProviderError Unknown registered provider: x
```

Thus exact component-graph identity is necessary but not sufficient: item-level bindings can outlive the authority they were registered against.

### 2.2 `MAJOR-V4-01` — same-id remove/re-register

The more important same-id adversary was also reproduced.

A provider `x` was registered with:

```text
https://old.example/v1
```

A model, connection and route were registered under it.

The provider was then removed and a different `ProviderSpec` instance with the same id was registered:

```text
https://new.example/v1
```

The dependent entries survived.

Read-only recovery showed:

```text
OLD_PROVIDER_IS_NEW_PROVIDER=False
CURRENT_PROVIDER_BASE_URL=https://new.example/v1
SURVIVING_CONNECTION_ENDPOINT=https://old.example/v1
SURVIVING_CONNECTION_IS_OLD=True
SURVIVING_MODEL_PROVIDER_ID=x

REREG_CAPTURE_ACCEPTED=True
REREG_STATE_PROVIDER_BASE_URL=https://new.example/v1
REREG_STATE_CONNECTION_ENDPOINT=https://old.example/v1
REREG_RESTORE_FAILS=False
```

This proves that a simple current-id presence check is not enough.

A same-id replacement can make stale dependents appear referentially valid by id while they still belong to an earlier authority generation.

Canonical restore then preserves the mixed state.

### 2.3 `MAJOR-V4-02`

Canonical Codex metadata reported:

```text
CANONICAL_REQUIRES_ISOLATION=True
CANONICAL_ENDPOINT=https://api.openai.com/v1
CANONICAL_BILLING_CLASS=subscription
```

A caller directly constructed a public `ConnectionProposal` with:

```text
provider_id=codex
endpoint=https://evil.example/v1
requires_isolation=False
source_home=None
```

and a successful validator.

Read-only recovery reproduced:

```text
FORGED_ACCEPTED=True
STATUS=connected
ENDPOINT=https://evil.example/v1
ISOLATION_REF=None
PROFILE_EXISTS=False
CONNECTION_COUNT_AFTER_ACCEPT=1
```

Therefore proposal evidence can currently override canonical endpoint and fail-closed isolation policy at the final acceptance boundary.

### 2.4 `MAJOR-V4-03`

The active canonical DeepSeek manifest had one activation policy.

A separately constructed same-id `ProviderManifest` with a different allowlist was passed directly to:

```text
ProviderRegistryStateCoordinator.discover_models(...)
```

The operation accepted the foreign manifest and persisted route availability/audit state derived from it.

The defect exists after graph construction: the coordinator graph can be coherent while an operation injects a foreign metadata authority.

### 2.5 `MINOR-V4-01`

Discovery first observed a route at:

```text
T1=2026-09-15T02:00:00+00:00
```

and later received:

```text
T0=2026-09-15T01:00:00+00:00
```

Current behavior regressed:

```text
last_seen_at: T1 -> T0
revision: 1 -> 2
```

and emitted an audit record for the later revision at the older timestamp.

`last_seen_at` must be monotonic.

## 3. Architectural principle

Remediation V4 must close the findings by strengthening existing catalogs and operation boundaries.

It must not introduce a new authority.

Forbidden solution classes include:

- persistent provider generation ids;
- a `ProviderRegistryGraph` aggregate;
- another provider registry;
- another model/connection/route registry;
- cascading provider teardown as a new global lifecycle engine;
- registry synchronization infrastructure;
- generic dependency injection;
- proposal signatures/tokens/cryptography;
- generic transaction frameworks;
- generic rollback frameworks;
- new persistence frameworks;
- new routing engines;
- new validation runtimes.

The approved corrective model is:

```text
registration binds dependent item to exact current authority object
→ capture verifies that exact binding is still current
→ operation boundaries revalidate canonical authority
→ stale/foreign inputs fail closed before mutation
```

## 4. `MAJOR-V4-01` — exact item-level authority binding

### 4.1 Identity, not id equality

The canonical authority relation for dependent items is exact object identity.

For a model:

```text
ModelSpec(provider_id=P.id)
```

is not sufficient to prove that the model belongs to the currently active `ProviderSpec P`.

The catalog must remember the exact `ProviderSpec` instance resolved when the model was registered.

For a connection, the same rule applies.

For a route, the catalog must remember the exact `ProviderConnection` instance resolved when the route was registered.

### 4.2 Reuse the established manifest binding pattern

`ProviderManifestRegistry` already uses the correct conceptual pattern: manifest metadata is bound to the exact `ProviderSpec` authority resolved at registration, and stale same-id metadata does not silently become active after provider replacement.

Remediation V4 extends that authority-binding idea to the remaining dependent catalogs.

This is not a new registry.

It is private binding metadata inside the existing canonical catalogs.

### 4.3 `ModelCatalog` binding rule

When `ModelCatalog.register(model)` succeeds:

1. resolve the current provider through the catalog's canonical `ProviderRegistry`;
2. retain the exact resolved `ProviderSpec` object alongside the `ModelSpec`;
3. preserve existing public `ModelSpec` shape;
4. preserve existing public lookup/list semantics.

Conceptually:

```text
model key
  -> (
       bound exact ProviderSpec instance,
       ModelSpec
     )
```

The implementation may use:

- a tuple storage layout; or
- an adjacent private binding map

depending on the existing internal representation.

Either representation is acceptable only if:

- it is private;
- it introduces no second lookup authority;
- public model inventory remains the existing `ModelCatalog`;
- there is no rebinding API.

### 4.4 `ProviderConnectionRegistry` binding rule

When `ProviderConnectionRegistry.register(connection)` succeeds:

1. resolve the current provider from the exact bound `ProviderRegistry`;
2. retain the exact resolved `ProviderSpec` object alongside the connection;
3. preserve existing public `ProviderConnection` shape;
4. preserve current duplicate and lookup behavior.

Conceptually:

```text
connection_id
  -> (
       bound exact ProviderSpec instance,
       ProviderConnection
     )
```

No public generation id is added.

### 4.5 `ModelRouteCatalog` binding rule

When `ModelRouteCatalog.register(route)` succeeds:

1. resolve the current canonical `ProviderConnection` from the exact bound `ProviderConnectionRegistry`;
2. retain the exact resolved connection object alongside the route;
3. preserve existing public `ModelRoute` shape and route ids.

Conceptually:

```text
route_id
  -> (
       bound exact ProviderConnection instance,
       ModelRoute
     )
```

No route-generation field is persisted.

### 4.6 Mutation methods must preserve bindings

Any existing catalog mutation that replaces an item in place must preserve or refresh the correct bound object intentionally.

Examples include:

```text
ModelRouteCatalog.mark_seen(...)
ModelRouteCatalog.mark_unavailable(...)
restore_all(...)
```

A field-only route update such as:

```text
last_seen_at
available
unavailable_since
```

must keep the existing exact bound `ProviderConnection`.

A full registration/replacement that intentionally establishes a new canonical item must resolve and store the current exact authority anew.

Do not silently transfer the old binding to a logically new dependent item unless existing catalog semantics already define that item as the same registration.

### 4.7 Restore behavior

Canonical restore creates dependencies in order:

```text
providers
→ manifests
→ models
→ connections
→ routes
```

Restored models/connections/routes must therefore establish bindings to the exact newly restored authority objects.

A freshly restored coherent graph must immediately pass all new capture checks.

No persistent object-identity token is required.

## 5. Capture-time referential authority validation

`capture_provider_registry_state()` must keep the Remediation V3 component graph checks:

```python
manifests.provider_registry is providers
models.provider_registry is providers
connections.provider_registry is providers
routes.connections is connections
```

After those checks and before returning a state envelope, it must also verify each active dependent item against its stored exact binding.

### 5.1 Models

For every current model:

```text
current_provider = providers.get(model.provider_id)
```

Capture succeeds only if:

```text
current_provider is model's bound ProviderSpec
```

Failure cases include:

- provider missing;
- provider removed and same-id re-registered as a different object.

### 5.2 Connections

For every current connection:

```text
current_provider = providers.get(connection.provider_id)
```

Capture succeeds only if:

```text
current_provider is connection's bound ProviderSpec
```

Failure cases include:

- provider missing;
- provider same-id replacement.

### 5.3 Routes

For every current route:

```text
current_connection = connections.get(route.connection_id)
```

Capture succeeds only if:

```text
current_connection is route's bound ProviderConnection
```

Failure cases include:

- connection missing;
- connection removed and same-id re-registered while the route survives.

### 5.4 Error behavior

Use the existing:

```text
ProviderStateCoherenceError
```

Do not add a new error hierarchy.

Messages must be deterministic and sanitized.

Preferred shape:

```text
model <id> is bound to a stale or missing ProviderSpec
connection <id> is bound to a stale or missing ProviderSpec
route <id> is bound to a stale or missing ProviderConnection
```

Do not include object reprs, credentials, environment paths or config payloads.

### 5.5 No silent omission

Do not make capture "coherent" by dropping stale models, connections or routes from the serialized state.

The existence of stale dependent state is itself a coherence failure.

Fail closed.

### 5.6 No automatic cascading teardown

Remediation V4 does not add:

```text
ProviderRegistry.remove()
  -> delete manifests/models/connections/routes automatically
```

Such a global lifecycle policy belongs to a separate explicitly designed feature if ever needed.

For this remediation, stale dependent state remains visible in memory and capture refuses to persist it.

## 6. `MAJOR-V4-01` connected acceptance

Strengthen `AT-DP-134` with canonical components.

### 6.1 Provider removed with dependents

Create:

```text
provider x
model m -> x
connection x:main -> x
route x:main:m -> x:main
```

Then:

```text
providers.remove("x")
```

Require:

```text
capture raises ProviderStateCoherenceError
no state envelope produced
```

### 6.2 Same-id provider replacement

Create dependents under ProviderSpec A.

Then:

```text
remove("x")
register ProviderSpec B with id="x"
```

Require:

```text
A is not B
capture raises ProviderStateCoherenceError
```

Id equality must not revive stale model/connection authority.

### 6.3 Same-id connection replacement with surviving route

Create route bound to Connection A.

Then remove/re-register a different `ProviderConnection` with the same `connection_id`.

Require:

```text
old_connection is not new_connection
capture raises ProviderStateCoherenceError
```

### 6.4 Clean restore remains valid

Capture a coherent state, persist, restore, and recapture.

Require:

```text
restored graph capture succeeds
```

This proves object identity is intentionally local to each coherent runtime generation and does not require persistent generation ids.

### 6.5 Coordinator persistence failure boundary

If a coordinator mutation reaches `_commit()` while the runtime graph is item-level incoherent, capture must fail before repository save and before publishing the next revision/audit batch.

Require:

```text
repository durable state unchanged
coordinator revision unchanged
coordinator audit log unchanged
```

The underlying external incoherence that already existed before the coordinator call does not need to be silently repaired.

## 7. `MAJOR-V4-02` — `ConnectionProposal` remains evidence, never authority

### 7.1 Public proposal contract is preserved

Do not make `ConnectionProposal` private.

Do not remove it from exports solely to close this finding.

Do not introduce signed/minted proposal tokens.

A caller may still construct a `ConnectionProposal`.

Therefore `accept()` must treat every proposal as untrusted evidence.

### 7.2 Acceptance-time canonical revalidation

Before any acceptance side effect, `ProviderOnboardingService.accept()` must re-resolve:

```text
canonical ProviderSpec
active canonical ProviderManifest
```

from the service's exact bound registries using:

```text
proposal.provider_id
```

If either canonical authority is absent, reject.

The active manifest must belong to the exact current canonical provider authority through the already-established manifest binding rules.

### 7.3 Canonical authority fields

For the current Phase 11.34 onboarding contract, these proposal fields cannot weaken or contradict active canonical metadata:

```text
provider_id
display_name
billing_class
endpoint
requires_isolation
```

Required checks:

```text
proposal.provider_id identifies the active canonical provider
proposal.display_name == canonical manifest display_name
proposal.billing_class == canonical manifest billing_class
proposal.endpoint == canonical manifest default_base_url
```

For isolation:

```text
canonical.requires_isolation=True
proposal.requires_isolation=False
    -> reject

canonical.requires_isolation=True
proposal.requires_isolation=True
    -> allowed to proceed

canonical.requires_isolation=False
proposal.requires_isolation=False
    -> allowed to proceed

canonical.requires_isolation=False
proposal.requires_isolation=True
    -> allowed to proceed
```

The last case preserves legitimate risk-derived isolation strengthening.

The canonical manifest defines the minimum isolation requirement.

A proposal may strengthen that minimum but may never weaken it.

### 7.4 External evidence does not become endpoint authority

Existing detector/candidate evidence may cause:

```text
proposal.requires_isolation=True
source_home present
risk markers present
```

but the final accepted connection endpoint remains canonical.

A proposal-only endpoint override is not acceptance authority.

If a future phase wants endpoint override as a supported canonical feature, it must define a separate authenticated/canonical contract.

Remediation V4 does not add one.

### 7.5 Revalidation must happen before side effects

Canonical proposal validation must complete before:

- credential `put`;
- isolation profile creation;
- validator invocation;
- connection registration;
- route mutation;
- coordinator revision/audit persistence.

A forged proposal must fail without invoking the injected validator.

This keeps validation-policy hooks from accidentally legitimizing a noncanonical proposal.

### 7.6 Ownership-safe onboarding remains intact

After canonical proposal revalidation succeeds, preserve existing V2/V3 ordering:

```text
duplicate connection preflight
pre-existing credential-ref preflight
pre-existing isolation-target preflight
operation-owned side effects
validation
connection registration
coordinator persistence
```

Do not regress operation-owned compensation.

## 8. `MAJOR-V4-02` connected acceptance

### 8.1 Forged Codex isolation downgrade

Using canonical subscription bridge bootstrap, prove:

```text
canonical codex requires_isolation=True
proposal requires_isolation=False
```

causes rejection before all side effects.

Require:

```text
validator calls = 0
credential writes = 0
profile creation = 0
connections unchanged
revision unchanged
repository unchanged
```

### 8.2 Forged canonical endpoint

For Codex:

```text
proposal.endpoint=https://evil.example/v1
```

must fail before side effects even if:

```text
proposal.requires_isolation=True
validator would return success
```

### 8.3 Forged billing class

A proposal with billing class different from the active manifest must fail before side effects.

### 8.4 Forged display name

A proposal with a noncanonical display name must fail before side effects.

This field is included to ensure an accepted proposal is one deterministic canonical representation, not a partly caller-authored connection definition.

### 8.5 Isolation strengthening remains possible

For a canonical provider whose manifest does not require isolation, a legitimate proposal with:

```text
requires_isolation=True
```

must not be rejected merely because the proposal is stricter.

Normal isolation prerequisites still apply.

If the proposal lacks the source/profile information required to create isolation, the existing fail-closed isolation path may reject it for that separate reason.

### 8.6 Stale proposal

Create a valid proposal, then change/remove the active canonical provider/manifest authority before `accept()`.

Require acceptance-time revalidation to reject the stale proposal before side effects.

Do not encode proposal provenance; simply re-resolve current authority.

## 9. `MAJOR-V4-03` — discovery manifest authority

### 9.1 Keep the public signature

Retain the existing public coordinator method shape:

```python
discover_models(
    connection,
    manifest,
    client,
    *,
    seen_at=...,
)
```

unless implementation inspection proves a strictly backward-compatible internal resolution can remove the manifest parameter without changing public callers.

The approved default is to keep it.

### 9.2 Caller manifest is a claim, not authority

At operation entry, the coordinator already canonicalizes the connection through its exact bound `ProviderConnectionRegistry`.

After resolving the registered connection:

```text
registered = self._connections.get(connection.connection_id)
```

the coordinator must resolve:

```text
canonical_manifest = self._manifests.get(registered.provider_id)
```

Then require:

```text
canonical_manifest is manifest
```

Exact identity is required.

Same `provider_id` and equal field values are not sufficient.

### 9.3 Provider relation

The canonical active manifest must correspond to:

```text
registered.provider_id
```

If there is no active canonical manifest for the connection's provider, fail closed.

Do not use the caller manifest to determine which provider to look up.

### 9.4 Fail before external work or mutation

A foreign/stale manifest must be rejected before:

- client model-list call;
- route mutation;
- audit mutation;
- revision increment;
- repository save.

Where practical, tests should use a recording discovery client and require:

```text
client.list_models calls = 0
```

for the rejected foreign manifest.

### 9.5 No silent substitution

Do not silently ignore the caller-supplied manifest and proceed with the canonical one.

The method currently exposes a manifest parameter; passing the wrong object is a caller composition error.

Fail closed so the defect remains observable.

A future API simplification may remove the parameter in a separate phase.

## 11. `MINOR-V4-01` — monotonic observation time

### 11.1 Discovery is a connection-level snapshot

Administrative discovery does more than update one route timestamp.

For one connection it may:

- create routes;
- mark routes seen;
- mark routes unavailable;
- restore routes.

Therefore an older observation cannot safely be applied partially.

A snapshot older than already-persisted connection state must be rejected before discovery reconciliation starts.

### 11.2 Coordinator monotonicity rule

Before invoking canonical `discover_models()`, inspect existing routes belonging to the registered canonical connection.

Let:

```text
latest_seen = max(route.last_seen_at for routes of connection)
```

if any routes exist.

Require:

```text
seen_at >= latest_seen
```

If:

```text
seen_at < latest_seen
```

raise:

```text
ProviderStateCoherenceError
```

with a deterministic message such as:

```text
discovery seen_at precedes current route state
```

### 11.3 Equality remains valid

If:

```text
seen_at == latest_seen
```

the operation is allowed to proceed.

Consequences:

- if no resulting field changes, the V3 same-timestamp behavior remains a true no-op;
- if some route has an older timestamp while another route already equals `latest_seen`, the equal snapshot may legitimately advance the older route to the shared current observation time.

### 11.4 No existing routes

If the connection has no existing routes, any otherwise valid aware `seen_at` is allowed.

Preserve existing timezone-awareness validation.

### 11.5 Fail before client call

An older snapshot must be rejected before:

```text
client.list_models()
```

so stale external observations cannot alter availability or trigger unnecessary discovery work.

### 11.6 Direct `ModelRouteCatalog.mark_seen()` callers

Remediation V4 does not automatically move the monotonicity rule into `ModelRouteCatalog.mark_seen()`.

During implementation, inspect non-test callers.

If the coordinator is the only Phase 11.34 route-refresh path that accepts arbitrary observation timestamps, keep the rule at the coordinator boundary.

If an existing canonical direct caller can independently regress `last_seen_at`, add the same minimal monotonic guard locally without creating a new time-policy abstraction.

Any such additional guard must be justified in the implementation ledger as directly required by `MINOR-V4-01`.

## 13. Error taxonomy

Reuse:

```text
ProviderStateCoherenceError
```

for:

- stale/missing item-level authority binding during capture;
- stale/foreign canonical manifest passed to coordinator discovery;
- stale discovery timestamp relative to current route state;
- proposal authority mismatch where the supplied value contradicts current canonical provider/manifest state.

If onboarding already has a narrower public error class that existing callers rely on for invalid proposals, implementation may preserve that class only if:

- it remains fail-closed;
- the same class is already canonical for proposal validation;
- no new error hierarchy is introduced.

The implementation plan must freeze the exact class after inspecting current onboarding tests/contracts.

Error messages must not contain secrets or object reprs.

## 14. No persistent generation ids

The same-id remove/re-register adversary proves generation semantics matter.

Remediation V4 solves this with exact in-memory object binding inside canonical catalogs.

Do not add:

```text
provider_generation
connection_generation
generation_uuid
authority_epoch
```

to:

- `ProviderSpec`;
- `ModelSpec`;
- `ProviderConnection`;
- `ModelRoute`;
- persisted Provider Registry state;
- schema version.

Fresh canonical restore creates a new coherent in-memory generation naturally.

## 15. No global cascading teardown

Do not modify `ProviderRegistry.remove()` to reach into model, connection or route catalogs.

`ProviderRegistry` must remain independent of downstream catalogs.

Likewise do not make:

```text
ProviderConnectionRegistry.remove()
```

reach into `ModelRouteCatalog`.

That would introduce bidirectional lifecycle coupling and hidden side effects.

Instead:

```text
remove authority
→ stale dependent state remains visible
→ capture/persistence refuses incoherent aggregate
→ caller must explicitly reconcile dependents
```
