# 4. Inspection finding — existing canonical primitive

Phase 11.1 already owns:

```text
CompositionConfiguration.expected_contracts
ServiceExpectation
CompositionConfiguration.expected_contract_for(service_id)
ApplicationContainer expected-contract verification
```

This is the existing canonical mechanism that associates:

```text
service_id
→ expected contract
```

The current `ApplicationContainer` already verifies configured expectations before reaching READY.

Therefore Remediation V3 must extend that existing mechanism.

It must not create:

```text
ExactServiceRegistry
RuntimeContractRegistry
CanonicalTypeRegistry
ServicePolicyRegistry
ClientBackendRegistry
```

---

# 5. Root cause

V2 places exactness on:

```text
ServiceBinding.runtime_contract
ServiceBinding.runtime_contract_match
ClientBackend.__cmm_exact_runtime_contract__
```

The registry computes effective exactness from:

```python
binding.runtime_contract
```

But `runtime_contract` belongs to the same caller-authored `ServiceBinding` being validated.

Therefore:

```text
binding says "my contract is ClientBackend"
→ exact marker works

binding says "my contract is object/None/subclass"
→ marker is no longer visible
→ binding author changed the premise being validated
```

This is structurally circular.

The binding cannot be the authority for the contract against which that same binding is judged.

---

# 6. V3 architectural ruling

The authoritative runtime contract for a canonical configured service moves to the already-existing:

```text
CompositionConfiguration.expected_contracts
```

path.

The final authority chain is:

```text
CompositionConfiguration
    ↓
ServiceExpectation(service_id, contract, runtime expectation)
    ↓
IntegrationServiceRegistry
    ↓
ServiceBinding validation
```

For services with an authoritative runtime expectation:

```text
ServiceBinding.runtime_contract
```

becomes a declaration that must agree with the expectation.

It is no longer the authority.

---

# 7. ServiceExpectation extension

Extend the existing canonical `ServiceExpectation` contract with optional runtime semantics.

Required conceptual shape:

```python
@dataclass(frozen=True, slots=True)
class ServiceExpectation:
    service_id: str
    contract: ContractMetadata
    runtime_contract: type[Any] | None = None
    runtime_contract_match: RuntimeContractMatch | None = None
```

Exact field spelling may follow existing Phase 11.1 conventions, but semantics are frozen here.

---

# 8. Backward compatibility

Existing expectations such as the Phase 11.1 provider-registry expectation currently declare only:

```text
service_id
contract
```

They must continue to work unchanged.

Therefore:

```text
runtime_contract=None
runtime_contract_match=None
```

means:

```text
no authoritative runtime-type policy is added by this expectation
```

and existing V1/V2 Phase 11.1 behavior is preserved.

---

# 9. Runtime expectation validation

`ServiceExpectation` must fail closed when malformed.

Rules:

```text
runtime_contract is None
→ runtime_contract_match must be None

runtime_contract is a real Python type
→ runtime_contract_match must be RuntimeContractMatch

runtime_contract_match=EXACT_TYPE
→ runtime_contract must be a real Python type
```

No strings, import paths, callables or arbitrary objects as runtime contracts.

---

# 10. ClientBackend expectation

Phase 11.50 must define one canonical expectation for:

```text
service_id=client.backend
contract=<existing client.backend ContractMetadata>
runtime_contract=ClientBackend
runtime_contract_match=EXACT_TYPE
```

This expectation is the authority for the runtime identity.

The V2 class marker remains defense in depth but is not the authority.

# 11. Expectation factory location

The canonical client-backend expectation should be constructed in the existing:

```text
cmm/client_backend/platform_module.py
```


Suggested internal function:

```text
client_backend_service_expectation()
```

or an equivalent narrow name.

Do not add it to the public first-party `cmm.client_backend.__all__` unless an existing platform convention requires that export.

# 12. No platform → client_backend dependency

`cmm.platform` must not import:


The expectation object is constructed by the higher layer and injected downward through existing composition configuration.

```text
cmm.client_backend
→ cmm.platform contracts/configuration

cmm.platform
→ cmm.client_backend
```

# 13. IntegrationServiceRegistry expectation state

The existing `IntegrationServiceRegistry` may hold the configured expectations needed to validate its bindings.

This is not a second registry.

It is additional validation state inside the one canonical registry.

Conceptual state:

```text
_bindings
_expected_contracts
_frozen
```

No module-level singleton.

No global service map.

No product-specific map.

# 14. Registry construction

Allow the registry to receive zero or more existing `ServiceExpectation` values at construction.

Conceptually:

```python
IntegrationServiceRegistry(
    expected_contracts: tuple[ServiceExpectation, ...] = ()
)
```

Default empty preserves generic Phase 11.1 unit-test and low-level use.

The tuple must be copied/canonicalized into immutable deterministic state.

---

# 15. No duplicate expectations

Within one registry expectation set:

```text
service_id must be unique
```

Duplicate expectations fail closed.

This must reuse the same semantics already enforced by `CompositionConfiguration.expected_contracts`.

Do not permit order-dependent policy.

---

# 16. Existing-registry composition path

Phase 11.1 explicitly supports composing an already-populated `IntegrationServiceRegistry`.

Therefore ApplicationContainer must be able to attach the configuration's expectations to a supplied registry before READY.

This attachment must be:

```text
one-time
monotonic
idempotent for the exact same expectation set
non-downgradable
```

A later weaker or different expectation set must fail closed.

---

# 17. Suggested registry operation

A narrow internal/platform operation may be added, conceptually:

```python
registry.configure_expected_contracts(expectations)
```

Exact naming may follow repository style.

It is not:

```text
a service locator
a policy registry
a global registry
a runtime resolver
```

It only configures validation constraints on the existing registry.

---

# 18. Atomic expectation attachment

When expectations are attached to a registry that already contains bindings:

```text
1. validate the entire candidate expectation set
2. validate every already-registered binding affected by it
3. only if all pass, install the expectation set
```

On failure:

```text
registry expectation state unchanged
binding state unchanged
```

No partial mutation.

---

`ApplicationContainer.build(...)` must become the canonical point that ensures:

Two paths:

```text

supplied registry

```

# 23. Runtime contract agreement

When an expectation declares a runtime contract:

```text
binding.runtime_contract is expectation.runtime_contract
```

must hold.

Reject:

```text
None
object
ClientBackendSubclass
any other type
```

for the canonical `client.backend` expectation.

The binding may not substitute the expected runtime contract.

---

# 24. Runtime match agreement

When an expectation declares:

```text
runtime_contract_match=EXACT_TYPE
```

the binding declaration must not weaken or contradict it.

For `client.backend`, the canonical binding should declare:

```text
runtime_contract_match=EXACT_TYPE
```

and any caller-authored:

```text
INSTANCE_OF
```

declaration is rejected as inconsistent with the expectation.

The expectation may not be downgraded.

---

# 25. Runtime implementation check

The implementation must be tested against the expectation, not merely against the binding declaration.

For:

```text
expectation.runtime_contract=ClientBackend
expectation.runtime_contract_match=EXACT_TYPE
```

authoritative check is:

```python
type(binding.implementation) is ClientBackend
```

regardless of what the binding claims.

---

not on discovering the marker through the binding field.

# 31. Bare registry semantics

An empty:

```python

```

is a generic low-level composition registry.

Without `CompositionConfiguration.expected_contracts`, it does not possess enough information to establish a service-specific canonical runtime type.

Therefore DP-150 closure is judged on:

```text

```

not on an unconfigured registry pretending to know every future higher-layer service.

However, if the canonical descriptor itself declares that an expectation is required, the bare registry must fail closed for that descriptor.
