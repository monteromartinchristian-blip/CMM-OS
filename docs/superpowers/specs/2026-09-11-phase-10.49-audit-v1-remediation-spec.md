## 4. MAJOR-01 remediation — real Domain-specific first-party schemas

### 4.1 Root cause

All twelve audited first-party schemas use the same effective policy template,
changing mainly:

```text
domain_id
schema id
minimum_sensitivity
metadata
```

The common body universally requires:

```text
facts.required_non_empty=True
```

and otherwise applies the same generic epistemic/uncertainty/contradiction
shape.

That does not satisfy the approved requirement that each Domain schema declare
Domain-specific restrictions based on its existing semantics.

### 4.2 Required remediation principle

Each first-party schema must be derived from that Domain's existing canonical:

```text
resource rules
profile semantics
workflow/rule semantics
memory/knowledge authority
temporal requirements
provenance requirements
uncertainty/contradiction needs
privacy/sensitivity evidence
```

Do not invent behavior.

Do not copy the same policy block to all twelve Domains.

### 4.3 Universal fact requirement

Remove:

```text
facts.required_non_empty=True
```

from any Domain where canonical Phase 8 packages may be valid without facts.

A Domain may require facts only if existing Domain semantics justify it.

At least one first-party Domain must be proven compatible with a canonical
observation-only package when its own declared policy permits that package.

The remediation test must demonstrate:

```text
NON_FACT_CANONICAL_PACKAGE_COMPATIBILITY=PASS_WHERE_DOMAIN_POLICY_ALLOWS
```

### 4.4 Minimum required Domain differentiation

The exact final policy set must be justified from repository evidence, but the
following semantic distinctions must exist where current Domain contracts
support them.

#### General

General must remain broad.

Prefer minimal structural constraints.

Do not require a fact merely because the common V1 template did.

Use General as a likely compatibility case for a valid canonical package that
contains observations but no facts, if current canonical General semantics
support it.

#### Health

Health should emphasize existing canonical:

```text
provenance
temporal validity/currentness
uncertainty preservation
contradiction visibility
sensitive handling
```

A Health policy may require stronger evidence than General.

#### Relationships

Relationships should emphasize:

```text
ambiguity/uncertainty preservation
contradiction visibility
sensitive handling
```

Do not force factual certainty where the Domain is intrinsically interpretive.

#### University

University should emphasize:

```text
provenance
temporal validity for deadlines/rules/current academic state
constraints
```

Do not copy Health's sensitive/uncertainty shape mechanically.

#### Oppositions

Oppositions should emphasize:

```text
official/current-source provenance
temporal validity
constraints/deadlines
```

#### Reflection

Reflection should emphasize:

```text
uncertainty preservation
avoidance of false certainty
sensitive handling
```

It should not universally require factual evidence.

#### Concerns

Concerns should emphasize:

```text
uncertainty preservation

sensitive handling
```

#### Languages

Languages should emphasize:

```text
evidence/provenance for proficiency claims
temporal state where relevant
```

It should not inherit unrelated contradiction requirements automatically.

#### Parenthood

Parenthood should emphasize:

```text
provenance
temporal validity
uncertainty where applicable
sensitive handling
```

#### Sport

Sport should emphasize:

```text
temporal validity

```

Do not claim Health authority.

#### Life Plan

Life Plan should emphasize:

```text

```

#### Project

Project should emphasize:

```text

```

Add an explicit test proving the twelve schemas are not one normalized policy
shape.

The test must not merely compare IDs or sensitivity.

Normalize away at least:


## 5. MAJOR-02 remediation — canonical contradiction preservation

### 5.1 Root cause

The audited validator rejects:

```text
ContradictionStatus.RESOLVED
```

when:

```text
preserve_contradictions=True
```

This is incorrect.

A resolved contradiction that remains present in:

```text
KnowledgePackage.contradictions
```

is still visible and auditable.

Resolution status is not erasure.

### 5.2 Required semantic rule

`preserve_contradictions=True` means:

```text
existing canonical contradiction evidence must not be silently removed,
hidden, rewritten, or mutated by Phase 10.49
```

It does **not** mean:

```text
contradictions may never have status RESOLVED
```

### 5.3 Required accepted statuses

All canonical Phase 8 contradiction statuses that can validly exist in a
`KnowledgePackage` must remain representable under preservation.

At minimum test:

```text
UNRESOLVED
RESOLVED
DEFERRED
ACKNOWLEDGED
```

unless the current canonical Phase 8 constructor independently rejects one.

Phase 10.49 must not add a stricter status prohibition.

### 5.4 No mutation

For every accepted contradiction status:

```text
validated is package
package serialization before == package serialization after
contradiction object/status unchanged
```

### 5.5 Evidence-based absence rule

Do not reject a package merely because `package.contradictions` is empty when
the package contains no canonical evidence proving that a contradiction was
erased.

Phase 10.49 must not invent hidden contradictions.

### 5.6 Test replacement

Remove or rewrite the incorrect test:

```text
test_validation_rejects_resolved_contradiction_when_preserved
```

Replace it with a regression proving:

```text
RESOLVED_CONTRADICTION_PRESERVATION=PASS
```

### 5.7 AT-DP-049 extension

Connected acceptance must include a canonical Phase 8 package containing a
resolved contradiction and prove:

```text
preserve_contradictions=True
```

accepts it unchanged.
