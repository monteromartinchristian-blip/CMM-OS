## 1. Purpose

Phase 10.39 prevents Domain specialization from fragmenting CMM OS into independent, incompatible subsystems.

A Domain Pack may specialize domain knowledge, resources, reasoning rules, operations, workflows, permissions, presentation, profiles, and other domain-owned declarations only through the canonical shared infrastructure already established by earlier phases.

A Domain Pack must not recreate, redefine, bypass, fork, or privately own infrastructure whose authority already belongs to CMM OS.

Phase 10.39 therefore hardens the existing canonical Domain Validation fragmentation boundary. It does **not** create a second architecture-validation subsystem.

---

## 2. Architectural decision

The roadmap's conceptual `DomainArchitectureGuard(...)` is realized by extending the existing canonical validation owner:

```text
PipelineDomainValidator
└── domain.fragmentation
    └── DomainFragmentationValidator
        └── analyze_fragmentation(...)
```

Canonical implementation already exists in:

- `cmm/domains/validation.py`
- `cmm/domains/validation_steps.py`
- `cmm/domains/validation_validators.py`
- `cmm/domains/validation_fragmentation.py`

Existing integration already provides:

- the canonical `domain.fragmentation` validation step;
- strict-mode mandatory inclusion;
- shared scan-session integration;
- `DomainValidationResult.fragmentation_valid`;
- installation blocking via `ensure_domain_validation_allows_install(...)`;
- fail-closed behavior for missing scan sessions;
- strict-mode blocking behavior for unreadable or invalid UTF-8 Python sources.

Phase 10.39 MUST extend this existing authority rather than introduce a parallel `DomainArchitectureGuard` engine, pipeline, registry, runtime, store, loader, resolver, or validation service.

---

## 3. Problem statement

The existing Phase 10.5 fragmentation analyzer detects a useful but incomplete subset of architectural violations.

Current checks include:

- `MemoryStore` duplication;
- `Planner` duplication;
- `AgentRuntime` duplication;
- `KnowledgeStore` duplication;
- broad contract/interface/protocol redefinition heuristics;
- selected backend bypass imports;
- selected policy-bypass wording;
- one narrow provenance-omission pattern.

Phase 10.39 must close the demonstrated architectural gaps required by the roadmap while preserving legitimate use of canonical infrastructure and legitimate adapter patterns.

The goal is not to perform complete semantic verification through regex or AST inspection. The goal is to ensure that Domain Packs cannot escape the canonical owners responsible for those semantics.

---

## 4. Scope

Phase 10.39 SHALL harden canonical Domain fragmentation validation against architectural attempts to:

1. create private or parallel memory infrastructure;
2. create private or parallel Knowledge Store infrastructure;
3. create private or parallel Knowledge Graph infrastructure;
4. create private or parallel reasoning-engine infrastructure;
5. create private or parallel Agent Runtime infrastructure;
6. create private or parallel Planner infrastructure;
7. create private or parallel Workflow Engine infrastructure;
8. create private or parallel permission-system infrastructure;
9. create private or parallel session stores or session-context systems;
10. redefine protected canonical contracts rather than use them;
11. bypass canonical persistence boundaries through known direct backend access;
12. recreate global services already owned by canonical CMM OS infrastructure;
13. introduce incompatible operation-result infrastructure instead of canonical Domain Operations results;
14. bypass global validation or policy boundaries in statically demonstrable ways;
15. introduce duplicated core architectural models whose authority belongs to canonical owners.

The guard SHALL remain conservative enough not to reject ordinary Domain-specific classes merely because their names contain generic words such as `Rule`, `Resource`, `Engine`, or `Result`.

## 5. Canonical owners that must be protected

Phase 10.39 does not reimplement these systems. It protects their ownership boundaries.

### 5.1 Cognitive and epistemic ownership

Canonical shared owners include:

- `KnowledgeItem`
- `Evidence`
- `TemporalScope`
- `Resource`
- `ResourceProvenance`
- `MemoryUpdateProposal`
- canonical Knowledge Store contracts and implementations
- canonical knowledge/reasoning infrastructure

Domains may reference and specialize behavior around these contracts. They may not create independent equivalents that become competing sources of truth.

### 5.2 Agent/runtime ownership

Canonical shared owners include:

- Agent Runtime
- operation registries and execution adapters
- Domain Operation contracts
- `DomainOperationResult`
- canonical runtime/session infrastructure

Domains may register canonical operations and provide injected implementations. They may not introduce a private execution runtime.

### 5.3 Workflow ownership

Domains must use the canonical workflow contracts, registries, and executor infrastructure.

No Domain-specific Workflow Engine may become an independent workflow runtime.

### 5.4 Permission and approval ownership

Domains must reuse canonical Phase 10 permission and approval infrastructure.

A Domain Pack may declare domain permission policy, but it may not create a separate permission system or alternate approval authority.

### 5.5 Resolution/composition ownership

Domains must reuse:

- `DomainRegistry`
- `DefaultDomainResolver`
- canonical composition
- canonical cross-domain contracts
- canonical conflict resolution

No per-domain resolver ecosystem may be introduced.

### 5.6 Session ownership

Phase 10.34 established shared Domain Session integration.

Domains must use canonical shared session infrastructure and `DomainSessionContext` semantics. They must not persist or resume Domain sessions through private session stores.

### 5.7 Event ownership

The canonical Domain Event catalog is frozen at the current invariant:

```text
CANONICAL_DOMAIN_EVENTS = 23 unique events
```

Phase 10.39 must preserve this invariant. It does not redesign Domain Events.

## 6. Architectural invariants

The implementation MUST preserve all inherited invariants, including:

### 6.1 One shared architecture

Phase 10 specializes one shared:

- Kernel;
- Cognitive Layer;
- Knowledge Model;
- Knowledge Store;
- Knowledge Graph;
- Agent Runtime;
- workflow system;
- operation system;
- validation system;
- memory infrastructure.

### 6.2 Epistemic integrity

Phase 10.39 must not weaken the canonical preservation of:

- epistemic kind;
- confidence;
- provenance;
- temporality;
- gaps;
- contradictions.

The architecture guard protects ownership boundaries. Semantic correctness remains the responsibility of the canonical cognitive owners and their existing validation/tests.

### 6.3 Memory invariants

Domains may build reference-only Domain memory views/proposals/bindings through canonical contracts.

Domains must not own private persistent memory.

`READ`, `PROPOSE`, `APPROVE`, and `APPLY` remain distinct authorities.

### 6.4 Permission invariants

Sensitive inference, transfer, persistence, external effects, and execution remain subject to existing permission/approval infrastructure.

Phase 10.39 may not weaken or bypass Phase 10.15 or Phase 10.38 trust ceilings.

### 6.5 Traceability

The guard must not introduce an alternate trace system.

Domains continue using canonical trace contracts and reference-based trace assembly.

### 6.6 Session invariants

Domain sessions remain attached to shared Session Context infrastructure.

No independent Domain session repository or private session runtime may be introduced.

### 6.7 Operation invariants

Domain operations continue through canonical Domain Operation orchestration and results.

A parallel operation result hierarchy must not replace `DomainOperationResult`.

### 6.8 Domain Event invariant

The canonical event catalog remains:

```text
23 events / 23 unique
```

No Phase 10.39 change may expand or fork that catalog.

## 7. Enforcement model

### 7.1 Static architectural enforcement

The fragmentation guard may inspect Python source using AST and narrowly-scoped static checks to detect architecture violations.

Appropriate static checks include:

- prohibited core class declarations;
- protected contract redefinitions;
- direct imports of prohibited backend implementation layers;
- direct persistence/backend calls whose use would bypass canonical services;
- statically identifiable policy/validation bypasses;
- known parallel runtime/store/engine/session/permission structures.

### 7.2 Semantic ownership, not semantic reinvention

The guard MUST NOT pretend to prove runtime semantic properties that belong to other canonical owners.

It must not build new logic attempting to fully establish:

- provenance completeness;
- temporality correctness;
- epistemic classification correctness;
- entity deduplication correctness;
- truth-vs-inference correctness;
- runtime permission correctness;
- runtime trace completeness.

Instead, it protects against Domain Packs redefining or bypassing the canonical systems responsible for those guarantees.

### 7.3 Fail-closed behavior

Existing fail-closed semantics must remain intact:

- missing scan session => failure;
- unreadable source => strict-mode blocker;
- invalid UTF-8 => strict-mode blocker;
- blocking fragmentation finding => `fragmentation_valid=False`;
- invalid fragmentation => installation blocked.

No Phase 10.39 change may silently downgrade a blocking architectural violation into a warning.

---

## 8. False-positive policy

The guard must distinguish architectural duplication from legitimate specialization.

The following are permitted when they reuse canonical infrastructure:

- Domain-specific operation implementations registered through canonical registries;
- Domain-specific workflows expressed through canonical workflow contracts;
- Domain-specific reasoning rules implementing canonical rule contracts;
- Domain-specific memory request/proposal/view/binding factories using shared memory contracts;
- adapters wrapping or extending canonical components where the existing architecture explicitly permits adapters;
- presentation-only or semantic domain classes that do not claim canonical infrastructure authority.

A name alone is insufficient when it would generate unreasonable false positives.

Tests must explicitly prove at least one legitimate canonical adapter/reuse path remains accepted.

## 11. Design Point — DP-039

### DP-039 — Canonical Domain Architecture Guard

> Domain specialization is constrained by the existing canonical Domain Validation fragmentation boundary, which fails closed on architectural attempts to recreate, redefine, or bypass shared CMM OS infrastructure while permitting legitimate adapters and canonical service reuse. No parallel architecture guard, runtime, store, registry, resolver, loader, semantic engine, session system, or permission system is introduced.

DP-039 is satisfied only when the guard operates through the existing `domain.fragmentation` validation step and installation gate.

## 12. Connected Acceptance Test — AT-DP-039

AT-DP-039 must prove real behavior through canonical components rather than isolated mocks.

Required connected path:

```text
test Domain Pack source
        ↓
DomainValidationRequest
        ↓
PipelineDomainValidator
        ↓
canonical validation steps
        ↓
domain.fragmentation
        ↓
DomainFragmentationValidator
        ↓
DomainValidationResult.fragmentation_valid
        ↓
ensure_domain_validation_allows_install(...)
```

### 12.1 Required positive scenario

A valid Domain Pack that reuses canonical infrastructure must:

- complete canonical validation without fragmentation blockers;
- produce `fragmentation_valid=True`;
- remain eligible with respect to the fragmentation installation gate;
- demonstrate that legitimate canonical adapters/reuse are not rejected.

### 12.2 Required negative scenarios

AT-DP-039, or directly connected supporting tests, must prove that representative packs are rejected for attempts to introduce at least:

1. parallel memory/store infrastructure;
2. parallel Knowledge Store;
3. parallel Knowledge Graph;
4. parallel Planner;
5. parallel Agent Runtime;
6. parallel reasoning engine;
7. parallel Workflow Engine;
8. parallel permission system;
9. parallel session store/context infrastructure;
10. protected contract redefinition;
11. direct known persistence/backend bypass;
12. a statically demonstrable global validation/policy bypass;
13. incompatible/parallel operation-result infrastructure.

For each blocking scenario the test must show:

```text
finding emitted
→ fragmentation step fails
→ fragmentation_valid=False
→ installation gate rejects
```

### 12.3 Inherited regression assertions

AT-DP-039 or the Phase 10.39 gate suite must additionally prove:

- DP-036 structural anti-fragmentation remains green;
- current canonical Domain Pack anti-fragmentation tests remain green;
- `CANONICAL_DOMAIN_EVENTS` remains 23/23;
- no DomainAPI architectural expansion occurs;
- validation remains side-effect-free with respect to domain registries, persistence, sessions, permissions, and event infrastructure;
- scanner never executes untrusted Domain Pack Python code.
