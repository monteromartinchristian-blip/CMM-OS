## 1. Purpose

Remediation V3 exists only to close the three findings reported by Independent Re-audit V3:

- `MAJOR-V3-01` — canonical Provider Registry graph identity is not enforced across public composition/capture boundaries;
- `MAJOR-V3-02` — successful rediscovery of an already-known route can mutate live `last_seen_at` without durable persistence;

- CMMChat deferral;

## 2. Authoritative findings and evidence

### 2.1 `MAJOR-V3-01`

Independent Re-audit V3 demonstrated that two simultaneously live `ProviderRegistry` instances can contain the same normalized provider id while holding different provider definitions.

A `ProviderManifestRegistry` bound to ProviderRegistry A can then be cross-wired with:

- ProviderRegistry B;
- `ModelCatalog(B)`;
- `ProviderConnectionRegistry(B)`;
- `ModelRouteCatalog(connections_B)`.

The current graph is accepted because public composition/capture boundaries verify types and provider ids, but not exact object authority.

Consequences independently reproduced:

```text
CAPTURE_ACCEPTED_CROSS_AUTHORITY=True
PERSISTED_PROVIDER_BASE_URL=https://canonical-provider.example/v1
PERSISTED_MANIFEST_BASE_URL=https://foreign-manifest.example/v1
```

and onboarding can derive an accepted connection endpoint from the foreign manifest while registering the connection under the other provider authority.

This violates the load-bearing `DP-134` invariant that Provider Registry identity has exactly one authoritative inventory.

### 2.2 `MAJOR-V3-02`

Canonical `discover_models()` calls `ModelRouteCatalog.mark_seen()` for an already-known available route.

That advances:

```text
last_seen_at
```

without producing any of the lifecycle tuples:

```text
new_route_ids
restored_route_ids
unavailable_route_ids
```

The coordinator currently persists only when at least one lifecycle event exists.

Therefore:

```text
live last_seen_at = T1
persisted last_seen_at = T0
restart restores T0
```

A successful phase-owned state mutation is lost on restart.

This violates the persistent-state portion of `DP-134`.

## 3. Architectural principle

Remediation V3 must close the findings by strengthening existing boundaries, not by introducing new infrastructure.

Forbidden solution classes include:

- `ProviderRegistryGraph` or equivalent new aggregate authority;
- a second provider registry;
- synchronization between registries;
- automatic re-binding/adoption of foreign components;
- generic dependency injection containers;
- generic transaction frameworks;
- new persistence frameworks;
- new routing engines;
- new validation runtimes;
- repository-wide formatting cleanup.

The corrective pattern is:

```text
validate exact canonical object graph
→ fail closed before mutation

and

detect real route-state mutation
→ audit
→ persist through existing coordinator
```

## 4. `MAJOR-V3-01` — exact canonical graph identity

### 4.1 Canonical identity rule

The canonical Provider Registry graph for one runtime is:

```text
ProviderRegistry P
├── ProviderManifestRegistry(provider_registry=P)
├── ModelCatalog(provider_registry=P)
├── ProviderConnectionRegistry(provider_registry=P)
└── ModelRouteCatalog(connections=<the exact ProviderConnectionRegistry above>)
```

The same normalized `provider_id` appearing in two different `ProviderRegistry` objects does not establish identity.

The required invariant is exact object identity.

### 4.2 Required read-only binding accessor

`ProviderManifestRegistry` already exposes:

```python
provider_registry
```

`ProviderConnectionRegistry` already exposes:

```python
provider_registry
```

`ModelRouteCatalog` already exposes:

```python
connections
```

`ModelCatalog` must add the smallest missing read-only accessor:

```python
@property
def provider_registry(self) -> ProviderRegistry:
    ...
```

This accessor exposes the existing binding only.

It must not allow rebinding or mutation.

### 4.3 Capture guard

`capture_provider_registry_state()` must reject a graph before enumeration/serialization unless all exact-object conditions hold:

```python
manifests.provider_registry is providers
models.provider_registry is providers
connections.provider_registry is providers
routes.connections is connections
```

If any condition fails, raise:

```text
ProviderStateCoherenceError
```

with a sanitized message identifying the mismatched component kind.

Do not attempt to:

- normalize by id;
- copy data into the supplied authority;
- rebuild components silently;
- ignore the mismatch;
- select one registry heuristically.

No `ProviderRegistryState` may be produced from a cross-authority graph.

### 4.4 Coordinator construction guard

`ProviderRegistryStateCoordinator.__init__()` must enforce the same graph invariants before assigning any component to internal state.

Construction must fail before the coordinator can be used when:

```text
manifests.provider_registry is not providers
models.provider_registry is not providers
connections.provider_registry is not providers
routes.connections is not connections
```

A focused coherence/configuration error must be raised.

Preferred error class:

```text
ProviderStateCoherenceError
```

if that existing error semantically fits all graph mismatches.

Do not add a second error hierarchy unless required by existing public contracts.

### 4.5 Coordinator read-only binding properties

`ProviderOnboardingService` must be able to verify that an optional coordinator belongs to the exact same graph.

Expose only the minimal read-only properties necessary, e.g.:

```python
@property
def providers(self) -> ProviderRegistry: ...

@property
def manifests(self) -> ProviderManifestRegistry: ...

@property
def models(self) -> ModelCatalog: ...

@property
def connections(self) -> ProviderConnectionRegistry: ...

@property
def routes(self) -> ModelRouteCatalog: ...
```

These expose existing object references.

They must not permit rebinding.

If repository conventions favor one internal graph-validation method plus fewer properties, that is acceptable only if onboarding can still prove exact object identity without reaching into private attributes.

### 4.6 Onboarding construction guard

`ProviderOnboardingService.__init__()` must fail before accepting candidates if:

```python
manifests.provider_registry is not providers
connections.provider_registry is not providers
```

When `state_coordinator` is present, it must additionally prove that the coordinator is wired to the same exact graph used by onboarding.

At minimum:

```python
state_coordinator.providers is providers
state_coordinator.manifests is manifests
state_coordinator.connections is connections
```

If the coordinator exposes complete graph properties, onboarding may also verify models/routes only when onboarding already owns those exact objects. Do not invent dependencies solely to perform redundant checks.

The service must not be constructible with foreign manifests carrying the same provider ids.

### 4.7 Fail-before-mutation requirement

Every graph-identity rejection must occur:

```text
during construction or before first operation mutation
```

No credential write, profile creation, connection registration, route mutation, audit record, revision increment or persistence save may occur before rejection.

### 4.8 Restore behavior

`restore_provider_registry_state()` already rebuilds one graph in dependency order:

```text
providers
→ manifests
→ models
→ connections
→ routes
```

Remediation V3 must preserve that behavior.

No new graph wrapper is introduced.

The restored graph must naturally satisfy all new exact-object guards.

## 6. `MAJOR-V3-02` — durable refresh mutation

### 6.1 Preserve canonical discovery

Do not change the architectural role of:

```text
kernel/llm/model_discovery.py
```

`discover_models()` remains:

- administrative;
- inference-free;
- injected-client based;
- responsible for route reconciliation rules.

The fix belongs in the state coordinator's interpretation/persistence of the resulting canonical state mutation.

### 6.2 Route refresh is a real mutation

For an existing route that is:

```text
available=True
```

and is advertised again successfully at a newer aware timestamp:

```text
T0 → T1
```

`mark_seen()` changes:

```text
last_seen_at
```

This is phase-owned durable state.

The coordinator must not leave that mutation live-only.

### 6.3 Pre/post route-state comparison

Before discovery:

```python
routes_before = routes.list()
```

After canonical `discover_models()`:

```python
routes_after = routes.list()
```

The coordinator must determine which routes changed.

Lifecycle transitions continue to use:

```text
route.discovered
route.unavailable
route.restored
```

For a route that:

- existed before;
- remained available;
- was not newly discovered;
- was not restored;
- was not newly marked unavailable;
- has `last_seen_at` changed;

emit:

```text
route.refreshed
```

### 6.4 Refresh audit record

A `route.refreshed` record must be sanitized.

Allowed detail may include:

```text
connection_id
available=true
```

Do not persist:

- provider payload;
- model-list response;
- raw config;
- credential material;
- source authentication data.

The route timestamp already exists in canonical state and does not need duplication in audit detail unless existing audit conventions require it.

### 6.5 Revision semantics

One discovery call that changes any durable route state is one mutation batch.

Whether it produces:

- one lifecycle event;
- multiple lifecycle events;
- only refresh events;
- a mixture of lifecycle and refresh events;

the coordinator advances:

```text
revision + 1
```

exactly once after successful repository save.

All records in that batch carry the same next revision.

### 6.6 No duplicate refresh event

A route must not receive `route.refreshed` in the same pass when it already receives:

```text
route.discovered
route.restored
route.unavailable
```

Lifecycle transition semantics take precedence.

### 6.7 True no-op definition

A discovery pass is a true no-op only when canonical phase-owned state does not change.

Examples:

#### True no-op

- empty discovery result protected by the existing empty-result guard;
- repeated unavailable/deferred state with no timestamp or availability change;
- an identical pass using the same `seen_at` where all resulting route fields remain equal.

#### Durable mutation

- `last_seen_at` advances;
- availability changes;
- a route is created;
- a route is restored;
- a route becomes unavailable.

### 6.8 Persistence failure rollback

If discovery mutates routes and the repository save fails:

```text
routes restore exactly to routes_before
revision unchanged
audit_log unchanged
durable state unchanged
original failure propagates
```

This includes a refresh-only discovery failure.

No general transaction system may be introduced.

Use the existing:

```text
ModelRouteCatalog.restore_all()
```

rollback seam.

## 7. `MAJOR-V3-02` adversarial acceptance

Strengthen `AT-DP-134`.

### 7.1 Durable refresh across restart

Run:

```text
discover route at T0
persist
rediscover same route at T1
persist
reload repository
restore graph
```

Require:

```text
revision after T0 = R
revision after T1 = R + 1
live last_seen_at = T1
persisted last_seen_at = T1
restored last_seen_at = T1
route.refreshed present
```

### 7.2 Refresh-only event semantics

For the second pass:

```text
route.discovered absent
route.unavailable absent
route.restored absent
route.refreshed present
```

for the already-known available route.

### 7.3 Same-timestamp true no-op

After a persisted route at `T1`, rerun discovery with exactly `T1`.

If no field changes:

```text
revision unchanged
audit_log unchanged
repository bytes/state unchanged
```

### 7.4 Refresh persistence failure

Force repository failure on the refresh-only pass.

Require:

```text
live route rolled back to T0
revision remains previous revision
audit log unchanged
repository remains at T0
```
