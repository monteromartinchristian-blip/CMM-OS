## 2. Objective

Phase 11.1 will create the platform-level integration core that composes already-existing CMM OS subsystems through stable, explicit and version-aware contracts without taking ownership away from those subsystems.

The outcome is that CMM OS can be assembled and validated as one application composition graph while preserving the architecture and invariants of Phases 0–10 and the already-closed Phase 11.34.

Phase 11.1 is an integration phase, not a rewrite phase.

## 3. Problem statement

CMM OS already contains mature, independently-owned subsystems for kernel execution, workflows, execution, validation, cognition, memory/knowledge, agents, domains, approvals, events, providers and related infrastructure.

The missing platform capability is a single explicit application composition boundary that can answer, deterministically and inspectably:

1. which platform services are active;
2. which canonical implementation owns each service;
3. which dependencies each service requires;
4. whether those dependencies are present and compatible;
5. whether the service graph contains cycles;
6. whether an implementation can be replaced without changing its consumers;
7. which public contract/version a service boundary exposes;
8. whether the resulting application composition is valid before operational use.

The solution must not introduce a parallel planner, runtime, registry family, store, event system, provider registry, domain system or cognitive system.

## 4. Design choice

### 4.1 Selected approach

Phase 11.1 will implement a **thin canonical composition root over existing authorities**.

The platform integration layer will hold references to canonical services and validate their relationships. It will not absorb or reimplement their domain logic.

Conceptually:

```text
Existing canonical subsystems
        ↓
Platform service descriptors
        ↓
IntegrationServiceRegistry
        ↓
ApplicationContainer
        ↓
Validated application composition snapshot
```

### 4.2 Rejected alternatives

#### A. New central framework that owns every subsystem

Rejected because it would duplicate existing registries, repositories, engines and runtimes and violate the Phase 11 no-duplication principle.

#### B. Import-only facade

Rejected because imports alone cannot prove dependency completeness, compatibility, replaceability, cycle freedom or active-service inspection.

#### C. Thin composition root with explicit metadata and validation

Selected because it adds only the missing platform boundary while preserving canonical ownership.

## 5. Scope

### 5.1 In scope

Phase 11.1 includes:

- `ApplicationContainer` as the platform composition root;
- `IntegrationServiceRegistry` as an explicit registry of platform-level service bindings;
- immutable service descriptors;
- dependency declaration and deterministic resolution;
- missing-dependency detection;
- incompatible-registration detection;
- duplicate-authority detection;
- dependency-cycle detection;
- implementation replacement through explicit bindings;
- test/in-memory adapters through the same binding mechanism;
- modular contribution of bindings without import-time mutation;
- inspection of active services and their dependency graph;
- public-contract metadata and compatibility validation;
- strict composition configuration sufficient for 11.1;
- composition validation before the container becomes ready;
- composition tests;
- `DP-101` and connected `AT-DP-101`;
- integration reference documentation;
- requirements-matrix traceability for `F11-015`.

### 5.2 Explicitly out of scope

Phase 11.1 must not implement or silently pull forward:

- Phase 11.2 Orchestrator;
- Intent Resolver;
- Context Resolver;
- Domain Router or Agent Router;
- application API/backend;
- conversational flow;
- a new Event Bus;
- global persistence/storage architecture;
- migrations;
- authentication or authorization;
- secrets management;
- Model Gateway;
- routing policy;
- provider discovery beyond reuse of the closed Provider Registry;
- plugin installation, sandboxing, upgrade or uninstall lifecycle;
- remote transport protocols;
- UI or CMMChat integration;
- new domain logic;
- new agent-runtime logic;
- changes to canonical provider identity semantics from Phase 11.34.

A later phase may consume the 11.1 integration surface. 11.1 itself only establishes and validates that surface.

## 6. Permanent architectural invariants

The implementation must preserve all inherited invariants, including:

1. one shared kernel;
2. one canonical Cognitive Layer;
3. one canonical Agent Runtime;
4. one canonical domain system;
5. one canonical validation system;
6. one canonical memory/knowledge architecture;
7. no parallel executable Tool Registry;
8. no second Provider Registry;
9. no direct bypass of canonical permission/approval boundaries;
10. no import-time global registration side effects;
11. no new hidden side effects from composition;
12. no weakening of fail-closed behavior;
13. structured results whenever a structured contract exists;
14. no silent contract-version downgrade;
15. canonical authorities remain owners of their internal state and lifecycle;
16. platform composition may hold references but must not clone stateful subsystems;
17. the quarantine stash is never modified by Phase 11.1 work;
18. no push or merge as part of the subphase workflow.

## 7. Canonical reuse boundary

The inspected repository already contains significant reusable infrastructure. Phase 11.1 must treat this as authoritative unless implementation-time inspection demonstrates a blocking incompatibility.

### 7.1 Existing composition roots

Phase 9 already introduced existing-system integration composition roots and tests asserting that the composition root holds references rather than constructing parallel subsystems.

Phase 11.1 must reuse that architectural principle. It may supersede the *platform-level entry boundary* but not recreate the underlying runtime/planner/cognitive systems.

### 7.2 Existing subsystem registries

Existing registries include, among others:

- domain registries and domain component registries;
- workflow registries;
- operation registries;
- execution registries;
- validation registries;
- cognitive rule registries;
- agent-runtime registries;
- Provider Registry from Phase 11.34.

`IntegrationServiceRegistry` is therefore **not** a replacement for any of them.

It registers platform service **bindings**, not domain operations, models, workflows, rules, providers, agents or validators themselves.

### 7.3 Phase 11.34 Provider Registry

The Provider Registry is already closed and audited under `F11-014` / `DP-134`.

Phase 11.1 may bind the canonical provider-registry service into the application container, but it must not:

- create an alternate provider identity owner;
- persist parallel provider state;
- infer providers independently;
- redefine provider manifests, connections, routes, models or onboarding ownership;
- modify `DP-134` semantics.

## 8. Platform package boundary

The preferred new package boundary is:

```text
cmm/platform/
```

Its responsibility is platform composition only.

A likely internal structure is:

```text
cmm/platform/
├── __init__.py
├── contracts.py
├── service_registry.py
├── container.py
├── configuration.py
├── compatibility.py
├── modules.py
├── errors.py
└── inspection.py
```

The implementation plan may refine file names after re-reading the exact source tree, but it must preserve these responsibility boundaries and avoid a monolithic module.

## 9. Public contract strategy

### 9.1 Principle

The Phase 11 roadmap lists the minimum public contract vocabulary:

- `Command`;
- `Query`;
- `Event`;
- `Operation`;
- `Workflow`;
- `Goal`;
- `Session`;
- `ApprovalRequest`;
- `ValidationResult`;
- `ReasoningResult`;
- `KnowledgeItem`;
- `MemoryRecord`;
- `DomainDefinition`;
- `AgentResult`;
- `ErrorResult`.

Phase 11.1 must not interpret this list as permission to duplicate already-existing models.

### 9.2 Canonicalization matrix

Before creating any new public model, implementation must classify each roadmap contract as exactly one of:

- `CANONICAL_EXISTING` — an existing production type remains authoritative;
- `CANONICAL_ADAPTED` — an existing authoritative type is exposed through a stable reference/facade without copying its state model;
- `NEW_PLATFORM_BOUNDARY` — no suitable canonical contract exists and a minimal platform-boundary contract is necessary.

The matrix must record:

- roadmap contract name;
- canonical Python symbol/module when existing;
- canonical owner/subsystem;
- public contract metadata;
- compatibility rule;
- classification;
- justification for any new contract.

### 9.3 Known inspected anchors

The inspection confirms at least:

- `DomainDefinition` exists under the canonical domain contracts;
- `AgentResult` exists under `cmm.agent_runtime.contracts`;
- `ErrorResult` was not found as an existing production symbol by the inspection;
- `ContractMetadata` was not found as an existing production symbol by the inspection;
- existing subsystems already use several independent version/schema-version mechanisms.

Therefore, implementation must reuse existing types where present and may introduce a minimal platform `ErrorResult` and `ContractMetadata` only if re-inspection at implementation time confirms that no canonical equivalent exists.

### 9.4 No model cloning

An adapter/facade must not create a second persisted copy of an authoritative object merely to make it look like a Phase 11 contract.

Reference-only wrappers or descriptors are preferred where a stable public surface is needed.

## 10. Contract metadata and compatibility

### 10.1 `ContractMetadata`

The integration layer needs an immutable metadata value describing the public contract boundary.

Minimum semantic fields:

```text
contract_name
contract_version
schema_version
owner
```

Optional metadata may include deprecation state or compatibility notes only if needed by the implementation plan.

`ContractMetadata` describes a boundary. It does not replace version fields already owned by canonical models.

### 10.2 Compatibility

Phase 11.1 will implement deterministic compatibility checks.

Initial policy should be deliberately conservative:

- exact schema-version compatibility by default;
- explicit compatible ranges only where a canonical subsystem already defines them or where the spec/plan explicitly adds a tested rule;
- unknown or malformed versions fail closed;
- no silent coercion or downgrade;
- no network lookup during compatibility validation.

The design intentionally avoids a general migration framework; migrations belong to later Phase 11 work.

## 11. Service descriptor

Each platform service binding will be described by immutable metadata equivalent to:

```text
service_id
contract
implementation_id
dependencies
mode
metadata
```

Where:

- `service_id` is a stable platform-level identity such as `domain.registry` or `validation.application`;
- `contract` identifies the public contract metadata required/exposed;
- `implementation_id` identifies the bound implementation for inspection and diagnostics;
- `dependencies` is an ordered/canonical set of required service dependencies plus compatibility constraints;
- `mode` may identify local/in-process versus adapter-backed binding when needed;
- `metadata` is non-authoritative descriptive data only.

Descriptors must not contain secrets, provider credentials, mutable runtime state or copied sensitive domain content.

## 12. IntegrationServiceRegistry

### 12.1 Responsibility

`IntegrationServiceRegistry` is the authoritative registry of **platform composition bindings only**.

It must support:

- explicit registration;
- lookup by stable service ID;
- deterministic listing;
- dependency inspection;
- replacement of a binding before container readiness;
- test adapter registration through the same API;
- modular contribution of bindings;
- validation of the complete service graph.

### 12.2 Registration rules

Registration must fail closed when:

- `service_id` is empty or malformed;
- the same service ID is registered twice without an explicit replacement operation;
- a replacement violates the required contract;
- the descriptor declares malformed contract metadata;
- an implementation object does not satisfy the required runtime/protocol boundary where this can be verified safely;
- a dependency references an unavailable required service;
- a contract/schema version is incompatible;
- a dependency cycle exists;
- two bindings claim the same singleton platform authority under incompatible identities.

### 12.3 Replacement

Replacement exists to support testing and replaceable adapters.

It must be explicit and validated. Consumers depend on the stable service contract/ID, not on concrete implementation classes.

Replacement must not mutate canonical internal registries owned by the service being replaced.

### 12.4 No service locator leakage

The registry is a composition mechanism, not permission for arbitrary runtime code to fetch global dependencies from anywhere.

Normal production components should continue to receive collaborators through explicit dependency injection.

## 13. Dependency graph

The registry will build a deterministic directed dependency graph over platform service IDs.

Validation must detect:

- missing required dependencies;
- self-dependencies;
- circular dependencies;
- incompatible dependency contract versions;
- duplicate authority claims.

Cycle detection must happen before the container becomes ready.

Failure diagnostics must identify safe service IDs and reason codes without leaking sensitive configuration.

## 14. ApplicationContainer

### 14.1 Responsibility

`ApplicationContainer` is the platform composition root.

It owns the assembled **references** and the readiness state of the application composition. It does not own the internal state semantics of those referenced services.

### 14.2 Construction flow

Canonical flow:

```text
Read/receive strict 11.1 composition configuration
        ↓
Create or receive canonical subsystem instances
        ↓
Build service descriptors/bindings
        ↓
Register bindings
        ↓
Validate dependency graph and contract compatibility
        ↓
Freeze/mark registry ready
        ↓
Expose immutable inspection snapshot
```

### 14.3 Container states

The minimal state model should distinguish at least:

- building;
- ready;
- invalid/failed.

No operational request execution is introduced here.

### 14.4 Readiness

A container is `ready` only if all required service bindings pass compatibility and dependency validation.

Partial success is not readiness.

### 14.5 Immutability after readiness

The default production container must not allow arbitrary service replacement after readiness.

If later lifecycle phases need hot replacement, that behavior must be introduced under an explicit later contract rather than implicitly added to 11.1.

## 15. Configuration

### 15.1 Scope

Phase 11.1 configuration is **composition configuration only**.

It may define:

- enabled composition modules;
- required service IDs;
- selected implementation binding where multiple authorized implementations exist;
- mode flags required to choose local/in-process versus explicit adapter-backed implementations;
- expected contract/schema versions.

### 15.2 Non-scope

It must not become the Phase 11.12 Configuration Center and must not own:

- secrets;
- user preferences;
- model-routing policy;
- domain privacy policy;
- autonomy policy;
- credentials;
- general application settings unrelated to composition.

### 15.3 Validation

Configuration must be validated before service graph finalization.

Unknown required modules/services, malformed version constraints or impossible selections fail closed.

## 16. Modular loading and plugin boundary

The roadmap requires modular component loading and future plugin compatibility.

Phase 11.1 satisfies this through a small module/contributor contract that can contribute service bindings without import-time global mutation.

This is **not** the Phase 11.19 Plugin System.

Phase 11.1 does not:

- discover untrusted plugin packages;
- install plugins;
- execute arbitrary plugin entrypoints;
- manage plugin permissions;
- sandbox plugins;
- upgrade/uninstall plugins.

A future plugin system may adapt validated plugin capabilities into this composition contract.

## 17. Local and remote execution boundary

The 11.1 roadmap requires support for local and remote execution, but remote transport itself is out of scope.

11.1 therefore defines the composition capability necessary to bind either:

- an in-process/local implementation; or
- a future adapter-backed implementation satisfying the same stable service contract.

The registry/container must remain transport-agnostic.

No HTTP, RPC, subprocess or network client is required solely to claim 11.1 completion.

## 18. Error model

Composition failures must be structured and deterministic.

Expected categories include:

- invalid configuration;
- duplicate registration;
- missing dependency;
- incompatible contract;
- circular dependency;
- invalid replacement;
- duplicate authority;
- container not ready.

If a minimal platform `ErrorResult` is introduced, it is a boundary result only and must not replace canonical subsystem-specific error types internally.

No traceback, secret, credential or sensitive payload should be required in the public error representation.

## 19. Inspection surface

A ready container must expose a deterministic, side-effect-free inspection snapshot sufficient to determine:

- active service IDs;
- implementation IDs;
- public contract/version metadata;
- dependency IDs;
- binding mode;
- readiness/validation status.

Inspection must not expose:

- secrets;
- credentials;
- private prompts;
- sensitive domain content;
- private reasoning;
- mutable service internals.

## 20. `F11-015` requirement

`F11-015` is assigned to Phase 11.1 because `F11-001`…`F11-013` are inherited Phase 11 planning requirements and `F11-014` is already owned by the closed Phase 11.34 Provider Registry.

Canonical requirement text:

> **F11-015 — Canonical Integration Core.** CMM OS shall compose existing canonical subsystems through one explicit, version-aware application composition root and platform service-binding registry that preserves subsystem ownership, validates configuration and dependency/contract compatibility, prevents circular or duplicate authority, supports explicit implementation replacement/test adapters, exposes safe deterministic inspection, reuses the closed Provider Registry, and fails closed without implementing Phase 11.2 orchestration.

Planned requirement state before implementation: `NEW_CONTRACT_REQUIRED` / `REQUIRES_IMPLEMENTATION` as appropriate to the repository matrix vocabulary.

## 21. Design Point DP-101

### DP-101 — Canonical Application Composition Root

There must be exactly one Phase 11 platform composition root that assembles references to canonical subsystem implementations through explicit version-aware service bindings.

Verification requires proving all of the following:

1. canonical subsystem objects are reused rather than cloned into parallel runtimes/registries;
2. the closed Provider Registry is bound as the provider authority rather than reconstructed;
3. service dependencies are explicit and inspectable;
4. incompatible or missing dependencies fail before readiness;
5. dependency cycles fail before readiness;
6. implementation replacement works through the same contract without changing consumers;
7. a test/in-memory adapter can replace a compatible binding;
8. duplicate platform authority is rejected;
9. the ready container exposes a deterministic safe snapshot;
10. no orchestration behavior from 11.2 is implemented to satisfy the acceptance.

## 22. Acceptance Test AT-DP-101

`AT-DP-101` must be a connected acceptance test, not a mock-only unit test.

It must instantiate the real `ApplicationContainer` and `IntegrationServiceRegistry` with a representative set of canonical or official in-memory subsystem implementations.

At minimum the connected graph must include representatives of:

- validation;
- Cognitive Layer / knowledge-memory boundary;
- Agent Runtime integration;
- Domain Intelligence/Domain Registry;
- workflow/execution boundary where canonical construction permits;
- the canonical Phase 11.34 Provider Registry.

The acceptance must prove a successful ready composition and then exercise fail-closed variants for:

- missing dependency;
- incompatible contract/schema version;
- circular dependency;
- duplicate authority;
- invalid implementation replacement.

It must also prove a compatible test-adapter replacement without consumer modification and verify the safe deterministic inspection snapshot.

The test must use real canonical components or their official in-memory implementations. Isolated mocks may support narrow unit tests but cannot be the sole evidence for `AT-DP-101`.

## 24. Implementation discipline

Implementation must follow:

```text
TEST RED
→ minimal implementation
→ GREEN
→ controlled refactor
→ next block
```

Each block must preserve previously closed phases.

No implementation block may proceed while a newly introduced regression remains unresolved.

No new registry, loader, resolver, store, runtime or engine may be added merely because it is convenient. Every new abstraction must be justified by a missing 11.1 responsibility and must not overlap a canonical owner.

## 27. Expected completion state

When Phase 11.1 is complete and independently audited:

- CMM OS has one explicit platform composition root;
- canonical subsystems remain authoritative;
- platform service dependencies are explicit;
- the application composition can be validated before use;
- compatible implementations/test adapters can be substituted explicitly;
- incompatible, missing, cyclic or duplicate-authority compositions fail closed;
- public contract boundaries are version-aware;
- active services can be inspected safely;
- the closed Provider Registry remains canonical;
- Phase 11.2 can build orchestration on top of this stable integration surface without reopening the architectural foundation.
