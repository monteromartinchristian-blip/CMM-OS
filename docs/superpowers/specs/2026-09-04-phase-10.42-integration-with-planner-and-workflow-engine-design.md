## 1. Purpose

Phase 10.42 integrates Domain Intelligence with the canonical Planner and Workflow Engine without creating parallel planning, workflow, runtime, approval, validation, registry, persistence, or state infrastructure.

The phase exists to make domain capabilities first-class planning inputs while preserving the ownership boundaries already established by Phase 9 and hardened through Phase 10.39–10.41.

The roadmap objective is:

> Allow plans to use domain capabilities without introducing incompatible nodes.

The Phase 10.42 boundary must let the canonical planning path:

- query available Domain operations;
- query available Domain workflows;
- check dependencies;
- check effective permissions;
- account for multi-domain impact;
- represent required approvals;
- represent required validations;
- replan through the canonical replanning path;
- reuse Domain workflows/subworkflows through the existing Workflow Engine;
- stop fail-closed on conflicts, missing capabilities, or stale authority.

It must not:

- invent operations;
- invent workflows;
- expand permissions;
- assume that all registered domains or workflows are executable;
- duplicate workflows;
- create a Domain-specific Planner;
- create a Domain-specific Workflow Engine;
- maintain workflow state outside the canonical Workflow Engine;
- create a second planning store, workflow store, approval service, validation service, or execution runtime.

## 3. Architectural principle

Phase 10.42 follows one rule above all others:

> Domain Intelligence contributes a constrained, read-only capability view to canonical planning and delegates execution to existing owners.

The dependency direction remains:

```text
cmm.domains → cmm.agent_runtime
cmm.domains → cmm.workflows

cmm.agent_runtime → cmm.domains = 0
cmm.workflows → cmm.domains = 0
```

No Phase 9 module may import `cmm.domains`.

No shared Workflow Engine module may import `cmm.domains`.

If Phase 9 requires a new extension seam, it must be:

1. generic;
2. domain-agnostic;
3. minimal;
4. justified by a failing Phase 10.42 test;
5. reusable without knowing Domain concepts;
6. incapable of granting authority by itself.

## 4. Design Point DP-042

**DP-042 — Domain-specialized Planner and Workflow Engine integration**

Domain Intelligence exposes only registered, available, dependency-compatible and permission-compatible Domain operations and workflows to the canonical Phase 9 planning path through Domain-owned read-only adapters and, where strictly necessary, generic domain-agnostic extension seams. The canonical `TaskPlanner` / `AgentPlanningService` remains the sole plan owner and produces existing `AgentWorkflowPlan` contracts. Domain operations execute through the established Phase 10.41 dispatch path. Domain workflows and subworkflows execute through the existing `DomainWorkflowExecutor` backed by the shared `WorkflowEngine`. Approvals, validations, dependencies, checkpoints, replanning and workflow state remain owned by their existing canonical services. Domain permissions may only restrict capabilities. Authority is revalidated at execution boundaries and after pause/resume. `cmm.agent_runtime → cmm.domains` remains zero. No parallel planner, workflow engine, runtime, registry, store, approval, validation, event, checkpoint, persistence or state infrastructure is introduced.

## 6. Domain planning capability view

Phase 10.42 should introduce one Domain-owned read-only integration boundary that can project the effective Domain capability set needed for planning.

The design may use production names equivalent to:

```text
cmm/domains/planner_workflow_integration_contracts.py
cmm/domains/planner_workflow_integration.py
```

The public contract names are frozen in Section 6.4. Private helper names may be finalized in the implementation plan, but ownership and behavior are frozen by this spec.

### 6.1 Required input

The integration boundary must receive or derive, using existing canonical components:

- goal/objective identity;
- agent run identity when planning is attached to an Agent Runtime run;
- primary Domain;
- supporting Domains;
- Domain composition;
- effective profile where relevant;
- canonical resource references;
- available Domain operations;
- available Domain workflows;
- Domain dependencies;
- effective permissions;
- Domain approval requirements;
- Domain workflow/node permission decisions;
- relevant cross-domain coordination constraints;
- already-existing canonical budget/autonomy constraints when applicable.

### 6.2 Required output

The output is a read-only planning projection sufficient to populate or constrain existing Phase 9 planning contracts.

It must not be a second plan.

It may contain immutable records equivalent to:

```text
effective_domain_ids
available_operation_ids
available_workflow_ids
operation_dependencies
workflow_dependencies
required_permissions
required_approvals
required_validations
cross_domain_constraints
capability_references
authority_version/reference
metadata
```

The output must contain references and planning constraints, not execution state.

### 6.3 Authority semantics

The planning capability view is advisory to planning and restrictive to execution.

A capability appearing in the view does not permanently authorize it.

Before actual operation or workflow execution, current canonical permission/availability authority must be evaluated again.

Therefore:

```text
planned != authorized forever
registered != available
available at planning != available at execution
workflow selected != workflow authorized
approval node present != approval granted
validation node present != validation passed
```

### 6.4 Frozen Phase 10.42 public contract surface

The initial canonical Domain-owned surface is frozen to the following names:

```text
DomainPlanningCapabilityView
DomainPlannerWorkflowIntegrationRequest
DomainPlannerWorkflowIntegrationResult
DomainPlannerWorkflowIntegrator
DefaultDomainPlannerWorkflowIntegrator
```

`DomainPlanningCapabilityView` is an immutable value object only. It is not a registry, plan, store, permission context owner, or workflow state owner. Its conceptual fields are:

```text
primary_domain_id
supporting_domain_ids
available_operation_ids
prohibited_operation_ids
available_workflow_ids
operation_dependency_ids
workflow_dependency_ids
required_permission_ids
required_approval_ids
required_validation_ids
cross_domain_constraint_ids
authority_reference_ids
metadata
```

The exact nested representation may use tuples or immutable mappings according to neighboring Domain contract conventions, but the semantics above are required. Raw service/store/registry handles are forbidden.

`DomainPlannerWorkflowIntegrationRequest` binds:

```text
request_id
canonical DomainResolutionContext
canonical AgentPlanningRequest
optional current AgentWorkflowPlan reference for replan/resume
metadata
```

Identity conflicts between the Domain resolution context and the Agent planning request must fail closed.

`DomainPlannerWorkflowIntegrationResult` binds canonical objects by reference/value without cloning their ownership:

```text
request_id
DomainResolutionResult
DomainComposition
DomainPlanningCapabilityView
prepared AgentPlanningRequest
AgentWorkflowPlan | None
selected_domain_workflow_ids
blocked
reason_codes
metadata
```

`DomainPlannerWorkflowIntegrator` is a protocol. `DefaultDomainPlannerWorkflowIntegrator` is the only approved integration owner name. It owns coordination only and receives all stateful owners by dependency injection.

No Phase 10.42 service/store/engine/registry may be hidden inside this integrator.

### 6.5 Existing AgentPlanningRequest fields are the primary planning seam

Phase 9 already exposes generic planning fields sufficient for most Domain constraints:

```text
allowed_operations
prohibited_operations
required_validations
required_approvals
constraints
requirements
resource_ids
permissions
budget
autonomy_level
metadata
```

Phase 10.42 must project Domain operation authority into these existing fields before proposing any Phase 9 contract expansion. The most-restrictive combination wins. In particular:

```text
prepared.allowed_operations ⊆ incoming.allowed_operations when incoming restriction exists
prepared.prohibited_operations ⊇ incoming.prohibited_operations
prepared.permissions cannot add grants
prepared.autonomy_level cannot increase
prepared budget cannot increase
required approvals/validations are additive obligations, never removable obligations
```

Workflow identity is the only known capability not represented by a dedicated current `AgentPlanningRequest` field. The implementation plan must first characterize whether an existing generic metadata/reference seam can carry workflow references safely and be consumed deterministically. If not, exactly one minimal generic, domain-agnostic workflow-reference field or provider seam may be added to Phase 9 under RED. It must not import or name Domain types.

## 7. Operation discovery and planning

Phase 10.42 must allow the canonical planning path to plan Domain operations without inventing operation names.

### 7.1 Source of truth

Only operations present in the existing Domain operation infrastructure may be exposed.

The integration must reuse:

- existing operation registry/catalog contracts;
- existing availability logic;
- effective Domain permissions;
- existing composition result;
- existing Phase 10.41 execution path.

### 7.2 Planning projection

A Domain operation eligible for planning may be translated into the existing:

```text
AgentWorkflowOperation
```

The projection must preserve, when available:

- canonical operation identifier;
- task association;
- parameters or parameter references;
- required permissions;
- required validations;
- approval requirement;
- reversibility;
- rollback reference;
- risk;
- timeout;
- model/economic requirements already supported by the canonical contract;
- provenance/reference metadata.

No Phase 10.42 contract may redefine `AgentWorkflowOperation`.

### 7.3 Fail-closed rules

The planner integration must never expose or execute:

- nonexistent operations;
- unregistered operations;
- unavailable operations;
- operations outside the effective Domain composition;
- prohibited operations;
- operations whose required dependencies cannot be satisfied;
- operations blocked by current permissions;
- operations made stale by a later authority change.

---

## 8. Domain workflow discovery and planning

Phase 10.42 must make registered Domain workflows available as planning capabilities without converting Domain workflow ownership into Agent Runtime ownership.

### 8.1 Source of truth

Only existing `DomainWorkflowDefinition` instances resolved through canonical Domain workflow infrastructure may be exposed.

A workflow may be planned only when:

- it exists;
- it belongs to an effective Domain;
- its dependencies are satisfied or explicitly represented;
- its effective permissions permit planning/use;
- its required approvals/validations are representable;
- it is compatible with the current composition;
- it is not blocked by a conflict or unavailable capability.

### 8.2 Representation in the Agent plan

A Domain workflow must be represented by reference inside the existing planning model.

Phase 10.42 must not create `DomainAgentWorkflowPlan`, `DomainPlan`, or an alternative plan DAG.

The integration may use existing task metadata or a minimal generic Phase 9 extension seam to carry a referenced workflow identity, but:

- the workflow definition remains owned by `cmm.domains`;
- workflow state remains owned by the canonical workflow path;
- execution remains delegated to `DomainWorkflowExecutor`;
- the underlying engine remains `cmm.workflows.engine.WorkflowEngine`.

### 8.3 Subworkflow reuse

Subworkflow reuse must use existing Domain workflow/subworkflow semantics and the shared Workflow Engine.

A subworkflow must never be expanded by copying its implementation into a second plan-owned workflow runtime.

The planner may reference it, constrain it, and order it; execution ownership remains unchanged.

## 9. Dependencies

The planner must be able to account for dependencies from both operations and workflows.

Dependencies must be projected into existing planning topology, preferably through existing:

```text
AgentWorkflowDependency
```

Dependency handling must:

- preserve deterministic ordering;
- detect missing dependencies;
- detect cycles using canonical validation where applicable;
- stop or fail closed on blocking unresolved dependencies;
- never synthesize nonexistent dependency capabilities;
- preserve cross-domain dependency provenance;
- avoid silently dropping a supporting Domain dependency.

---

## 10. Permissions and most-restrictive authority

Phase 10.42 does not create permissions.

It consumes existing Domain permission resolution and must preserve the rule:

> Domain specialization may restrict authority but may never expand authority granted by canonical global/runtime policy.

The effective planning capability set must be no broader than all applicable constraints.

The execution boundary must re-evaluate current authority.

At minimum:

```text
Domain permission deny wins
global/runtime deny wins
missing required permission fails closed
supporting Domain does not grant authority to primary Domain
primary Domain does not grant authority to supporting Domain
planning-time permission does not survive a later downgrade automatically
```

---

## 11. Approvals

Phase 10.42 may represent Domain-required approvals inside the canonical plan using existing:

```text
AgentWorkflowApprovalNode
```

It must not create:

- a Domain approval service;
- a Domain approval store;
- a Domain approval lifecycle;
- a second pause/resume mechanism.

Actual approval ownership remains Phase 9 canonical approval infrastructure.

The Phase 10.41 stale-authority protection is inherited:

- approval completion does not revive stale Domain authority;
- after approval/resume, current Domain permission state must still allow execution;
- an approval does not expand Domain permissions;
- an approval for one scope cannot authorize another scope.

---

## 12. Validations

Phase 10.42 may represent required validations using existing:

```text
AgentWorkflowValidationNode
```

It must not implement Phase 10.43.

The boundary in 10.42 is limited to:

- discovering validation requirements already declared by operation/workflow contracts;
- representing them in the canonical plan;
- preserving required validation ordering;
- ensuring required validations cannot be silently omitted or bypassed.

Phase 10.43 remains owner of broader Domain Validation System integration, policy families, pack validation, and result validation architecture.

---

## 13. Replanning

Replanning remains owned by:

```text
AgentPlanningService
DefaultWorkflowPlannerAdapter.replan(...)
InMemoryWorkflowPlanStore
```

Phase 10.42 may provide updated Domain planning capability projections to a replanning request or generic planning seam.

It must not create a Domain replanning engine.

Replanning must occur when a material constraint invalidates the prior plan, including:

- operation becomes unavailable;
- workflow becomes unavailable;
- permission is downgraded;
- approval cannot be satisfied;
- required dependency disappears;
- Domain composition changes;
- conflict becomes blocking;
- operation/workflow failure triggers canonical recovery/replanning;
- supporting Domain changes invalidate a cross-domain dependency.

A stale plan may be superseded, but must not gain authority merely because it was once valid.

---

## 14. Cross-domain planning and handoff

Multi-domain planning must reuse existing composition and cross-domain contracts.

`CrossDomainPlannerPort` and `CrossDomainWorkflowPort` remain coordination ports.

Phase 10.42 may provide concrete adapters connecting those ports to canonical planning/workflow capabilities where required, but must preserve:

- primary/supporting Domain distinction;
- explicit dependency/provenance;
- most-restrictive permissions;
- conflict propagation;
- explicit handoff;
- no implicit context transfer;
- no second planner inside `DefaultCrossDomainEngine`.

A cross-domain handoff must be represented as a planning/coordinating decision, not as untracked execution.

---

## 15. Workflow execution

When the canonical plan reaches a Domain workflow reference:

```text
Agent plan
→ Phase 10.42 Domain workflow dispatch adapter
→ DomainWorkflowExecutor
→ WorkflowEngine
```

The Phase 10.42 adapter is a thin integration boundary only.

It must not own:

- workflow run persistence;
- workflow node state;
- workflow transitions;
- pause state;
- retry state;
- rollback state;
- engine lifecycle.

Those remain in the existing Domain workflow / shared Workflow Engine infrastructure.

Current permission and dependency gates must be evaluated at the appropriate Domain workflow execution boundaries.

---

## 16. Operation execution

When the canonical plan reaches a Domain operation:

```text
Agent plan
→ existing Phase 10.41 operation projection
→ Agent Runtime canonical operation execution
→ DomainOperationDispatchAdapter
→ DefaultDomainOperationOrchestrator
→ current DomainPermissionGate
→ DomainOperationExecutionDelegate
→ registered implementation
```

Phase 10.42 must not add a shorter route.

Every planned Domain operation must ultimately traverse the current gate at actual dispatch time.

## 17. Error and conflict handling

Phase 10.42 must be fail-closed.

Expected classes of outcome include:

```text
capability unavailable
capability not registered
dependency missing
dependency cycle
permission denied
approval required
validation required
domain conflict
stale authority
workflow unavailable
subworkflow unavailable
workflow execution blocked
operation execution blocked
replan required
```

The exact public error/result contracts should reuse existing status/error families where possible.

A new Phase 10.42 error type is justified only for integration-specific contract/configuration failures that cannot be represented by an existing canonical error.

Do not use broad exception swallowing to translate programmer/configuration errors into successful planning results.

Unexpected exceptions should propagate unless an existing canonical boundary explicitly defines a safe failure result.

## 24. Required adversarial acceptance scenarios

AT-DP-042 and focused integration tests must prove at least:

### 24.1 Nonexistent operation

```text
operation not registered
→ not exposed as planning capability
→ not present in executable plan
→ implementation calls = 0
```

### 24.2 Prohibited operation

```text
operation registered
+ effective permission deny
→ not executable
→ implementation calls = 0
```

### 24.3 Unavailable workflow

```text
workflow requested
+ unavailable / ineligible
→ workflow does not start
→ WorkflowEngine execution calls = 0
```

### 24.4 Permission downgrade after planning

```text
plan created while permitted
→ Domain authority changes to deny
→ execution boundary re-evaluates authority
→ stale plan does not execute
```

### 24.5 Approval-required capability

```text
plan contains canonical approval node
→ no valid approval
→ execution pauses/blocks
→ approval cannot be bypassed
→ valid scoped approval + unchanged authority may continue
```

### 24.6 Validation-required capability

```text
plan contains required validation node
→ required validation cannot be silently removed or skipped
```

### 24.7 Cross-domain conflict

```text
primary + supporting Domains
→ blocking capability conflict
→ no silent authority merge
→ fail closed or canonical replan
```

### 24.8 Subworkflow reuse

```text
Domain workflow references subworkflow
→ shared WorkflowEngine path used
→ no copied/parallel workflow runtime
```

### 24.9 Replanning

```text
material capability change
→ canonical AgentPlanningService replanning path
→ previous plan version superseded
→ no Domain replanning engine
```

## 34. Frozen architectural decisions

The following are frozen by this approved design:

1. **Single Planner owner:** canonical Phase 9 planning path.
2. **Single plan contract:** `AgentWorkflowPlan`.
3. **Single workflow engine:** `cmm.workflows.engine.WorkflowEngine`.
4. **Domain workflow owner:** existing Domain workflow infrastructure.
5. **Operation execution:** existing Phase 10.41 path.
6. **Domain-owned integration boundary:** Domain-specific knowledge stays in `cmm.domains`.
7. **Zero reverse import:** Phase 9 and shared Workflow Engine do not import Domains.
8. **Read-only planning projection:** planning view does not own runtime state.
9. **Most-restrictive permissions:** Domain specialization only restricts.
10. **Execution-time revalidation:** planning-time authority is not durable.
11. **Canonical approvals/validations:** represented in existing plan nodes, enforced by existing owners.
12. **Canonical replanning:** no Domain replanning engine.
13. **Subworkflow reuse:** through existing workflow infrastructure, not duplication.
14. **Connected acceptance:** real canonical / official in-memory components.
15. **No closure before independent PASS.**

Any implementation that violates one of these decisions requires stopping and revising the spec before proceeding.
