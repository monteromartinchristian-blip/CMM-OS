## 5. MAJOR-01 — Canonical Conversational Intent Entry

### 5.1 Problem

Phase 11.2 already owns deterministic intent resolution.

Its `DeterministicIntentResolver` recognizes the existing structural input:

```text
question
```

as `IntentKind.QUESTION`.

`QUESTION` is not a side-effect intent and is not shape-bound beyond that structural text field.

The current Phase 11.3 adapter maps an `ApplicationMessage` to:

```text
message_id
content
content_type
metadata
```

so a normal conversation has no canonical intent signal and stops at clarification.

### 5.2 Locked remediation

Do **not** modify the Phase 11.2 intent resolver.

Do **not** implement natural-language classification in `cmm.conversation`.

Do **not** add a model call.

Do **not** let arbitrary caller metadata choose intent.

Instead, the narrow application seam shall be:

```text
ApplicationChannel.CONVERSATION
+
ApplicationMessage.content
↓
RequestApplicationService application→orchestration mapping
↓
existing OrchestrationRequest.input["question"] = content
↓
existing DeterministicIntentResolver
↓
IntentKind.QUESTION
↓
existing canonical Domain routing
```

The existing `content` field remains present for backward-safe application semantics.

The `question` structural signal is added **only** for `ApplicationChannel.CONVERSATION`.

The existing API and CLI message mappings remain byte/semantically unchanged unless tests require a purely additive serialization update.

### 5.3 Why this does not create a router

The application adapter does not infer a domain, operation, Agent, workflow, capability, provider, permission, or execution route.

It only translates the meaning of the newly introduced Phase 11.5 application channel into a pre-existing Phase 11.2 canonical non-side-effect structural intent signal.

Phase 11.2 still decides:

```text
intent
authorized context
Domain route
execution route
policy
approval evidence
terminal orchestration status
```

### 5.4 Side-effect protection

The remediation must not map arbitrary conversation text to:

```text
COMMAND
GOAL
WORKFLOW_REQUEST
APPROVAL_RESPONSE
CANCELLATION
CONFIGURATION_CHANGE
INFORMATION_UPDATE
CONTINUATION
```

Those remain subject to their existing canonical structured shapes and later explicit application commands.

## 6. MAJOR-02 — Request/Session-Bound Domain Projection

### 6.1 Problem

A bare `ConversationalDomainView` is a value object, not provenance.

The current public service methods allow callers to supply it directly.

That permits a detached or cross-session view to become visible in another response.

### 6.2 Canonical authority already available

Phase 10.45 already defines:

```text
DomainInterfaceProjection
```

with:

```text
projection_id
request_id
resolution_reference_id
composition_reference_id
session_reference_id
conversational
content_digest
```

The constructor verifies the projection content digest.

The Orchestrator/application path already exposes canonical same-request evidence including:

```text
request_id
session_id
primary_domain
supporting_domains
trace_refs
```

and canonical Domain routing emits trace references containing the real Domain resolution identifier.

### 6.3 Public API rule

The public conversational call surface must no longer accept:

```text
domain_view: ConversationalDomainView | None
```

or any equivalent caller-provided raw conversational projection.

Public HTTP request models must not gain a domain projection input.

Clients cannot authorize Domain visibility by sending references or projection-shaped data.

### 6.4 Trusted projection-source seam

`ConversationService` may depend on one **read-only projection source protocol** composed at service construction time.

Conceptual contract:

```python
class AuthorizedDomainProjectionSource(Protocol):
    def get_projection(
        self,
        *,
        request_id: str,
        session_id: str,
        application_response: ApplicationResponse,
    ) -> DomainInterfaceProjection | None:
        ...
```

The final implementation name may differ only to match repository naming conventions; its semantics are fixed here.

This dependency:

- is not public per-turn caller data;
- stores nothing;
- resolves no Domain;
- composes no Domain;
- selects no Domain;
- owns no permission;
- owns no approval;
- owns no workflow;
- owns no session;
- must return either an already-authorized Phase 10.45 `DomainInterfaceProjection` or `None`.

It is a read-only bridge to canonical Phase 10.45 authority, not a new authority.

### 6.5 Mandatory binding verifier

Before the conversational projector can consume `projection.conversational`, the service/projector boundary must verify all applicable bindings.

At minimum:

```text
projection.request_id == application_response.request_id == current request_id
projection.session_reference_id == current canonical session_id
application_response.data["session_id"] == current canonical session_id
projection.conversational is not None
projection content_digest is valid by the Phase 10.45 contract
projection.conversational.primary_domain == application_response.data["primary_domain"]
projection.conversational.supporting_domains == application_response.data["supporting_domains"]
```

The projection's:

```text
resolution_reference_id
```

must also be bound to canonical same-request orchestration evidence.

The implementation shall use the existing Domain-resolution trace reference emitted by canonical Domain routing rather than inventing a second resolution identifier.

A mismatched:

```text
request_id
session_reference_id
resolution_reference_id
primary_domain
supporting_domains
```

fails closed and exposes **zero** Domain references.

### 6.6 Composition reference

`composition_reference_id` remains mandatory because it is part of the Phase 10.45 canonical projection contract.

Phase 11.5 must not synthesize or rewrite it.

Where the current orchestration result cannot independently cross-check composition identity, trust comes from the injected canonical projection source plus the Phase 10.45 content-bound projection contract.

The conversation layer must not create a second composer merely to validate this field.

### 6.7 No source available

If no canonical authorized projection source is composed:

```text
domain_projection = UNAVAILABLE
```

or equivalent truthful fail-closed state.

The conversational response must not reconstruct Domain visibility from:

```text
ApplicationResponse.data
metadata
Orchestration trace payloads
session metadata
caller references
```

### 6.8 AT-DP-105 implication

The corrected acceptance must demonstrate that the projection consumed by `AssistantResponse`:

1. carries the same request ID as the real conversational application/orchestration request;
2. carries the same canonical session ID;
3. binds to the same canonical Domain resolution evidence emitted by that Orchestrator traversal;
4. carries primary/supporting Domain membership equal to the real application result;
5. was produced through the Phase 10.45 projection contract/integrator, not manually reconstructed by `cmm.conversation`.

A direct Orchestrator-only control cannot count as the connected acceptance.

## 8. MAJOR-04 — Action / Approval / Workflow Truth

### 8.1 No new authority

The remediation must not implement:

```text
approval mutation
workflow mutation
workflow executor
action executor
permission engine
retry engine
replan engine
cancellation runtime
```

It only adds truthful public projection.

### 8.2 Action status contract

Add one narrow public status enum containing exactly the minimum Phase 11.5 statuses:

```text
proposed
approval_required
approved
rejected
blocked
unavailable
completed
failed
cancelled
```

Add one immutable public action-state value object conceptually equivalent to:

```python
ConversationActionState(
    reference: str,
    status: ConversationActionStatus,
    reason: str | None = None,
)
```

The final implementation may add one non-authoritative categorical `kind` field if needed to distinguish action versus approval without inventing owners.

No arbitrary executable payload belongs in this contract.

### 8.3 AssistantResponse amendment

`AssistantResponse` may gain one additive field:

```text
action_state
```

or the closest repository-consistent plural form.

It is a tuple/list of the new immutable action-state values.

Existing:

```text
proposed_actions
approval_requests
workflow_updates
```

remain reference-first surfaces and are not execution authority.

### 8.4 Approval projection

When an authorized Phase 10.45 projection exposes an approval reference that is awaiting approval, the conversational response may represent:

```text
status = approval_required
```

Visibility never becomes approval.

If canonical state exposes approved/rejected/blocked/completed/failed/cancelled later, only that canonical state may determine the status.

The conversation layer must not infer those terminal states.

### 8.5 Explicit unavailable controls

The Phase 11.5 capability surface is amended to add explicit control capabilities for operations required by the original spec but lacking canonical application commands.

At minimum:

```text
approval_response
workflow_pause
workflow_resume
workflow_cancel
workflow_retry
workflow_replan
action_execution
```

At the current baseline, each remains:

```text
status = UNAVAILABLE
effective = None
```

unless a pre-existing canonical application capability already proves otherwise.

`request_cancellation` remains a separate capability and keeps its existing semantics.

No route name alone is proof of availability.

### 8.6 Workflow visibility

Authorized workflow references may remain visible in:

```text
workflow_updates
```

but workflow control operations remain explicitly unavailable until a canonical application command exists.

No synthetic progress or workflow state may be fabricated.

```text

```

### 9.3 Authority

A mode:

- is interface/session metadata;
- creates no runtime;
- grants no capability;
- grants no Domain;
- grants no workflow;
- grants no goal;
- grants no permission.

This remediation does not require mode-specific execution semantics beyond the existing canonical message path.

The MAJOR-01 conversational structural mapping remains non-side-effecting.
