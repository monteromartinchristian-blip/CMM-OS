## 1. Purpose

Phase 10.41 connects the already completed Domain Intelligence subsystem to the already completed Phase 9 Autonomous Agent Runtime without creating a second runtime, planner, approval system, budget system, cognitive engine, memory system, persistence layer, event bus, trace system, or execution engine.

The objective is the roadmap objective:

> Allow the Phase 9 agent to use Domain specialization throughout its operation cycle.

The resulting system must allow a canonical Phase 9 agent execution to be constrained and informed by Domain resolution, Domain composition, Domain profiles, Domain cognition, Domain permissions, Domain operations, Domain autonomy limits, and Domain-specific budget ceilings while preserving all Phase 9 runtime ownership.

Phase 10.41 is therefore an **integration boundary**, not a new runtime subsystem.

## 3. Architectural decision

### 3.1 Chosen direction

Phase 10.41 is owned by `cmm.domains` and depends on the public contracts and services of `cmm.agent_runtime`.

Canonical dependency direction:

```text
cmm.domains
    ↓
cmm.agent_runtime
```

Forbidden reverse dependency:

```text
cmm.agent_runtime
    ✕
    ↓
cmm.domains
```

The Agent Runtime must remain Domain-agnostic.

### 3.2 Rejected architecture

The following design is explicitly rejected:

```text
AgentRuntimeIntegrationService
    ↓ imports
DomainResolver / DomainComposer / DomainProfile / DomainPermission
```

It would reverse the current dependency boundary, make Phase 9 aware of Phase 10, and create a permanent coupling that Phase 9 explicitly avoided.

### 3.3 Conditional fallback

A generic modification inside `cmm/agent_runtime/**` is permitted only if all of the following are true:

1. a focused RED test proves that the existing generic extension seam cannot express a required Phase 10.41 behavior;
2. the missing capability is generic Agent Runtime behavior rather than Domain-specific behavior;
3. the change does not import `cmm.domains`;
4. the change does not transfer ownership from Phase 9 to Phase 10;
5. the implementation report documents the reason and the regression surface;
6. all relevant Phase 9 regressions remain green.

No convenience-driven modification of Phase 9 is allowed.

## 5. Design Point DP-041

### DP-041 — Domain-specialized Agent Runtime integration

**Definition:**

Domain Intelligence configures and constrains the canonical Phase 9 Agent Runtime through existing generic extension seams and Domain-owned adapters, while preserving the one-way `cmm.domains → cmm.agent_runtime` dependency and canonical ownership of runtime lifecycle, cognition, planning, execution, validation, approvals, budgets, traces, persistence, recovery, and memory-update application.

DP-041 requires all of the following:

1. Domain resolution occurs before a Domain-specialized agent execution is created.
2. Supporting domains may be composed through the canonical Domain composition contracts.
3. The effective Domain profile is resolved by existing Domain profile infrastructure.
4. Phase 10.40 supplies Domain-specialized cognitive preparation; Phase 9 remains the runtime cognitive owner.
5. Domain permissions are intersected with Agent Runtime permissions; they never widen them.
6. Domain autonomy limits are ceilings; they never raise the global/session/agent level.
7. Domain budget policy only restricts the one canonical Phase 9 Action Budget.
8. Specialized Domain operations execute through the existing Agent execution / Domain operation orchestration path.
9. Domain workflow identity may be carried as already-resolved context, but Planner/Workflow Engine capability discovery and node integration remain Phase 10.42.
10. Approval is requested/resolved by canonical approval infrastructure.
11. Memory and knowledge changes remain proposal-driven and use existing Phase 8/9/10.18 contracts.
12. Domain and Agent traces are linked by identifiers/references rather than duplicated.
13. Domain resolution may be reevaluated at explicitly defined safe runtime boundaries.
14. No Phase 10.41 runtime store, state machine, event bus, planner, execution engine, approval service, budget service, cognitive engine, memory store, knowledge store, or trace store is introduced.
15. `cmm.agent_runtime` keeps zero imports from `cmm.domains`.

Initial requirements-matrix state after implementation but before independent audit:

```text
DP-041=IMPLEMENTED_PENDING_AUDIT
AT-DP-041=PASS
```

Final closure requires independent audit to establish:

```text
DP-041=VERIFIED_EXISTING
AT-DP-041=PASS
```

## 7. Proposed Phase 10.41 production surface

The implementation plan should begin with the following narrow surface unless a RED test demonstrates that a smaller or differently named surface is required by existing repository conventions.

### 7.1 New module: `cmm/domains/agent_runtime_integration_contracts.py`

This module contains only immutable integration value objects.

It must not contain services, stores, registries, loaders, executors, planners, or state machines.

#### `DomainActionBudget`

A frozen, slotted, deeply immutable Domain-side **constraint value object**, not a mutable budget and not a service.

Conceptual shape:

```python
@dataclass(frozen=True, slots=True)
class DomainActionBudget:
    domain_id: str
    maximum_operations: int | None = None
    maximum_iterations: int | None = None
    maximum_questions: int | None = None
    maximum_external_calls: int | None = None
    maximum_duration_seconds: int | None = None
    maximum_cost: Decimal | None = None
    metadata: Mapping[str, Any] = field(default_factory=dict)
```

Rules:

- values are ceilings, never allocations of new authority;
- booleans are rejected as integers;
- numeric values must be finite and non-negative/positive according to canonical Agent Runtime budget semantics;
- metadata must be immutable and secret-safe;
- a supporting Domain may only make the effective budget more restrictive;
- the object has no counters and no mutation methods;
- consumed/reserved state remains exclusively inside Phase 9 `ActionBudget` / `ActionBudgetService`.

Where Phase 9 has a native `BudgetResourceType`, the ceiling is projected onto the canonical budget using that type. At minimum the inspected repository already owns canonical operation, duration, and cost limits. Any additional roadmap dimension must bind to an existing Phase 9 counter/limit or remain a fail-closed pre-execution ceiling derived from canonical runtime evidence; Phase 10.41 must not invent an independent consumption ledger.

#### `DomainAgentRuntimeIntegrationRequest`

Conceptual shape:

```python
@dataclass(frozen=True, slots=True)
class DomainAgentRuntimeIntegrationRequest:
    request_id: str
    resolution_context: DomainResolutionContext
    agent_request: IntegratedAgentExecutionRequest
    cognitive_resources: tuple[DomainCognitiveResourceInput, ...] = ()
    domain_budget: DomainActionBudget | None = None
    force_domain_reevaluation: bool = False
    metadata: Mapping[str, Any] = field(default_factory=dict)
```

The wrapper binds canonical objects rather than cloning their contents.

Required invariants:

- `request_id` is non-empty;
- `resolution_context` is the canonical Domain contract;
- `agent_request` is the canonical Phase 9 contract;
- goal/session/actor identity must not conflict when represented in both objects;
- resources are Phase 10.40 inputs, not copied Phase 8 resource models;
- metadata is immutable and secret-safe;
- no raw service/store handles are serialised into the request.

#### `DomainAgentRuntimeDecision`

An immutable, structured decision record for Domain-specific integration decisions.

Minimum decision codes:

```text
DOMAIN_RESOLVED
DOMAIN_REEVALUATED
PRIMARY_DOMAIN_CHANGED
SUPPORTING_DOMAIN_ADDED
DOMAIN_COMPOSED
PROFILE_RESOLVED
DOMAIN_PERMISSION_RESTRICTED
DOMAIN_APPROVAL_REQUIRED
DOMAIN_AUTONOMY_RESTRICTED
DOMAIN_BUDGET_RESTRICTED
DOMAIN_OPERATION_SELECTED
DOMAIN_WORKFLOW_BOUND
DOMAIN_COGNITIVE_BOUND
DOMAIN_RUNTIME_BLOCKED
DOMAIN_RUNTIME_COMPLETED
```

Decision records contain IDs, reason codes, and safe metadata only. They must not contain hidden reasoning or copied upstream traces.

#### `DomainAgentRuntimeIntegrationResult`

Conceptual shape:

```python
@dataclass(frozen=True, slots=True)
class DomainAgentRuntimeIntegrationResult:
    request_id: str
    resolution: DomainResolutionResult
    composition: DomainComposition
    profile: ResolvedDomainProfile
    cognitive_result: DomainCognitiveIntegrationResult | None
    agent_result: IntegratedAgentExecutionResult | None
    decisions: tuple[DomainAgentRuntimeDecision, ...]
    domain_trace_id: str | None
    agent_trace_id: str | None
    memory_binding_ids: tuple[str, ...] = ()
    blocked: bool = False
    metadata: Mapping[str, Any] = field(default_factory=dict)
```

The result is an integration aggregate. It is not a replacement for `DomainResult` or `IntegratedAgentExecutionResult`.

It must preserve canonical objects/references rather than translate them into private duplicates.

### 7.2 New module: `cmm/domains/agent_runtime_integration.py`

## 8. Domain resolution and reevaluation

### 8.1 Initial resolution

Every Phase 10.41 execution must resolve the Domain from the canonical `DomainResolutionContext` before handing the specialized request to Phase 9.

The integration layer may not perform keyword-only or private resolution logic.

### 8.2 Reevaluation boundaries

The roadmap requires the Agent Runtime to reevaluate and change the active Domain. Phase 10.41 satisfies that without changing Phase 9's state machine by allowing the Domain-owned integration boundary to reevaluate only at explicit safe boundaries where new canonical evidence exists.

Permitted reevaluation boundaries:

1. initial execution;
2. explicit continuation/resume request;
3. retry or replan entry after Phase 9 returns a recoverable state and new observation/context is available;
4. explicit external request to reevaluate the Domain;
5. a Domain resolution result that itself requires clarification or signals that the current specialization is no longer valid.

Reevaluation must not occur silently inside an Agent operation after authorization has already been calculated.

If reevaluation changes the primary Domain or adds/removes supporting Domains, all of the following must be recalculated before further execution:

```text
composition
profile
permissions
autonomy ceiling
budget ceiling
cognitive context
operation/workflow eligibility
```

A previous approval must not be reused if the changed Domain makes its scope or fingerprint invalid.

### 8.3 Fail-closed reevaluation

A high-risk Domain becoming unavailable, disabled, unauthorized, ambiguous, or incompatible must not silently fall back to a less restrictive Domain when that would widen permissions or autonomy.

Existing Domain Resolver semantics remain authoritative.

Phase 10.41 must reuse it.

```python

```

The projection must be deterministic and contract-bound.

It may contain stable IDs and JSON-safe structured context such as:

```text
resolution_context_id

composition_id
primary_domain
supporting_domains
resolved_profile identifier/version
knowledge_package_id
canonical resource references
reasoning/rule result references
presentation/trace references when needed
```

- copied Phase 8 stores;

- mutable service objects;

## 10. Permission integration

Domain Permissions must only restrict Agent Runtime authority.

The effective execution authorization follows the established most-restrictive principle:

```text
Global / Agent policy
∩ User / Actor permissions
∩ Session permissions
∩ Domain composition permissions
∩ Operation requirements
∩ Autonomy policy
= effective authority
```

The Phase 10.41 boundary must use existing Domain permission infrastructure and then project the allowed/restricted result into the canonical Phase 9 `AgentPermissionContext` / security checks.

It must not synthesize permissions from Domain names, metadata labels, or operation strings.

Required rules:

1. Domain `DENY` remains denial.
2. Domain `APPROVAL_REQUIRED` cannot be translated into `ALLOW`.
3. A Domain `ALLOW` does not override an Agent Runtime denial.
4. Supporting Domains cannot widen the primary/effective permission set.
5. Cross-Domain access continues to use existing Phase 10.15 contracts.
6. Permission recalculation is mandatory after Domain reevaluation.
7. Raw approval booleans in metadata are not authority.
8. Existing approval/grant fingerprints, scope, actor, session, action and expiry semantics remain authoritative.

---

## 11. Approval integration

Phase 10.41 introduces no approval service.

Existing Domain permission gates and bridges may produce a canonical approval requirement, but the actual approval lifecycle remains owned by Phase 9 approval infrastructure.

The integration must prove:

```text
no valid approval → no sensitive operation execution
valid scoped approval → execution may proceed if all other gates allow
expired/mismatched/consumed approval → fail closed
Domain change invalidating scope → approval cannot be reused
```

`IntegratedAgentExecutionRequest.metadata["requires_approval"]` may be used only as the existing Phase 9 hint where appropriate; it is never sufficient proof of approval by itself.

## 12. Autonomy integration

Existing Domain policy already exposes `DomainAutonomyLimits`.

Phase 10.41 computes:

```text
effective_max_autonomy = min(
    globally_authorized_max,
    agent/session request max,
    effective_domain_max,
)
```

Equivalent fail-closed logic applies to reversible and irreversible change capabilities.

Required invariant:

```text
DOMAIN_AUTONOMY <= GLOBAL_AUTHORIZED_AUTONOMY
```

A Domain may reduce autonomy to proposal-only behavior even when the global runtime could execute more.

A Domain may never raise `IntegratedAgentExecutionRequest.max_autonomy_level` above the already authorized request/global ceiling.

## 13. Budget integration

### 13.1 Single master budget

Phase 9 `ActionBudgetService` is the only mutable budget owner.

Phase 10.41 must not create:

```text
DomainActionBudgetService
DomainBudgetStore
DomainBudgetRepository
DomainBudgetLedger
DomainBudgetCounter
```

`DomainActionBudget` is only a constraint value object.

### 13.2 Restrictive composition

For multiple Domains, effective limits are the most restrictive non-null ceiling for each dimension.

For every supported canonical `BudgetResourceType`:

```text
effective_limit = min(existing_master_limit, domain_ceiling)
```

If the existing master budget is already stricter, Phase 10.41 leaves it unchanged.

Phase 10.41 may use the canonical `ActionBudgetService.decrease_budget(...)` or equivalent existing restriction mechanism where needed. It must never call the budget increase path to satisfy a Domain request.

An attempted Domain-driven budget increase is an architectural violation.

### 13.3 Budget state

Consumed, reserved, available, exhausted, paused, completed and adjusted state remain Phase 9 state.

Phase 10.41 may record only reference IDs and decisions describing which Domain ceiling was applied.

## 15. Domain workflows and Phase 10.42 boundary

Phase 10.41 may bind an already-resolved Domain workflow identity or existing compatible `AgentWorkflowPlan` into the Agent Runtime request when such a plan already exists through canonical infrastructure.

Phase 10.41 does **not** implement:

- planner discovery of Domain operations;
- planner discovery of Domain workflows;
- Domain-specific planner nodes;
- new workflow node types;
- Domain subworkflow composition;
- workflow dependency insertion;
- planner-generated cross-Domain handoff nodes;
- a new Domain Workflow Engine.

Those belong to Phase 10.42.

If a requested Domain workflow cannot be represented using the current Phase 9 seam without implementing 10.42 behavior, Phase 10.41 must return a structured blocked/unsupported decision rather than expanding scope.

## 16. Validation and outcome evaluation

Phase 10.41 must not create another validation engine.

Before Agent execution, it must validate integration invariants such as:

```text
resolution is valid
composition is coherent
profile is valid
Domain permissions do not widen Agent permissions
Domain autonomy does not widen global autonomy
Domain budget does not widen master budget
selected operation exists and is authorized
cognitive projection is valid and secret-safe
identity/correlation bindings are consistent
```

After Agent execution, the Phase 10.41 result may record Domain-specific outcome references and decision codes based on already produced canonical results.

It may not reinterpret a failed Phase 9 validation as success.

Broad Domain Validation System integration remains Phase 10.43.

## 19. Error handling and fail-closed behavior

Introduce only a narrow Domain integration error family if existing Domain errors cannot express Phase 10.41 contract failures cleanly.

Conceptual family:

```python

DomainAgentRuntimeContractError
```

- expose safe identifiers and reason codes;
- avoid embedding secrets, raw resources, provider payloads, or sensitive content;
- distinguish malformed contract input from policy/permission blocks and infrastructure failure;
- never silently downgrade a blocked specialized Domain to unrestricted General behavior.

A blocked Domain integration must not execute operations.

## 23. Acceptance Test AT-DP-041

### 23.1 Purpose

`AT-DP-041` must prove the real connected Domain-to-Agent execution boundary using canonical components or their official in-memory implementations.

Mocks may be used only for truly external side effects where no canonical in-memory implementation exists. Mocks cannot replace the core architectural owners under test.

### 23.2 Required connected scenario

The acceptance test must construct a realistic Domain-specialized Agent execution through this path:

```text
real/in-memory Domain registries
→ DefaultDomainResolver
→ canonical Domain composition
→ real profile resolution
→ real Domain permission resolution/gate
→ DefaultDomainCognitiveIntegrator
→ DomainAgentRuntime integration projection
→ real AgentRuntimeIntegrationService stack
→ canonical operation registry / execution path
→ canonical approval path where required
→ canonical ActionBudgetService with InMemoryActionBudgetRepository
→ Phase 9 validation/recovery owners
→ IntegratedAgentExecutionResult
→ DomainAgentRuntimeIntegrationResult
```

### 23.3 Minimum assertions

AT-DP-041 must prove at least the following behavior:

1. **Resolution:** the correct specialized primary Domain is selected from a canonical `DomainResolutionContext`.
2. **Composition:** supporting Domains are included only when eligible and cannot widen restrictions.
3. **Profile:** the actual effective Domain profile comes from the existing profile resolver.
4. **Cognition:** Phase 10.40 produces canonical cognitive evidence and the Phase 9 request receives a deterministic Domain cognitive projection.
5. **No reverse import:** AST dependency check remains `AGENT_RUNTIME_TO_DOMAIN_IMPORTS=0`.
6. **Permission narrowing:** a Domain restriction prevents an Agent action that would otherwise be permitted.
7. **Approval:** an approval-required Domain operation does not execute without a valid canonical approval.
8. **Approved execution:** the same operation may execute only after valid scoped approval and all remaining gates pass.
9. **Autonomy ceiling:** the Domain cannot raise the incoming/global autonomy level and can reduce it.
10. **Budget ceiling:** the Domain reduces or preserves the master Phase 9 budget; it cannot increase it.
11. **Budget exhaustion:** canonical Action Budget exhaustion blocks further resource consumption/execution according to Phase 9 semantics.
12. **Specialized operation:** a Domain operation is executed through the registered Agent/Domain operation orchestration stack, never by direct implementation invocation.
13. **Trace links:** Domain and Agent traces/results are linked by IDs/references without copied trace ownership.
14. **Memory proposals:** any update remains a proposal/binding; the integration layer performs zero direct store mutations.
15. **Reevaluation:** new canonical context can trigger a reevaluation that changes the primary/supporting Domain set before a subsequent execution boundary.
16. **Reevaluation invalidates authority:** stale approval/permission assumptions are not reused after a material Domain change.

## 33. Final design summary

Phase 10.41 does not teach Phase 9 about Domains.

It teaches Domain Intelligence how to prepare, constrain, invoke, observe, and bind the already canonical Phase 9 Agent Runtime.

The architectural rule is:

```text
Domain Intelligence specializes.
Agent Runtime owns agency.
Cognitive Layer owns cognition.
Permission systems restrict authority.
Approval owns human authorization.
ActionBudgetService owns mutable budget state.
Canonical operation infrastructure owns execution.
Memory/Knowledge owners own persistence.
Trace owners own traces.
Phase 10.41 owns only the integration boundary.
```

That rule is the core of `DP-041` and must remain true after implementation, audit, and closure.
