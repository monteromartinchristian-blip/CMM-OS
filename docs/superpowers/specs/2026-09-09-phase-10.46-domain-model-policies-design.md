## 1. Purpose

Phase 10.46 defines how Domain Packs express model-related **objective inference requirements** without coupling domain logic to any concrete model, provider, subscription, deployment, benchmark result, or routing implementation.

The central architectural rule is:

> A Domain Pack describes what an operation needs.
> The user controls which model and reasoning level to use.
> CMM OS selects a model only when the user explicitly delegates that choice to automatic routing.

This phase must preserve the canonical Kernel, Cognitive Layer, Agent Runtime, privacy, economic, fallback, validation, and routing infrastructure already established in prior phases.

Phase 10.46 must **not** create a domain-specific model router, provider registry, model catalog, gateway, runtime, store, resolver, fallback engine, benchmark system, or provider invocation path.

---

## 2. Design decision

### 2.1 User ownership of model choice

The effective model is primarily a **user choice**, not a domain choice.

The user-facing chat configuration conceptually exposes at least:

- `model`
  - explicit concrete model selected by the user; or
  - `AUTO`, meaning CMM OS may choose a model;
- `reasoning`
  - user-selected reasoning/effort level supported by the chosen model/runtime.

The exact UI belongs outside Phase 10.46, but the architectural ownership is fixed here.

### 2.2 Chat-level persistence

Model choice and reasoning level are persisted as **chat/session defaults**.

They:

- apply to subsequent turns in that chat;
- can be changed by the user during the conversation;
- are not properties of a Domain Pack;
- are not inferred from the domain;
- are not rewritten silently by the domain;
- are not, by default, independent per-message settings.

A later phase may add per-message overrides if explicitly designed, but Phase 10.46 does not introduce them.

### 2.3 Domain neutrality

A Domain Pack MUST NOT contain concrete model or provider identifiers.

The following are prohibited inside `DomainModelPolicy` and equivalent domain declarations:

- preferred model IDs;
- prohibited model IDs;
- preferred provider IDs;
- prohibited provider IDs;
- provider-specific aliases;
- local model names;
- premium fallback model names;
- hard-coded vendor names;
- model-version pinning;
- routing weights tied to concrete models/providers.

The domain layer must remain valid when the entire model catalog changes.

## 3. Architectural boundary

The intended separation is:

```text
DOMAIN PACK
    │
    │ objective inference requirements only
    ▼
DomainModelPolicy
    │
    ▼
canonical domain → runtime adapter
    │
    ▼
ModelRequirementsSource
    │
    ▼
resolve_model_requirements(...)
    │
    ├── agent / goal
    ├── workflow
    ├── operation
    ├── global/user/session policy
    ├── privacy
    ├── approvals
    └── other canonical constraints
    │
    ▼
ResolvedModelRequirements
    │
    ├───────────────┐
    │               │
    │          User chat choice
    │          model + reasoning
    │               │
    └───────┬───────┘
            ▼
        routing path
            │
            ├── explicit model: validate compatibility
            │
            └── AUTO: canonical routing/evaluation path
            ▼
        Kernel ModelRouter
            │
            ▼
      RoutingDecision
```

Domain logic ends before concrete routing and provider construction.

No `kernel.llm` component may import `cmm.domains`.

## 4. Existing canonical infrastructure to reuse

The inspected repository already provides the relevant canonical infrastructure.

### 4.1 Kernel model requirements

`kernel.llm.model_selection.ModelRequirements` already models hard requirements for:

- minimum context window;
- reasoning capability;
- tool calling;
- structured output;
- JSON mode;
- JSON schema;
- vision;
- audio input;
- audio output;
- embeddings;
- privacy;
- allowed providers;
- excluded providers;
- input cost ceiling;
- output cost ceiling;
- premium allowance.

These remain canonical.

Phase 10.46 does not create a parallel requirements type for routing.

### 4.2 Agent Runtime requirement composition

The existing Agent Runtime `ModelRequirementsSource` / `ResolvedModelRequirements` contracts and `resolve_model_requirements()` remain the canonical composition mechanism.

Their established most-restrictive semantics must be preserved:

- capabilities combine conservatively;
- minimum context resolves to the greatest minimum;
- provider allowlists intersect;
- provider exclusions union;
- privacy resolves to the strictest value;
- maximum costs resolve to the smallest ceiling;
- premium permission is restrictive;
- conflicts fail closed.

The domain contributes another requirements source; it does not become another resolver.

### 4.3 Model ranking and routing

`kernel.llm.model_ranking.ModelRankingPolicy` and `kernel.llm.model_router.ModelRouter` remain canonical.

Phase 10.46 does **not** add concrete model preferences to the domain layer.

The current Kernel therefore does not require a Phase-10.46 extension for `preferred_models` or `excluded_models`.

### 4.4 Model and provider catalogs

`ProviderRegistry`, `ModelCatalog`, `ProviderSpec`, and `ModelSpec` remain canonical and application-scoped.

Availability is determined by these canonical components, not by Domain Packs.

### 4.5 Fallback

Existing `ModelFallbackPolicy` and `ModelFallbackDecisionEngine` remain canonical.

A Domain Pack may declare objective fallback requirements only through existing typed contracts where semantically justified, but it must never implement or invoke fallback selection itself.

### 4.6 Privacy and permissions

Existing privacy and permission systems dominate Domain Model Policy.

In particular:

- a domain requirement can make processing more restrictive;
- a domain requirement cannot make an ancestor policy less restrictive;
- `allow_external_models=False` cannot be bypassed;
- egress restrictions cannot be bypassed;
- prohibited providers remain prohibited;
- a model selected manually by the user still cannot bypass hard privacy/permission constraints.

### 4.7 Economic policy

`EconomicBudget` and `EconomicBudgetResolver` remain canonical.

Phase 10.46 does not convert a domain preference into a monetary budget and does not allow a domain to widen a stricter user/session/workflow/operation budget.

## 5. `DomainModelPolicy`

### 5.1 Role

`DomainModelPolicy` is an immutable, serializable declaration of **objective inference requirements intrinsic to a domain or domain operation**.

It is not:

- a router;
- a model selector;
- a provider policy;
- a user preference;
- a benchmark table;
- a cost optimizer;
- a subscription policy;
- a provider invocation contract.

### 5.2 Proposed semantic surface

The exact Python representation must follow existing CMM OS contract conventions, but the semantic surface is:

```python
DomainModelPolicy(
    domain_id="domain:health",

    require_reasoning=False,
    require_tool_calling=False,
    require_structured_output=False,
    require_json_mode=False,
    require_json_schema=False,
    require_vision=False,
    require_audio_input=False,
    require_audio_output=False,
    require_embeddings=False,

    minimum_context_window=None,

    require_context_validation=False,
    require_response_validation=False,

    fallback_policy=None,

    metadata={},
)
```

### 5.3 Field semantics

#### `domain_id`

Stable domain identifier.

It identifies provenance only. It must not influence routing through hard-coded domain branches.

#### Capability booleans

These fields express requirements only when the domain operation objectively cannot function correctly without the capability.

Examples:

- an operation that requires schema-constrained output may set `require_structured_output=True`;
- an operation that must invoke tools may set `require_tool_calling=True`;
- an image-analysis operation may set `require_vision=True`.

A domain must not set these merely to obtain a “better” model.

#### `minimum_context_window`

Optional objective minimum context requirement.

`None` means the domain adds no context constraint.

If present, the adapter converts it into the canonical `ModelRequirements.minimum_context_window` contribution.

#### Validation requirements

`require_context_validation` and `require_response_validation` declare whether canonical validation stages are required.

They do not create validators inside the domain policy.

They must connect to existing validation infrastructure.

#### `fallback_policy`

When used, this must reference/reuse the existing typed `ModelFallbackPolicy`.

It must not contain concrete provider/model execution logic.

#### `metadata`

Serializable audit metadata only.

Metadata must not become a hidden routing channel for concrete model/provider identifiers.

## 6. Explicitly excluded fields

The roadmap's earlier conceptual shape included fields that are deliberately rejected by this approved design.

The following are out of `DomainModelPolicy`:

```text
preferred_models
prohibited_models
preferred_providers
prohibited_providers
local_models
premium_fallback containing concrete models/providers
minimum_quality
latency_tolerance
recommended_budget_eur
concrete provider/model routing weights
```

### 6.1 Why concrete model/provider preferences are excluded

Model/provider selection belongs to:

- the user;
- the user/session policy layer;
- automatic routing when explicitly delegated;
- provider/model availability;
- benchmark/evaluation evidence;
- privacy;
- budget;
- permissions.

Embedding these identifiers into Domain Packs would couple long-lived domain knowledge to fast-changing infrastructure.

### 6.2 Why `minimum_quality` is excluded

A domain cannot honestly assert a routing-grade quality threshold until there is a canonical measured quality system.

Phase 10.47 owns Domain Benchmark Suites and later evaluation infrastructure can provide evidence-based quality dimensions.

Phase 10.46 must not pre-implement those systems.

### 6.3 Why `latency_tolerance` is excluded

There is no canonical latency model or measured routing policy established for this field.

Phase 10.46 must not invent arbitrary thresholds.

### 6.4 Why `recommended_budget_eur` is excluded

Budget preference belongs to the user/session/workflow/operation/economic-policy layers.

A domain must not decide how much a conversation is worth to the user.

## 7. User model and reasoning controls

### 7.1 Explicit model mode

When the user selects a concrete model:

```text
model = <concrete model>
reasoning = <user-selected level>
```

CMM OS must attempt to use that model **only if it satisfies all applicable hard constraints**.

Hard constraints include, where applicable:

- model/provider availability;
- required capabilities;
- minimum context;
- privacy;
- permissions;
- egress;
- budget ceilings;
- premium permissions;
- other canonical policy restrictions.

A Domain Pack cannot override the selection.

### 7.2 Failure of explicit model compatibility

If the user-selected model cannot satisfy a hard constraint:

- the system must fail transparently;
- the incompatibility must be auditable;
- the system must not silently substitute another model as though the user's choice had been honored.

Automatic fallback to a different model may occur only if a separately established user/session fallback policy explicitly permits it.

Phase 10.46 does not invent that permission mechanism.

### 7.3 AUTO model mode

When the user selects `AUTO`, the user explicitly delegates model selection to CMM OS.

Automatic selection may consider canonical information such as:

- effective hard requirements;
- model capabilities;
- model/provider availability;
- privacy;
- permissions;
- budget;
- ranking policy;
- future benchmark/evaluation evidence.

The Domain Pack itself never chooses the candidate.

### 7.4 Reasoning level

Reasoning/effort is a user-controlled chat configuration.

The domain may require that the chosen model be reasoning-capable if an operation objectively needs reasoning support, but the domain must not set the user's reasoning effort level.

Mapping UI reasoning levels to provider-specific request parameters belongs outside `DomainModelPolicy`.

## 8. Domain → runtime adapter

Phase 10.46 introduces a thin adapter from `DomainModelPolicy` into canonical runtime contracts.

Its responsibilities are limited to:

1. validate the domain policy;
2. translate objective capability/context requirements to `ModelRequirements`;
3. wrap them in `ModelRequirementsSource` with domain provenance;
4. expose validation/fallback declarations through existing typed seams;
5. preserve deterministic serialization;
6. preserve fail-closed semantics.

It MUST NOT:

- query `ProviderRegistry`;
- query `ModelCatalog`;
- call `ModelRouter`;
- select a model;
- rank models;
- create providers;
- execute inference;
- inspect API keys;
- inspect subscriptions;
- invent benchmark scores;
- mutate user chat configuration.

## 9. Composition rules

The domain contribution participates in existing canonical most-restrictive composition.

### 9.1 Hard requirements

For domain-derived hard requirements:

- required capabilities accumulate;
- minimum context can only increase the effective minimum;
- privacy can only become stricter where a domain produces a legitimate privacy constraint through canonical policy;
- cost/permission/premium restrictions from other layers cannot be widened.

### 9.2 User choice versus hard constraints

The precedence is:

```text
HARD SAFETY / PRIVACY / PERMISSION / TECHNICAL CONSTRAINTS
    >
USER'S EXPLICIT MODEL CHOICE
    >
AUTOMATIC ROUTING PREFERENCES
    >
DOMAIN METADATA
```

This does **not** mean CMM OS should silently override the user.

If the explicit model conflicts with a hard constraint, the result is an explained incompatibility unless an explicitly authorized fallback policy applies.

### 9.3 Domain independence

Changing:

- provider inventory;
- model inventory;
- model versions;
- benchmark scores;
- subscription status;
- routing weights;

must not require editing a Domain Pack.

---

## 10. Multi-domain behavior

If a chat or operation composes multiple Domain Packs, their objective hard requirements compose through the same canonical resolver.

Examples:

- if one domain requires tools and another requires structured output, both requirements survive;
- if one domain requires a larger context window, the larger minimum survives;
- if requirements become impossible to satisfy, resolution/routing must fail closed.

Domains do not vote on models.

There is no domain priority scheme for concrete model selection in Phase 10.46.

## 11. Design Point

### DP-046 — User-Controlled, Model-Agnostic Domain Policy

> Domain Packs declare only objective, typed, serializable, and auditable inference and validation requirements. They contain no concrete model/provider identifiers and cannot prefer, prohibit, select, construct, or invoke concrete models or providers. Model choice and reasoning level are user-controlled chat settings. CMM OS performs model selection only when the user explicitly delegates that choice to automatic routing, always through canonical requirements, privacy, budget, availability, evaluation, and routing infrastructure.

### Required invariants

1. Domain Packs contain no concrete model/provider identifiers.
2. Domain Packs never invoke providers.
3. Domain Packs never call `ModelRouter`.
4. Domain Packs never own provider/model registries.
5. Domain requirements are translated into canonical `ModelRequirementsSource`.
6. Existing most-restrictive resolution remains canonical.
7. User model choice belongs to chat/session configuration.
8. User reasoning level belongs to chat/session configuration.
9. Model/reasoning settings may change during a chat.
10. Per-message independent model/reasoning configuration is not introduced by this phase.
11. Explicit user model selection is never silently replaced when incompatible.
12. AUTO routing occurs only after explicit delegation.
13. Privacy, permission, capability, availability, and budget restrictions remain authoritative.
14. Domain requirements cannot widen stricter ancestor constraints.
15. Provider/model availability remains owned by `ProviderRegistry` / `ModelCatalog`.
16. Fallback remains owned by canonical fallback infrastructure.
17. Economic resolution remains owned by canonical economic infrastructure.
18. Phase 10.46 does not implement benchmark/evaluation infrastructure.
19. Kernel must not import `cmm.domains`.
20. No parallel routing/resolver/store/registry/runtime/engine is introduced.

## 12. Acceptance Test

### AT-DP-046 — Real canonical model-policy boundary

The acceptance test must demonstrate DP-046 through real canonical components or their official in-memory implementations.

Mocks isolated from the real composition/routing path are insufficient.

### 12.1 Fixture

Construct:

- one real representative Domain Pack;
- its real `DomainModelPolicy`;
- canonical `ModelRequirementsSource`;
- canonical requirements resolver;
- official in-memory `ProviderRegistry`;
- official in-memory `ModelCatalog`;
- canonical `ModelRouter`;
- multiple models with different:
  - capabilities;
  - context windows;
  - provider types;
  - costs;
  - availability.

The Domain Pack must contain **zero concrete model/provider IDs**.

### 12.2 Scenario A — explicit compatible model

User chat configuration:

```text
model = explicit-compatible-model
reasoning = high
```

Domain requires objective capabilities.

Assert:

- domain requirements appear in provenance;
- selected explicit model satisfies effective hard requirements;
- domain has not selected the model;
- no alternate model is silently substituted;
- routing/provider creation remains outside the Domain Pack.

### 12.3 Scenario B — explicit incompatible model

User selects a model that fails an objective hard requirement.

Assert:

- incompatibility is detected;
- the constraint is preserved;
- the model is not executed;
- another model is not silently substituted;
- the result is deterministic/auditable.

### 12.4 Scenario C — AUTO

User chat configuration:

```text
model = AUTO
reasoning = high
```

Assert:

- effective requirements are composed canonically;
- `ModelRouter` evaluates the official in-memory catalog;
- unavailable models are rejected;
- capability/context/privacy/cost constraints remain effective;
- one compatible candidate is selected deterministically, or `no_match` is returned;
- the Domain Pack remains unchanged regardless of which concrete models exist in the catalog.

### 12.5 Scenario D — catalog replacement

Replace the available model inventory while keeping the same Domain Pack and same objective domain requirements.

Assert:

- no Domain Pack code/data changes;
- routing adapts to the new catalog;
- the domain contains no stale model/provider references.

### 12.6 Scenario E — multi-domain restrictive composition

Compose two domain policies with independent objective hard requirements.

Assert:

- requirements accumulate conservatively;
- no domain votes for or against a concrete model;
- impossible composition fails closed;
- no requirement is weakened to force a match.

### Acceptance success

`AT-DP-046=PASS` requires all scenarios above to pass using canonical infrastructure.

## 16. Future compatibility

This design intentionally leaves future phases room to add evidence-based automatic routing.

Phase 10.47 may establish benchmark evidence by domain without modifying the Domain Packs to name models.

Future evaluation/routing can therefore implement:

```text
same DomainModelPolicy
    +
user chooses AUTO
    +
benchmark/evaluation evidence
    +
privacy
    +
budget
    +
availability
    ↓
best currently eligible model
```

The selected model can change over time while the domain contract remains stable.

## 17. Security and fail-closed behavior

The adapter and composition path must fail closed on:

- invalid requirements;
- incompatible hard constraints;
- impossible multi-domain composition;
- explicit model incompatibility;
- unavailable provider/model;
- privacy violation;
- permission violation;
- budget violation.

No incompatibility may be “fixed” by weakening a hard requirement.

No metadata field may be interpreted as an undocumented escape hatch.

- modify or remove the quarantine stash.

## 21. Design conclusion

Phase 10.46 establishes a durable boundary:

> **Domains know the task. Users choose the model and reasoning effort. The runtime enforces constraints. The router chooses only when the user delegates.**

This keeps Domain Intelligence stable while model catalogs, providers, prices, subscriptions, benchmarks, and routing strategies evolve independently.
