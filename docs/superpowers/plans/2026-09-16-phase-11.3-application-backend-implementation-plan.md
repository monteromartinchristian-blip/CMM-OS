# Phase 11.3 — Application Backend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the first stable, versioned and fail-closed product-facing backend of CMM OS as a transport-neutral application core plus a separate HTTP/OpenAPI/SSE adapter, without duplicating any canonical subsystem authority.

**Architecture:** `cmm/application/` owns public application semantics, contracts, safe errors, session/request services, idempotency and the one canonical `ApplicationGateway`; `cmm/api/` adapts that boundary to `/v1` HTTP/OpenAPI/SSE. The central user-request path reuses Phase 11.1 `ApplicationContainer`, Phase 11.2 `Orchestrator`, canonical `SessionStore` implementations and all existing domain/agent/provider owners; no HTTP handler may bypass the application layer.

**Tech Stack:** Python 3.10+, frozen dataclasses, existing CMM OS Phase 11.1/11.2 contracts, FastAPI `>=0.115,<1`, Starlette streaming via FastAPI, Pydantic v2 transitively through FastAPI, `httpx>=0.28,<1` for in-process API tests, pytest 9, Ruff.

**Spec:** `docs/superpowers/specs/2026-09-16-phase-11.3-application-backend-design.md`

**Starting branch:** `feature/phase-11-stable-integrated-platform`

**Starting HEAD after spec commit:** `3a2bc9e74ba1350761600b67e2815696d9f41dbc`

**Starting tree:** `b7839d0bb41615caa2eb9275d4ccf63fd1ee26b5`

## Global Constraints

- `F11-017 — Canonical Application Backend`.
- `DP-103 — Versioned, Fail-Closed Application Gateway`.
- `AT-DP-103 — Connected Application Backend Acceptance`.
- Architecture is fixed to **transport-neutral application core + separate HTTP adapter**.
- Canonical packages are `cmm/application/` and `cmm/api/`.
- The one canonical application boundary is named `ApplicationGateway`.
- Public API version is `v1`; HTTP base path is `/v1`.
- HTTP transport is an adapter and owns no business/domain authority.
- Central user-request processing must pass through the canonical Phase 11.2 `Orchestrator`.
- Phase 11.1 `ApplicationContainer` remains the sole composition root.
- `SessionStore`, `InMemorySessionStore`, `FileSessionStore` remain the session persistence authority.
- Phase 11.3 must not create new Domain, Agent, Provider, Workflow, Operation, Validation, Memory, Knowledge, Event, Plugin or Model-routing authorities.
- Phase 11.3 must not call provider/model routing directly.
- Phase 11.3 must not implement auth/RBAC.
- Phase 11.3 must not implement durable application storage, SQL/SQLite migrations, backups or a general transaction manager.
- Phase 11.3 must not create a global scheduler, worker pool, task broker or background-job runtime.
- Phase 11.3 must not integrate CMMChat or CMM Bots directly.
- Phase 11.3 must not implement full downstream operation/workflow/agent/model execution.
- Public errors must never expose traceback, exception repr, filesystem paths, secrets, hidden reasoning or raw sensitive context.
- Public metadata must be bounded, JSON-safe and secret-free.
- Unknown/missing capabilities fail closed as `CAPABILITY_UNAVAILABLE`.
- Idempotency is Phase 11.3 application-boundary state only; official implementation is in-memory.

- [ ] **Step 4: Implement bounded in-memory repository**

Constructor:

```python

```

Rules:

- capacity must be positive int and not bool;
- same key + same exact record is idempotent no-op;
- same key + different fingerprint/response is rejected with
  `IdempotencyConflictError`;
- when full, evict oldest inserted record deterministically.

Use `OrderedDict`, not a new cache framework.
