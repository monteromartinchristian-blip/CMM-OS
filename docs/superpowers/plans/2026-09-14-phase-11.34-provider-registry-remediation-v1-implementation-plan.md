# Phase 11.34 — Provider Registry — Remediation V1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remediate all Phase 11.34 Independent Audit V1 findings by restoring a single canonical provider authority, adding local-first versioned persistence, enforcing provider-aware fail-closed isolation, making onboarding atomic, fixing supported-Python immutability coverage, and connecting `DP-134` to `AT-DP-134`.

**Architecture:** `ProviderRegistry` remains the sole provider-identity authority. Provider manifests become subordinate declarative metadata; `ProviderConnectionRegistry`, `ModelCatalog`, and `ModelRouteCatalog` retain distinct entity ownership but are referentially bound to canonical providers. A focused Provider Registry state repository persists the aggregate without secrets, while onboarding uses normalized isolation evidence and compensating rollback for side effects.

**Tech Stack:** Python 3.10+, dataclasses, pathlib, JSON, existing CMM OS LLM kernel, pytest, Ruff, macOS Keychain adapter tests with injected runner.

**Spec:** `docs/superpowers/specs/2026-09-14-phase-11.34-provider-registry-remediation-v1-design.md`

**Historical Audit:** `docs/audits/phase-11.34-provider-registry-independent-audit-v1.md`

**Starting branch:** `feature/phase-11-stable-integrated-platform`

**Starting HEAD:** `eb8755fd887f646fd0c73354e429e380e01fea18`

## Global Constraints

- Preserve `ProviderRegistry`, `ProviderSpec`, `ModelCatalog`, `ModelSpec`, `ModelRouter`, `ProviderFactory`, and Phase 10.46 compatibility.
- `ProviderRegistry` is the only authoritative provider identity inventory.
- `ProviderManifestRegistry` may survive only as a non-authoritative compatibility adapter bound to `ProviderRegistry`.
- Do not solve authority fragmentation with bidirectional synchronization.
- Raw secrets must never enter manifests, candidates, persistence, logs, events, inventory snapshots, or Git-tracked artifacts.
- Qwen Token Plan and Qwen Cloud PAYG remain separate provider/account surfaces.
- Discovery remains administrative and must never invoke inference.
- `requires_isolation=True` may never reach `CONNECTED` without a successful isolation outcome.
- Duplicate onboarding must fail before mutating a pre-existing credential.
- A failed onboarding operation must not advance persisted state revision.
- CMM Usage integration remains deferred.
- CMMChat integration remains deferred.
- Do not implement Phase 11.35 Routing Policy Engine, a general Model Gateway, or the whole Phase 11.15 storage subsystem.
- Do not add a general transaction engine or a second provider registry.
- Do not push or merge.
- Do not use `git stash`, `git reset`, `git clean`, or `git worktree`.
- Preserve the quarantine stash.
- Every implementation task follows `TEST RED → MINIMAL IMPLEMENTATION → GREEN → CONTROLLED REFACTOR → COMMIT`.
- Historical Audit V1 must remain unchanged.
