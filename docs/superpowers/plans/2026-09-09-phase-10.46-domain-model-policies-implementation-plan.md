# Phase 10.46 Domain Model Policies Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement DP-046 so Domain Packs can declare model-agnostic objective inference and validation requirements that feed the existing Agent Runtime/Kernel model-requirements pipeline without choosing concrete models/providers, while user model/reasoning choice remains outside the domain layer.

**Architecture:** Add a focused immutable `DomainModelPolicy` contract to the domain package, attach it optionally to `DomainDefinition`, and adapt it from the Agent Runtime side into existing `ModelRequirementsSource` and `ValidationRequirement` contracts. Reuse `resolve_model_requirements`, `ModelRouter`, `ProviderRegistry`, `ModelCatalog`, `ModelFallbackPolicy`, and canonical validation infrastructure; do not add any new router, registry, catalog, fallback engine, benchmark system, or provider invocation path.

**Tech Stack:** Python 3, dataclasses, immutable/serializable CMM OS contracts, `kernel.llm`, Phase 9 Agent Runtime model requirements/fallback/validation contracts, pytest, Ruff.

**Spec:** `docs/superpowers/specs/2026-09-09-phase-10.46-domain-model-policies-design.md`

## Global Constraints

- Starting branch for implementation: `feature/phase-10-domain-intelligence`.
- Starting HEAD after plan commit must be recorded in the implementation-agent prompt; the design-spec commit is `ce264659adda1b42f0d1c22e8b9fc04ca7deb7cc`.
- A Domain Pack MUST NOT contain concrete model or provider identifiers in `DomainModelPolicy`.
- Domain Packs MUST NOT select, rank, construct, invoke, or fall back to concrete providers/models.
- Model choice and reasoning level belong to chat/session/user configuration; Phase 10.46 does not implement CMMChat UI or per-message overrides.

class DomainModelPolicy:
